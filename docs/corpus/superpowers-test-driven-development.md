## 1. 원문은 어떤 문서인가

- **골격 판정: 규율형(discipline)**. `Common Rationalizations`(L212)와
  `Red Flags`(L228)가 둘 다 있고, 그 위에 `The Iron Law`(L31)와
  `Final Rule`(L313)이 리터럴 블록으로 문서를 앞뒤에서 잠근다. Tailor 코퍼스가
  규율형의 표지로 규정한 두 섹션이 **표본 그대로** 있는 문서다.
- **다만 절차가 박혀 있다.** `Red-Green-Refactor`(L47–197)가 6개 하위 절로
  된 완전한 절차 블록이라, requesting-code-review·frontend-design과 같은
  **규율형 + 내장 절차 혼합형**이다. 순수 규율형이 아니다.
- **2파일 역할 분담**: `SKILL.md`는 "언제·어떤 순서로"(주기), `wgt`는
  "그 안에서 테스트를 어떻게 쓰나"(품질). 후자는 **로드 조건이 문서 첫 줄에
  명시**돼 있다(wgt L3–4: 테스트를 쓰거나 고칠 때, mock을 추가할 때, 테스트용
  정리·헬퍼 메서드를 추가할 때). 항상 읽는 문서가 아니라 **조건부 참조 문서**로
  설계돼 있다.
- **독자 가정**: 사람 파트너와 짝을 이룬 실행 주체. 예외 승인·막혔을 때 질문이
  전부 "your human partner"로 향한다(L20, L301, L321). 혼자 판단하는 문서가
  아니다.
- **자체 규정 출력 형식: 있다.** 다만 성격이 다르다. requesting-code-review는
  **보고서 형식**을 규정했지만 TDD가 규정하는 것은 **작업 순서와 그 순서를
  지켰는지 확인하는 방법**이다(TD-08, TD-09, TD-15). 산출물이 문서가 아니라
  코드이기 때문이다.

## 3. 원문이 규정하는 산출물 형식

### 3-1. Red-Green-Refactor는 목록이 아니라 상태 기계다 (TD-06, L47–70)

원문은 이 주기를 graphviz `digraph`로 그린다. 노드 6개(RED / 실패 확인 /
GREEN / 통과 확인 / REFACTOR / 다음)에 **되돌아가는 화살표 3개**가 붙어 있다.

```
실패 확인 --(잘못된 이유로 실패)--> RED        (테스트를 고쳐 다시)
통과 확인 --(아직 실패)--> GREEN               (코드를 고쳐 다시)
REFACTOR --(초록 유지)--> 통과 확인            (정리 후 재검증)
```

**빨강 → 초록 → 리팩터 세 단어로 요약하면 이 세 화살표가 전부 사라진다.**
그리고 현 코퍼스 `test-first`가 정확히 그 세 단어 요약이다.

### 3-2. 검증 단계의 확인 항목과 분기 (TD-08 / TD-09, L113–129 / L168–184)

두 검증 절이 **같은 형태**로 쓰여 있다: `MANDATORY` 표시 → 실행 명령 한 줄 →
확인 항목 3개 → **어긋났을 때의 분기 2개**.

| | RED 검증 (L113–129) | GREEN 검증 (L168–184) |
|---|---|---|
| 확인 1 | 실패한다(에러가 아니라) | 통과한다 |
| 확인 2 | 실패 메시지가 예상대로다 | 다른 테스트도 여전히 통과한다 |
| 확인 3 | **기능이 없어서** 실패한다(오타가 아니라) | 출력이 깨끗하다(에러·경고 없음) |
| 분기 A | 통과했다 → 기존 동작을 테스트한 것. 테스트를 고친다 | 실패했다 → **테스트가 아니라 코드를 고친다** |
| 분기 B | 에러가 났다 → 에러를 고쳐 제대로 실패할 때까지 다시 | 다른 테스트가 깨졌다 → 지금 고친다 |

**분기가 형식의 핵심이다.** 실패를 확인하라는 지시만 남기면 *실패하지 않았을 때
무엇을 할지*가 사라지는데, 그 자리가 바로 TDD가 무너지는 자리다.

### 3-3. 완료 체크리스트 — 8항목 전부 과거형 (TD-15, L283–297)

체크박스 8개이고, **전부 이미 한 일을 묻는 형태**다: 모든 새 함수에 테스트가
있는가 / 각 테스트가 실패하는 것을 **봤는가** / 각 테스트가 예상한 이유로
실패했는가(오타가 아니라) / 통과할 최소 코드를 썼는가 / 전부 통과하는가 /
출력이 깨끗한가 / 테스트가 실제 코드를 쓰는가 / 엣지 케이스와 에러를 덮는가.

닫는 문장이 판정이다 — **다 못 채우면 TDD를 건너뛴 것이니 다시 시작하라.**
체크리스트가 장식이 아니라 **게이트**임을 한 줄로 못박는다.

### 3-4. 관문 함수 2벌 (TD-25, wgt L65–80 / L135–149)

wgt는 두 원칙 각각의 끝에 **의사코드 블록**을 둔다. 형태가 조건 → 처방의
분기표다.

```
테스트 본문을 쓰기 전에:
  이 테스트를 실패시킬 제품 코드 변경을 명명하라.

  명명 못 하겠다        → 관측 가능한 행동을 중심으로 재설계
  원문 텍스트가 바뀜    → 산출물을 실행해 효과를 단언
  의도적 결정만 실패    → 변경 감지기. 그 결정에 의존하는 행동을 재라
```

**규칙을 문장으로 적은 뒤 같은 규칙을 분기표로 한 번 더 적는다.** 5-4에서
다루는 반복 장치의 한 형태다.

### 3-5. 형식이 아닌 것 — 구분해 둘 것

- `Debugging Integration`(L307–312)은 다른 스킬(systematic-debugging)과의
  접속점이지 이 스킬의 산출물 형식이 아니다. 다만 **두 카테고리를 잇는
  다리**라서 2차 회차에서 testing·debugging을 같이 채우는 근거가 된다.
- wgt L3–4의 로드 조건은 **superpowers 런타임의 파일 로딩 규약**이다. Tailor는
  단일 SKILL.md를 만들므로 그대로는 못 쓴다 — 옮기려면 번역이 필요하고,
  그러면 `adapted` 대상이다(9-3).

## 5. 문장 기법 — 왜 이렇게 썼는가

### 5-1. 예외를 형식으로 봉쇄한다

세 겹이다. ⓐ 문언을 어기는 것은 정신을 어기는 것이라고 못박아(L14) "정신은
지켰다"는 우회로를 미리 막는다. ⓑ 예외 3종을 **열거하고 그마저 사람 파트너에게
묻게** 한다(L24–28). ⓒ 예외를 생각하는 것 자체를 신호로 규정한다 — 이번만
건너뛸까 싶으면 멈추라, 그건 합리화다(L30).

**규칙 → 예외 목록 → 예외를 원하는 마음까지 규칙화**의 3단이고,
requesting-code-review의 `Never` 4항목보다 한 단계 더 나아간 형태다.

### 5-2. 나쁜 예를 코드로 못박는다

산문으로 "mock 동작을 단언하지 마라"라고 쓰는 대신, mock 체인으로 짠 테스트를
실물로 보여주고 아래에 한 줄 판정(모호한 이름이고 코드가 아니라 mock을
테스트한다)을 붙인다(L88–105). 값이 문자열이 아니라 **코드 형태**라서, 읽는
쪽이 자기 코드에서 같은 모양을 알아볼 수 있다.

**요약하면 무엇이 죽는가**: "mock보다 실제 코드를 쓴다"만 남으면 *어디까지가
불가피한 mock인가*가 사라진다. 그 경계가 wgt L97–110의 대조쌍(설정 쓰기까지
삼키는 mock은 과하고, 느린 서버 기동만 막는 mock은 적절)에 실물로 그려져 있다.

### 5-3. 변명을 1인칭으로 적고 기술적 사유로 되받는다

requesting-code-review와 같은 기법인데 **규모가 다르다**(11행 대 2행).
그리고 반박의 성격이 다르다 — 예의나 원칙이 아니라 **인과**를 댄다.

- 나중에 테스트하겠다 → 나중에 쓴 테스트는 즉시 통과하고, **즉시 통과는 아무것도
  증명하지 못한다.** 실패를 본 적이 없으므로 그 테스트가 버그를 잡을 수 있다는
  증명이 없다
- 이미 여러 시간 썼는데 지우는 건 낭비다 → **매몰비용**이다. 그 시간은 어느
  쪽을 골라도 이미 썼다. 진짜 선택지는 신뢰도 높은 재작성이냐, 신뢰도 낮은
  사후 테스트 부착이냐다
- TDD는 느리다 → 커밋 전에 버그를 잡고 회귀를 막고 두려움 없이 리팩터하게
  해준다. 실용적이라는 지름길은 운영 환경 디버깅을 뜻하고 **그쪽이 더 느리다**

**금지문과 다른 점**: 금지는 규칙을 어긴 뒤에 걸리지만 변명표는 **어기기 직전의
생각**을 걸어낸다. 이 기법은 반박이 길어야 성립한다.

### 5-4. 같은 항목을 다른 형태로 되풀이한다 — E축 정정의 실물 근거

`SKILL.md`에서 **변명 표와 위험 신호에 같은 항목이 5쌍 겹친다.**

| 항목 | 변명 표(사유 붙은 반박) | 위험 신호(사유 없는 짧은 신호) |
|---|---|---|
| 이미 수동으로 테스트했다 | L219 | L236 |
| 정신이지 의례가 아니다 | L218 | L238, L239 |
| 여러 시간을 지우는 건 낭비 | L220 | L240 |
| 참고용으로 남긴다 | L221 | L239 |
| TDD는 느리다 / 나는 실용적이다 | L224 | L241 |

"실패를 봤는가"는 더 여러 곳에 나온다 — **원칙**(L12) → **필수 절차 단계**
(L113–129) → **변명 반박**(L217) → **완료 체크리스트**(L288). 네 번 나오지만
하는 일이 매번 다르다: 정의 → 실행 → 반박 → 검증.

**이것이 handoff의 E축 재정의가 기대는 자료다.** 옛 E축은 이 반복을 감점했는데,
그러면 **원저자가 의도적으로 배치한 장치를 뺄수록 점수가 오른다.** 폐기된 옛
B축(용어를 뺄수록 점수가 오르던 것)과 같은 종류의 오류다.

한계도 적어 둔다 — 위 표는 **이 한 소스에서 확인한 것**이다. handoff가 근거로
든 "E=2 40건 중 17건이 3종 이상"은 여전히 형태 기계 분류이고, 전수 검증이
아니다.

### 8-3. 논증이 죽었다 — 새로운 종류의 소실

design·code-review에서 죽은 것은 **형식**(개수·섹션·템플릿)이었다. 여기서는
그 위에 **논증**이 죽었다. 변명 표 11행의 오른쪽 칸은 형식이 아니라 **왜
그런지에 대한 설명**이고, 200~330자짜리다. `detail` 한 줄로는 담을 자리가
아예 없다.

**구조적 함의**: 지금 `ReferencePattern`에는 `format`·`examples`·`options`가
있지만 **"규칙에 붙는 반박·사유"를 담을 자리가 없다.** 이 소스를 제대로 채우려면
`detail`을 길게 쓰거나 필드를 추가해야 한다. 2차 회차에서는 **필드를 늘리지
않고 `detail` 안에 담는 쪽**을 택한다 — 구조를 바꾸면 모든 카테고리의 렌더가
동시에 변해 대조군이 사라진다(handoff 「반복하지 말 것」).

### 8-4. 검증 분기가 사라진 자리

TD-08/TD-09의 분기 4개(통과했다 / 에러났다 / 실패했다 / 다른 게 깨졌다)는

실제로 사라졌다. code-review에서 사라진 것이 "리뷰를 끝내는 조건"이었던 것과
같은 자리다 — **둘 다 예상대로 안 됐을 때를 다루는 대목이다.**

2. **`rationalization-table`** — 변명 표를 **규율형 스킬의 산출물 형식**으로
   승격. 행 수(원문 11)와 "왼쪽은 1인칭 속말, 오른쪽은 인과로 되받기"를
   `format`에 담는다. (TD-12, TD-03)
3. **`name-the-break`** — 테스트를 쓰기 전 어떤 제품 변경이 이걸 실패시키는지
   명명. 관문 블록을 `format.template`로. (TD-20, TD-25)
4. **`no-mock-assertions`** — mock 단언 금지 + 좋은/나쁜 코드 대조쌍.
   (TD-26, TD-27)
5. **`green-verification-gate`** — GREEN 검증 확인 3 + 테스트가 아니라 코드를
   고친다. (TD-09)
6. **`past-tense-completion-checklist`** — 완료 체크리스트를 **과거형 8항목 +
   판정 한 줄** 형식으로. (TD-15) *baseline 후보이기도 하다 — 4차에서 재검토*
7. **`mutation-check`** — 돌연변이 5종. (TD-32)
8. **`red-flags-list`** — 사유 없는 짧은 신호 목록 + 닫는 판정. (TD-13, TD-34)
   *code-review·debugging과 겹치므로 baseline 승격 후보*

### 9-2. 기존 패턴 보강

- `test-first` — 복귀 화살표 3개를 `detail`에 넣는다(TD-06). 빨강→초록→리팩터
  직선 요약을 깬다
- `one-behavior-per-test` — 좋은 테스트 표 3행을 `format.sections`로,
  나쁜 예 문자열을 `examples`(polarity: bad)로 (TD-11)
- `minimal-green` — 코드 대조쌍을 `examples`로 (TD-10)

### 9-3. `adapted` 표기 대상

- wgt의 **로드 조건**(wgt L3–4)은 superpowers 런타임 규약이라 그대로는 못 쓴다.
  "테스트 품질 규칙은 별도 절로 묶고 필요할 때 참조하게 한다"로 옮기면 원문에
  없는 판단이 섞이므로 `adapted: true`
- 특정 도구의 **테스트 실행 명령**은 Tailor 사용자의 스택을 모르므로 그대로
  옮기면 안 된다. "검증 명령을 리터럴로 적는다"로 일반화하면 `adapted: true`

### 9-4. kind 판정 주의

TD-05(먼저 쓴 코드를 지운다)·TD-20(본문 쓰기 전 파손 명명)은 **원문 기준으로는
artifact**지만, Tailor가 만든 SKILL.md에서는 **작성 과정의 규칙으로만 남고
문서에 흔적이 없을 수 있다.** 이 둘은 `kind: "process"` 후보다 —
2026-08-18 출처 정직성 실험에서 거짓 크레딧 8건이 정확히 이 착오였다.

반대로 TD-12(변명 표)·TD-15(체크리스트)·TD-13(위험 신호)은 **완성 문서에
섹션으로 드러나므로 확실히 artifact**다.

## 10. 판단 기록

- **34항목으로 쪼갠 기준**: 형식 규정이 붙어 있는지를 우선했다. 태도 문장은
  묶고(TD-02·TD-03), 개수·표·블록이 붙은 것은 쪼갰다. code-review 감사(22항목)
  보다 많은 것은 2파일이고 wgt의 규정 밀도가 높기 때문이다
- **wgt를 별도 소스로 나누지 않았다**: `LICENSE`가 같고 `SKILL.md`가 직접
  링크로 호출하므로 한 소스의 두 파일로 본다. 코퍼스 `sp-tdd` 하나에 붙인다
- **`Debugging Integration`(TD-17)을 testing에 두었다**: 내용은 디버깅과
  겹치지만 **원문이 이 파일에 쓴 규정**이므로 출처 계보를 따라 testing에 둔다.
  debugging 카테고리에서는 systematic-debugging 원문의 대응 항목을 쓴다
- **E축 근거(5-4)는 이 소스 한 건의 확인**이다. handoff의 40건 통계는 여전히
  형태 분류이며 이 감사가 그것을 전수 검증한 것은 아니다
