> 한국어로 요약하며, 요약하면 값이 사라지는 것(필드명·시간 단위·경로 규칙)만
> 원문 그대로 적는다. 인용 위치는 원문 줄번호로 표기한다.

> **판본 주의.** requesting-code-review 감사와 동일 — 코퍼스의 `collectedAt`과
> 커밋 날짜가 같은 날(2026-08-12)이지만 **동일 판본임은 확인된 것이 아니라
> 정황이다.**

**결론부터.** 원문에서 **19개 지시**를 추려냈는데 현 코퍼스에서 이 소스를
가리키는 패턴은 **2개**(`bite-sized-tasks`, `assume-low-context-reader`)다.

이 소스의 실패 유형은 앞선 두 감사와 조금 다르다. 형식이 통째로 빠진 게 아니라
**형식의 이름만 남고 그 안의 칸이 사라졌다.** 원문은 계획 문서의 골격을
리터럴 템플릿 두 벌(`Plan Document Header` L56–80, `Task Structure` L84–129)로
못박는데, 코퍼스에는 그 안을 채우는 **5단계 흐름의 이름만** 남아 있다 —
`Files:` 3종, `Interfaces:` 2종(Consumes/Produces), `Goal/Architecture/Tech
Stack/Spec` 4필드, `Global Constraints` 블록이 전부 없다.

**가장 큰 단일 누락은 `Interfaces:` 블록**이다. 원문이 그 자리에 **왜 필요한지**
까지 적어놨다 — 작업 실행자는 자기 작업만 보기 때문에, 이웃 작업이 쓰는 이름과
타입을 이 블록으로만 알 수 있다(L93–97). 계획을 여러 조각으로 쪼갤 때 **쪼갠
조각들을 다시 이어붙이는 유일한 장치**인데, 코퍼스에는 없다.

**두 번째 발견: `Self-Review`(L141–151) 3단계가 통째로 빠졌다.** 이것은 계획
작성의 **종료 게이트**다. code-review 감사에서 발견한 것과 같은 종류의 누락이며,
F축(절차 무결성)과 직결된다.

## 1. 원문은 어떤 문서인가

- **골격 판정: 절차형(workflow)에 가깝지만 순수하지 않다.** 번호 붙은 단계
  흐름이 문서 전체를 관통하지는 않고, "계획 문서가 갖춰야 할 모양"을 규정하는
  **참조형(reference) 성격**이 절반이다. `Plan Document Header`·`Task
  Structure`·`No Placeholders`는 전부 산출물 명세다. **절차형 + 참조형 혼합**
  으로 보는 것이 정확하다.
- **2파일 구성.** `SKILL.md`(80%)와 `plan-document-reviewer-prompt.md`(20%).
  후자는 계획 문서를 검토하는 프롬프트 템플릿이다. requesting-code-review와
  같은 2파일 구조지만 **무게 배분은 반대** — 여기서는 상위 파일이 본체다.
  이 소스도 handoff에 단일 파일로 적혀 있었으나 실제로는 2파일이다.
- **독자 가정이 문서에 명시돼 있다** — "이 코드베이스에 대한 맥락이 전혀 없고
  취향도 미심쩍은 엔지니어"(L10). 유능하지만 도구와 문제 영역을 거의 모르고,
  좋은 테스트 설계도 잘 모른다고 가정하라고 못박는다. **독자 가정을 문서가
  직접 선언한다는 점이 이 소스의 특징**이다.
- **자체 규정 출력 형식: 있다. 두 벌.** 계획 문서 머리말 템플릿과 작업 1개
  템플릿이 코드펜스로 통째로 박혀 있다.

이하 `pr` = `plan-document-reviewer-prompt.md`, 그냥 `L`은 `SKILL.md`.

## 2. 문서 해부 — 무게가 어디에 실려 있나

공백 제외 글자 수 기준(frontmatter·제목 제외). `SKILL.md` 본문 5,585자.

| 섹션 | 글자 | 비중 |
|---|---|---|
| Task Structure 템플릿 본체 | 884 | 15.8% |
| File Structure | 760 | 13.6% |
| Overview | 736 | 13.2% |
| Self-Review | 646 | 11.6% |
| Execution Handoff | 590 | 10.6% |
| Plan Document Header | 527 | 9.4% |
| No Placeholders | 452 | 8.1% |
| Task Right-Sizing | 329 | 5.9% |
| Scope Check | 225 | 4.0% |
| Global Constraints | 218 | 3.9% |
| Bite-Sized Task Granularity | 193 | 3.5% |
| Task Structure(제목만) / (도입) | 25 | 0.4% |

**관찰 1 — 코퍼스가 옮긴 것은 3.5% 섹션이다.** `bite-sized-tasks` 패턴이 옮긴
`Bite-Sized Task Granularity`는 **문서에서 가장 작은 실질 섹션**(193자, 3.5%)
이다. 반면 두 템플릿(15.8% + 9.4% = 25.2%)과 `File Structure`(13.6%)는 한 글자도
안 옮겨졌다.

**세 번째 소스에서 같은 현상이 반복된다** — frontend-design에서도, 이번에도,
**짧은 섹션일수록 살아남았다.** 요약이 중요도가 아니라 **압축 난이도**를
따라갔다는 진단이 이제 세 소스에서 확인됐다.

**관찰 2 — 산출물 형식이 문서의 절반이다.** `Plan Document Header` +
`Task Structure` + `No Placeholders` + `Global Constraints` = **37.2%**.
여기에 `File Structure`(파일 분해 규칙)까지 더하면 절반이 넘는다. 이 소스는
**"어떻게 할지"보다 "무엇을 적을지"를 규정하는 문서**인데, 코퍼스에는 그 부분이
없다.

## 3. 원문이 규정하는 산출물 형식

### 3-1. 계획 문서 머리말 — 필수 4필드 + 1블록 (W-08, L56–80)

원문이 "모든 계획은 반드시 이 머리말로 시작한다"(L56)고 못박는다.

| 필드 | 원문이 규정한 내용 |
|---|---|
| Goal | 무엇을 만드는지 **한 문장** |
| Architecture | 접근 방식 **2–3문장** |
| Tech Stack | 핵심 기술·라이브러리 |
| Spec | 이 계획이 구현하는 명세 문서의 경로 |

**`Spec` 필드에 사유가 붙어 있다**(L69–70) — 계획은 명세로부터 논증되므로
명세가 계획과 함께 이동해야 하고, 실행자는 둘 다 읽는다.

그리고 `Global Constraints` 블록(L72–79): 명세의 프로젝트 전역 요구사항(버전
하한, 의존성 제한, 이름·문구 규칙, 플랫폼 요구)을 **한 줄에 하나씩, 명세에서
정확한 값을 그대로 복사**해 적는다. **모든 작업의 요구사항이 이 섹션을 암묵적
으로 포함한다**는 규정까지 붙는다.

### 3-2. 작업 1개의 형식 (W-09 ~ W-11, L84–129)

```
### Task N: [Component Name]

**Files:**
- Create: 정확한 경로
- Modify: 정확한 경로:줄범위
- Test: 정확한 테스트 경로

**Interfaces:**
- Consumes: 앞선 작업에서 쓰는 것 — 정확한 시그니처
- Produces: 뒤 작업이 의존하는 것 — 정확한 함수명·매개변수·반환 타입

- [ ] Step 1 … Step 5   (각 단계에 체크박스, 코드 블록 포함)
```

세 가지가 동시에 규정된다.

1. **`Files:` 3종** — 만들 파일 / 고칠 파일(줄 범위까지) / 테스트 파일.
2. **`Interfaces:` 2종** — 이게 이 소스의 핵심 장치다(아래 5-2).
3. **단계는 체크박스 리스트**(`- [ ]`)이고, 코드가 필요한 단계는 **실제 코드
   블록**과 **실행 명령 + 기대 결과**를 함께 적는다(L106–121: 실행 명령, 기대
   `FAIL`/`PASS`까지 명시).

### 3-3. 5단계 흐름 (W-07, L47–52)

각 단계는 **하나의 행동, 2–5분**. 실패 테스트 작성 → 실패 확인 → 최소 구현 →
통과 확인 → 커밋. **현 코퍼스가 유일하게 옮긴 형식**이다.

### 3-4. 자리표시자 금지 — 6종 (W-12, L131–139)

"이건 계획의 실패다, 절대 쓰지 말라"고 규정하고 6가지를 열거한다.

| # | 금지 대상 |
|---|---|
| 1 | "TBD", "TODO", "나중에 구현", "세부 채우기" |
| 2 | "적절한 에러 처리 추가" / "검증 추가" / "엣지 케이스 처리" |
| 3 | "위 내용의 테스트 작성" (실제 테스트 코드 없이) |
| 4 | "Task N과 유사" (코드를 반복해 적을 것 — 실행자가 순서대로 안 읽을 수 있다) |
| 5 | 어떻게 하는지 없이 무엇을 할지만 적은 단계 |
| 6 | 어느 작업에서도 정의되지 않은 타입·함수·메서드 참조 |

**2번은 특히 중요하다** — 계획서에서 흔히 쓰는 무난한 표현을 **금지 문자열로
직접 인용**했다.

### 3-5. 자기 검토 3단계 (W-13, L141–151)

계획을 다 쓴 뒤 **직접 실행하는 체크리스트**다(별도 검토자를 부르는 게
아니라고 명시, L143).

1. **명세 커버리지** — 명세의 각 절/요구사항을 훑고, 그것을 구현하는 작업을
   짚을 수 있는가? 못 짚는 것을 목록으로 적는다.
2. **자리표시자 스캔** — 3-4의 6종을 검색해 고친다.
3. **타입 일관성** — 뒤 작업에서 쓴 타입·시그니처·속성명이 앞 작업에서 정의한
   것과 맞는가? **원문이 예시까지 준다**: Task 3에서 `clearLayers()`인데
   Task 7에서 `clearFullLayers()`면 버그다(L149).

끝에 **"문제를 찾으면 인라인으로 고치고, 재검토는 필요 없다"**(L151)는 종료
규칙이 붙는다 — 검토 루프가 무한히 늘어나는 것을 막는 장치다.

### 3-6. 형식이 아닌 것 — 구분해 둘 것

- **저장 경로 규칙**(L18): `docs/superpowers/plans/YYYY-MM-DD-<feature-name>.md`.
  superpowers 고유 경로다. **"날짜 + 기능명으로 파일명을 정한다"**는 판단만
  번역 가능(`adapted`).
- **시작 시 선언문**(L14, "writing-plans 스킬을 사용합니다"): 스킬 이름이
  들어간 실행 환경 관례. Tailor 결과물에는 그대로 못 쓴다.
- **하위 스킬 지정**(L165–171, `subagent-driven-development` 등): 실행 환경
  고유. "실행 방식을 사용자에게 고르게 한다"는 판단만 번역 가능.
- **`pr` 파일의 서브에이전트 디스패치 형식**: 위와 같음.

## 5. 문장 기법 — 왜 이렇게 썼는가

### 5-1. 독자를 인격으로 못박는다

L10은 독자를 "맥락이 없고 취향이 미심쩍은 엔지니어"로 정의하고, 바로 다음
문장에서 "유능하지만 우리 도구와 문제 영역을 거의 모른다, 테스트 설계도 잘
모른다"고 **능력의 방향까지 지정**한다. 추상적 "쉽게 쓰세요"와 다른 점은,
**무엇을 생략해도 되는지 판정할 수 있다**는 것이다 — 도구 지식은 설명하고,
프로그래밍 일반 지식은 설명하지 않는다.

현 코퍼스의 `assume-low-context-reader`는 이 문장을 옮겼지만 **"테스트 설계를
잘 모른다"는 절이 빠졌다.** 그 절이 빠지면 "테스트 코드를 직접 적어줘야 하는
이유"가 사라지고, 그것이 곧 3-4의 금지 3번(테스트 코드 없이 "테스트 작성"이라고
쓰지 말 것)의 근거다. **한 절을 빼자 다른 규칙의 근거가 끊긴 사례.**

### 5-2. 쪼갠 조각을 다시 잇는 장치를 형식으로 만든다

`Interfaces:` 블록(L92–97)이 이 문서에서 가장 정교한 대목이다. 원문이 사유를
직접 적는다 — **작업 실행자는 자기 작업만 본다.** 그러니 이웃 작업이 쓰는
이름과 타입을 알 방법이 이 블록밖에 없다.

이것은 "잘게 쪼개라"는 지시의 **필연적 짝**이다. 쪼개면 조각 사이의 계약이
사라지는데, 그 손실을 형식으로 메운다. **코퍼스는 "잘게 쪼개라"만 옮기고 짝을
버렸다** — 원문의 논리 구조가 절반만 전달된 상태다.

### 5-3. 금지를 문자열로 인용한다

"적절한 에러 처리 추가"(L135)는 계획서에서 지극히 자연스러운 문장이다. 원문은
**그 자연스러운 문장을 그대로 따다가 금지 목록에 넣었다.** 추상적으로 "구체적
으로 쓰라"고 하면 자기가 위반 중인지 모르지만, 문자열이 박혀 있으면 검색으로
잡힌다. 3-5의 검토 2단계가 실제로 "검색해서 고쳐라"인 이유다.

frontend-design 감사 5-2("금지를 값으로 못박아 반증 가능하게")와 같은 기법이,
디자인이 아닌 계획 도메인에서 재현됐다.

### 5-4. 판정을 사람 기준으로 환원한다

`Task Right-Sizing`(L36–43)은 작업 크기를 시간이나 줄 수로 재지 않는다.
**"검토자가 하나는 반려하고 그 옆은 승인할 수 있는 지점에서만 쪼갠다."**
설정·구성·문서 단계는 그 산출물이 필요한 작업 안으로 접어 넣는다.

크기 규정을 **다른 사람의 판단 행위**로 환원한 것이고, 그래서 "2–5분"이라는
시간 규정(3-3)과 층위가 다르다 — 시간은 단계(step)의 단위, 검토 가능성은
작업(task)의 단위다. **코퍼스는 두 층위 중 시간만 옮겨서 작업 경계 규칙이
통째로 없다.**

### 5-5. 검토 루프에 종료 조건을 붙인다

L151("고치고 넘어가라, 재검토 필요 없다")과 pr L27–32("실제 문제만 지적하라,
사소한 표현·취향은 아니다")는 둘 다 **검토가 무한히 늘어나는 것을 막는 규정**
이다. 검토 절차를 넣으면 반드시 따라오는 실패(끝없는 다듬기)를 원문이 미리
막아뒀다.

## 8. 소실된 것

### 8-1. 계획 문서의 형식이 통째로 없다

W-08 ~ W-11이 전부 빠졌다. 지금 코퍼스로 "계획 세우는 스킬"을 만들면 모델은
**"작업을 잘게 쪼개고 자리표시자를 쓰지 마라"까지만** 말할 수 있고, 계획 문서가
어떻게 생겼는지는 말하지 못한다. 기준선 측정에서 planning이 design과 함께
최하위(2.67/4)였던 것과 방향이 맞는다 — 다만 **정황이지 인과는 아니다.**

### 8-2. 검증 단계(W-13, W-14)가 없다

code-review 감사 8-2와 **같은 발견**이다. 두 소스 모두 종료 게이트를 갖고 있고,
두 번 다 코퍼스에서 사라졌다. F축이 낮은 이유를 카테고리 쪽에서 설명한다.

### 8-3. 논리적 짝의 한쪽만 옮겨졌다

- "잘게 쪼개라"(옮김) ↔ `Interfaces:`(안 옮김) — 5-2
- "독자는 테스트 설계를 모른다"(안 옮김) ↔ "테스트 코드를 실제로 적어라"(안 옮김)
  — 5-1. 이쪽은 양쪽 다 빠져서 일관되긴 하다.
- 단계 시간 규정(옮김) ↔ 작업 경계 규정(안 옮김) — 5-4

**한쪽만 남은 규칙은 근거가 끊긴 채로 프롬프트에 실린다.** 이것은 "구체값이
빠졌다"와는 다른 종류의 손상이고, 이번 감사에서 처음 명확해졌다.

### 8-4. 왜 이렇게 됐나 (추정)

- **`detail` 69자 상한** — 앞선 감사들과 동일.
- **템플릿은 요약 불가능하다.** 머리말 템플릿과 작업 템플릿은 코드펜스 안의
  구조물이라 문장으로 줄일 수가 없다. `format.template` 칸이 없던 시절에는
  **담을 자리 자체가 없었다.** 1단계에서 그 칸을 만들었으므로 이제 담을 수 있다.
- **하위 파일 미조회** — pr 파일에서 온 항목(W-17~W-19)이 0개다.

## 10. 판단 기록

- **`Overview`의 "DRY. YAGNI. TDD. Frequent commits."(L10)를 항목화하지
  않았다.** 네 단어는 다른 스킬을 가리키는 약칭이고, 이 문서 안에 그 내용이
  없다. 코퍼스에 옮기면 **문서가 설명하지 않는 용어를 심는 것**이 되어 B축

- **`Context:` 워크트리 안내(L16)는 실행 환경 전제**라 항목을 주지 않았다.

  항목으로 뒀다.** 겹쳐 보이지만 층위가 다르다 — 하나는 작성자가 직접 돌리는
  것, 하나는 별도 검토자에게 넘기는 것이고 원문이 그 차이를 명시한다(L143).
- **작업 템플릿의 예시 언어가 Python**(pytest, `def test_...`)이지만, 언어
  선택은 원문의 지시가 아니라 예시의 부수 사항이라 항목화하지 않았다.
