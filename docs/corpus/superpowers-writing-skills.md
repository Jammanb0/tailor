## 3. 원문은 어떤 문서인가

- **골격 판정: 규율형(discipline) + 절차형(workflow) 결합.** 그런데 결합 방식이
  독특하다 — **TDD라는 기존 규율을 문서 저술에 옮겨 붙인 구조**다. 첫 줄(L10)이
  그것을 선언한다: 스킬 쓰기는 **프로세스 문서에 적용한 TDD**다
- **다른 스킬에 의존한다.** L18이 `test-driven-development`를 **필수 배경**으로
  못박는다("You MUST understand"). 감사한 소스 중 **선행 스킬을 필수로 요구하는
  것은 이 문서가 처음**이다
- **독자 가정**: 스킬을 만들려는 에이전트/사람. 막으려는 것은 **테스트 없이
  문서를 쓰는 것**이다
- **자체 규정 출력 형식**: 산출물이 `SKILL.md` 자체다. 즉 **이 문서는 Tailor가
  하는 일과 정확히 같은 일을 규정한다.** 지금까지 감사한 여덟 소스 중 유일하게
  **제품의 산출물 형식을 직접 규정**하는 소스다
- **`alwaysApply: true`의 근거**: 이 소스가 `baseline`에 놓인 이유가 여기 있다.
  요청 종류와 무관하게 "SKILL.md를 어떻게 쓸 것인가"를 다룬다

## 5. 원문이 규정하는 산출물 형식

### 5-1. SKILL.md 골격 템플릿 (W-06, L105–137)

리터럴 템플릿이 코드블록으로 주어진다. 섹션 순서가 규정돼 있다.

```
frontmatter(name, description)
# 제목
## Overview        — 핵심 원칙 1~2문장
## When to Use     — 증상·사용례 목록 + 언제 쓰지 말지
## Core Pattern    — before/after 대조 (기법·패턴형)
## Quick Reference — 훑기용 표
## Implementation  — 간단하면 인라인, 무거우면 파일 링크
## Common Mistakes — 무엇이 잘못되고 어떻게 고치나
## Real-World Impact (선택)
```

**현 코퍼스의 `structureArchetypes`와 겹치지만 같지 않다.** 코퍼스의 4종 골격은
"규율형/절차형/참조형/설명형"인데, 이것은 **한 벌의 표준 순서**다.

### 5-2. description 규정 (W-03, L99–197)

**개수·문자수 규정이 셋 있다.**

- frontmatter 전체 **최대 1024자**
- description은 가능하면 **500자 이하**
- `name`은 문자·숫자·하이픈만

**형식 규정**: 3인칭, `Use when…`으로 시작, **워크플로를 절대 요약하지 말 것.**

**이 금지에는 근거가 붙어 있다**(L154–158) — 설명이 워크플로를 요약하면
에이전트가 **본문을 읽지 않고 설명만 따른다.** 실제 사례가 적혀 있다: 설명에
"작업 사이 코드 리뷰"라고 썼더니 순서도에 리뷰가 **두 단계**로 그려져 있는데도
에이전트가 **한 번만** 수행했다. 설명에서 워크플로 요약을 빼자 두 단계를 지켰다.

**좋은 예/나쁜 예가 8벌 주어진다**(L160–197). 나쁜 예 5개, 좋은 예 3개.

### 5-3. 「실패 유형에 형태를 맞춘다」 4행 대응표 (W-12, L463–468)

이 소스에서 **가장 밀도 높은 형식 규정**이다.

| 베이스라인 실패 | 맞는 형태 | 틀린 형태 |
|---|---|---|
| 압박받으면 규칙을 어긴다(알면서 그런다) | 금지문 + 변명 표 + 위험 신호 | 부드러운 권고("가급적…") |
| 따르긴 하는데 **출력 모양**이 틀리다 | **긍정형 레시피·계약** — 출력이 무엇인지, 어떤 부분이 어떤 순서로 | 금지 목록("~하지 마라") |
| 이미 만드는 산출물에서 **필수 요소를 빠뜨린다** | **구조적** — 템플릿에 필수 칸을 만든다 | 템플릿 옆 산문 주의문 |
| 조건에 따라 달라져야 한다 | **관찰 가능한 조건**으로 분기 | 무조건 규칙 + 예외 조항 |

**금지문이 왜 역효과인지 근거를 붙였다**(L470) — 경쟁하는 동기가 있을 때
에이전트는 "하지 마라"와 **협상한다.** 문구 대조 실험에서 금지문 쪽이 원치 않는
내용을 **더 많이** 만들었고, **가이드가 아예 없는 대조군보다도 나빴다.**
레시피는 협상할 여지가 없다 — 모양이 맞거나 안 맞거나다.

**추가 규칙 둘**(L473–474):
- **뉘앙스 조항 금지.** "중요한 경우가 아니면 하지 마라"는 협상을 다시 연다.
  이긴 레시피에 뉘앙스 조항 하나를 붙였더니 일관되던 것이 들쭉날쭉해졌다
- **면제 조항은 범위를 못 잡는다.** "이 제한은 코드블록에 적용되지 않는다"고
  써도 코드블록이 억제된다. 면제가 필요하면 **규칙이 닿지 않게 구조를 바꾼다**

### 5-4. 문구 마이크로 테스트 5단계 (W-16, L577–585)

전면 시나리오 전에 문구 자체를 검증하는 절차다. **수치가 둘 있다.**

```
1. 호출마다 새 맥락 1건 — 시스템 프롬프트는 그 가이드가 실제로 놓일 맥락 전체
2. 가이드 없는 대조군을 반드시 포함 — 대조군이 실패하지 않으면 고칠 게 없다.
   멈추고 가이드를 쓰지 마라
3. 변형당 5회 이상 — 단일 표본은 거짓말한다
4. 표시된 일치를 전부 사람이 읽는다 — 자동 집계는 실패와 성공을 둘 다 부풀린다
5. 분산이 지표다 — 가이드가 먹히면 반복이 같은 모양으로 수렴한다.
   5회가 다섯 갈래면 문구가 구속력이 없는 것이다
```

> **이 항목은 Tailor의 실험 방법론과 직접 겹친다.** 3차 회차에서 "표본 3건은
> 판정선보다 잡음이 크다"는 결론에 도달했는데, **원문은 5회 이상과 대조군 필수를
> 이미 규정하고 있었다.** 코퍼스에 이 항목이 없었던 것과 별개로, 실험 설계
> 자체에 참고할 값이다.

### 5-6. 철칙과 예외 봉쇄 (W-10, L374–393)

```
실패하는 테스트 없이는 스킬도 없다
```

**신규 스킬만이 아니라 기존 스킬 수정에도 적용된다**고 명시한다. 봉쇄 목록 6개가
붙는다 — "간단한 추가"도, "섹션 하나 더"도, "문서 갱신"도 예외가 아니고,
검증 안 한 변경을 "참고용"으로 남기지 말고, 테스트 도중에 "손보지" 말고,
**지우라면 지우는 것**이다.

### 5-7. 스킬 유형별 테스트 4종 (W-14, L399–442)

유형마다 **테스트 방법과 성공 기준이 다르게** 규정된다.

| 유형 | 테스트 방법 | 성공 기준 |
|---|---|---|
| 규율형 | 학술 질문 + 압박 시나리오 + 압박 조합(시간+매몰비용+피로) | 최대 압박에서도 규칙을 지킴 |
| 기법형 | 적용 시나리오, 변형 시나리오, 정보 누락 테스트 | 새 상황에 기법을 적용함 |
| 패턴형 | 인식 시나리오, 적용 시나리오, **반례** | 언제 쓸지/안 쓸지를 구분함 |
| 참조형 | 검색 시나리오, 적용 시나리오, 빈틈 테스트 | 찾아서 올바로 적용함 |

### 5-8. 압박 시나리오 작성법 (W-17, `testing-skills-with-subagents.md` L96–160)

**압박 유형 7종이 표로 주어진다** — 시간, 매몰비용, 권위, 경제적, 피로, 사회적,
실용주의. **최소 3종 조합**을 권한다.

**좋은 시나리오의 5요소**(L144–150): 구체적 선택지(A/B/C 강제), 실제 제약(구체적
시각과 결과), 진짜 파일 경로, **"무엇을 하겠는가"로 묻기**("무엇을 해야 하는가"가
아니라), 도피로 차단("사람에게 물어보겠다"로 빠져나갈 수 없게).

**나쁜 예/좋은 예/아주 좋은 예 3단 대조**가 실려 있다.

### 5-9. 순서도 사용 규정 (W-08, L290–322)

**순서도를 쓸 곳 3가지**(비자명한 결정 지점, 너무 일찍 멈출 수 있는 반복,
A와 B 중 고르는 결정)와 **쓰지 말 곳 4가지**(참조 자료→표·목록, 코드 예시→
마크다운, 선형 지시→번호 목록, 의미 없는 라벨).

`graphviz-conventions.dot`은 **그 DSL 자체로 쓰인 스타일 가이드**다 — 질문은
마름모, 행동은 상자, 명령은 plaintext, 상태는 타원, 경고는 팔각형(빨강),
시작·끝은 이중원.

### 5-10. 토큰 예산 (W-07, L213–266)

**목표 단어 수가 셋 규정된다** — 시작 워크플로 150단어 미만, 자주 로드되는 스킬
200단어 미만, 그 외 500단어 미만. 검증 방법까지 적혀 있다(`wc -w`).

압축 기법 4종(도구 도움말로 빼기, 상호 참조, 예시 압축, 중복 제거)에 각각
좋은 예/나쁜 예가 붙는다.

## 8. 소실된 것

### 8-1. 이 소스는 Tailor의 산출물 형식을 직접 규정한다

다른 여덟 소스는 "테스트를 어떻게 할까", "디자인을 어떻게 할까"처럼 **주제**를
다뤘다. 이 소스만 **"SKILL.md를 어떻게 쓸까"**를 다룬다 — Tailor가 만드는 바로
그 산출물이다.

**그런데 반영 비율이 가장 낮다.** 107KB 중 61KB가 감사 대상이고 그중 코퍼스에
남은 것이 1,082바이트다. 원문 대비 **1.8%**다.

### 8-2. 근거가 붙은 규정에서 근거만 빠졌다

W-03과 W-12는 둘 다 **원저자가 실험으로 확인한 근거**를 본문에 적어뒀다.

- W-03: 설명이 워크플로를 요약하자 에이전트가 순서도의 두 단계 중 하나만 했다
- W-12: 금지문 쪽이 원치 않는 내용을 더 만들었고 **무가이드 대조군보다 나빴다**

**코퍼스에는 규칙만 남고 근거가 없다.** 근거가 없으면 규칙이 왜 그 형태여야 하는지
모델이 알 수 없고, 상충하는 상황에서 협상 대상이 된다 — **원문이 정확히 그것을
경고한다.**

### 8-3. 완료 점검 장치 소실 — 아홉 번째다

24항목 체크리스트가 통째로 없다. 지금까지 감사한 아홉 소스에서 **완료 점검
장치를 가진 소스가 일곱인데, 코퍼스에 그 형식이 남은 것은 0건**이었다
(3차에서 `voice`에 처음 넣었다).

### 8-4. 실험 방법론이 원문에 있었다

W-16(마이크로 테스트 5단계)은 **Tailor가 3차에서 힘들게 도달한 결론을 이미
담고 있다** — 대조군 필수, 5회 이상, 분산이 지표. 코퍼스에 없었을 뿐 아니라
**우리 실험 설계에도 반영돼 있지 않았다.**

## 9. 반영 제안

### 9-1. 신규 패턴 (우선순위 순)

1. `failure-form-matrix` — 실패 유형 4종 ↔ 맞는 형태/틀린 형태 (W-12).
   **근거(금지문이 대조군보다 나빴다)를 detail에 넣는다**
2. `description-no-workflow-summary` — 워크플로 요약 금지 + **두 단계가 한 번으로
   줄어든 실제 사례** + 좋은·나쁜 예 (W-03)
3. `skill-creation-checklist` — 24항목을 5단계로 (W-18) · `role: verification`
4. `token-budget` — 150/200/500단어 + 압축 기법 4종 (W-07)
5. `rationalization-table` — 변명 표를 만드는 규정과 8행 예시 (W-13)
6. `skill-type-testing` — 유형 4종별 테스트 방법과 성공 기준 (W-14)
7. `bulletproofing-toolkit` — 우회로 봉쇄 / 문자 대 정신 / 위험 신호 (W-15)
8. `when-not-to-create` — 만들지 말 것 4항목, 기계적 제약은 자동화 (W-04)
9. `one-excellent-example` — 예시는 하나를 훌륭하게 (W-09)
10. `flowchart-when` — 쓸 곳 3 / 쓰지 말 곳 4 (W-08)
11. `skill-md-skeleton` — 표준 섹션 순서 (W-06)
12. `keyword-coverage` — 에러·증상·동의어·도구를 검색어로 (W-11)
13. `no-force-load-links` — 상호 참조는 이름으로, `@` 링크 금지 (W-21)
14. `anti-patterns` — 4종 (W-20)
15. `iron-law-edits-too` — 철칙이 **수정에도** 적용 + 봉쇄 6항목 (W-10)

**15개를 더하면 `baseline`은 3 → 18개**가 된다. 다만 이 카테고리는
`alwaysApply: true`라 **모든 생성에 들어간다** — 아래 9-3을 반드시 볼 것.

### 9-2. `adapted` 표기 대상

- `skill-creation-checklist` — 24항목을 5단계로 묶는 것은 원문 구조 그대로지만,
  한국어 생성 맥락에 맞춰 일부 항목(git push, PR 기여)을 뺀다면 `adapted: true`
- `failure-form-matrix` — 표 자체는 원문 그대로다. `adapted` 아님

### 9-3. ⚠️ 분량 경고 — 이 카테고리만은 다르다

`baseline`은 **요청 종류와 무관하게 모든 생성에 들어간다.** 15개를 다른
카테고리와 같은 밀도로 채우면 렌더가 **1,082 → 8,000바이트 안팎**이 되고,
그 증가분이 **10개 시나리오 전부에 그대로 실린다.**

3차까지의 자료는 이 상황을 겪은 적이 없다 — 지금까지 늘린 것은 전부
조건부 카테고리였다. **채운 뒤 반드시 확인이 필요하다.**

### 9-4. 원문의 규정 중 옮기지 않을 것

- **`anthropic-best-practices.md` 전체** — 라이선스(2장)
- **`render-graphs.js`의 사용법** — 그 저장소의 도구다. Tailor 사용자에게는
  존재하지 않는다. "순서도를 SVG로 렌더해 보라"는 지시는 실행 불가능하다
- **`@` 링크 금지(W-21)의 문법 자체** — Claude Code 특유의 문법이라 다른
  런타임 사용자에게는 뜻이 통하지 않는다. **"참조가 즉시 로드를 일으키지 않게
  한다"는 규정만** 옮기고 문법은 뺀다
- **설득 원리 7종(W-23)** — 판단이 갈린다. 10장 참조

### 9-5. 카테고리 배치

**전부 `baseline`에 둔다.** W-14(유형별 테스트)와 W-17(압박 시나리오)은
`testing` 카테고리에 어울려 보이지만, **출처 계보를 따라 원문이 쓴 파일의
카테고리를 따른다**는 기존 원칙을 적용한다. 그리고 이 항목들이 다루는 "테스트"는
소프트웨어 테스트가 아니라 **스킬 문서의 검증**이라 성격이 다르다.

## 10. 판단 기록

- **`anthropic-best-practices.md`를 라이선스 사유로 뺀 것은 감사자의 판단이다.**
  근거는 2장에 적었으나 **법적 확인이 아니다.** 저장소 저자가 Anthropic의 허락을
  받았을 수도 있고, 그 사실은 저장소 안에 적혀 있지 않다. **뺀 쪽이 안전하다**는
  판단이다. 이 파일 하나가 소스의 43%이므로 **영향이 크다는 점을 밝혀둔다**
- **설득 원리(W-23)를 넣을지 정하지 못했다.** 내용은 "에이전트를 더 잘 따르게
  하는 심리 기법"이고 원문도 윤리 절을 따로 둔다. Tailor 사용자가 만드는 스킬에
  이것을 권하는 것이 맞는지는 **제품 판단**이지 감사자 판단이 아니다. 별도 결정
  사항으로 남긴다
- **`examples/CLAUDE_MD_TESTING.md`는 항목을 뽑지 않았다.** 이 파일은 저자가
  자기 실험을 설계한 기록(변형 A~D를 만들어 준수율을 비교)이고, **규정이 아니라
  자료**다. 다만 이 파일의 존재 자체가 W-16의 실증 사례다
- **`render-graphs.js` 169줄은 코드로만 확인했다.** graphviz를 호출해 SVG로
  뽑는 도구이며 규정을 담고 있지 않다
- **`anthropic-best-practices.md`를 뺐으므로 이 감사는 소스의 57%만 다룬다.**
  나머지 43%에 여기 없는 규정이 있을 수 있다 — **감사하지 않은 것이지 없다고
  확인한 것이 아니다**
