## 1. 원문은 어떤 문서인가

- **골격 판정: 규율형(discipline)**. `SKILL.md`에 `Common Rationalizations`
  표와 `Red Flags` 섹션이 둘 다 있다. Tailor 코퍼스가 "규율형을 골랐을 때만
  쓰라"고 규정한 바로 그 두 섹션이 원문에 실물로 있다. 단 `How to Request`는
  1·2·3 번호가 붙은 절차 블록이라 **규율형 안에 절차가 박힌 형태**다
  (frontend-design과 같은 혼합형).
- **2파일 역할 분담이 뚜렷하다.** `SKILL.md`는 "언제·어떻게 부를 것인가"(호출
  측), `code-reviewer.md`는 "무엇을 어떤 형식으로 답할 것인가"(수행 측)다.
  후자는 그 자체가 **프롬프트 템플릿**이라 문서 안에 완성된 산출물 형식이
  통째로 들어 있다.
- **독자 가정**: 여러 작업을 이어 돌리는 조율자(coordinator). 자기가 직접
  리뷰하지 않고 **다른 자리에 위임**하는 것이 이 스킬의 전제다.
- **자체 규정 출력 형식: 있다. 그것도 매우 강하게.** `Output Format`(cr L89–118)
  이 섹션 제목까지 리터럴로 못박고, `Example Output`(cr L145–180)이 그 형식을
  채운 실물 예시를 한 벌 더 보여준다. **이 문서에서 가장 구체적인 대목이고,
  현 코퍼스가 통째로 놓친 대목이다.**

이하 `cr` = `code-reviewer.md`, 그냥 `L`은 `SKILL.md`.

## 2. 문서 해부 — 무게가 어디에 실려 있나

공백 제외 글자 수 기준(frontmatter·제목 제외).

**`SKILL.md` (본문 2,267자)**

| 섹션 | 글자 | 비중 |
|---|---|---|
| Example | 584 | 25.8% |
| How to Request | 528 | 23.3% |
| Common Rationalizations | 465 | 20.5% |
| Red Flags | 280 | 12.4% |
| When to Request Review | 209 | 9.2% |
| (도입) | 201 | 8.9% |

**`code-reviewer.md` (본문 4,360자)**

| 섹션 | 글자 | 비중 |
|---|---|---|
| 템플릿 본체(코드펜스 안 전체) | 3,509 | 80.5% |
| Example Output 하위 4개 | 848 | 19.5% |

두 파일을 합치면 **`code-reviewer.md`가 전체의 65.8%**다.

**관찰 1 — 최대 섹션이 「Example」이다.** `SKILL.md`에서 가장 무거운 것은 원칙
서술이 아니라 **실행 예시 한 벌**(L48–73)이다. 실제 SHA 추출 명령, 넘긴 4개 값,
리뷰어가 돌려준 결과, 그 다음 행동까지 한 흐름으로 보여준다. frontend-design에서
「Process」가 최대 섹션이었던 것과 같은 구조 — **분량 1위와 구체성 1위가 같은
자리**이고, **코퍼스가 가장 크게 잃은 곳도 같은 자리**다.

**관찰 2 — 태도 문장이 차지하는 비중은 생각보다 작다.** "자주 일찍 리뷰하라"는
핵심 원칙은 **L10 한 줄**(전체의 약 1%)이다. 그런데 현 코퍼스 3패턴 중 하나
(`review-early-often`)가 이 한 줄을 옮긴 것이다. **원문에서 1%인 문장이 코퍼스
에서는 33%를 차지한다** — 압축이 중요도가 아니라 "짧아서 옮기기 쉬운 것"을
따라갔다는 증거다.

## 3. 원문이 규정하는 산출물 형식

design 감사와 같은 기준으로, **문서가 결과물의 모양을 직접 못박은 대목**만 뽑는다.

### 3-1. 리뷰 보고서의 섹션 구성 (R-11, cr L89–118)

원문이 리터럴 제목까지 지정한다.

```
### Strengths
### Issues
#### Critical (Must Fix)
#### Important (Should Fix)
#### Minor (Nice to Have)
### Recommendations
### Assessment
```

### 3-2. 이슈 1건당 필수 4필드 (R-12, cr L105–109)

```
- File:line reference
- What's wrong
- Why it matters
- How to fix (if not obvious)
```

**"왜 중요한가"가 필수 필드로 박혀 있다**는 점이 이 형식의 핵심이다. 지적만
나열되는 것을 형식 차원에서 막는다.

### 3-3. 심각도 3단계의 정의 (R-13, cr L96–103)

이름만 있는 게 아니라 **무엇이 어디에 들어가는지**가 규정돼 있다.

| 단계 | 원문 규정 |
|---|---|
| Critical (Must Fix) | 버그, 보안 문제, 데이터 유실 위험, 기능 파손 |
| Important (Should Fix) | 아키텍처 문제, 누락된 기능, 부실한 에러 처리, 테스트 공백 |
| Minor (Nice to Have) | 코드 스타일, 최적화 여지, 문서 다듬기 |

### 3-4. 최종 판정 — 닫힌 3지선다 (R-14, cr L116–118)

```
**Ready to merge?** [Yes | No | With fixes]
**Reasoning:** [1-2 sentence technical assessment]
```

**이것이 이 스킬의 종료 게이트다.** 값이 셋으로 닫혀 있고 사유의 길이(1–2문장)
까지 규정된다. 코퍼스에 없다.

### 3-5. 호출 측이 채우는 4개 자리 (R-05, L36–40)

`{DESCRIPTION}` / `{PLAN_OR_REQUIREMENTS}` / `{BASE_SHA}` / `{HEAD_SHA}`.
넘기는 맥락이 **정확히 이 넷으로 닫혀 있다**는 것이 "맥락 격리"의 실체다.
현 코퍼스의 `isolated-reviewer-context`는 태도("diff와 요구사항만 준다")까지만
옮겼고 **네 자리의 목록은 없다.**

### 3-6. 형식이 아닌 것 — 구분해 둘 것

- `git rev-parse HEAD~1` 등 SHA 추출 명령(L26–30)은 **git 사용 환경 전제**다.
  Tailor가 만드는 스킬은 git 작업이 아닐 수 있으므로 그대로는 못 쓴다. 다만
  "리뷰 범위를 시작점·끝점 두 지점으로 못박는다"는 판단은 번역 가능하다
  (`adapted` 대상).
- 서브에이전트 디스패치(L32–34)는 superpowers 실행 환경 고유다. "리뷰는 작업한
  맥락과 분리된 자리에서 한다"로 번역한다(`adapted`).

## 5. 문장 기법 — 왜 이렇게 썼는가

### 5-1. 변명을 먼저 적고 반박을 붙인다

`Common Rationalizations` 표(L77–80)는 왼쪽 칸에 **회피하는 사람의 속마음을
1인칭으로** 적는다. "내가 직접 diff 보면 되지" / "리뷰어한테 세션 전체를 줘야
이해하지". 오른쪽 칸이 그것을 기술적 사유로 되받는다 — 인라인 리뷰는 조율에
써야 할 컨텍스트 창을 태운다, 세션 이력이 아니라 작업물에 리뷰어를 붙들어 둔다.

**금지문("~하지 마라")과 다른 점**: 금지는 규칙을 어긴 뒤에야 걸리지만,
변명표는 **어기기 직전의 생각**을 걸어낸다. 이 기법은 문장이 길어야 성립한다
(오른쪽 칸이 각각 200자·140자). `detail` 69자 상한으로는 옮길 수 없다.

### 5-2. 심각도를 이름이 아니라 내용물로 정의한다

`Critical`이라고만 쓰면 판정이 사람마다 갈린다. 원문은 **각 단계에 들어갈 사건
유형을 4개씩 열거**해서(3-3) 판정을 목록 대조로 환원한다. 현 코퍼스의
`치명적→중요→사소`는 **순서만 남고 판정 기준이 없다** — 이대로 생성 프롬프트에
실리면 모델은 세 단어를 제목으로 쓸 뿐 무엇을 어디에 넣을지 모른다.

### 5-3. 판정을 닫힌 선택지로 만든다

`Yes | No | With fixes`. 세 값 중 하나를 반드시 고르게 하고 사유 길이까지
1–2문장으로 묶는다. **"대체로 괜찮아 보입니다"로 빠져나갈 길을 형식으로 막은
것**이다. 짝이 되는 금지가 DON'T 목록에 있다 — 명확한 판정을 회피하는 것,
확인 없이 "괜찮아 보인다"고 말하는 것.

### 5-4. 잘한 점을 먼저 쓰게 하고, 그 이유를 밝힌다

`Calibration`(cr L78–87)은 "강점을 먼저 인정하라"고만 하지 않고 **왜인지**를
붙인다 — 정확한 칭찬이 있어야 나머지 피드백을 신뢰한다. 규칙과 사유가 한
문장에 붙어 있어서, 규칙만 떼어내면 예의범절처럼 읽히고 근거가 사라진다.

### 5-5. DO/DON'T 대조쌍

10개가 짝으로 놓여 있다(cr L120–135). 특히 DON'T 쪽이 **구체적인 실패 문구를
그대로 인용**한다 — 모호함의 예시로 "에러 처리를 개선하라"류의 문장이 박혀
있다. 나쁜 예를 문자열로 못박는 기법이고, frontend-design 감사 5-2와 같은
계열이다.

### 5-6. 요약이 무엇을 죽였는지

현 코퍼스 3패턴을 원문과 나란히 놓으면 패턴이 보인다.

| 코퍼스 패턴 | 원문에서 대응하는 분량 | 남은 것 | 죽은 것 |
|---|---|---|---|
| `review-early-often` | L10 한 줄 + L14–22 | 태도 + 필수 시점 3개 | 선택 시점 3개 |
| `severity-ordered-fixes` | L42–46 + cr L96–103 | 처리 순서 | **심각도 정의 12항목** |
| `isolated-reviewer-context` | L8 + L36–40 | 태도 | **넘길 4개 자리** |

세 번 다 **"무엇을 하라"는 남고 "무엇을 적어라"가 죽었다.**
design 감사의 결론("태도는 남고 형식은 빠졌다")이 **다른 저작자의 다른 소스에서
그대로 재현됐다.** 두 소스에서 우연히 같았던 것이 아니라 압축 방식 자체의
성질이다.

## 8. 소실된 것

### 8-1. 하위 파일 1개가 통째로 안 읽혔다

전체 분량의 66%, 항목 22개 중 12개가 그 파일에 있다. theme-factory의 `themes/`
누락과 **동일 유형**이며, 이번에는 **handoff의 다중 파일 목록에 이 소스가 아예
없었다** — 목록을 믿고 단일 파일로 처리했을 가능성이 크다.

**교훈은 목록을 고치는 것이 아니라 절차를 바꾸는 것이다.** 남은 소스도 GitHub
트리 API로 파일을 전수 조회한 뒤 감사에 들어가야 한다(이번에 그렇게 했고,
requesting-code-review와 writing-plans 둘 다 목록과 달랐다).

### 8-2. 없어진 것의 정체는 "리뷰를 끝내는 조건"이다

R-11 ~ R-14, R-20, R-21은 전부 **결과물이 갖춰야 할 모양**이다. 이게 없으면
생성된 스킬은 "리뷰를 하라"까지만 말하고, 무엇을 적어 어떻게 끝낼지는 말하지
않는다. **F축(절차 무결성)이 재는 것이 정확히 이 지점**이다.

골격 제목 한국어화 실험에서 code-review의 F가 3.00 → 1.00으로 떨어진 것은
"영어 `Verification Checklist`가 검증 단계를 못박고 있었는데 이름이 부드러워지며
흐려졌다"로 진단됐다. 이 감사는 그 진단을 보강한다 — **골격 이름이 유일한
버팀목이었던 이유는 카테고리 쪽에 검증 내용이 하나도 없었기 때문**이다.
R-11~R-14를 채우면 골격 이름에 의존하지 않고 F가 회복될 것으로 예상되고,
**그 예상이 맞는지는 이번 확장 실험에서 관측된다.**

### 8-3. 선택 시점 3개가 사라진 자리

R-04(막혔을 때 / 리팩터링 전 / 복잡한 버그 수정 후)는 "필수/선택" 두 층 중
선택 층 전체다. 필수만 남으면 리뷰가 **관문 통과 의례**로만 읽히고, 원문이
의도한 "도움이 되니까 부를 수도 있는 도구"라는 성격이 사라진다.

### 8-4. 왜 이렇게 됐나 (추정)

- **`detail` 69자 상한.** 심각도 정의 12항목, 확인 항목 20문, DO/DON'T 10개는
  어떤 요약을 해도 69자에 안 들어간다. **상한이 곧 "형식은 못 담는다"는 규칙**
  으로 작동했다. design 감사 8-4와 같은 진단이다.
- **하위 파일 미조회.** 위 8-1.
- **`SKILL.md`만 봐도 완결돼 보인다.** 이 소스는 theme-factory와 달리 상위
  파일만으로도 문서가 말이 된다. **그래서 더 위험하다** — 빠진 것을 눈치챌
  신호가 없다.
