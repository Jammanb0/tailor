## 0. 결론 세 줄

1. **code-review의 F축(절차 무결성)이 1.67 → 3.00으로 회복됐다.** 골격 제목
   한국어화 때 3.00 → 1.00으로 떨어졌던 것이고, 사전에 세워둔 가설
   ("카테고리를 채우면 회복될 수 있다")과 방향이 일치한다.
2. **planning은 before부터 A·B·F가 전부 4.00 천장이라 움직이지 않았다.**
   이 시나리오로는 planning 확장의 효과를 잴 수 없다. 다만 깎아먹지도 않았다.
3. **안 건드린 7개 카테고리에 부작용이 없다.** 렌더가 23KB → 41.8KB로 늘었지만
   전부 ±0.33 안이다.

부수로 **E축 채점 기준의 오류를 확인**했다(5장). 이번 실험의 결과보다 이쪽이

## 1. 무엇을 바꿨나

원문 감사 3편(`docs/corpus/superpowers-*.md`)이 지목한 것을 코퍼스에 옮겼다.
세 소스 모두 진단이 같았다 — **"태도는 남고 형식은 빠졌다."**

### code-review (패턴 3 → 12개)

이 소스는 2파일인데 **분량의 66%를 차지하는 `code-reviewer.md`에서 온 내용이
코퍼스에 하나도 없었다.** 그 파일이 곧 리뷰 결과물의 형식 명세다.

복원한 것 중 핵심:

- **심각도 3단계를 이름이 아니라 내용물로 정의**(`severity-with-definitions`) —
  기존 코퍼스에는 `치명적→중요→사소`라는 순서만 있어 판정이 불가능했다
- **이슈 1건당 4필드**(`issue-required-fields`) — 어디 / 무엇이 / **왜 중요한지** /
  어떻게. "왜"가 필수 칸이라 지적이 취향과 구분된다
- **닫힌 종료 판정**(`merge-verdict-gate`) — 세 값 중 하나를 반드시 고르게 해
  "대체로 괜찮아 보입니다"로 빠져나갈 길을 막는다
- 확인 항목 5영역 20문, DO/DON'T 대조쌍, 변명표

### planning (패턴 3 → 20개)

brainstorming 원문 15KB가 코퍼스에서 **패턴 1개·`detail` 두 문장**으로 줄어
있었다. 가장 큰 누락은 **"요청을 세 종류로 분류해 절차의 무게를 바꾼다"**는
중심 장치(원문의 11%)다. 그게 빠져서 코퍼스는 결과적으로 **모든 요청에 가장
무거운 절차를 붙이라**고 말하고 있었다 — 코퍼스 서문의 "작업이 단순하면 구조도
단순하게"와 정면으로 어긋난 상태였다.

복원한 것 중 핵심: `classify-before-process`(3경로 + 각 판정 기준),
`approval-gate-never-shrinks`, `plan-header-fields`, `task-interfaces-block`,
`plan-self-review`, `no-placeholder-strings`(금지 문장 6종 직접 인용).

### 대조군을 지킨 방법

렌더를 섹션별로 갈라 **바뀐 두 섹션 외 전부가 바이트 단위로 동일함**을 확인한
뒤에만 기준 파일을 갱신했다.

```
동일   테스트 / 디버깅 / 공통 기본 / 디자인 / 말투 / 문서 작성 / 설명형
동일   골격 머리말 4,464바이트
변경   계획·설계      904 → 13,580
변경   코드 리뷰      655 →  6,725
```

## 2. 측정 방법

- 시나리오 10종(카테고리 8 + 카테고리 미스매치 2) × 3회 = **30건, 30/30 성공**
- 비교 대상(before)은 기준선이 아니라 **직전 상태**
  (`2026-08-18-headings`, 골격 제목 한국어화 후) 30건
- 60건을 고정 시드로 섞고 조건·시나리오 라벨을 제거해 별도 채점자에게 넘김
- 채점자는 조건이 둘이라는 사실을 몰랐고, `answer-key/`와 코퍼스 소스를 열지
  않았다

**배치 균형**: 첫 셔플에서 before가 앞쪽에 몰려(`BBBBBABBB…`) 다시 짰다.
채점자가 뒤로 갈수록 기준이 흔들리면 그 흔들림이 조건 차이로 잘못 잡히기
때문이다. 최종 배치는 **어느 1/3을 잘라도 10:10**이다.

**B축은 새 앵커로 채점**했다("용어가 있는가"가 아니라 "모르는 용어가 문서 안에서
해소되는가"). before 30건도 함께 다시 채점했으므로 조건 간 비교는 성립하지만,
**예전 문서의 B 절대값과는 섞어 쓸 수 없다.**

## 4. 기계 집계 — 채운 내용이 실제로 문서에 실렸는가

### 4-1. 1차 시도가 틀렸다

처음에는 코퍼스에 적은 용어를 그대로 찾았다(`치명적`, `사소`, `확인용`).
결과가 거의 0이었는데, **모델이 용어를 번역해 쓰기 때문**이었다 —
`치명적` → "버그", `사소` → "취향". 문서를 직접 읽고서야 알았다.

**교훈: 코퍼스 문자열로 반영 여부를 세면 안 된다.** 개념이 드러나는 형태로
정규식을 짜야 한다.

### 4-2. 다시 센 결과

**code-review (3건)**

| 신호 | before → after |
|---|---|
| 닫힌 종료 판정 (3지선다류) | 0/3 → 1/3 |
| 심각도 3단계 + 각 정의 | 0/3 → 1/3 |
| 좋은 예 / 나쁜 예 대조쌍 | 1/3 → 2/3 |
| 파일:줄 수준의 위치 지목 | 2/3 → 3/3 |

**planning (3건)**

| 신호 | before → after |
|---|---|
| 승인 게이트 (멈추고 기다림) | **0/3 → 3/3** |
| 완료 전 점검 목록 | 0/3 → 2/3 |
| 요청이 크면 나눠서 알림 | 0/3 → 1/3 |
| 질문은 한 번에 하나 | 1/3 → 2/3 |

문서 길이도 늘었다 — planning 1,376 → 1,666자, code-review 1,519 → 1,721자
(전체 평균은 1,772 → 1,825자로 거의 변화 없음).

### 4-3. 안 실린 것

**세 갈래 분류(`classify-before-process`)는 그대로 옮겨지지 않았다.** 모델이
"아주 작은 작업은 절차를 생략해도 된다"는 **2단계로 눌러 썼다.** 세 경로의
판정 기준(특히 "바꿀 흐름이 이미 저장소에 있는가")은 나타나지 않았다.

## 5. E축 채점 기준의 오류 (이번 실험의 부수 발견)

### 5-1. 기존 진단이 틀렸다

E축은 두 실험 연속 최약이고 E=4가 한 건도 없었다. 원인을 **"규율형 골격의
구조적 문제"**로 적어뒀었는데, 근거를 확인해보니 그 진단이 성립하지 않는다.

TDD 원문은 같은 항목("이미 수동으로 테스트했다")을 **세 곳에 쓴다.**

| 자리 | 형태 |
|---|---|
| Common Rationalizations | 변명 + **사유가 붙은 반박**(각각 다름) |
| Red Flags | **사유 없는 짧은 신호 목록** + 공통 처방 한 줄 |
| Verification Checklist | **과거형 체크박스**("~했는가") |

같은 말을 세 번 하는 게 아니라 **설명 → 반박 → 감지 → 검증으로 하는 일이 매번
다르다.** 원저자가 의도적으로 쓰는 장치다.

### 5-2. 지금 E축은 그 장치를 감점한다

채점자 관찰이 결정적이다 — **"E=3인 문서들의 공통점은 변명 표·위험 신호 섹션을
아예 두지 않은 것"**. 즉 **원문이 일부러 쓰는 장치를 빼면 점수가 오르는 구조**다.
이는 폐기된 옛 B축("용어를 빼면 점수가 오른다")과 **같은 종류의 오류**다.

### 5-3. 근거

E=2로 매겨진 40건의 섹션 형태를 세었다.

| | 건수 |
|---|---|
| 형태 3~4종 (표 + 목록 + 체크박스가 다 다름) | **17건 (43%)** |
| 형태 1~2종 | 23건 |

특히 **테스트·디버깅 12건은 전부 4종**이다
(`절차`목록 → `변명`표 → `위험 신호`목록 → `완료 점검`체크박스).
디자인 문서도 같았다 — "뻔한 기본값 세 가지"가 description(트리거) /
2단계(hex까지 붙은 정의) / 4단계(만들기 전 자문) / 완료 확인(체크박스)의
**네 형태**로 나온다.

### 5-4. 새 앵커 (다음 회차부터 적용)

- **감점하지 않음** — 같은 내용이 **다른 형태·다른 기능**으로 다시 나올 때
  (정의 / 반박 / 감지 / 검증)
- **감점함** — 같은 내용이 **같은 형태로** 다시 나와 하는 일이 늘지 않을 때
- **원래 잡아야 할 것** — 앞뒤 규칙 충돌, 단계 참조 깨짐 같은 **진짜 모순**

### 5-5. 과거 판정에는 영향 없다

E축은 지금까지 **"떨어지지 않았는지 보는 안전장치"로만** 쓰였고
(`corpus-restoration` 판정선: "F축 상승 AND E축 비하락") 실제로 떨어진 적이
없다. 다만 앞으로 **변명표·위험신호를 제대로 넣은 좋은 변경이 E를 떨어뜨려
안전장치에 잘못 걸릴 수 있다.**

### 5-6. 한계

**깊이 읽은 것은 2건뿐이고 나머지 38건은 섹션 형태만 기계 분류했다.**
방향은 분명하나 전수 검증은 아니다. E=2 23건(형태 1~2종)이 진짜 중복인지는
확인하지 않았다.

## 6. 함께 확인된 미결

- **design의 B축은 채점 기준 탓이 아니었다.** 새 앵커로 재판정해도 2.00 → 2.33
  으로 여전히 최하위다. 채점자가 사유를 짚었다 — 테라코타·애시드 그린·헤어라인
  괘선이 **풀이 없이 체크리스트의 판정 자리**에 쓰인다. 대조군으로, 같은 세 룩을
  "신문 레이아웃형: 얇은 실선 + 신문처럼 빽빽한 다단"으로 옮긴 문서는 감점되지
  않았다. **용어를 빼는 게 아니라 짧은 풀이를 붙이는 것이 해법이다.**
- **파서 결함은 이번 30건에서 0건**이다(직전 30건에 1건 — `</review>`,
  `<questions>` 원시 태그가 되물음 목록에 노출). 여전히 발생하는 경로다.
- **게이트 분해도가 전체 −0.20**인데 F는 +0.20이다. 두 지표가 반대로 움직인
  이유는 확인하지 않았다.

## 7. 한계

- **시나리오당 3건.** code-review의 +1.33도 확정이 아니다. 다만 ⓐ 사전에 예측된
  방향이고 ⓑ 기계 집계와 방향이 같아서 우연으로 보기는 어렵다.
- **판정선을 사전 등록하지 않았다**(문서 상단).
- **F축은 시나리오가 거의 결정한다.** 채점자 관찰에 따르면 기획·설계 시나리오는
  6건 전원 4점, 라이브러리 설명은 6건 전원 1점이다. **카테고리 간 F 비교는
  무의미하고, 같은 시나리오의 before/after 비교만 유효하다.**
- **planning은 천장 효과로 측정 불가**였다. 이 카테고리의 효과를 재려면 더
  어려운 시나리오가 필요하다.
- **B·E 앵커 변경으로 예전 문서의 절대값과 섞어 쓸 수 없다.**

## 8. 다음 회차에 반영할 것

1. **판정선을 먼저 적고 시작한다.**
2. **E축은 5-4의 새 앵커로 채점한다.**
3. 기계 집계는 **코퍼스 문자열이 아니라 개념 형태로** 짠다(4-1).
4. planning처럼 천장에 걸린 카테고리는 **시나리오를 손볼지 판단**한다.
