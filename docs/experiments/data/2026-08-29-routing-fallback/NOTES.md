# 전체 코퍼스 전환 안전장치 결과 (2026-08-29)

사전등록한 다섯 축을 모두 통과했다. 선택 호출이 실패하거나, 10초를 넘거나,
형식이 깨지거나, 빈 목록·무효 목록·잘린 응답을 돌려주면 개발 전용 경로가 전체
코퍼스로 전환했다. 저장된 실제 선택 20건과 경계 사례 2건은 잘못 전환하지 않았다.

> 이 결과는 개발 전용 `/api/route-preview`의 안전장치 시험이다. 프로덕션
> `/api/generate-skill`은 여전히 전체 코퍼스를 직접 주입하며, 선택 라우팅과
> 전환 안전장치를 운영에 붙일지는 10단계에서 결정한다.

### 축 1 — 실패·애매 분기

F1~F7마다 서로 다른 세 변형을 넣었다. 실패 조건 F1~F6의 18건은 모두 전체
코퍼스로 전환했고, 일부만 무효인 F7 세 건은 사전등록대로 전환하지 않고
`ambiguityIds: ["F7"]`만 남겼다.

겹치는 이유도 정확히 보존됐다.

| 입력 | 기록된 이유 |
|---|---|
| deadline 취소 | `[F2]` |
| 잘림 + 유효 id | `[F6]` |
| 잘림 + 빈 `<bundles>` | `[F4, F6]` |
| 잘림 + 잘린 무효 id | `[F5, F6]` |
| 닫는 `</bundles>`만 있음 | `[F3]` |

F2 세 변형은 10,002~10,012ms에 끝났고 모두 취소 신호를 관측했다. 지연 fixture의
타이머는 취소 때 지워져 자연 완료로 이어지지 않았다. 실제 SDK 호출에도 같은
`AbortSignal`을 전달하지만, 외부 API를 일부러 10초 넘게 지연시키는 시험은 하지
않았다.

### 축 2 — 정상 선택 오탐

6단계의 실제 선택 17건과 8단계 end-to-end 선택 3건을 원문 그대로 재생했다.
20건 모두 `success`였고 전환은 0건이었다. 응답에 저장돼 있던 usage도 계측 필드에

9.5초에 끝난 정상 응답과 유효 묶음 하나만 고른 최소 성공도 전환하지 않았다.
이는 10초 deadline과 “유효 묶음 1개 이상” 경계가 판정식 그대로 동작한다는
확인이지, 운영 오탐률의 추정치는 아니다.

### 축 3·4 — 전체 렌더와 계측

전환된 fixture 18건의 실제 주입 본문은 `CORPUS_SECTION`과 문자열까지 같았고,

결과에는 전환 여부, 맞은 이유 id 전부, 선택 시간, 끝난 호출의 usage가 남았다.
10초 deadline이 만든 `AbortError`는 F1과 중복 집계하지 않고 F2로만 기록됐다.

## 3. 비용

저장소가 쓰는 Sonnet 5 표준가와 5분 캐시 배율을 usage에 적용했다.

| 조건 | 일반 입력 | 캐시 생성 | 캐시 읽기 | 출력 | 관측 비용 |
|---|---:|---:|---:|---:|---:|
| F1 | 1,812 | 63,999 | 0 | 1,695 | $0.1805715 |
| F3 | 1,807 | 0 | 63,999 | 3,974 | $0.0561538 |
| **합계** | **3,619** | **63,999** | **63,999** | **5,669** | **$0.2367253** |

첫 호출은 전체 코퍼스 캐시를 만들었고, 둘째 호출은 읽었다. 합계는 사전등록한
관측 비용 중단선 $0.50 아래다. 이 값은 usage로 계산한 값이지 청구서를 조회한
금액은 아니다.

전환 비용의 운영 판단은 이 두 호출 평균으로 하지 않는다. 8단계 실측으로 만든
사전등록 표처럼 full 캐시 적중률 `p`와 실제 전환율 `f`를 함께 봐야 한다. 실제
트래픽이 없어 `f`는 아직 관측하지 못했다.

## 5. 결론과 한계

개발 전용 경로에서는 안전장치가 의도대로 동작했다. 실패를 하한 코퍼스로 조용히
흘리지 않고 full로 전환했고, 정상 선택은 보존했으며, 전환 뒤 실제 생성도 2/2
완료했다. 따라서 9단계 판정은 **통과**다.

10단계 결정문으로 넘길 한계는 다음과 같다.

1. 실제 트래픽이 없어 운영 전환율 `f`를 모른다.
2. F7은 합성 사례에서 “전환하지 않고 기록”만 확인한 잠정 정책이다. 실제 애매
   응답의 품질·비용 근거는 없다.
3. 외부 선택 API가 실제로 지연될 때 요청이 서버 쪽에서도 취소되는지는 강제로
   재현하지 않았다. 코드가 SDK에 신호를 전달하고 fixture가 취소를 받은 것까지
   확인했다.
4. 전환 뒤 생성은 2건뿐이고 품질을 새로 채점하지 않았다.
5. 비용은 첫 호출의 캐시 생성과 둘째 호출의 캐시 읽기에 크게 좌우됐다. 운영
   판단에는 8단계의 `p`·`f` 민감도 표를 쓴다.

이번 단계에서는 코퍼스 내용, 묶음 구성, 선택 프롬프트와 프로덕션
`/api/generate-skill`을 변경하지 않았다.
