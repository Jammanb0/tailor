> 문서는 「무엇을 만들지」와 「무엇을 통과로 볼지」를 함께 고정한다. 구현하고
> 나서 통과선을 정하면 만든 것이 그대로 기준이 된다.
>
> 작성일: 2026-08-29 · 대상 커밋 `24efbf8`(브랜치 `corpus-routing`).
>
> 고정 대상은 셋이다 — 전환 조건 목록, 판정선, 「미리 적어두는 예측」.
> 실행 결과를 본 뒤에는 이 셋을 고치지 않는다.

## 이번 단계가 답할 것

8단계는 선택이 **정상일 때** 선택 주입이 전체 주입보다 나쁘지 않고 싸다는 것을
보였다. 9단계는 선택이 **정상이 아닐 때** 무슨 일이 벌어지는지를 본다.

1. 선택이 실패하거나 망가졌을 때 전체 코퍼스로 돌아가는가?
2. 정상 선택을 불필요하게 전환하지는 않는가?
3. 전환이 비용 우위를 얼마나 깎는가?

## 착수 전에 코드에서 확인한 사실

`src/app/api/generate-skill/routing.ts`(커밋 `24efbf8`)를 읽고 확인했다.
아래는 추정이 아니라 현재 동작이다.

- **전환 경로가 없다.** `selectBundles`는 API 오류를 그대로 던지고,
  `/api/route-preview`는 502를 돌려준다.
- **빈 선택은 조용히 하한으로 떨어진다.** `<bundles>` 태그가 없거나 id를 하나도
  못 꺼내면 `extractSelectedBundleIds`가 빈 배열을 준다. `resolveDelivery`는
  그것을 오류로 보지 않으므로 머리말·골격·`always` 5개만 실린 하한 코퍼스로
  생성이 진행된다(6,249토큰 / 14,056바이트, `design.md` 5단계 실측 표).
- **응답이 잘려도 알 수 없다.** `SelectionResult`에 `stop_reason`이 없다.
  `SELECTION_MAX_TOKENS`는 512이고, 잘린 목록은 「유효하지만 불완전한 선택」이
  되어 아무 신호 없이 통과한다.
- `resolveDelivery`는 `unknownBundleIds`와 `rejectedBundleIds`를 기록하지만,
  그 값이 있다고 해서 동작을 바꾸지는 않는다.

세 번째 항목은 이 단계에서 처음 찾은 것이다. 계측이 없으면 전환 조건으로 쓸 수
없으므로 구현에 포함한다.

## 선택 결과를 세 갈래로 나눈다

한 번의 선택 호출로 관측할 수 있는 것만으로 가른다. **같은 요청을 여러 번
선택해야 알 수 있는 것은 전환 조건으로 쓰지 않는다** — 비용과 지연이 늘고,
8단계에서 본 변동 두 건 중 하나는 오히려 선택이 좋아진 경우였다.
「이전과 다르면 전환」은 그 개선을 되돌린다.

| 갈래 | 정의 |
|---|---|
| **성공** | 유효한 온라인 묶음이 1개 이상이고, 아래 실패 조건에 하나도 걸리지 않음 |
| **애매** | 유효한 묶음이 1개 이상이지만 `unknownBundleIds`나 `rejectedBundleIds`가 섞임 |
| **실패** | 유효한 묶음을 하나도 얻지 못했거나 호출 자체가 끝나지 못함 |

**성공은 그대로 간다. 실패는 전체 코퍼스로 전환한다. 애매는 전환하지 않고
기록만 한다** — 유효한 묶음이 있는데 곁가지 id 때문에 64,002토큰을 다시 싣는
것은 과잉이라고 봤다.

**이것은 잠정 정책이며 아직 검증된 사실이 아니다.** 실제 선택 호출 20건에서
`unknown`·`rejected`가 한 건도 없었지만, 그 0건은 「이런 경우가 드물다」는
뜻이지 「섞였을 때 전환하지 않아도 안전하다」는 뜻이 아니다. 축 2의 오탐 0건도
이 정책을 뒷받침하지 않는다 — 애매 사례가 그 20건에 아예 없기 때문이다.
결과 문서에도 잠정 정책이라고 남기고, 실제로 섞인 사례가 관측되면 10단계에서
다시 논의한다.

## 전환 조건

| id | 조건 | 관측 방법 | 갈래 | 전환 |
|---|---|---|---|---|
| F1 | 선택 호출이 예외로 끝남 | `selectBundles`가 throw | 실패 | 한다 |
| F2 | 지연이 상한을 넘음 | **10초 deadline에서 요청을 취소** | 실패 | 한다 |
| F3 | 형식 파손 — 파서가 인식할 묶음 블록·여는 태그 없음 | 추출 결과 0개 | 실패 | 한다 |
| F4 | 빈 선택 — 태그는 있으나 id 없음 | 추출 결과 0개 | 실패 | 한다 |
| F5 | 고른 id가 전부 무효 | 유효 묶음 0개, `unknown`·`rejected` ≥ 1 | 실패 | 한다 |
| F6 | 응답 잘림 | `stop_reason === "max_tokens"` | 실패 | 한다 |
| F7 | 일부만 무효 | 유효 묶음 ≥ 1이면서 `unknown`·`rejected` ≥ 1 | 애매 | 안 한다 |

F3과 F4는 관측 신호가 같지만(추출 0개) 원인이 달라 따로 센다. 기준은 파서가
실제로 보는 것과 같게 둔다.

> 닫힌 `<bundles>…</bundles>` 블록이 **어느 위치에든** 있거나, 줄 머리에 여는
> `<bundles>` 태그가 있으면 F4 후보다. 둘 다 없으면 F3이다.

`extractTag`는 세 단계로 찾는다 — ① 줄 머리의 닫힌 태그, ② 위치를 가리지 않는
닫힌 태그, ③ 줄 머리의 닫히지 않은 태그(`extractUnclosedTag`, `00074ee`).
**줄 머리 조건은 ③에만 붙는다.** 줄 가운데 있어도 닫혀 있으면 ②가 잡는다.

되돌림 경로의 범위도 좁혀 적는다. **줄 머리에 여는 태그가 있고 유효 id가 있으면
복구돼 성공한다.** 같은 응답이라도 여는 태그가 줄 가운데 있으면 복구되지 않아
F3이고, 줄 머리에 있으나 내용이 비어 있으면 F4다. 잘린 응답 자체는 F6 fixture가
다룬다.

**F2의 10초**는 8단계 실측 선택 시간 평균 1.085초(범위 1.032~1.124초)의 약
9배다. 정상 호출이 걸릴 여지를 크게 두되, 생성이 40초대인 경로에서 선택이
10초를 넘으면 기다리는 값어치가 없다고 봤다.

**F2는 걸린 시간을 나중에 재는 방식으로 구현하지 않는다.** 응답이 12초 뒤에
도착한 다음 `ms > 10초`를 검사하면 전환은 되지만 사용자는 이미 12초를 기다린
뒤다. 상한을 실제로 지키려면 10초에 요청 자체를 끊어야 하므로, 구현은
`AbortSignal`로 SDK 호출을 취소하고 취소된 호출이 뒤에서 계속 돌지 않는지도
확인한다. 기록에는 취소 사유와 **취소 시점까지 실제로 흐른 시간**을 남긴다.

**F6의 잘림은 전환한다.** 잘린 목록도 일부는 유효하겠지만, 어디서 잘렸는지
모르므로 「필요한 묶음이 빠졌을 수 있다」는 상태다. 실제 선택 호출의 출력은
6단계 17건이 24~58토큰, 8단계 end-to-end 3건이 32~39토큰으로 **실측 최대가
58토큰**이라 512 상한과 거리가 멀다. 이 조건이 실제로 걸리는 일은 드물 것이다.
(`design.md`의 5단계 기록 30~62토큰은 그때 저장하지 않은 회차의 값이라 여기
실측과 섞어 쓰지 않는다.)

## 판정선

### 축 1 — 전환 조건이 의도한 분기로 가는가: 21/21

조건마다 **서로 다른 세 변형**을 넣어 21건을 시험한다. 판정 함수가 결정적이라
같은 입력을 세 번 넣는 것은 검증 범위를 넓히지 못한다.

| 조건 | 변형 1 | 변형 2 | 변형 3 |
|---|---|---|---|
| F1 | 네트워크 오류 | HTTP 500 | 인증 오류(401) |
| F2 | 10.5초 뒤 응답 | 무응답(계속 지연) | 12초 뒤 정상 형식 응답 |
| F3 | 태그 없는 평문 | 태그 이름 오타(`<bundle>`) | 닫는 `</bundles>`만 있음 |
| F4 | `<bundles></bundles>` | 공백만 들어 있음 | 빈 줄만 들어 있음 |
| F5 | 지어낸 id 2개 | 평가 전용 묶음 1개 | 지어낸 id 1개 + 평가 전용 1개 |
| F6 | 잘림 + 유효 id 2개 | 잘림 + 유효 id 0개 | 잘림 + 잘린 id 조각 |
| F7 | 유효 + 지어낸 id | 유효 + 평가 전용 | 유효 + 지어낸 id + 평가 전용 |

fixture 원문에서 쓰는 id와 잘림 형태도 구현 전에 고정한다.

- 유효 온라인 묶음: `tdd-cycle`, `test-discipline`
- 평가 전용 묶음: `skill-authoring-evaluation`
- 지어낸 묶음: `not-a-real-bundle`, `missing-bundle`
- 잘린 id 조각: `[implementation-plan-struc`

F6의 원시 응답과 종료 사유는 다음 셋으로 고정한다. 첫째는 줄 머리에서 연
`<bundles>` 뒤에 `[tdd-cycle]`, `[test-discipline]`을 두고 닫는 태그 없이 끝낸다.
둘째는 `<bundles></bundles>`다. 셋째는 줄 머리에서 연 `<bundles>` 뒤에
`[implementation-plan-struc`을 두고 끝낸다. 셋 모두
`stop_reason: "max_tokens"`를 함께 넣는다. 이에 따라 기대 집합은 차례로
`[F6]`, `[F4, F6]`, `[F5, F6]`이다.

각 fixture는 갈래와 전환 여부만이 아니라 **`fallbackReasonIds`의 정확한 집합**도
검사한다. 배열 순서는 판정하지 않는다. 집합까지 보지 않으면 잘린 빈 응답에
`[F6]`만 적어도 통과해 축 4가 헐거워진다.

| fixture | 기대 집합 |
|---|---|
| deadline 취소 | `[F2]` |
| 잘림 + 유효 id | `[F6]` |
| 잘림 + 빈 `<bundles>` | `[F4, F6]` |
| 잘림 + 무효 id 조각 | `[F5, F6]` |
| 닫는 `</bundles>`만 있음 | `[F3]` |
| F7 세 변형 | `[]` — 전환하지 않으므로 비고, 애매는 `ambiguityIds`에 `F7`로 남긴다 |

**결정적 코드 판정이므로 부분 점수를 두지 않는다.** 1건이라도 어긋나면 실패로
보고 구현을 고친다.

주입은 선택 결과를 만들어 넣는 방식이라 **선택 모델을 부르지 않는다.**
F1·F2는 호출을 대신하는 주입 지점에서 예외와 지연을 만든다.

### 축 2 — 정상 선택을 전환하지 않는가: 오탐 0건

저장된 **실제 선택 호출 20건**을 재생해 전환이 한 건도 일어나지 않아야 한다.

- 6단계 선택 결과 17건 (`../2026-08-28-routing-eval/selection-results.json`)
- 8단계 end-to-end 선택 결과 3건 (`../2026-08-28-routing-comparison/generation/end-to-end-results.json`)

**8단계 품질 24건은 여기 쓰지 않는다** — 그 실행은 6단계 묶음을 고정해 넣었고
선택 모델을 부르지 않았으므로 실제 선택 결과가 아니다.

경계 사례 2건을 함께 넣는다. 지연 상한 바로 아래(9.5초)에 도착한 정상 응답과,
유효 묶음 1개만 고른 최소 성공이다. 둘 다 전환하지 않아야 한다.

저장된 값을 재생하므로 API 호출이 없다. **오탐 1건이라도 나오면 실패다.**
안전장치가 비용 우위를 깎는 가장 흔한 방식이 과민한 전환이기 때문이다.

### 축 3 — 전환된 요청이 실제로 전체 코퍼스를 싣는가

전환된 요청의 코퍼스 렌더가 `CORPUS_SECTION`과 **바이트까지 같아야 한다**
(141,597바이트). 전달 패턴도 코퍼스 전체와 같아야 한다. 「전환했다」는 플래그만
서고 실제 전달물이 다르면 안전장치가 아니다.

### 축 4 — 무엇이 왜 전환됐는지 남는가

전환된 요청의 결과에 다음이 있어야 한다.

- 전환 여부
- 걸린 조건 id 전부 — `fallbackReasonIds: string[]`
- 선택 호출의 usage와 걸린 시간(호출이 끝났다면)

**조건은 겹칠 수 있으므로 하나만 고르지 않고 맞은 것을 모두 적는다.**
`max_tokens`로 잘리면서 빈 응답이면 F4와 F6이 함께 맞고, 잘리면서 무효 id만
남으면 F5와 F6이 함께 맞는다. 하나만 남기면 「잘려서 그렇게 됐다」는 원인이
사라진다. **F6은 다른 형식 오류와 겹쳐도 반드시 포함한다.**

예외가 하나 있다. **10초 deadline이 스스로 취소해서 생긴 오류는 F2로만 적는다.**
취소는 예외 형태로 올라오므로 F1에도 걸리지만, 우리가 끊은 것과 상대가 실패한
것은 원인이 다르다. 둘 다 적으면 운영 집계에서 「호출 실패」가 부풀려진다.

7단계가 실제 트래픽에서 전환 비율을 세려면 이 값이 필요하다. **사용자 원문과
생성 결과 전문은 남기지 않는다**(`decisions.md` 2026-08-27).

### 축 5 — 전환 뒤에도 문서가 나오는가: 2/2

F1과 F3으로 전환된 요청을 실제로 생성해 `<skill_md>`가 나오는지 본다.
**전환 분기의 품질을 여기서 새로 재지 않는다** — 전환 결과물은 정의상 전체
주입이고, 그 품질은 8단계에서 12건으로 이미 쟀다. 여기서 보는 것은 전환 경로가
생성까지 이어지는지다.

입력도 실행 전에 고정한다. F1은 `14-three-line-memo`, F3은
`10-mismatch-setup`을 쓴다. 원문은 각각
`../2026-08-28-routing-eval/scenarios-routing.json`과
`../2026-08-20-baseline-fill/scenarios-extra.json`에서 읽으며, 답은 8단계와 같이
`tool: "cli"`, `language: "ko"`, `situation: 시나리오 원문`으로 만든다.

## 전환 비율과 비용

### 자체 시나리오로는 운영 전환율을 알 수 없다

9단계가 재는 것은 **오탐율**(정상 선택이 전환되는 비율)이고, 실제 요청에서
전환이 얼마나 자주 일어나는지(`f`)는 트래픽이 없어 잴 수 없다. 7단계 몫이다.
그래서 `f`를 측정값으로 적지 않고, **`f`에 따라 비용이 어떻게 움직이는지 표로
남긴다.**

### 두 축을 곱해서 본다

캐시 적중률 `p`와 전환 비율 `f`는 다른 축이다. 8단계 실측 상수로 계산한다.

```
routed 경로 평균 = 선택 $0.00398
                 + (1−f) × routed 생성 $0.05795
                 + f × full 생성 비용(p)

full 생성 비용(p) = $0.03026 + $0.12800 × (1.25(1−p) + 0.1p)
```

| full 캐시 적중률 `p` | full 요청 비용 | 비용이 뒤집히는 전환율 `f` |
|---:|---:|---:|
| 0% | $0.19026 | 97.0% |
| 25% | $0.15346 | 95.8% |
| 50% | $0.11666 | 93.2% |
| 80% | $0.07250 | 72.7% |
| 87.2% | $0.06190 | 이미 뒤집힘(−0.6%) |

**운영 가정인 낮은 적중률에서는 전환이 아주 잦아도 routed가 싸다.** 반대로
full 캐시가 잘 맞는 환경에서는 작은 전환율도 우위를 지운다. 8단계에서 나온
손익분기 87.2%는 `p`의 값이지 `f`의 통과선이 아니다.

전환율은 8단계 원자료의 usage에서 **반올림 없이** 계산했다. 표에 적은 반올림
상수로 다시 풀면 80% 행이 72.6%로 나오지만, 원자료 기준값은 72.68%다.

표의 full 비용은 캐시를 켠 1.25배 모델이다. 8단계 보고서의 0% 환산(모든 입력
1.0배)으로 계산하면 `p=0`의 뒤집힘 전환율은 96.0%다. **두 값은 기준이 다르다.**

### 전환율에 통과선을 두지 않는다

이 단계에서 관측할 `f`는 우리가 만든 실패 주입의 비율이라 운영 빈도가 아니다.
통과선을 두면 주입 설계가 그대로 결과가 된다. 대신 위 표를 10단계 결정문으로
넘긴다.

## 미리 적어두는 예측

빗나가면 빗나간 대로 남긴다.

- **오탐은 0건일 것이다.** 6·8단계 통틀어 `unknownBundleIds`와
  `rejectedBundleIds`가 한 건도 없었다.
- **F6(잘림)은 실제 트래픽에서 거의 안 걸릴 것이다.** 실측 20건의 출력 최대가
  58토큰으로 512 상한과 멀다. 그래도 계측이 없으면 「안 걸린다」를 확인할
  방법조차 없어 넣는다.
- **가장 손보게 될 자리는 F7(애매)의 판정일 것 같다.** 지금은 전환하지 않기로
  정했지만, 유효 묶음이 1개뿐인데 무효 id가 3개 섞인 경우처럼 경계가 애매한
  조합이 실제로 나오면 규칙을 나눠야 할 수 있다.

## 예산

축 5의 생성 2건만 API 비용이 든다. 8단계 실측으로 full 생성 1건은 관측
약 $0.055, 캐시 미적중 환산 약 $0.190이다. **누적 관측 실행 비용이 $0.50을
넘으면 다음 호출을 시작하지 않고 다시 승인받는다.**

축 1~4는 API 호출이 없다.

## 이 단계에서 손대지 않는 것

- **프로덕션 `/api/generate-skill`.** 안전장치도 개발 전용 경로에만 만든다.
  운영 전환은 10단계에서 정한다.
- **코퍼스 내용, 묶음 구성, 선택 카드 문구, 선택 프롬프트.** 8단계가 잰 대상과
  같은 상태를 유지한다.
- **8단계 자료.** 축 2는 저장된 선택 결과를 읽기만 한다.

## 실행 전에 만들 준비물
