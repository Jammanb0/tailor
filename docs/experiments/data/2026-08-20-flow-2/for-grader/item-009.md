# 근본 원인 디버깅

## 개요

**왜 고쳐졌는지 설명할 수 없으면, 아직 고친 게 아니다.**

버그를 고칠 때 여러 곳을 손대다 보면 증상이 사라지는 순간이 옵니다. 이때 바로 "됐다"고 넘어가면, 사실은 다른 이유로 우연히 증상만 가려진 것일 수 있습니다. 원인 모를 수정은 대개 며칠 안에 같은 문제나 다른 문제로 되돌아옵니다.

이 스킬은 증상을 없애는 게 아니라 **원인을 찾아서 없애는 순서**를 강제합니다.

## 언제 적용하나

- 항상 적용: 에러가 나거나, 기대와 다르게 동작하거나, "왜 이러지?"라는 말이 나오는 모든 상황
- 예외(사람에게 확인하고 넘어가도 되는 경우): 급하게 서비스가 멈춘 상황이라 응급 처치(임시 우회)가 먼저 필요할 때. 이 경우에도 "이건 임시방편이고 원인 조사는 따로 필요하다"는 것을 사용자에게 분명히 말합니다.

## 디버깅 절차

### 1단계 — 에러 메시지를 끝까지 읽는다

에러 메시지의 일부만 보고 넘어가지 않습니다. 줄 번호, 파일 경로, 에러 코드, 스택 트레이스(에러가 발생하기까지 코드가 호출된 순서를 보여주는 목록) 전체를 확인합니다.

- 좋은 예: "TypeError가 났는데, 스택 트레이스를 보니 `user.js` 42번째 줄에서 `user.name`을 읽으려는데 `user`가 `undefined`(값이 아예 없는 상태)였다"
- 나쁜 예: "TypeError가 났다" (어디서, 왜 났는지 없음)

### 2단계 — 재현 방법을 확정한다

같은 절차를 밟으면 매번 똑같이 문제가 재현되는지 확인합니다. 재현이 안 되면 다음 단계로 넘어가지 말고, 재현 조건부터 더 찾습니다.

- 좋은 예: "로그인 후 새로고침을 하면 매번 이 에러가 난다"
- 나쁜 예: "가끔 이런 것 같다" (추측 상태로 조사를 진행하지 않는다)

### 3단계 — 최근에 무엇이 바뀌었는지 확인한다

코드 변경 이력(git log 등), 새로 추가된 라이브러리, 설정 파일 변경 등을 살펴봅니다. 문제가 갑자기 생겼다면 그 직전에 바뀐 것이 원인일 확률이 높습니다.

### 4단계 — 여러 조각을 거치는 문제는 경계마다 확인한다

프론트엔드→백엔드→데이터베이스처럼 여러 단계를 거치는 문제라면, 어느 단계에서 값이 잘못되는지 모르는 채로 아무 곳이나 고치지 않습니다. 순서를 지킵니다:

1. 각 경계(단계와 단계 사이)마다 값이 잘 넘어가는지 기록(로그, `print`, 콘솔 출력 등)을 남긴다
2. 한 번 실행해서 어느 경계에서 값이 비거나 잘못됐는지 증거를 모은다
3. 증거로 문제가 있는 조각을 특정한다
4. 그 조각만 파고든다

- 나쁜 예: "제일 의심 가는 부분부터 일단 고쳐보자"
- 좋은 예: "로그를 찍어보니 서버는 값을 제대로 보냈는데, 화면에서 받을 때 비어 있었다. 그러니까 문제는 화면 쪽 코드에 있다"

### 5단계 — 값이 잘못된 위치가 아니라, 처음 생긴 자리까지 거슬러 올라간다

에러가 터진 곳과 진짜 원인이 생긴 곳은 다를 때가 많습니다. 에러가 난 자리에서 값만 억지로 맞춰주면 증상은 사라지지만 원인은 남습니다. 한 단계씩 "이 값은 어디서 왔지?"를 거슬러 올라가 원인이 처음 생긴 지점을 찾습니다.

- 예외: 정말 더 이상 거슬러 올라갈 수 없다면 증상이 발생한 자리에서 방어 코드를 넣어도 됩니다. 단, 이때는 왜 더 못 올라가는지, 어떤 방어를 넣었는지를 함께 기록합니다.

### 6단계 — 가설은 한 번에 하나만 세우고, 가장 작은 변경으로 시험한다

"이게 원인일 것이다"를 명확한 문장으로 먼저 말합니다. 그다음 그 가설만 확인할 수 있는 최소한의 변경 하나만 해서 시험합니다.

- 나쁜 예: 의심되는 곳 세 군데를 한꺼번에 고치고 돌려본다 (어느 게 원인이었는지 알 수 없게 됨)
- 좋은 예: "설정값이 다음 단계로 안 넘어가는 것 같다" → 그 값 하나만 로그로 찍어 확인

가설이 틀렸다면, 그 위에 다른 수정을 쌓지 말고 새로 가설을 세웁니다.

## 흔한 변명과 현실

| 이럴 때 이렇게 생각하기 쉽다 | 실제로는 이렇다 |
|---|---|
| "일단 이렇게 하니까 되긴 하네, 넘어가자" | 왜 되는지 모르면 다음에 비슷한 상황에서 또 안 될 수 있습니다. 운으로 고친 것과 이해하고 고친 것은 다릅니다. |
| "시간이 없으니까 원인 찾는 건 나중에" | 원인을 안 찾고 넘어가면 같은 문제가 다른 모습으로 다시 나타나고, 그때 가서 처음부터 다시 조사해야 해서 결국 시간이 더 듭니다. |
| "이 부분 고치면 될 것 같다" (느낌만으로) | 느낌은 가설일 뿐입니다. 가설을 검증하지 않고 고치면, 우연히 맞을 수도 있지만 틀렸는데도 맞았다고 착각할 수도 있습니다. |
| "에러가 사라졌으니 원인도 없어진 거겠지" | 에러가 사라진 것과 원인이 사라진 것은 다릅니다. 다른 곳에서 값을 덮어써서 증상만 안 보이는 경우가 흔합니다. |
| "여러 군데를 한꺼번에 고쳤는데 됐다" | 어느 수정이 실제로 효과가 있었는지 모릅니다. 나머지 수정은 불필요했거나 오히려 다른 문제를 숨기고 있을 수 있습니다. |

## 위험 신호 — 나타나면 멈추고 처음부터 다시

- 왜 고쳐졌는지 한 문장으로 설명하지 못하고 있다
- 같은 문제를 세 번째 고치고 있다 (→ 이 경우 개별 수정을 그만 시도하고, 구조 자체에 문제가 있는지 의심합니다)
- "일단 되니까"라는 말이 스스로 나오고 있다
- 에러 메시지를 끝까지 읽지 않고 코드부터 고치고 있다
- 재현 방법이 확실하지 않은 채로 수정하고 있다
- 여러 곳을 한꺼번에 고치고 나서 "이 중 하나가 됐겠지"라고 생각하고 있다

## 완료 전 점검

- [ ] 에러 메시지(또는 증상)를 끝까지 읽고 정확한 위치를 확인했는가
- [ ] 문제를 재현하는 정확한 절차를 알고 있는가
- [ ] 원인이 어디서 처음 생겼는지 설명할 수 있는가
- [ ] 그 수정이 왜 문제를 해결하는지 한두 문장으로 설명할 수 있는가
- [ ] 수정한 부분을 되돌리면 다시 문제가 재현되는지 확인했는가
- [ ] 다른 기능이 이 수정 때문에 깨지지 않았는지 확인했는가

이 목록을 다 채우지 못했다면, "고쳤다"고 말하지 말고 1단계부터 다시 진행합니다.
