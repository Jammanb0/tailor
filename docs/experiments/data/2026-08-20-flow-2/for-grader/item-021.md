# 근본 원인 디버깅

## 개요

**증상이 사라졌다고 고친 것이 아니다. 왜 그 증상이 생겼는지 설명할 수 있어야 고친 것이다.**

버그를 여기저기 찔러보다 우연히 사라지면, 그 문제는 안 고쳐진 채로 숨어 있다가 나중에 더 나쁜 타이밍에 다시 나타난다. 이 스킬은 "무엇을 조사했는지 → 무엇을 확인했는지 → 왜 이게 원인인지"의 순서를 강제해서, 추측으로 고치는 것을 막습니다.

## 언제 적용하나

- 에러가 나거나, 예상과 다르게 동작하거나, 테스트가 실패할 때 — 항상 적용
- "일단 이렇게 바꿔보고 되나 보자" 같은 시도를 하려는 순간 — 이 스킬로 대체
- 예외: 원인이 이미 명백하고 한 줄로 설명 가능한 매우 사소한 오타 수준의 문제는 절차를 간소화해도 되지만, 그 경우에도 "왜 이 오타가 이 증상을 냈는지"는 한 문장으로 말할 수 있어야 합니다. 판단이 애매하면 절차를 전부 밟습니다.

## 조사 절차

### 1단계 — 증거부터 모은다 (추측 금지)

고칠 방법을 생각하기 전에 먼저 사실을 모읍니다.

- 에러 메시지를 끝까지 읽는다 — 줄 번호, 파일 경로, 에러 코드까지 전부
- 정확히 어떤 절차를 밟으면 문제가 재현되는지 적는다. 매번 재현되는지, 가끔만 재현되는지도 확인
- 최근에 무엇이 바뀌었는지 본다 — 코드 변경 이력, 새로 추가된 라이브러리(외부 코드 묶음), 설정 변경
- 여러 파일·모듈을 거치는 문제라면, 값이 어느 지점까지는 정상이고 어느 지점부터 이상해지는지 각 경계마다 로그(임시로 남기는 기록)를 찍어 확인한다

좋은 예: "로그인 후 3번째 요청부터 401 에러가 난다. 어제 배포된 토큰 만료 로직 변경 커밋이 있다."
나쁜 예: "로그인이 이상해요. 토큰 쪽인 것 같아서 일단 만료 시간을 늘려봤어요."

### 2단계 — 잘못된 값이 처음 생긴 곳까지 거슬러 올라간다

에러가 발생한 지점이 아니라, 그 원인이 된 값이 **처음으로 잘못되기 시작한 지점**을 찾습니다.

- 증상이 보이는 곳에서 시작해 한 단계씩 위로(호출한 쪽으로) 거슬러 올라간다
- "이 함수를 부른 곳은 어디인가", "이 값은 어디서 왔는가"를 계속 묻는다
- 손으로 따라가기 어려우면, 의심되는 지점 직전에 로그를 남겨 값을 확인한다 (에러가 난 뒤가 아니라 나기 전에 찍어야 함)

예외: 더 이상 위로 거슬러 올라갈 수 없는 경계(외부 API, 사용자 입력 등)에 도달했다면 거기서 원인을 확정하되, 같은 문제가 다른 경로로도 들어올 수 있으니 값을 검사하는 코드를 여러 층에 추가하는 것을 고려합니다(아래 4단계 참고).

### 3단계 — 가설은 한 번에 하나만 세우고 검증한다

- "X 때문에 Y가 발생한다"처럼 명확한 문장으로 가설을 적는다
- 그 가설이 맞다면 나타나야 할 증거가 무엇인지 먼저 말한 뒤 확인한다
- 검증할 때는 가장 작은 변경 하나만 넣고 돌려본다. 여러 곳을 한꺼번에 고치면 무엇이 효과가 있었는지 알 수 없다
- 가설이 틀렸으면 그 변경을 되돌리고 새 가설을 세운다. 틀린 수정 위에 다른 수정을 계속 얹지 않는다

**세 번 시도해도 안 고쳐졌다면, 네 번째 수정을 바로 시도하지 말고 멈춥니다.** 이건 가설이 틀린 게 아니라 구조 자체를 의심해야 하는 신호입니다 (아래 위험 신호 참고).

### 4단계 — 원인을 고치고, 재발을 막는 검사를 추가한다

- 증상이 나타난 자리가 아니라 1~2단계에서 찾은 진짜 원인 지점을 고친다
- 가능하면 값이 지나가는 여러 지점(입력받는 곳, 처리하는 곳, 저장/기록하는 곳)에 방어 코드를 추가해서, 다음에 비슷한 문제가 다른 경로로 들어와도 걸리게 한다
- **이 버그를 재현하는 테스트를 먼저 만든다.** 그 테스트가 수정 전에는 실패하고, 수정 후에는 통과하는지 반드시 확인한다

## 흔한 변명과 현실

| 이런 생각이 든다면 | 현실은 이렇다 |
|---|---|
| "일단 이거 바꿔보고 되나 보자" | 왜 되는지 모르면 언제 다시 깨질지도 모른다. 가설을 먼저 말로 적어라 |
| "고쳐졌으니까 됐어, 원인은 안 궁금해" | 원인을 모르면 같은 문제가 다른 곳에서 또 터진다. 지금 설명 못 하면 나중엔 더 못 한다 |
| "시간이 없어서 근본 원인까지 팔 여유가 없다" | 증상만 가리면 나중에 디버깅 시간이 몇 배로 늘어난다. 지금 10분 더 쓰는 게 싸다 |
| "여러 곳을 한꺼번에 고치면 더 빠르다" | 무엇이 효과 있었는지 알 수 없게 되고, 멀쩡한 코드까지 건드리게 된다 |
| "환경 문제인 것 같다, 재현이 안 된다" | 정말 그런지 확인할 것을 다 확인했는지부터 보자. 대부분의 "환경 탓"은 조사가 덜 된 것이다 |
| "테스트까지 쓸 필요는 없다, 이미 확인했다" | 지금 확인은 이번만 맞다. 재발 방지 테스트가 없으면 다음 사람(또는 미래의 나)이 또 겪는다 |

## 위험 신호 — 멈추고 다시 시작할 것

아래 중 하나라도 해당하면 지금 하던 시도를 멈추고 1단계로 돌아갑니다.

- 증거 없이 "아마 이것 때문일 것"이라고 짐작만으로 코드를 고치고 있다
- 왜 이 수정이 문제를 없앴는지 한 문장으로 설명이 안 된다
- 같은 문제를 세 번째 고치고 있다
- 여러 군데를 동시에 바꾸고 한 번에 돌려보고 있다
- "일단 되니까 넘어가자"는 생각이 든다
- 재현 조건을 정확히 모르는 채로 고치고 있다

## 완료 전 점검

- [ ] 증상이 왜 생겼는지 한두 문장으로 설명할 수 있는가
- [ ] 잘못된 값/동작이 처음 발생한 지점을 찾았는가 (증상이 보인 곳이 아니라)
- [ ] 이 버그를 재현하는 테스트를 만들었고, 수정 전에는 실패하는 것을 확인했는가
- [ ] 수정 후 그 테스트가 통과하는가
- [ ] 다른 기존 테스트들도 여전히 통과하는가
- [ ] 비슷한 문제가 다른 경로로 다시 들어올 가능성을 한 번이라도 생각해봤는가

위 항목을 다 채우지 못했다면 "고쳤다"고 말하지 않고 조사를 계속합니다.
