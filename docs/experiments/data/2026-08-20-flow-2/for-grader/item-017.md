# 근본 원인 디버깅

## 개요

**원인을 모르는 수정은 수정이 아니라 운입니다.** 증상이 사라졌다고 끝난 게 아닙니다 — 왜 사라졌는지 설명할 수 있어야 끝난 것입니다. 이 스킬은 추측으로 코드를 여기저기 건드리는 것을 막고, 증거 → 가설 → 검증 → 수정의 순서를 강제합니다.

## 언제 적용하나

버그·에러·예상과 다른 동작을 다룰 때는 항상 적용합니다. "간단한 버그니까 그냥 고치자"는 예외로 삼지 않습니다 — 간단해 보이는 버그일수록 추측으로 찔러보다 우연히 사라지는 경우가 많습니다.

예외: 사용자가 "시간이 없으니 일단 임시로 막아달라"처럼 명시적으로 임시 조치를 요청하면 그렇게 하되, 반드시 "이건 원인을 못 찾은 임시 조치이며 다시 터질 수 있다"고 알립니다. 이 경우에도 혼자 판단하지 말고 사용자에게 확인받습니다.

## 디버깅 절차

이 네 단계는 순서대로 진행하며, 각 단계를 마치기 전에는 다음 단계로 넘어가지 않습니다.

### 1단계 — 증거를 모은다 (고칠 방법을 제안하기 전에)

아직 아무것도 고치려 하지 않습니다. 다음을 순서대로 확인합니다.

- **에러 메시지를 끝까지 읽는다** — 줄 번호, 파일 경로, 에러 코드까지 전부 확인합니다. 앞부분만 보고 짐작하지 않습니다.
- **재현 방법을 확정한다** — 정확히 어떤 단계를 거치면 재현되는지, 매번 재현되는지를 확인합니다. 재현이 안 되면 추측으로 넘어가지 말고 로그나 기록을 더 모읍니다.
- **최근 무엇이 바뀌었는지 확인한다** — 최근 커밋, 새로 추가된 의존성, 바뀐 설정값을 봅니다.
- **여러 부분(컴포넌트)을 거치는 문제라면 경계마다 표시를 남긴다** — 예: API 요청이 들어오는 지점, 처리하는 지점, 응답을 내보내는 지점마다 값을 출력해보고 한 번 실행해서 "어디까지는 정상, 어디서부터 깨지는지"를 먼저 찾습니다. 짐작으로 의심되는 곳부터 고치지 않습니다.
- **잘못된 값이 처음 어디서 생겼는지 거슬러 올라간다** — 에러가 난 자리가 아니라, 그 잘못된 값이 처음 만들어진 자리를 찾습니다. 에러 난 자리에서만 고치면 증상만 가려질 수 있습니다.

이 단계가 끝나기 전에는 "이렇게 고치면 될 것 같다"는 말을 하지 않습니다.

### 2단계 — 비슷한데 잘 되는 경우와 비교한다

같은 종류의 코드인데 잘 동작하는 예가 있다면 찾아서, 문제가 되는 코드와 무엇이 다른지 전부 나열합니다. 이 차이 목록이 다음 단계의 재료가 됩니다.

### 3단계 — 가설은 한 번에 하나만 세우고, 가장 작게 검증한다

- 가설은 "~ 때문에 ~가 원인일 것이다"처럼 분명한 문장으로 적습니다.
- 검증은 가능한 가장 작은 변경 하나로 합니다. 짐작되는 여러 곳을 한꺼번에 고치고 돌려보지 않습니다 — 그렇게 하면 무엇이 실제 원인이었는지 알 수 없게 됩니다.
- 가설이 맞지 않았다면, 방금 만든 수정을 그대로 둔 채 다음 걸 더 얹지 않습니다. 일단 되돌리고 새 가설을 세웁니다.
- 모르는 부분이 있으면 아는 척하지 않고 "여기까지는 확인했고, 이 부분은 아직 모른다"고 밝힙니다.

**같은 수정을 세 번째 시도하고 있다면 멈춥니다.** 세 번 넘게 고쳐도 안 됐다면 개별 버그가 아니라 구조 자체가 잘못됐을 가능성이 큽니다. 이때는 네 번째 수정을 바로 시도하지 말고, 무엇이 구조적으로 잘못됐는지 먼저 짚고 넘어갑니다.

### 4단계 — 원인을 재현하는 테스트를 먼저 만들고 나서 고친다

- 고치기 전에, 그 버그를 재현하는 실패하는 테스트(또는 재현 스크립트)를 먼저 만듭니다. 이게 없으면 나중에 "진짜로 고쳐졌는지" 증명할 방법이 없고, 같은 문제가 돌아와도 알아채지 못합니다.
- 정식 테스트 틀이 없는 프로젝트라면 임시 재현 스크립트라도 만듭니다.
- 고칠 때는 한 번에 하나만 고칩니다. 고치는 김에 다른 것도 정리하거나 손보지 않습니다 — 무엇이 실제로 문제를 해결했는지 구분할 수 없게 됩니다.

## 원인 없이 "고쳐졌다"고 말하지 않기

아래 표현은 원인을 설명하지 못한 채로 쓰면 안 됩니다. 왼쪽처럼 말하고 싶어질 때, 오른쪽처럼 스스로 되묻습니다.

| 이렇게 말하고 싶을 때 | 스스로 되물을 것 |
|---|---|
| "이거 바꾸니까 되네요, 일단 넘어갈게요" | 왜 되는지 설명할 수 있는가? 설명 못 하면 아직 끝난 게 아니다 |
| "증상이 사라졌으니 고쳐진 것 같습니다" | 원인이 된 값이 어디서 왔는지 짚을 수 있는가? |
| "다시 실행해보니 안 나네요" | 재현 조건이 원래부터 불안정했던 건 아닌가? 우연히 피해간 것 아닌가? |
| "여러 군데를 고쳤는데 이제 됩니다" | 그중 어느 수정이 실제로 원인을 없앤 것인지 알고 있는가? |

정말로 "환경 문제였다", "타이밍 문제였다"처럼 뚜렷한 원인 없이 끝내야 하는 경우도 있습니다. 이렇게 결론 내리려면 다음을 모두 지킵니다.
- 1단계 조사를 끝까지 마쳤다.
- 무엇을 확인했는지 기록으로 남긴다.
- 그런 상황을 견딜 수 있도록 재시도, 시간 제한, 사용자 안내 문구 등의 처리를 넣는다.
- 나중에 다시 볼 수 있도록 로그나 기록을 남겨둔다.

이 네 가지 없이 "원인 불명"으로 끝내지 않습니다.

## 완료 전 점검

다음 질문에 모두 답할 수 있어야 "고쳤다"고 말합니다. 하나라도 막히면 3단계(가설 검증)로 돌아갑니다.

- [ ] 이 버그가 왜 일어났는지 한두 문장으로 설명할 수 있는가?
- [ ] 그 원인이 된 값이나 코드가 어디서, 왜 그렇게 만들어졌는지 짚을 수 있는가?
- [ ] 이 버그를 재현하는 테스트(또는 스크립트)를 만들었고, 수정 전에는 실패하는 것을 직접 봤는가?
- [ ] 수정 후 같은 테스트가 통과하는 것을 직접 돌려서 확인했는가?
- [ ] 관련된 다른 테스트나 기능이 이 수정으로 깨지지 않았는가?
- [ ] "왜 고쳐졌는지 모르지만 일단 된다"에 해당하는 부분이 남아있지 않은가?
