# 근본원인 디버깅

## 개요

**증상이 아니라 원인을 고친다. 왜 고쳐졌는지 설명할 수 없으면 아직 고친 게 아니다.**

여기저기 값을 바꿔보다가 우연히 통과하면, 그건 고친 게 아니라 운이 좋았던 것이다. 운으로 통과한 수정은 다른 곳에서 같은 문제를 다시 일으키거나, 지금 당장은 안 보이는 자리에서 조용히 실패한다.

## 언제 적용하나

- 항상 적용: 에러·버그 리포트·테스트 실패·예상과 다른 동작을 다룰 때
- 예외(사람에게 확인하고 넘어가도 되는 경우): 정말 급한 임시 조치(hotfix)가 필요하고, 나중에 근본 원인을 다시 조사하기로 명시적으로 합의한 경우. 이때도 "임시 조치이며 원인 조사가 남아있다"는 사실을 사용자에게 분명히 말한다.

## 디버깅 절차

아래 네 단계를 순서대로 밟는다. 각 단계를 끝내지 못했으면 다음 단계로 넘어가지 않는다.

### 1단계 — 원인 조사 (고칠 방법을 제안하기 전에)

증거를 다 모으기 전에는 "이렇게 고치면 될 것 같다"는 말을 하지 않는다.

- **에러 메시지를 끝까지 읽는다** — 줄 번호, 파일 경로, 오류 코드까지 전부
- **재현 방법을 확인한다** — 정확히 어떤 절차를 밟으면 재현되는가? 매번 재현되는가, 가끔만 재현되는가?
- **최근에 무엇이 바뀌었는지 본다** — 커밋 이력, 새로 추가된 의존성(라이브러리), 설정 변경
- **값이 어디서 왔는지 거슬러 올라간다** — 잘못된 값이 어느 지점에서 처음 만들어졌는지 추적한다

좋은 예: "TypeError가 사용자 목록을 렌더링하는 지점에서 나는데, 그 목록은 API 응답을 그대로 쓰고 있다. API가 빈 배열이 아니라 null을 돌려줄 때만 이 에러가 난다."

나쁜 예: "에러가 나니까 일단 null 체크를 여기저기 추가해보자."

### 2단계 — 패턴 분석

같은 종류의 코드 중 **잘 작동하는 예**를 찾아서 무엇이 다른지 전부 나열한다.

- 비슷한 기능인데 문제가 없는 코드는 무엇을 다르게 하고 있는가?
- 문제가 생긴 코드와 정상 코드 사이의 차이를 하나도 빠짐없이 적는다

이 단계를 건너뛰면, 우연히 비슷해 보이는 곳만 고치고 진짜 차이는 놓친다.

### 3단계 — 가설을 하나 세우고 검증한다

- 가설은 한 번에 **하나만** 세운다: "OO 때문에 XX가 원인이라고 본다"처럼 분명한 문장으로 적는다
- 가장 작은 변경으로 시험한다 — 한 번에 한 가지만 바꾼다
- 여러 곳을 한꺼번에 고치면, 나중에 무엇이 실제로 문제를 해결했는지 알 수 없다

좋은 예: "설정 값이 다음 단계로 안 넘어가서 실패한다고 본다 → 그 값 하나만 바꿔서 확인한다"

나쁜 예: "짚이는 곳 세 군데를 한꺼번에 고치고 다시 돌려본다"

- 가설이 맞았으면 → 4단계(고치기)로 간다
- 가설이 틀렸으면 → 그 수정을 남겨두지 말고 걷어낸 뒤, 새 가설을 세우고 3단계를 다시 밟는다

**세 번 규칙**: 시도한 가설이 세 번째도 안 맞았으면, 네 번째 가설을 바로 시도하지 않는다. 대신 멈추고 "이건 개별 버그가 아니라 구조 자체가 잘못된 것 아닐까?"를 사람과 논의한다. 고칠 때마다 엉뚱한 곳에서 새로운 문제가 튀어나오거나, 하나 고치면 다른 곳이 깨지는 것이 이런 구조적 문제의 신호다.

### 4단계 — 고친다

- 원인이 되는 지점(가능하면 값이 처음 잘못 만들어진 자리)을 고친다. 에러가 겉으로 드러난 자리가 아니다
- 이 문제를 재현하는 테스트나 확인 절차를 먼저 만들어, 지금은 실패하는 것을 확인한다
- 고친 뒤 그 테스트가 통과하는지 확인한다
- 한 번에 하나만 고친다 — 온 김에 다른 부분을 정리하거나 손보지 않는다

## 흔한 변명과 현실

| 이럴 때 드는 생각 | 현실 |
|---|---|
| "이거 바꾸니까 됐어, 이유는 모르겠지만" | 이유를 모르면 다른 입력값이나 다른 상황에서 같은 문제가 다시 난다. 왜 되는지 설명 못 하면 아직 고친 게 아니다 |
| "시간이 없으니 일단 이걸로 넘어가자" | 원인 모르고 넘어간 버그는 나중에 훨씬 알아보기 어려운 형태로 다시 나타난다. 지금 10분 더 쓰는 게 나중에 몇 시간 아낀다 |
| "비슷한 곳에서 이렇게 고쳤으니 여기도 이렇게 하면 되겠지" | 비슷해 보여도 원인이 다를 수 있다. 이 코드에서 직접 원인을 확인하지 않은 추측이다 |
| "에러가 없어졌으니 됐다" | 에러가 안 뜨는 것과 문제가 해결된 것은 다르다. try-catch로 에러를 삼켜도 에러는 안 뜬다 |
| "여러 군데를 동시에 고쳤는데 이제 되네" | 어느 수정이 실제로 원인을 해결했는지 모른다. 나머지 수정은 불필요하거나 오히려 다른 문제를 숨기고 있을 수 있다 |
| "재현이 잘 안 되니 그냥 넘어가자" | 재현이 어렵다는 건 조사가 덜 됐다는 신호다. 로그를 더 남기거나 조건을 더 좁혀서 재현 방법부터 확인한다 |

## 위험 신호

아래 중 하나라도 해당하면 멈추고 1단계(원인 조사)로 돌아간다.

- 왜 이 수정으로 문제가 해결됐는지 한 문장으로 설명할 수 없다
- 여러 곳을 한꺼번에 고치고 한 번에 돌려봤다
- "일단 되니까 넘어가자"는 생각이 들었다
- 같은 버그를 세 번째 고치고 있다
- 에러 메시지를 끝까지 읽지 않고 코드를 고치기 시작했다
- 재현 방법을 정확히 말할 수 없다
- 이 문제를 재현하는 테스트 없이 코드만 고쳤다

## 완료 전 점검

- [ ] 에러 메시지를 끝까지 읽었는가
- [ ] 재현 방법을 정확히 확인했는가 (매번 재현되는지 포함)
- [ ] 왜 문제가 생겼는지 한 문장으로 설명할 수 있는가
- [ ] 이 문제를 재현하는 테스트나 확인 절차를 만들고, 고치기 전에 실패하는 것을 확인했는가
- [ ] 고친 뒤 그 테스트가 통과하는지 확인했는가
- [ ] 한 번에 하나의 원인만 고쳤는가 (여러 곳을 동시에 바꾸지 않았는가)
- [ ] 이 수정이 다른 곳을 깨뜨리지 않았는지 확인했는가

위 항목을 다 채우지 못했다면 "고쳤다"고 말하지 않는다. 대신 지금까지 확인한 것과 아직 확실하지 않은 부분을 그대로 말한다.
