## 0. 이번 채점에서 추가한 두 축의 조작적 정의

**F — 절차 무결성 (0~4, 해당 없으면 N/A)**

- 적용 여부 판정: 문서가 "순서가 있는 절차"를 주장하는가. 주장하지 않으면 N/A.
- 4 = 순서 있는 단계 + `제시/제안했다`와 `승인/확인받았다`가 **서로 다른 문장** + 게이트 미통과 시 행동 명시 + **같은 게이트로 재진입하는** 예외/대체 경로
- 3 = 순서 + 분리된 게이트는 있으나 예외 경로가 없거나 미통과 시 행동이 불분명
- 2 = 순서는 있으나 단계가 뭉쳐 있어 제3자가 어느 단계를 건너뛰었는지 판정 불가
- 1 = 순서만 주장하고 게이트가 없거나 판정 불가
- 0 = 순서를 주장하는데 단계 참조가 깨졌거나 모순

**게이트 분해도 (0~4, 기계적 계수)**

{제시·보여주기, 질문, 명시적 대기·확인, 적용} 네 요소 중, 문서에서 **가장 강한 게이트 구절**에서 각각 **독립된 문장·불릿·화살표 체인 세그먼트**로 등장하는 것의 개수. 한 문장 안에서 접속으로 묶인 둘("보여주고 확인받은 뒤에만 진행한다")은 1개로 셌다. 이 규칙은 60건 전체에 동일하게 적용했다.

## 3. 주목할 관찰 (인용 근거 포함)

### 3.1 B축을 끌어내린 것 — ①번역 안 된 골격 용어, ②설명 없이 던져진 영어 약어

B=2 판정 24건 중 **19건**은 §9.2가 명시적으로 지목한 골격 용어(`Handoff`, `게이트`)가 독자가 실제로 수행해야 할 위치에 그대로 박혀 있다.

- item-002: 절 제목 자체가 "### 2단계 게이트". 초심자에게 "게이트"는 수행 지시가 아니라 미지의 명사다.
- item-011: "4. **게이트: 승인 대기**" — 절차의 한 단계 이름이 번역되지 않은 골격 용어다.
- item-046: "**게이트: 사용자가 답을 주기 전까지 다음 단계로 넘어가지 않는다.**" — 문장 자체는 판정 가능하지만 라벨이 미번역.
- item-006 / 007 / 035 / 037 / 040 / 041 / 046 / 052 / 055 / 058 / 060: "## Handoff / Done"이 완료 조건을 담는 섹션 제목으로 쓰인다. 완료 판정을 하려면 이 섹션을 읽어야 하므로 장식이 아니라 실행 경로 위에 있다.

②는 **주석 없는 영어 약어**다.

- item-019 / 020 / 045: 표 안에 "YAGNI"가 풀이 없이 등장 ("YAGNI. 지금 테스트가 요구하지 않는 코드는 아직 쓰지 않는다"). item-048은 같은 단어를 "(YAGNI 위반)"으로 괄호에 넣어 부수적으로 처리했기에 B=3으로 올렸다.
- item-032 / 049: "off-by-one"이 한글 문장 안에 원문 그대로. item-004는 "오프바이원 에러"로 음차되어 있으나 뜻은 여전히 미정의.
- item-045: "mock이 호출됐는지 여부만 확인하지 않습니다" — `mock`이 원문 그대로.
- item-056: "광고성 CTA 문구" — `CTA`가 풀이 없이 등장.
- item-019: "프로토타입/스파이크성 코드" — "스파이크"는 초심자에게 미정의.

③ 랜딩 페이지 계열(013 / 015 / 017 / 047 / 055 / 057)은 **디자인 전문어 밀도** 때문에 일괄 B=2다. 한 문서 안에서만 다음이 전부 무정의로 등장한다: "고대비 세리프 디스플레이", "테라코타 액센트", "애시드 그린/버밀리언", "헤어라인 괘선", "신문식 조밀 다단", "히어로 섹션", "브리프", "디자인 토큰", "ASCII 와이어프레임", `prefers-reduced-motion`, `border-radius: 0`. 초심자가 "이 룩으로 흘러갔는지" 스스로 판정하는 것은 불가능하다.

### 3.2 B축을 끌어올린 것 — 용어를 "나쁜 예"로만 쓰는 문서

B=4는 8건이며, 그중 6건이 라이브러리 설명 계열이다. 공통 장치는 **전문어를 금지 예시로만 등장시키고 본문에서는 쓰지 않는 것**이다.

- item-021: "'라이브러리', '프레임워크', '패키지' 같은 말도 처음엔 되도록 피하고 '도구', '도우미' 같은 말로 풀어씁니다." — 자기 문서의 어휘까지 통제한다.
- item-023: 나쁜 예로 "이것은 비동기 처리를 위한 프로미스 기반 라이브러리입니다"를 제시하고, 정작 "프로미스(Promise)"는 마지막에 괄호로만 붙인다.
- item-026: 나쁜 예 "axios는 Promise 기반의 HTTP 클라이언트입니다"와 좋은 예 "카페에서 주문을 대신 넣어주는 알바생"이 나란히 있다.
- item-053: "전문용어, 영어 약어, 프로젝트 이름을 이 문장에 넣지 않는다"가 첫 지시다.
- item-014 / 051: 기획 문서 계열인데 골격 용어를 전부 한국어로 옮겼다("자리표시자", "전체 점검", "마무리"). 같은 시나리오의 006 / 007 / 038 / 040이 `Handoff`·`게이트`를 남긴 것과 대비된다.

### 3.3 F=4를 만든 결정적 문장 — "보여준 것"과 "승인받은 것"의 명시적 분리

F=4인 17건 중 다수가 게이트 분리를 **한 문장으로 못 박는다**.

- item-018: "계획을 보여준 것과 승인받은 것은 다른 사건입니다 — 보여주기만 하고 넘어가지 않습니다."
- item-041: "정리해서 '보여준 것'과 '확인받은 것'은 다른 사건이다 — 보여주기만 하고 바로 코드를 쓰기 시작하지 않는다."
- item-046: "계획을 보여주기만 하고 바로 코드를 쓰는 것은 확인받은 것이 아니다."
- item-057: "제시만 하고 넘어가지 말고 명시적인 확인을 기다린다. 수정 요청이 있으면 반영 후 다시 확인받는다." — 수정 시 **같은 게이트로 재진입**하는 경로까지 갖춘 유일한 형태의 문장.
- item-050: 게이트가 아예 별도 단계 번호를 가진다. "3. 접근 방식 제시" / "4. 승인 받기" — 제3자가 어느 단계를 건너뛰었는지 즉시 판정된다.

게이트 미통과 시 행동까지 갖춘 예:

- item-022: "확인 전까지는 해당 행을 표시(하이라이트 또는 별도 메모)해 두고 나머지 정리는 계속 진행합니다." — 대기 중 무엇을 할지까지 지정.
- item-039: "하나라도 안 맞으면 정리 작업을 끝냈다고 말하지 않는다 / 구체적으로 짚어서 보고한다 / 물은 뒤에만 다음 단계로 넘어간다" — 세 요소가 세 개의 불릿으로 분해됨.
- item-058: "하나라도 남아있으면 그 항목으로 돌아가 2단계를 반복합니다."

### 3.4 F=1이 된 이유 — 게이트가 아예 없는 "템플릿형" 문서

F=1인 13건은 순서는 명확하지만 사용자 승인 지점이 없다. 라이브러리 설명 계열(016 / 021 / 023 / 028 / 053)과 코드 리뷰 일부(004 / 030 / 049), 말투 계열(001 / 005 / 008 / 025)이다. 이들은 "출력 순서"를 강제할 뿐 "진행 여부를 사람이 결정하는 지점"이 없다. 같은 코드 리뷰 시나리오라도 item-035("버그로 분류된 항목에 대해 고칠지 여부를 사용자에게 확인합니다")와 item-037("사용자가 🔴 항목에 대해 고쳐달라고 하면 그때 수정한다. 먼저 나서서 고치지 않는다")는 F=3으로 갈라진다.

### 3.5 E축이 3을 넘지 못한 이유 — 반복 섹션의 구조적 상습화

E=4가 한 건도 없다. 60건 전부 최소한 마무리 체크리스트 수준의 재기술이 있고, E=2인 25건은 **동일 규칙이 3개 이상 섹션에 재등장**한다. 전형은 디버깅·테스트 계열이다: 절차 본문 → "흔한 변명과 현실" 표 → "위험 신호" → "완료 전 점검"에 같은 규칙이 네 번 나온다(item-003 / 010 / 012 / 019 / 020 / 027 / 036 / 044 / 045). 랜딩 페이지 계열은 "흔한 기본값 3종" 목록이 description, 본문, 제약 섹션, 체크리스트에 최대 4번 반복된다(item-015 / 017 / 047 / 055 / 057).

### 3.6 자기모순 / 순서 파손

§9.2는 baseline에서 모순이 발견되지 않았다고 기록했으나, 이번에는 **절차 순서상의 모순 2건**이 있었다.

- **item-015**: "## Apply — 확인 후 전체 적용"(적용 단계)이 문서상 앞에 오고, 그 뒤에 "## 마지막 점검 (코드 쓰기 전)"이 와서 "고유성이 확인된 뒤에만 실제 코드를 작성한다"고 말한다. 적용 뒤에 "코드 쓰기 전" 점검이 배치되어 실행 순서가 스스로 어긋난다. → F=2, E=2.
- **item-031**: "## 적용 절차"의 3번이 "**적용 전 확인** — 프로필에 채워지지 않은 항목이 있으면 지어내지 말고 사용자에게 먼저 물어본다"인데, 1번(새 글 쓰기)·2번(기존 글 고치기)이 이미 적용 행위다. "적용 전"이 목록의 마지막에 온다. → F=2.

그 외 사실 관계 모순은 발견되지 않았다. item-025 / 031의 "금지 문구 목록에 있는 표현은 어떤 경우에도 쓰지 않는다"와 "금지 문구 목록(필요시 추가)"은 목록의 가변성과 준수 의무를 각각 말하는 것이므로 모순으로 세지 않았다.

### 3.7 A=4가 48건이 된 근거 (인용)

핵심 지시 자리에 리터럴·수치·명명된 포맷이 2종 이상 들어 있는 경우가 압도적이다.

- item-029: "수량 10 × 단가 5,000 = 50,000인데 공급가액이 45,000으로 적혀 있습니다."
- item-042: "공급가액 × 10% ≈ 부가세 (반올림 오차 1원 이내는 허용)" — 임계값이 명시된 유일한 검증 규칙.
- item-043: "전월 대비 증감률이 ±50%를 넘는 거래처가 있는가"
- item-020: `NameError: apply_discount is not defined`, `pytest.raises(ValueError)`
- item-060: `git config --list`, `npm list --depth=0`
- 반대로 A=2인 item-005는 프로필 항목이 전부 "(예: …)" 슬롯이고, 조작적 지시는 "짧은 문장 우선", "핵심으로 시작" 같은 태도 문장이다(§9.1(e)에 따라 슬롯은 지시로 세지 않았다).
