# 사전 등록 — flow 필드 A/B (2026-08-20)

> **생성 실행 전에 작성했다.** 1차·2차에서 판정선을 사후에 정해 두 번 어겼고,
> 3차에서 사전 등록으로 바로잡았다. 이번에도 같은 순서를 지킨다.

## 무엇을 재나

커밋 `a6e23bf`가 넣은 `flow` 필드(패턴 `four-phase-debugging-order`)가
**생성된 SKILL.md의 단계 구성에 닿는가.**

두 조건의 차이는 시스템 프롬프트에서 **9줄**뿐이다.

```
off : 75,687바이트 (커밋 74e33e2 시점 렌더와 바이트 단위 동일)
on  : 76,525바이트 (+838, 디버깅 섹션에만)
```

## 조건

| 시나리오 | 역할 | 반복 | 조건 | 합 |
|---|---|---|---|---|
| `02-debugging` | 측정 | 6 | on/off | 12 |
| `05-design` | 대조 | 3 | on/off | 6 |
| `09-mismatch-office` | 대조 | 3 | on/off | 6 |
| | | | | **24** |

10종을 다 돌리지 않는 이유: `flow`는 디버깅 카테고리에만 렌더된다. 대신 측정
셀의 반복을 3 → **6**으로 올린다. 3차에서 "3회로는 한 건만 튀어도 셀 평균이
±0.33을 넘는다"가 드러났으므로, 셀을 줄이고 반복을 늘리는 쪽을 택한다.

대조 시나리오 2종을 넣는 이유: 코퍼스는 요청 종류와 무관하게 통째로 주입되므로
+838바이트가 무관한 요청을 방해할 수 있다. `05-design`은 코퍼스가 풍부한 곳,
`09-mismatch-office`는 맞는 카테고리가 없는 요청이다.

## 판정 항목 (평균 아니라 건수로 센다)

디버깅 생성물 6건씩을 열어 셋을 본다. 각각 **예/아니오**다.

| # | 항목 | 예로 치는 조건 |
|---|---|---|
| A | **순서** | 절차가 `조사 → (분석) → 가설 → 구현` 순서로 놓였는가. 원인 조사 단계가 수정 단계보다 **앞**에 있으면 예 |
| B | **게이트** | "이 단계를 끝내야 다음으로" 류의 진행 조건이 **문장으로** 있는가. 단계 나열만 있으면 아니오 |
| C | **되돌아감** | "안 고쳐졌으면 앞 단계로 돌아간다" 류의 경로가 있는가 |

## 성공/실패 조건 (지금 못박는다)

- **채택**: A·B·C 중 **어느 하나라도** on이 off보다 **2건 이상** 많다
- **기각**: 세 항목 모두 차이가 **1건 이하**다
- **되돌림**: off에서 이미 A·B·C가 **각각 5/6 이상** 나온다
  → 잃은 것이 없었다는 뜻이므로 커밋 `a6e23bf`를 되돌리고 접는다
- **부작용**: 대조 시나리오에서 **구조 골격(archetype)이 바뀌거나** 생성 실패가
  나면 그것부터 조사한다. 대조군은 "안 바뀜"이 정상이다

3차에서 정한 판정 규칙을 그대로 쓴다 — **평균 차이는 보고는 하되 판정 근거로
쓰지 않는다.** 한 건만 움직인 것은 효과로 세지 않고, 그 한 건을 열어 원인을 적는다.

## 미리 적어두는 예상과 그 근거

- **A(순서)는 off에서도 상당수 나올 것이다.** `root-cause-first`의 `summary`가
  "증상이 아니라 근본 원인부터 조사한다"라 순서 힌트가 이미 있다. A만으로는
  변별이 안 될 가능성이 높다
- **B(게이트)가 가장 변별력이 클 것이다.** "끝내야 다음"은 어느 패턴에도 없다
- **C(되돌아감)는 off에서도 나올 수 있다.** `three-fix-rule`이 산문으로
  "3회 미만이면 조사 단계로 복귀"를 담고 있다

**빗나가면 그대로 적는다.** 2차에서 "상황이 묻힐 것"이라는 예측이 빗나갔고,
그것을 기록해둔 덕에 3차에서 같은 예측을 반복하지 않았다.

## 채점 방식

생성 직후 조건 라벨을 떼고 섞어 `for-grader/`에 넣는다. 정답지는 `answer-key/`에
분리 저장한다. 3차까지 쓴 방식과 같다 — 실험 설계자가 라벨을 보며 채점하면
자문자답이 된다.
