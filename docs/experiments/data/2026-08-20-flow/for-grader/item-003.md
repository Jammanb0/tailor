# 근본 원인 디버깅

## 개요

**왜 고쳐졌는지 설명할 수 없으면, 아직 고친 게 아니다.**

버그를 잡는 가장 빠른 것처럼 보이는 방법은 코드 여기저기를 바꿔보다가 증상이 사라지면 멈추는 것이다. 하지만 이렇게 고친 버그는 원인을 모르기 때문에 다른 모습으로 되돌아오거나, 방금 고친 자리 옆에서 새로운 문제를 만든다. 이 스킬은 "증상 제거"가 아니라 "원인 규명"을 목표로 삼도록 순서를 강제한다.

## 언제 적용하나

- 항상 적용: 에러, 실패하는 테스트, 예상과 다른 동작을 발견했을 때
- 예외(사람에게 확인 후 건너뛸 수 있음): 급하게 임시 방편(hotfix)만 필요하고, 근본 원인은 별도 일감으로 남기기로 명시적으로 합의한 경우. 이 경우에도 "임시 방편이며 원인 미상"이라고 반드시 기록한다.

## 절차

### 1단계 — 증상을 있는 그대로 읽는다

고치는 방법을 떠올리기 전에 먼저 관찰한다.

- 에러 메시지를 끝까지 읽는다 — 줄 번호, 파일 경로, 에러 코드까지 전부
- 정확히 어떤 단계를 밟으면 재현되는지 적는다
- 매번 재현되는지, 가끔만 재현되는지 확인한다
- 최근에 무엇이 바뀌었는지 확인한다 — 코드 변경 이력(커밋), 새로 추가된 의존성, 설정 변경

재현이 안 되면 "아마 이것 때문일 것"이라고 추측으로 넘어가지 말고, 재현되는 조건을 더 좁혀서 다시 시도한다.

### 2단계 — 여러 조각을 거치는 문제는 경계마다 증거를 남긴다

프론트엔드→백엔드→데이터베이스처럼 여러 구성 요소를 거치는 문제라면, 어느 구성 요소가 문제인지부터 알아내야 한다. 짐작으로 하나를 찍어서 고치기 시작하지 않는다.

1. 각 경계(구성 요소 사이의 연결 지점)마다 값을 기록(로그)한다 — 무엇이 들어왔는지, 무엇이 나갔는지, 설정값이 제대로 넘어갔는지, 그 단계의 상태는 어떤지
2. 한 번 실행해서 그 기록들을 모은다
3. 기록을 보고 어느 경계에서 값이 이상해지는지(깨지는지) 찾는다
4. 그 구성 요소만 집중해서 더 조사한다

좋은 예: 로그를 찍어보니 A 단계까지는 값이 정상인데 B 단계 진입 시점에는 비어 있다 — B로 넘어가는 경계가 문제 지점이다.
나쁜 예: "이게 제일 의심스러워 보인다"며 증거 없이 특정 구성 요소부터 고치기 시작한다.

### 3단계 — 문제가 터진 자리가 아니라, 잘못된 값이 "처음 생긴" 자리를 찾는다

에러가 표면화된 위치와 진짜 원인이 만들어진 위치는 대체로 다르다. 표면 위치에서 고치면 증상만 감춰질 뿐 같은 원인이 다른 곳에서 다시 터진다.

- 증상이 나타난 지점을 본다
- 그 직접적인 원인이 된 지점을 찾는다
- 그 지점을 호출한(부른) 곳을 확인한다
- 값이 처음 만들어진 곳에 도달할 때까지 계속 거슬러 올라간다

손으로 따라가기 어려우면, 의심되는 동작 직전에 로그를 남겨서 실패하기 전 상태를 눈으로 확인한다.

예외: 정말로 더 이상 거슬러 올라갈 수 없는 경계(예: 외부 API 응답)라면 그 지점에서 방어 코드를 넣되, 그 사실을 "여기가 진짜 원인이 아니라 방어선"이라고 명시한다.

### 4단계 — 가설은 한 번에 하나만 세우고, 가장 작은 변경으로 검증한다

"이것 때문일 것 같다"는 생각이 들면, 그것을 말로 분명하게 적는다. 예: "설정값 X가 다음 함수로 전달되지 않아서 실패한다고 본다."

- 가설을 검증할 때는 그 가설과 직접 관련된 가장 작은 변경 하나만 만든다
- 여러 곳을 한꺼번에 고치고 돌려보지 않는다 — 그러면 무엇이 실제로 효과가 있었는지 알 수 없다
- 가설이 틀렸으면, 그 수정을 남겨둔 채 다음 가설을 시도하지 않는다. 되돌리고 새로 시작한다
- 모르는 부분이 있으면 "확실하다"고 하지 말고 "모른다"고 인정한다

### 5단계 — 고치기 전에 그 문제를 재현하는 "실패하는 테스트"를 먼저 만든다

원인을 찾았다고 판단되면, 곧바로 코드를 고치지 말고 먼저 그 버그를 재현하는 테스트(혹은 재현 스크립트)를 만든다. 이 테스트는 지금은 실패해야 정상이다.

- 자동화된 테스트 프레임워크가 있으면 그것을 쓰고, 마땅한 게 없으면 간단한 재현 스크립트라도 만든다
- 이 테스트가 없으면 나중에 "진짜 고쳐졌는지", "왜 고쳐졌는지"를 증명할 방법이 없다
- 이 단계에서 발견한 다른 문제나 개선점을 함께 고치지 않는다 — 한 번에 하나만 고친다

### 6단계 — 세 번 고쳐도 안 되면 구조 자체를 의심한다

시도한 수정이 통하지 않았다면 몇 번째 시도인지 센다.

- 3회 미만이면: 1~4단계로 돌아가 새로 알게 된 정보를 반영해 가설을 다시 세운다
- 3회 이상이면: 멈춘다. 개별 버그가 아니라 설계·구조 자체가 잘못됐을 가능성을 검토한다. 이 논의 없이 네 번째 수정을 바로 시도하지 않는다

구조 문제일 때 나타나는 징후:
- 고칠 때마다 예상치 못한 다른 곳에서 새로운 문제가 튀어나온다
- 제대로 고치려면 큰 범위의 재작업이 필요해 보인다
- 하나를 고치면 다른 곳에서 비슷한 증상이 또 생긴다

### 7단계 — 원인을 찾은 뒤에는 여러 층에 방어를 넣는다

원인 지점 한 곳만 고치면, 그 검사를 우회하는 다른 경로에서 같은 문제가 다시 생길 수 있다. 가능하면 값이 지나가는 여러 층에 각각 검사를 추가한다.

- 입력 지점 — 명백히 잘못된 값을 여기서 걸러낸다
- 처리 지점 — 이 작업 맥락에서 말이 되는 값인지 확인한다
- 실행 환경 — 특정 상황에서 위험한 동작을 막는다
- 기록(로깅) — 나중에 문제가 다시 생기면 추적할 수 있도록 맥락을 남긴다

## 흔한 변명과 현실

| 이런 생각이 들 때 | 실제로는 |
|---|---|
| "일단 이거 바꿔보고 되는지 보자" | 우연히 되면 왜 됐는지 영원히 모른다. 가설 없이 바꾸는 건 조사가 아니라 도박이다 |
| "증상이 없어졌으니 됐다" | 증상 소멸과 원인 해결은 다르다. 원인을 말로 설명 못 하면 아직 모르는 상태다 |
| "시간이 없으니 대충 고치고 넘어가자" | 임시 방편이면 그렇다고 기록해야 한다. 기록 없이 넘기면 나중에 아무도 이게 임시라는 걸 모른다 |
| "이 정도면 딱 봐도 원인 같다" | 짐작이 맞는지 확인하는 데는 로그 한 줄, 테스트 하나면 충분하다. 확인 없이 넘어갈 이유가 없다 |
| "여러 군데 동시에 고치면 더 빠르다" | 무엇이 효과가 있었는지 구분할 수 없게 된다. 나중에 또 같은 조사를 반복해야 한다 |
| "재현이 안 되니 그냥 넘어가자" | 재현 조건을 더 좁혀볼 여지가 남아있다. 환경 탓으로 돌리는 결론은 조사를 다 마친 뒤에만 내린다 |
| "테스트까지 쓸 정도는 아니다" | 테스트가 없으면 이 수정이 진짜 원인을 잡았는지 증명할 방법이 없다 |

## 위험 신호

아래 중 하나라도 해당하면 멈추고 1단계로 돌아간다.

- 왜 고쳐졌는지 한 문장으로 설명하지 못한다
- 여러 곳을 한꺼번에 고치고 한 번에 돌려봤다
- "일단 되는 것 같다"는 느낌만으로 다음 작업으로 넘어가려 한다
- 같은 파일을 세 번째 고치고 있다
- 재현 테스트 없이 "고쳐졌다"고 말하려 한다
- 에러 메시지를 끝까지 읽지 않았다
- 최근 변경 이력을 확인하지 않았다

## 완료 전 점검

- [ ] 원인을 한두 문장으로 설명할 수 있는가
- [ ] 그 원인이 값이 처음 잘못된 지점까지 거슬러 올라간 결과인가 (증상이 나타난 자리가 아니라)
- [ ] 이 버그를 재현하는 테스트를 실패하는 것으로 먼저 확인했는가
- [ ] 수정 후 그 테스트가 통과하는가
- [ ] 수정한 이유를 한 번에 하나의 변경으로 검증했는가 (여러 곳을 동시에 바꾸지 않았는가)
- [ ] 임시 방편이라면 그렇다고 명시적으로 기록했는가

위 항목을 다 채우지 못했다면 아직 "고쳤다"고 말할 단계가 아니다.
