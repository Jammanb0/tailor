# 근본원인 디버깅

## 개요

**원인을 말로 설명할 수 없으면, 아직 고친 게 아니다.**

버그가 사라졌다고 해결된 게 아닙니다. "왜 이 코드가 문제를 일으켰는지"와 "왜 이 수정이 그것을 없애는지"를 둘 다 설명할 수 있을 때만 고친 것입니다. 우연히 사라진 버그는 다른 곳에서, 다른 모습으로 반드시 돌아옵니다.

## 언제 적용하나

- 항상 적용: 에러, 실패하는 테스트, 예상과 다른 동작을 고칠 때 전부
- 예외: 사용자가 명시적으로 "빨리 임시로 막고 넘어가자"고 요청한 경우. 이때도 "이건 근본 원인을 고친 게 아니라 증상만 가린 것"임을 반드시 말로 밝히고 넘어갑니다.

## 절차

### 1단계 — 증거부터 모은다 (추측 금지)

고칠 방법을 생각하기 전에 아래를 순서대로 확인합니다.

- **에러 메시지를 끝까지 읽는다** — 줄 번호, 파일 경로, 에러 코드까지 전부. 앞부분만 보고 짐작하지 않습니다.
- **재현 절차를 명확히 한다** — 정확히 어떤 단계를 밟아야 재현되는지, 매번 똑같이 재현되는지 확인합니다.
  - 재현이 안 되거나 들쭉날쭉하면 다음 단계로 넘어가지 말고 재현 조건부터 더 좁힙니다.
- **최근 변경사항을 확인한다** — 커밋 이력(코드 변경 기록), 새로 추가된 의존성(외부 라이브러리), 설정 변경.
- **여러 조각을 거치는 문제라면 경계마다 증거를 남긴다** — 예: 프론트엔드 → API → 데이터베이스처럼 여러 층을 거치는 요청이라면, 각 층에 값이 들어오고 나가는지 로그나 출력을 찍어 실제로 한 번 돌려봅니다. "아마 여기가 문제일 것 같다"가 아니라 "찍어보니 여기서부터 값이 비어있다"를 확보합니다.

좋은 예: "로그를 찍어보니 API까지는 값이 정상적으로 들어오는데, 데이터베이스 저장 함수 진입 시점엔 이미 null이다 — 그 사이 어딘가가 범인이다."
나쁜 예: "데이터베이스 쪽 문제인 것 같으니까 일단 그 코드를 고쳐보자."

### 2단계 — 잘못된 값이 처음 생긴 자리까지 거슬러 올라간다

에러가 발생한 지점이 원인이 아닌 경우가 대부분입니다. 값이 잘못되기 시작한 지점을 찾아야 합니다.

- 증상이 나타난 지점에서 시작해서, 그 값을 넘겨준 곳, 또 그 값을 넘겨준 곳으로 한 단계씩 거슬러 올라갑니다.
- 손으로 따라가기 어려우면, 의심되는 동작 **직전**에 로그를 남겨서 값을 확인합니다. (실패한 뒤에 로그를 남기면 이미 늦습니다.)
- 더 이상 거슬러 올라갈 수 없는 경계(예: 외부 API 응답, 사용자 입력)에 도달하면 거기서 멈추되, 그 경계 자체를 검증하는 방어 코드를 추가할 계획을 세웁니다.

### 3단계 — 가설은 한 번에 하나만 세우고, 최소한으로 시험한다

- "OO 때문에 이 문제가 생긴다"라고 한 문장으로 분명하게 말할 수 있어야 합니다. 말로 못 하면 아직 가설이 아닙니다.
- 가설을 시험할 때는 **가장 작은 변경 하나만** 해서 확인합니다. 여러 곳을 한꺼번에 고치면 무엇이 원인이었는지 알 수 없게 됩니다.
- 가설이 틀렸으면, 방금 한 수정을 남겨둔 채 다음 걸 시도하지 말고 **원상복구한 뒤** 새 가설을 세웁니다.
- 모르겠으면 "모르겠다"고 말합니다. 아는 척하고 넘어가지 않습니다.

### 4단계 — 원인을 찾았으면, 재현하는 테스트(또는 확인 절차)부터 만든다

- 고치기 전에 이 문제를 그대로 재현하는 테스트를 먼저 만듭니다. 자동화된 테스트가 있는 프로젝트면 테스트 코드로, 없으면 재현 스크립트나 수동 확인 절차라도 만듭니다.
- 이 테스트가 지금은 실패하는 것을 직접 확인합니다.
- 그 다음 원인이 되는 지점만 고칩니다. 고치는 김에 다른 것도 손보거나 정리하지 않습니다.

### 5단계 — 고친 뒤, 되돌려서 다시 확인한다 (증명 단계)

"고쳤다"고 말하기 전에 아래를 실제로 실행해서 확인합니다.

1. 방금 만든 테스트(재현 절차)를 돌려서 **통과하는지** 확인합니다.
2. 방금 한 수정을 잠깐 되돌려서, 테스트가 다시 **실패하는지** 확인합니다. (이게 안 되면 이 테스트는 애초에 이 버그를 잡을 수 없는 테스트입니다.)
3. 수정을 다시 되살리고, 통과하는지 마지막으로 확인합니다.
4. 관련된 다른 테스트나 기능이 이번 수정으로 깨지지 않았는지 확인합니다.

이 왕복(통과 → 되돌려서 실패 → 되살려서 통과)을 하지 않았다면, "고쳐졌다"는 아직 증명되지 않은 주장입니다.

## 세 번 고쳐도 안 되면 구조를 의심한다

같은 문제를 고치려고 세 번째 시도를 하고 있다면, 멈추고 다음을 확인합니다.

- 고칠 때마다 예상 못 한 다른 곳에서 문제가 튀어나오는가
- 하나 고치면 다른 데서 증상이 생기는가
- "제대로 고치려면 대공사가 필요하다"는 느낌이 드는가

위에 해당하면 이건 가설이 틀린 게 아니라 **구조 자체가 잘못된 것**입니다. 이 경우 네 번째 임시 수정을 바로 시도하지 말고, 무엇이 근본적으로 잘못됐는지를 먼저 정리해서 사용자에게 알립니다.

## 흔한 변명과 현실

| 이런 생각이 든다면 | 실제로는 이렇습니다 |
|---|---|
| "이거 바꾸니까 되네, 일단 넘어가자" | 왜 되는지 모르면 다른 조건에서 다시 터집니다. 설명 못 하면 아직 고친 게 아닙니다. |
| "시간이 없으니까 원인 조사는 나중에" | 원인을 모르고 고친 버그는 높은 확률로 재발하고, 그때는 지금보다 더 급한 상황일 겁니다. |
| "테스트까지 만들 정도는 아닌 것 같다" | 테스트(또는 재현 절차) 없이는 정말 고쳐졌는지 확인할 방법이 없습니다. "될 것 같다"는 증거가 아닙니다. |
| "여러 군데를 한꺼번에 고치면 더 빠르지 않을까" | 여러 곳을 동시에 바꾸면 어느 것이 원인이었는지 영원히 알 수 없게 됩니다. |
| "이 정도면 충분히 원인을 안 것 같다" | "~인 것 같다"는 가설이지 확인이 아닙니다. 실제로 값을 찍어보거나 되돌려서 확인해야 압니다. |

## 위험 신호 — 이 중 하나라도 해당하면 멈추고 1단계로 돌아간다

- 왜 이 수정으로 문제가 사라졌는지 한 문장으로 설명하지 못한다
- 여러 곳을 동시에 고치고 한 번에 돌려봤다
- 재현 절차 없이 "이제 안 될 것이다"라고 생각하고 있다
- 에러 메시지를 끝까지 읽지 않고 코드부터 고쳤다
- 이번이 같은 문제에 대한 세 번째 이상의 수정 시도다
- "일단 되니까 넘어가자"는 생각이 스치고 있다

## 완료 전 점검

- [ ] 에러 메시지와 재현 절차를 끝까지 확인했는가
- [ ] 잘못된 값이 어디서 처음 생겼는지 거슬러 올라갔는가
- [ ] 가설을 한 문장으로 말할 수 있는가
- [ ] 이 문제를 재현하는 테스트(또는 확인 절차)를 만들었는가
- [ ] 수정 후 테스트가 통과하는 것을 확인했는가
- [ ] 수정을 되돌렸을 때 테스트가 다시 실패하는 것을 확인했는가
- [ ] 관련된 다른 기능이 깨지지 않았는지 확인했는가

위 항목을 다 채우지 못했다면 "고쳤다"고 말하지 않습니다.
