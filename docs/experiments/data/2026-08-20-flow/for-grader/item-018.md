# 근본원인 디버깅

## 개요

**원인을 말로 설명할 수 없으면, 아직 고친 게 아니다.**

버그를 고치는 가장 빠른 길처럼 보이는 방법은 의심되는 곳을 이것저것 바꿔보다가 증상이 사라지면 끝내는 것입니다. 하지만 이 방식은 왜 됐는지 모르기 때문에, 같은 버그가 다른 모습으로 곧 다시 나타나거나, 고치는 과정에서 멀쩍이 있는 다른 기능을 조용히 망가뜨립니다. 이 스킬은 그런 "찍어서 고치기"를 막고, 항상 다음 순서를 따르게 합니다:

**원인 조사 → 가설 검증 → 재현 테스트 작성 → 수정 → 확인**

이 순서에서 어떤 단계도 건너뛰지 않습니다. 특히 "증상이 사라졌다"는 것과 "원인을 찾았다"는 것은 다른 사건이라는 점이 이 스킬의 핵심입니다.

## 언제 적용하나

- 버그 리포트, 에러 메시지, 예상과 다른 동작을 다룰 때는 항상 이 절차를 적용합니다.
- 다음의 경우는 예외로 삼을 수 있지만, 예외로 할지는 반드시 사용자에게 먼저 확인합니다:
  - 버릴 프로토타입 코드에서 발생한 문제
  - 명백한 오타 수준의 문제(예: 변수명 철자 하나 틀림)를 눈으로 바로 확인한 경우

## 절차

### 1단계 — 원인 조사 (증거를 모으기 전에는 고칠 방법을 제안하지 않는다)

다음을 순서대로 확인합니다. 이 단계를 끝내기 전에는 "이렇게 고치면 될 것 같다"는 말을 하지 않습니다.

1. **에러 메시지를 끝까지 읽는다** — 줄 번호, 파일 경로, 에러 코드까지 전부 확인합니다. 일부만 보고 넘어가지 않습니다.
2. **재현 절차를 확정한다** — 정확히 어떤 단계를 거치면 문제가 나타나는지 적고, 매번 똑같이 재현되는지 확인합니다. 재현이 안 되면 추측으로 넘어가지 말고 자료(로그, 재현 조건)를 더 모읍니다.
3. **최근에 무엇이 바뀌었는지 확인한다** — 최근 코드 변경 내역, 새로 추가된 의존성, 설정 변경 등을 살핍니다.
4. **여러 부분(컴포넌트)을 거치는 문제라면 경계마다 증거를 남긴다** — 예를 들어 화면 → API 서버 → 데이터베이스처럼 여러 층을 거치는 경우, 각 층에 값을 출력하거나 기록해서 "값이 들어오고 나가는지"를 확인합니다. 어느 층까지는 정상이고 어느 층부터 이상한지 먼저 좁힌 뒤에, 그 층만 자세히 들여다봅니다.
   - 좋은 예: 여러 층에 값을 찍어보니 앞 단계까지는 정상이고 다음 단계에서 비어 있었다 → 그 사이가 범인이다.
   - 나쁜 예: 증거 없이 "제일 그럴듯해 보이는 곳"부터 고쳐본다.
5. **잘못된 값이 어디서 처음 생겼는지 거슬러 올라간다** — 에러가 난 자리가 아니라, 그 잘못된 값이 맨 처음 만들어진 자리를 찾습니다. 에러가 난 자리에서만 고치면 증상만 가려질 뿐입니다.

### 2단계 — 가설은 한 번에 하나만 세우고 검증한다

- "OO 때문에 XX가 원인이라고 본다"처럼 가설을 명확한 문장으로 적습니다.
- 검증은 **가장 작은 변경**으로, **한 번에 한 가지만** 바꿔서 합니다. 여러 곳을 동시에 고치면 무엇이 실제 원인이었는지 알 수 없게 됩니다.
- 가설이 맞지 않았다면, 그 위에 다른 수정을 덧붙이지 말고 **그 시도를 되돌린 뒤** 새 가설을 세웁니다.
- 모르는 부분이 있으면 아는 척하지 말고 "이 부분은 아직 확실하지 않다"고 표시합니다.
  - 좋은 예: "설정 값이 다음 단계로 넘어가지 않아서 실패한다"는 가설을 세우고, 그 값 하나만 바꿔서 확인한다.
  - 나쁜 예: 짚이는 세 곳을 한꺼번에 고치고 한 번에 돌려본다.

### 3단계 — 원인을 재현하는 실패 테스트를 먼저 만든다

수정 코드를 쓰기 전에, 이 버그를 다시 실패시켜 보여주는 테스트(또는 재현 스크립트)를 만듭니다.

- 테스트가 없으면 "고쳤다"는 것을 증명할 방법이 없고, 나중에 같은 문제가 다시 생겨도 알아채지 못합니다.
- 정식 테스트 프레임워크가 있으면 그것을 쓰고, 마땅한 도구가 없으면 문제를 재현하는 간단한 스크립트라도 만듭니다.
- 이 테스트가 **지금은 실패하는 것**을 실제로 확인합니다. (에러가 나는 것과 "의도한 이유로 실패하는 것"은 다릅니다 — 오타 때문에 실행 자체가 안 되는 것이 아니라, 버그 자체 때문에 원하는 결과가 안 나오는지 확인합니다.)

### 4단계 — 딱 하나만 고친다

- 2단계에서 확인한 원인에 대해서만 수정합니다.
- "온 김에" 다른 부분을 정리하거나 관련 없는 개선을 함께 넣지 않습니다.
- 원인이 되는 값이 지나가는 여러 지점이 있다면, 가능한 지점마다 방어 코드를 넣는 것도 고려합니다(예: 값이 들어오는 자리에서 걸러내기, 처리하는 자리에서 유효성 검사, 문제 상황을 기록으로 남기기).

### 5단계 — 확인한다 (여기서 되돌아갈 곳은 코드다, 테스트가 아니다)

- 3단계에서 만든 테스트를 다시 돌려서 **통과하는지** 확인합니다.
- 관련된 다른 테스트들도 여전히 통과하는지 함께 확인합니다.
- 재현 절차(1단계에서 확정한 절차)를 실제로 다시 밟아서 증상이 사라졌는지 직접 확인합니다.
- 만약 테스트가 실패한다면, **테스트를 고쳐서 통과시키지 않습니다.** 테스트가 옳다면 코드를 다시 고칩니다.
- 원인을 한 문장으로 설명할 수 있어야 이 단계가 끝난 것입니다. 설명이 안 되면 3단계나 1단계로 돌아갑니다.

## 세 번 고쳐도 안 되면 구조를 의심한다

같은 문제를 고치려는 시도가 세 번째에 접어들었다면, 네 번째 시도를 바로 하지 않습니다. 대신 멈추고 다음을 의심합니다:

- 고칠 때마다 예상치 못한 곳에서 새로운 문제가 튀어나온다
- 제대로 고치려면 훨씬 큰 규모의 수정이 필요해 보인다
- 하나를 고치면 다른 곳에서 비슷한 증상이 또 생긴다

이런 신호가 보이면 "가설이 틀렸다"가 아니라 "설계나 구조 자체가 문제"일 가능성이 높습니다. 이때는 사용자에게 상황을 설명하고 구조적인 논의를 먼저 합니다.

## 흔한 변명과 현실

| 이런 생각이 들 때 | 현실은 이렇다 |
|---|---|
| "일단 이거 바꿔보고 되면 그걸로 끝내자" | 왜 됐는지 모르면 같은 문제가 다른 모습으로 곧 재발합니다. 재현 테스트 없이는 "고쳤다"는 것 자체가 증명되지 않은 주장입니다. |
| "시간이 없으니 원인 조사는 나중에" | 원인을 모른 채 수정한 코드는 리뷰도, 재발 방지도 안 됩니다. 나중에 같은 버그가 또 나오면 조사 시간을 두 번 쓰게 됩니다. |
| "증상이 사라졌으니 됐다" | 증상이 사라진 것과 원인을 찾은 것은 다른 사건입니다. 다른 원인 때문에 우연히 증상이 안 보이게 됐을 수도 있습니다. |
| "여러 군데를 동시에 고치면 더 빠르다" | 여러 곳을 한꺼번에 바꾸면 어느 수정이 실제로 효과가 있었는지 알 수 없어, 결국 원인 불명 상태로 남습니다. |
| "이 정도면 자명한 원인이니 테스트는 생략해도 된다" | 자명해 보였던 원인이 틀렸던 경우가 실제로 가장 많이 재발합니다. 재현 테스트는 그 확신을 검증하는 유일한 방법입니다. |
| "일단 되니까 왜 됐는지는 나중에 알아도 된다" | "나중에"는 대부분 오지 않고, 다음에 비슷한 문제가 나면 처음부터 다시 조사해야 합니다. |

## 위험 신호 (하나라도 해당하면 멈추고 1단계로 돌아간다)

- 왜 이 수정으로 문제가 해결됐는지 한 문장으로 설명할 수 없다
- 재현 테스트 없이 "이제 됐다"고 말하려는 참이다
- 여러 곳을 동시에 고치고 한 번에 돌려서 결과만 봤다
- 에러 메시지를 끝까지 읽지 않고 짐작으로 넘어갔다
- 같은 문제를 세 번째 이상 고치는 중이다
- "일단 이렇게 해두고 나중에 제대로 보자"는 생각이 든다
- 테스트가 실패해서 테스트 쪽을 고쳐 통과시키려 하고 있다

## 완료 전 점검

- [ ] 에러 메시지를 끝까지 읽었는가
- [ ] 문제를 재현하는 절차를 확정하고 실제로 재현해봤는가
- [ ] 가설을 한 문장으로 명확히 세웠는가
- [ ] 그 가설을 검증하는 최소한의 변경만으로 확인했는가
- [ ] 이 버그를 재현하는 테스트를 먼저 만들고, 그것이 실패하는 것을 직접 봤는가
- [ ] 수정 후 그 테스트가 통과하는 것을 확인했는가
- [ ] 다른 기존 테스트들도 여전히 통과하는가
- [ ] 왜 이 수정으로 문제가 해결됐는지 한 문장으로 설명할 수 있는가

위 항목을 다 채우지 못했다면 "고쳤다"고 말하지 않고, 못 채운 항목에 해당하는 단계로 돌아갑니다.
