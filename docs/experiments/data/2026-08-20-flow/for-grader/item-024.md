# 근본원인 디버깅

## 개요

**원인을 말로 설명할 수 없으면, 아직 고친 게 아니다.** 코드를 이리저리 건드리다 증상이 사라지면 순간은 편하지만, 왜 사라졌는지 모르기 때문에 같은 문제가 다른 모습으로 돌아온다. 이 스킬은 "어디를 고쳤더니 됐다"가 아니라 "왜 이렇게 됐고, 그래서 여기를 고쳤다"는 순서로 작업하게 만든다.

## 언제 적용하나

- 에러 메시지, 예외, 크래시, 잘못된 결과값 등 버그를 다룰 때 항상 적용한다.
- 사용자가 "그냥 빨리 아무거나 시도해봐 달라"고 명시적으로 요청하면, 이 절차를 생략해도 되는지 먼저 확인받는다. 급한 임시 조치(hotfix)가 필요한 상황이라도, 조치 후에는 반드시 원인 조사로 돌아온다는 점을 사용자에게 알린다.

## 절차

### 1단계 — 증상을 있는 그대로 읽는다
- 에러 메시지, 스택 트레이스(에러가 어느 함수를 거쳐 발생했는지 보여주는 호출 기록)를 끝까지 읽는다. 줄 번호, 파일 경로, 에러 코드를 빠짐없이 확인한다.
- "대충 이런 에러겠지"라고 짐작하고 넘어가지 않는다. 실제 메시지 원문을 그대로 인용한다.

### 2단계 — 재현 조건을 확정한다
- 정확히 어떤 단계를 밟으면 문제가 나타나는지 적는다.
- 매번 재현되는지, 가끔만 재현되는지 확인한다.
- 재현이 안 되면 다음 단계로 넘어가지 않는다. 대신 재현할 방법을 더 찾거나, 로그·기록을 늘려 정보를 더 모은다. 재현되지 않는 상태에서의 수정은 추측일 뿐이다.

### 3단계 — 최근에 바뀐 것을 확인한다
- 최근 코드 변경 이력(커밋), 새로 추가된 의존성(라이브러리), 설정 변경을 살펴본다.
- 여러 부분(프론트엔드/백엔드, 여러 서비스 등)이 얽힌 문제라면, 각 경계마다 실제로 어떤 값이 들어오고 나가는지 로그나 출력으로 남긴 뒤 한 번 돌려서 어느 지점에서 값이 이상해지는지부터 좁힌다. 짐작으로 의심되는 코드부터 고치지 않는다.

### 4단계 — 잘못된 값의 출처까지 거슬러 올라간다
- 에러가 발생한 지점에서 멈추지 않는다. "이 값이 왜 이렇게 됐는가"를 한 단계씩 위로 따라 올라가, 그 값이 처음 만들어진 자리를 찾는다.
- 손으로 따라가기 어려우면, 의심되는 동작 직전에 값을 출력하거나 기록해서 확인한다. (문제가 터진 뒤가 아니라 터지기 전에 기록해야 한다.)
- 예외: 정말 더 이상 거슬러 올라갈 수 없다면, 지금 발견한 지점에서 고치되 다른 지점들에도 같은 문제를 막는 확인 코드를 함께 넣는다.

### 5단계 — 가설은 한 번에 하나만 세우고 검증한다
- "이것 때문에 이 문제가 생긴다"를 한 문장으로 분명히 말한다. 말로 설명이 안 되면 아직 원인을 모르는 것이다.
- 가장 작은 변경 하나로 그 가설을 시험한다. 여러 곳을 한꺼번에 고치지 않는다 — 그러면 무엇 때문에 고쳐졌는지 다시 알 수 없게 된다.
- 가설이 틀렸으면, 방금 한 수정을 남겨둔 채 다음 걸 얹지 말고 정리한 뒤 새 가설을 세운다.
- 같은 문제를 세 번째 고치려는 시점이 오면 일단 멈춘다. 그 전까지는 조사가 부족했던 것일 수 있지만, 세 번째부터는 접근 자체(코드 구조)가 잘못됐을 가능성을 의심하고, 계속 진행하기 전에 사람에게 알린다.

### 6단계 — 고치기 전에 실패하는 테스트(또는 재현 스크립트)를 먼저 만든다
- 이 문제를 그대로 재현하는 테스트나 스크립트를 먼저 만들고, 그것이 실제로 실패하는 것을 확인한다.
- 그 다음 원인이 되는 지점 하나만 고친다. 겸사겸사 다른 것도 정리하지 않는다.

### 7단계 — 고쳤다고 말하기 전에 직접 돌려서 확인한다
- 방금 만든 테스트(또는 재현 절차)를 처음부터 다시 실행해서 통과하는지 본다.
- 기존에 있던 다른 테스트들도 여전히 통과하는지 확인한다.
- "고쳤을 것이다", "이제 될 것 같다" 같은 표현은 실행 결과를 직접 확인하기 전에는 쓰지 않는다.
- 확인할 수 있다면, 고친 부분을 잠깐 되돌려서 테스트가 다시 실패하는지도 본다. 그래야 이 테스트가 진짜로 그 문제를 잡아낼 수 있다는 게 증명된다.

## 흔한 변명과 현실

| 이런 생각이 들 때 | 실제로는 |
|---|---|
| "일단 이거 하나 바꿔보고 되나 보자" | 왜 되는지 모르면 다음에 비슷한 문제가 또 터진다. 무엇을 확인하려는 변경인지 먼저 말로 정하고 바꾼다 |
| "재현이 잘 안 되니까 그냥 짐작 가는 곳부터 고치자" | 재현이 안 되는 채로 고치면 우연히 사라진 것과 구별이 안 된다. 정보를 더 모으는 쪽을 먼저 시도한다 |
| "여러 군데를 한꺼번에 고치면 더 빠르지 않나" | 그럼 뭐가 원인이었는지 영영 알 수 없다. 하나씩 확인해야 다음에 써먹을 수 있다 |
| "테스트 나중에 만들면 되지" | 나중에 만든 테스트는 이미 통과하는 코드에 맞춰지므로 실패하는 걸 본 적이 없다. 정말 이 문제를 잡아내는지 증명이 안 된다 |
| "돌려보진 않았지만 이 정도면 될 것 같다" | 될 것 같다는 느낌은 증거가 아니다. 실제로 실행한 결과만 증거다 |
| "세 번째 고치는 거지만 이번엔 될 것 같다" | 세 번 이상 안 됐다면 코드 구조 자체가 문제일 가능성이 크다. 멈추고 다시 생각한다 |

## 위험 신호

아래 중 하나라도 해당하면 하던 작업을 멈추고 3단계(재현 조건 확인)나 4단계(원인 추적)로 돌아간다.

- 왜 고쳐졌는지 한 문장으로 설명할 수 없다
- 같은 문제를 벌써 세 번째 고치고 있다
- 코드를 여러 군데 한꺼번에 바꿨다
- 실행해보지 않고 "이제 될 것 같다"고 말하려던 참이다
- 재현이 안 되는 상태에서 그냥 코드를 바꾸고 있다
- 에러 메시지를 끝까지 읽지 않고 넘어갔다

## 완료 전 점검

- [ ] 원인을 한 문장으로 설명할 수 있는가 ("이것 때문에 이 문제가 생겼다")
- [ ] 그 원인을 재현하는 테스트(또는 스크립트)를 만들고 실패하는 것을 직접 봤는가
- [ ] 수정 후 그 테스트가 통과하는 것을 직접 실행해서 확인했는가
- [ ] 기존 테스트들도 여전히 통과하는가
- [ ] 고친 부분 외에 다른 곳을 건드리지 않았는가

위 항목을 다 채우지 못했다면 "고쳤다"고 말하지 말고, 어느 단계에서 막혔는지를 그대로 알린다.
