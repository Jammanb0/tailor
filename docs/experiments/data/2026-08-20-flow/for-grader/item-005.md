# 근본원인 디버깅

## 개요

**원인을 말로 설명할 수 없으면, 아직 고친 게 아니다.**

우연히 고쳐진 버그는 다시 돌아온다. 왜 고쳐졌는지 설명하지 못한다면, 그건 고친 게 아니라 운이 좋았던 것이다. 이 스킬은 증상을 더듬어 고치는 대신, 원인을 먼저 찾고 그 원인에 맞는 수정을 하도록 순서를 강제한다.

## 언제 적용하나

- 버그, 에러, 예상과 다른 동작을 고칠 때 항상 적용한다.
- 예외: 원인이 이미 명확하고 한 줄로 설명 가능한 아주 단순한 오타·타입 실수는 조사 단계를 짧게 건너뛸 수 있다. 다만 이 판단이 맞았는지는 이후에도 계속 의심한다 — 고쳤는데 안 됐다면 즉시 1단계로 돌아간다.

## 절차

### 1단계 — 근본 원인부터 조사한다 (고칠 방법을 제안하기 전에)

아래 순서로 증거를 모은다. 증거를 다 모으기 전에는 "이렇게 고치면 될 것 같다"는 말을 하지 않는다.

1. **에러 메시지를 끝까지 읽는다** — 줄 번호, 파일 경로, 에러 코드까지 전부.
2. **일관되게 재현한다** — 정확히 어떤 단계를 밟아야 재현되는지 확인하고, 매번 똑같이 재현되는지 본다.
3. **최근에 무엇이 바뀌었는지 확인한다** — 코드 변경 이력, 새로 추가된 의존성(라이브러리), 설정값.
4. **여러 조각(모듈·서버·화면 등)을 거치는 문제라면 경계마다 증거를 남긴다** — 각 조각에 "무엇이 들어왔고, 무엇이 나갔는지"를 로그(기록)로 찍어 한 번 돌려보고, 그 증거로 어느 조각이 문제인지 먼저 좁힌다. 좁히기 전에 특정 조각을 고치기 시작하지 않는다.
5. **잘못된 값이 처음 생긴 자리까지 거슬러 올라간다** — 에러가 터진 자리가 아니라, 그 값이 애초에 잘못되기 시작한 자리를 찾는다. 손으로 못 따라가겠으면 의심되는 동작 직전에 로그를 남겨서 확인한다.

> 예외: 정말로 조사를 끝까지 마쳤는데도 원인을 못 찾겠다면, "환경 문제" "타이밍 문제"로 결론 내릴 수 있다. 단, 이때는 (a) 무엇을 확인했는지 적어두고 (b) 그 상황을 견디는 처리(재시도, 안내 문구 등)를 넣고 (c) 나중에 다시 볼 수 있게 로그를 남겨둔다. 이 세 가지 없이 "원인 불명"으로 끝내지 않는다.

### 2단계 — 패턴을 분석한다

- 같은 기능이 잘 작동하는 다른 사례(비슷한 코드, 비슷한 화면 등)를 찾는다.
- 잘 되는 경우와 안 되는 경우의 차이를 하나씩 전부 나열한다.

### 3단계 — 가설을 하나만 세우고 검증한다

- "OO 때문에 이 문제가 생긴다고 본다"처럼 가설을 명확한 한 문장으로 적는다.
- 가장 작은 변경 하나로 그 가설만 시험한다. 한 번에 여러 곳을 동시에 고치지 않는다 — 여러 개를 바꾸면 무엇이 실제로 원인이었는지 알 수 없게 된다.
- **맞았다** → 4단계로 간다.
- **안 맞았다** → 방금 만든 수정을 남겨둔 채 다음 걸 얹지 말고, 새로운 가설을 다시 하나 세워 3단계를 반복한다.

**하지 말 것:** 짚이는 곳 세 군데를 한꺼번에 고치고 돌려본다 → 뭐가 진짜 원인인지 끝내 모른다.

### 4단계 — 재현 테스트를 먼저 만들고 나서 고친다

- 고치기 전에, 이 버그를 실제로 재현하는 **실패하는 테스트**(또는 재현 스크립트)를 먼저 만든다.
- 이 테스트가 없으면 "고쳤다"는 것을 증명할 방법이 없고, 나중에 같은 문제가 돌아와도 알아채지 못한다.
- 그다음 한 번에 하나만 고친다. 온 김에 다른 것도 정리하거나 손보지 않는다.

### 고친 횟수를 센다 — 3번째부터는 구조를 의심한다

```
수정이 안 먹혔다 → 몇 번째 수정인지 센다
  → 3회 미만이면: 1단계(조사)로 돌아가 새로 알게 된 것을 반영한다
  → 3회 이상이면: 멈추고 구조 자체를 의심한다. 이 논의 없이 4번째 수정을 바로 시도하지 않는다
```

구조 문제일 때 나타나는 신호: 고칠 때마다 다른 곳에서 새로운 문제가 튀어나온다 / 하나를 고치면 다른 데서 증상이 생긴다 / 제대로 고치려면 대공사가 필요해 보인다. 이건 가설이 틀린 게 아니라 설계·구조가 틀린 것이다.

## 완료 전 점검

아래 항목을 **직접 새로 실행한 결과**를 보고 확인한다. "될 것 같다"는 느낌만으로는 통과시키지 않는다.

- [ ] 원인을 한두 문장으로 설명할 수 있는가 — "왜 이 버그가 생겼는지" 누가 물어도 바로 답할 수 있는가
- [ ] 재현 테스트를 실제로 돌려서 실패하는 것을 직접 봤는가
- [ ] 수정한 뒤 그 테스트를 다시 돌려서 통과하는 것을 직접 봤는가
- [ ] 수정을 잠시 되돌려서 테스트가 다시 실패하는지 확인했는가 (이 왕복 없이는 "이 테스트가 진짜 버그를 잡는지" 증명되지 않는다)
- [ ] 관련된 다른 테스트들도 여전히 통과하는가
- [ ] 원인이 되는 값이 지나가는 다른 자리에도 비슷한 문제가 있을 수 있는지 살펴봤는가

하나라도 "아니오"면 완료로 보고하지 않는다.

## 흔한 변명과 현실

| 이런 생각이 든다면 | 현실은 이렇다 |
|---|---|
| "일단 이렇게 바꿔보고 되면 그게 원인이었나 보다" | 우연히 될 수도 있다. 됐다는 사실만으로는 원인을 증명하지 못한다 — 왜 되는지 설명 못 하면 다음에 또 다른 모습으로 돌아온다 |
| "여러 군데 한꺼번에 고치면 더 빠르지 않나" | 여러 곳을 동시에 바꾸면 정작 어떤 변경이 문제를 해결했는지 알 수 없게 되고, 나중에 그중 하나를 되돌렸을 때 왜 다시 깨지는지도 알 수 없다 |
| "시간이 없으니 원인 조사는 나중에" | 원인 모르고 고친 버그는 비슷한 형태로 반드시 재발한다. 재발했을 때 처음부터 다시 조사해야 해서 결국 시간이 더 든다 |
| "테스트까지 만들 필요는 없을 것 같다" | 재현 테스트가 없으면 "고쳤다"는 말이 증명되지 않은 주장으로 남는다. 나중에 똑같은 문제가 조용히 돌아와도 알아채지 못한다 |
| "이미 두 번 고쳤는데 세 번째는 그냥 밀어붙이자" | 세 번째부터는 개별 수정이 아니라 구조 자체가 틀렸을 확률이 높다. 그대로 밀어붙이면 네 번째, 다섯 번째로 이어진다 |

## 위험 신호

아래 중 하나라도 해당하면 하던 작업을 멈추고 1단계(조사)로 돌아간다.

- 왜 이 버그가 생겼는지 한 문장으로 설명하지 못한다
- 실패하는 걸 직접 본 적 없이 "고쳐졌을 것"이라고 말하고 있다
- 짚이는 곳을 여러 군데 한꺼번에 고쳤다
- 같은 문제를 이미 세 번째 고치고 있다
- "일단 되니까 넘어가자"고 생각하고 있다
- 재현 테스트 없이 코드만 바꿨다
