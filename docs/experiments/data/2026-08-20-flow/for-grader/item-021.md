# 근본원인 디버깅

## 개요

**증상이 사라졌다고 끝난 게 아니다. 왜 사라졌는지 설명할 수 있어야 끝난 것이다.**

여기저기 코드를 고치다 보면 우연히 에러가 사라지는 경우가 있습니다. 이때 "됐다!"하고 넘어가면, 사실은 원인을 건드리지도 못한 채 증상만 잠깐 가려진 것일 수 있습니다. 이 스킬은 버그가 나타났을 때 감으로 여기저기 고치지 않고, 정해진 순서를 따라 진짜 원인을 찾아내고, 그 원인을 고쳤다는 것을 증거로 확인한 뒤에야 끝내도록 안내합니다.

## 언제 적용하나

- 항상 적용: 에러, 예외, 잘못된 결과, 예상과 다른 동작이 보고됐을 때
- 예외(사람에게 확인): 정말 급하게 임시로 우회(workaround)만 필요한 상황이라면, "지금은 임시 처방만 하고 근본 원인 조사는 나중에 하겠다"는 것을 사용자에게 먼저 말하고 동의를 받습니다. 혼자 판단해서 건너뛰지 않습니다.

## 절차

이 절차는 순서대로 진행하며, 각 단계를 끝내야 다음으로 넘어갑니다. 단계를 건너뛰거나 뒤섞으면 "왜 고쳐졌는지 모르는" 상태로 돌아갑니다.

### 1단계 — 증거부터 모은다 (아직 고치지 않는다)

이 단계에서는 고칠 방법을 제안하지 않습니다. 다음을 순서대로 확인합니다.

1. **에러 메시지를 끝까지 읽는다** — 줄 번호, 파일 경로, 에러 코드까지 다 봅니다. 일부만 보고 넘어가면 힌트를 놓칩니다.
2. **재현 절차를 확정한다** — 정확히 어떤 단계를 밟으면 매번 재현되는지 적습니다. 재현이 안 되면 다음 단계로 넘어가지 말고, 로그나 재현 조건을 더 모읍니다.
3. **최근에 뭐가 바뀌었는지 확인한다** — 코드 변경 이력, 새로 추가된 의존성, 설정 변경 등을 봅니다.
4. **여러 부분(모듈, 서비스, 컴포넌트 등)을 거치는 문제라면, 경계마다 값을 확인한다** — 어디까지는 값이 정상이고 어디서부터 깨지는지 표시를 남겨 한 번 실행해봅니다. 이 증거로 "어느 부분이 문제인지"를 좁힙니다. 증거 없이 "여기가 문제일 것 같다"고 짐작으로 고르지 않습니다.
5. **잘못된 값이 어디서 처음 생겼는지 거슬러 올라간다** — 에러가 난 지점이 아니라, 그 잘못된 값이 맨 처음 만들어진 지점을 찾습니다. 에러 난 곳만 고치면 증상만 가려지고 원인은 남습니다.

### 2단계 — 비슷하게 동작하는 예와 비교한다

같은 종류의 기능인데 정상 동작하는 사례가 있다면 찾아서 차이를 전부 나열합니다. 어떤 조건, 어떤 값, 어떤 코드 경로가 다른지 구체적으로 적습니다.

### 3단계 — 가설을 하나만 세우고, 가장 작은 변경으로 검증한다

- 가설은 이런 형태로 명확히 적습니다: "OO 값이 넘어오지 않아서 XX가 실패한다고 본다."
- 검증은 한 번에 하나만 바꿔서 합니다. 여러 곳을 동시에 고치면 무엇이 원인이었는지 알 수 없게 됩니다.
- 검증 결과 가설이 맞았다면 → 4단계(고치기)로 갑니다.
- 가설이 틀렸다면 → 그 변경을 남겨둔 채 다음 가설을 덧붙이지 말고, 새 가설을 다시 세웁니다.
- 모르는 부분이 있으면 "모른다"고 명확히 말합니다. 아는 척하고 넘어가지 않습니다.

**세 번 규칙**: 시도한 수정이 안 먹혔다면 몇 번째 시도인지 셉니다.
- 3회 미만이면 1단계(증거 모으기)로 돌아가 새로 알게 된 것을 반영합니다.
- 3회 이상이면 멈추고 "구조 자체가 잘못된 것은 아닌지"를 의심합니다. 이 논의 없이 네 번째 수정을 바로 시도하지 않습니다. (신호: 고칠 때마다 엉뚱한 곳에서 새 문제가 생긴다 / 제대로 고치려면 큰 구조 변경이 필요해 보인다 / 하나 고치면 다른 데서 증상이 튄다)

### 4단계 — 재현하는 테스트나 확인 절차를 먼저 만들고 나서 고친다

- 문제를 그대로 재현하는 가장 단순한 테스트나 확인 절차를 먼저 만듭니다. 이게 없으면 "고쳤다"는 것을 증명할 방법이 없고, 나중에 같은 문제가 다시 생겨도 알아채지 못합니다.
- 자동화된 테스트를 만들 수 있으면 만들고, 여건이 안 되면 일회성 확인 스크립트라도 만듭니다.
- 이 단계에서는 딱 그 문제 하나만 고칩니다. 온 김에 다른 부분을 정리하거나 손대지 않습니다.

## 흔한 변명과 현실

| 이런 생각이 든다면 | 현실은 이렇다 |
|---|---|
| "일단 이거 바꿔보고 안 되면 딴 거 해보자" | 증거 없이 찍어서 고치면, 어쩌다 되더라도 왜 됐는지 모른 채 남습니다. 다음에 비슷한 문제가 나면 처음부터 다시 헤매게 됩니다. |
| "에러가 없어졌으니 됐다" | 에러가 사라진 것과 원인이 사라진 것은 다릅니다. 에러 조건을 피해가게 만든 것일 수도 있습니다. 원인을 설명할 수 있는지 스스로 확인하세요. |
| "시간이 없어서 일단 넘어가야 한다" | 원인 조사를 건너뛴 수정은 대개 재발하고, 재발했을 때 다시 처음부터 조사해야 해서 결국 시간을 더 씁니다. |
| "이 부분이 딱 봐도 문제인 것 같다" | 감으로 짚은 지점이 맞을 수도 있지만, 증거로 확인하지 않으면 틀렸을 때 못 알아챕니다. 경계마다 값을 확인해서 좁히세요. |
| "테스트까지 만들 필요는 없을 것 같다" | 재현 절차가 없으면 "고쳤다"는 주장이 증명되지 않은 상태로 남습니다. 나중에 똑같은 버그가 조용히 돌아옵니다. |
| "비슷한 곳을 여러 개 동시에 고치면 빠르다" | 여러 곳을 한꺼번에 바꾸면 무엇이 실제로 효과가 있었는지 알 수 없게 됩니다. 하나씩 바꿔서 확인하세요. |

## 위험 신호 — 멈추고 다시 시작할 신호

- 코드부터 고치고 왜 그게 원인인지는 나중에 생각하려 한다
- "이유는 모르겠지만 이렇게 하면 될 것 같다"는 생각이 든다
- 왜 실패했는지 설명하지 못하는 상태로 다음 시도를 하려 한다
- 이미 세 번 넘게 고쳤는데 또 비슷한 방식으로 네 번째를 시도하려 한다
- 여러 곳을 동시에 바꾸고 한 번에 확인하려 한다
- "이번만 원인 조사 건너뛰자"는 생각이 든다

이 중 하나라도 해당하면 멈추고 1단계(증거 모으기)로 돌아갑니다.

## 완료 전 점검

다음 질문에 전부 "예"라고 답할 수 있어야 끝난 것입니다. 하나라도 아니라면 해당 단계로 돌아갑니다.

- [ ] 잘못된 값이나 동작이 처음 시작된 지점을 찾았는가?
- [ ] 왜 이 문제가 발생했는지 한두 문장으로 설명할 수 있는가?
- [ ] 세운 가설을 실제로 검증했는가 (짐작이 아니라 확인했는가)?
- [ ] 문제를 재현하는 테스트나 확인 절차를 만들고, 고치기 전에는 실패(또는 재현)하는 것을 직접 봤는가?
- [ ] 고친 뒤 그 테스트나 확인 절차가 통과하는 것을 직접 봤는가?
- [ ] 이 수정이 다른 기존 기능을 깨뜨리지 않았는지 확인했는가?

전부 확인되지 않았다면 "고쳤다"고 말하지 않고, 어느 단계가 비어있는지 밝힌 뒤 그 단계로 돌아갑니다.
