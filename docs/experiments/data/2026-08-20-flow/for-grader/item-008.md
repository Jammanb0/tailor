# 랜딩 페이지 디자인 — 뻔한 룩 피하기

## 개요

랜딩 페이지를 만들 때마다 "어디서 본 것 같은" 결과가 나오는 이유는, 주제와 상관없이
AI가 반사적으로 집어드는 몇 가지 기본값이 있기 때문입니다. 이 스킬은 (1) 그 기본값이
무엇인지 알아채고, (2) 주제 자체에서 디자인 선택을 끌어내고, (3) 코드를 쓰기 전에
계획을 한 번 스스로 검토해서, 결과물이 "이 프로젝트만의 것"처럼 보이게 만듭니다.

## 1단계 — 주제를 구체화한다

브리프(요청 내용)가 주제를 명확히 안 정했으면, 코드를 쓰기 전에 먼저 아래를 스스로
정하고 사용자에게 확인합니다:

- 구체적 주제 1개 (예: "생산성 앱" 대신 "혼자 쓰는 습관 트래커")
- 청중이 누구인지
- 이 페이지 하나가 하려는 단일 목적 (가입 유도? 정보 전달? 데모 체험?)

디자인 선택(색, 폰트, 문구, 히어로 구성)은 이 주제의 세계 — 그 분야에서 쓰는 소재,
도구, 산물, 용어 — 에서 끌어냅니다. 일반적인 "깔끔한 SaaS 느낌" 같은 방향이 아니라,
"이 주제이기 때문에 이런 선택을 했다"고 설명할 수 있어야 합니다.

히어로(첫 화면)는 주제 세계에서 가장 특징적인 것으로 엽니다. 아래 중 브리프와 가장
잘 맞는 방식을 고르되, 카피가 이미 강하면 헤드라인 문장만으로도 충분합니다.

- **헤드라인**: 카피 자체가 강할 때
- **이미지**: 주제의 실물·질감을 바로 보여줄 때
- **애니메이션**: 변화나 과정이 핵심일 때
- **라이브 데모**: 직접 만져보는 것이 가장 설득력 있을 때
- **인터랙티브 순간**: 참여 자체가 메시지일 때

주의: "큰 숫자 + 작은 라벨 + 보조 텍스트 + 그라데이션 액센트" 조합은 히어로의
정답처럼 보이지만 실제로는 가장 많이 반복되는 기본 답안입니다. 이게 정말 최선일
때만 쓰세요.

## 2단계 — 흔한 AI 기본값 3종을 피한다

아래 세 가지는 어떤 브리프에는 정당한 선택일 수 있지만, 대부분은 주제와 무관하게
반사적으로 튀어나오는 기본값입니다. 지금 만드는 페이지가 이쪽으로 흘러가고 있는지
만들면서 계속 확인하세요.

- **크림톤 + 세리프 조합**: 따뜻한 크림색 배경(#F4F1EA 근처) + 고대비 세리프 디스플레이 폰트 + 테라코타색 액센트
- **다크 네온 조합**: 니어블랙 배경 + 밝은 라임 그린 또는 버밀리언 색 액센트 하나
- **신문식 레이아웃**: 얇은 헤어라인 괘선 + 각진 모서리(border-radius 0) + 조밀한 다단 구성

예외: 사용자가 이 중 하나를 명시적으로 요청했다면(예: "다크모드로 해줘") 그건 브리프의
지시이므로 그대로 따릅니다. 이 규칙은 "아무 말 없었는데 저절로 이렇게 흘러가는 것"을
막는 규칙입니다.

## 3단계 — 시그니처 요소 하나를 정하고 나머지는 절제한다

전체를 화려하게 만들려 하지 말고, 기억에 남을 시그니처 요소 하나만 정합니다.
나머지 요소는 조용하고 규율 있게 두고, 브리프에 실제로 복무하지 않는 장식은 잘라냅니다.

번호·구분선·라벨 같은 구조 장치를 쓸 때는 내용에 대한 진짜 정보를 담아야 합니다.
장식으로 붙이는 것은 피하세요.

- 이렇게: 실제 진행 순서나 시점을 보여주는 타임라인에 번호를 매긴다
- 이러지 말 것: 순서와 무관한 카드 세 개에 그냥 01 / 02 / 03을 붙인다

## 4단계 — 색·폰트·시그니처를 토큰 계획으로 먼저 정한다

코드를 쓰기 전에, 아래 네 가지를 짧은 계획으로 먼저 정리합니다. 이 계획이 이후
모든 결정의 기준이 됩니다.

- **Color**: 이름 붙인 hex 코드 4~6개 (예: Deep Navy #1B2A41, Warm Sand #E8D9C5 ...)
- **Type**: 헤더(디스플레이)용 폰트와 본문용 폰트, 필요하면 캡션/데이터용 유틸리티 폰트까지
- **Layout**: 한두 문장 산문 설명 + 간단한 ASCII 와이어프레임 (참고 사이트 이름 대신 구조로 설명)
- **Signature**: 이 페이지에서 기억에 남을 단 하나의 요소가 무엇인지

타이포그래피는 주제에 맞게 고릅니다. 참고로:

- 세리프 헤더 → 격식·전통·신뢰를 말할 때
- 산세리프 헤더 → 현대적·기술적·명료함을 말할 때
- 본문은 웬만하면 산세리프로 — 긴 글에서도 읽기 쉽습니다
- 개성은 헤더에서 내고, 본문은 가독성을 우선합니다

## 5단계 — 계획을 브리프에 비춰 스스로 검토한다 (코드 쓰기 전)

계획을 다 세운 뒤, 코드를 쓰기 전에 한 번 스스로 물어봅니다:

> "이 계획의 각 항목이, 비슷한 주제의 다른 프로젝트였어도 그냥 나왔을 법한
> 기본값인가?"

2단계에서 피하기로 한 세 가지 조합과 겹치는 부분이 있으면 그 자리에서 고칩니다.
계획이 주제 세계에서 끌어온 근거 없이 "무난하고 세련된" 방향으로만 흐르고 있다면,
1단계로 돌아가 주제의 구체적인 디테일을 다시 반영합니다.

이 검토를 통과한 뒤에야 실제 코드를 작성합니다.

## 지켜야 할 조건

- 모바일까지 반응형으로 만든다
- 키보드로 포커스했을 때 눈에 보이게 처리한다
- `prefers-reduced-motion`(사용자가 애니메이션 최소화를 설정한 경우)을 존중해 과한 모션을 줄인다
- 위 세 가지는 자랑하듯 언급하지 않고 그냥 기본으로 지킨다
- 애니메이션을 쓸 때는 "왜 여기에 쓰는지"를 먼저 정한다 — 페이지 로드 시퀀스(한 번만, 짧게), 스크롤 등장, 호버 마이크로 인터랙션(작고 빠르게), 배경의 은은한 분위기 중 어디에 해당하는지
- 복잡도는 고른 방향에 맞춘다 — 화려한 방향이면 정교하게 실행하고, 미니멀한 방향이면 여백과 디테일의 정밀함으로 완성도를 낸다
