# 근본원인 디버깅

## 개요

**원인을 모른 채로 "고쳐졌다"고 넘어가지 않는다.** 코드를 이것저것 바꿔보다 증상이 사라지면 멈추고 싶어지지만, 그건 고친 것이 아니라 운이 좋았던 것이다. 왜 고장났는지 설명할 수 없다면, 왜 고쳐졌는지도 설명할 수 없다. 이 스킬은 버그를 만났을 때 추측으로 코드를 건드리기 전에 반드시 밟아야 하는 순서를 정한다.

## 언제 적용하나

- 에러가 나거나, 기대와 다른 동작이 나타났을 때 — 항상 적용
- "이렇게 하면 될 것 같다"는 감으로 코드를 고치려는 순간 — 항상 적용
- 정말 급하게 임시로만 막아야 하는 상황(예: 운영 장애 중 우선 서비스 복구) — 예외로 두되, 반드시 사람에게 "지금은 임시 조치만 하고 원인 조사는 나중에 하겠다"고 먼저 확인받은 뒤 진행한다

## 디버깅 절차

아래 네 단계는 순서대로 진행하며, 각 단계를 마치기 전에는 다음 단계로 넘어가지 않는다.

### 1단계 — 근본 원인 조사 (증거를 모으기 전엔 고칠 방법을 말하지 않는다)

다음을 순서대로 확인한다.

- **에러 메시지를 끝까지 읽는다** — 줄 번호, 파일 경로, 에러 코드까지 전부
- **재현 절차를 확정한다** — 정확히 어떤 조작을 하면 재현되는지, 매번 똑같이 재현되는지
- **최근에 바뀐 것을 확인한다** — 최근 커밋(코드 변경 기록), 새로 추가된 의존성(라이브러리), 설정 변경
- **여러 구성요소를 거치는 문제라면 경계마다 증거를 남긴다** — 예: A 함수 → B 함수 → C 함수로 값이 넘어간다면, 각 경계에서 "무엇이 들어왔고 무엇이 나갔는지"를 로그(기록)로 찍어 확인한다. 어느 구간에서 값이 깨지는지 먼저 좁혀야, 그 구간만 파고들 수 있다
- **잘못된 값이 어디서 왔는지 거슬러 올라간다** — 에러가 발생한 지점이 아니라, 그 잘못된 값이 "처음 생긴" 지점을 찾는다. 한 단계씩 위로 올라가며 추적한다

이렇게: 로그인 실패가 났을 때, 세션 값이 언제 비었는지 단계별로 찍어보고 "로그인 처리 함수를 나가는 순간엔 값이 있었는데 다음 요청에서 비어 있다"까지 좁힌다
이러지 말 것: 로그인 실패를 보자마자 "세션 만료 시간을 늘려보자"며 설정값부터 바꾼다

### 2단계 — 패턴 분석

- 같은 종류인데 **정상 작동하는 사례**를 찾는다
- 정상 사례와 실패 사례의 차이를 전부 나열한다 (입력값, 환경, 순서, 조건 등)

### 3단계 — 가설 하나 세우고 검증

- 가설은 한 번에 **하나만** 세운다: "OO 때문에 XX가 원인이라고 본다"처럼 명확한 문장으로 적는다
- 가장 작은 변경으로 시험한다 — 한 번에 한 가지만 바꾼다. 여러 곳을 동시에 바꾸면 무엇이 효과를 냈는지 알 수 없다
- 검증 결과에 따라 갈린다:
  - **가설이 맞았다** → 4단계(고치기)로 진행
  - **가설이 틀렸다** → 기존 수정을 남겨둔 채 다음 수정을 얹지 말고, 되돌린 뒤 3단계를 다시 (새 가설 하나)
- 모르는 것이 있으면 아는 척하지 않는다. "이 부분은 아직 확실하지 않다"고 그대로 말한다

이러지 말 것: 의심되는 세 곳을 한꺼번에 고치고 돌려본 뒤 "됐다"고 한다
이렇게: 넘어가는 값이 문제라는 가설이면, 그 값 하나만 바꿔서 확인한다

**세 번 규칙**: 같은 증상에 대해 세 번째 수정을 시도하려 한다면 멈춘다. 개별 원인이 아니라 구조 자체가 잘못됐을 가능성이 높다는 신호다. 고칠 때마다 새로운 곳에서 얽힌 문제가 나오거나, 하나 고치면 다른 데서 증상이 생긴다면 구조 문제다. 이 경우 사람과 상의 없이 네 번째 수정을 시도하지 않는다.

### 4단계 — 고치기

- 고치기 전, **그 문제를 재현하는 실패 테스트(검증 코드)**를 먼저 만든다. 자동화된 테스트가 있는 프로젝트면 테스트 코드로, 없으면 최소한 재현 스크립트로 만든다
- 이 테스트가 없으면 나중에 "정말 고쳐졌는지", "다시 터졌는지" 확인할 방법이 없다
- 한 번에 **하나의 원인만** 고친다. 고치는 김에 다른 부분을 정리하거나 손대지 않는다
- 원인을 찾았다면, 값이 지나가는 여러 지점(들어오는 자리, 처리하는 자리, 로그 남기는 자리 등)에 방어 코드를 함께 넣어 같은 문제가 다른 경로로 재발하지 않게 한다

## 원인 없음으로 결론 내릴 조건

정말로 환경 문제나 타이밍 문제일 수도 있다. 다만 그렇게 결론 내리기 전에 아래를 모두 확인한다.

- [ ] 1~3단계 조사를 끝까지 마쳤는가
- [ ] 무엇을 확인했는지 기록으로 남겼는가
- [ ] 그 상황을 견딜 수 있는 처리(재시도, 타임아웃, 안내 메시지 등)를 넣었는가
- [ ] 나중에 다시 볼 수 있도록 로그를 남겨뒀는가

위 네 가지를 채우지 못했다면 "원인 없음"이 아니라 "조사가 덜 된 것"이다. 1단계로 돌아간다.

## 흔한 변명과 현실

| 이런 생각이 들 때 | 현실은 이렇다 |
|---|---|
| "이거 고치면 될 것 같은데, 일단 해보자" | 감으로 고친 코드는 원인을 설명하지 못한다. 증상이 사라져도 왜 사라졌는지 모르면 언제든 다시 나타난다 |
| "돌려보니 진짜로 됐네, 그럼 됐지" | 우연히 다른 부작용으로 증상이 가려진 것일 수 있다. 원인을 설명할 수 없다면 "됐다"고 말할 근거가 없다 |
| "시간이 없어서 원인 조사할 여유가 없다" | 원인 모르고 고친 버그는 대개 다시 돌아온다. 재발하면 처음부터 다시 조사해야 하니 오히려 시간이 더 든다 |
| "여러 곳을 한꺼번에 고치면 더 빠르지 않나" | 여러 곳을 동시에 바꾸면 무엇이 효과가 있었는지 알 수 없어, 다음에 비슷한 문제가 생겼을 때 배운 게 없다 |
| "이 정도 작은 수정은 테스트 안 만들어도 되겠지" | 재현 테스트가 없으면 "정말 고쳐졌다"는 주장 자체가 증명되지 않은 상태다 |
| "세 번째 수정인데 이번엔 진짜 맞을 것 같다" | 세 번째부터는 개별 원인이 아니라 구조 문제일 가능성이 크다. 감이 아니라 구조를 다시 봐야 한다 |

## 위험 신호

아래 중 하나라도 해당하면 멈추고 1단계로 돌아간다.

- 왜 고쳐졌는지 설명하지 못한다
- 에러 메시지를 끝까지 읽지 않았다
- 재현 절차 없이 고치기 시작했다
- 의심되는 곳을 여러 개 동시에 바꿨다
- "일단 되니까 넘어가자"고 생각하고 있다
- 같은 증상에 세 번째 수정을 시도하려 한다
- 고쳤는데 다른 곳에서 새로운 증상이 나타났다
- 재현 테스트 없이 고쳤다고 말하려 한다

## 완료 전 점검

- [ ] 근본 원인을 한 문장으로 설명할 수 있는가
- [ ] 그 원인이 왜 증상을 일으켰는지 설명할 수 있는가
- [ ] 재현하는 실패 테스트를 먼저 만들고, 그 테스트가 실패하는 것을 직접 봤는가
- [ ] 수정 후 그 테스트가 통과하는 것을 직접 봤는가
- [ ] 다른 기존 테스트들도 여전히 통과하는가
- [ ] 값이 지나가는 다른 경로에도 방어가 필요한지 검토했는가

위 항목을 다 채우지 못했다면 아직 "고쳐졌다"고 말할 수 없다.
