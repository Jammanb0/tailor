# 근본 원인 디버깅

## 개요

**왜 고쳐졌는지 말할 수 없으면, 아직 고친 것이 아니다.**

버그를 여기저기 찔러보다 우연히 사라지는 경우, 실제로는 원인을 없앤 게 아니라 증상이 잠깐 안 보이는 상태일 뿐인 경우가 많다. 이 스킬은 추측으로 코드를 바꾸는 것을 막고, 원인을 증거로 특정한 뒤 그 원인만 고치도록 순서를 강제한다.

## 언제 적용하나

아래 여섯 종류의 문제에는 항상 이 절차를 적용한다.

- 테스트 실패
- 운영 중인 버그
- 예상과 다른 동작
- 성능 문제
- 빌드 실패
- 다른 시스템·API와의 연동 문제

**특히 다음 상황일수록 반드시 적용한다** — 이런 상황이 바로 절차를 건너뛰고 싶어지는 순간이기 때문이다.

- 시간에 쫓기고 있을 때
- "딱 하나만 빨리 고치면 될 것" 같아 보일 때
- 이미 여러 번 고쳐봤을 때
- 직전 수정이 안 먹혔을 때
- 문제를 아직 온전히 이해하지 못했을 때

예외: 버리는 프로토타입 코드처럼 이후 아무도 안 쓸 코드라면 절차를 간소화할 수 있다. 다만 이걸 예외로 둘지는 스스로 판단하지 말고 사람에게 먼저 확인한다.

## 절차 — 4단계, 순서를 건너뛰지 않는다

### 1단계: 근본 원인 조사 (고칠 방법을 제안하기 전에 끝낸다)

증거를 다 모으기 전에는 어떤 수정도 제안하지 않는다.

1. 에러 메시지를 끝까지 읽는다 — 줄 번호, 파일 경로, 에러 코드까지 전부.
2. 문제를 일관되게 재현한다. 정확한 재현 단계는 무엇이고, 매번 똑같이 재현되는가?
   - 재현이 안 되면 추측으로 넘어가지 말고 자료를 더 모은다.
3. 최근에 무엇이 바뀌었는지 확인한다 — 최근 변경 내역, 새로 들어온 의존성, 설정 변경.
4. 여러 컴포넌트를 거치는 문제라면 경계마다 증거를 남긴다: 각 지점에서 무엇이 들어왔는지, 무엇이 나갔는지, 설정값이 제대로 넘어갔는지, 그 지점의 상태는 어땠는지를 기록하고 실행해본다. 그 증거로 어느 지점이 문제인지 특정한 뒤에야 그 부분만 조사한다.
5. 잘못된 값이 어디서 처음 생겼는지 거슬러 올라간다: 증상이 보인 자리 → 직접 원인이 된 지점 → 그걸 호출한 곳 → 계속 위로 → 값이 최초로 만들어진 자리. 더 이상 거슬러 올라갈 수 없으면 그 자리에서 고치되, 값이 지나는 다른 지점에도 방어 코드를 함께 넣는다.

모르는 것이 있으면 아는 척하지 말고 "이 부분은 아직 모르겠다"고 그대로 말하고, 더 조사하거나 도움을 요청한다.

### 2단계: 패턴 분석 — 정상 동작하는 사례와 비교

같은 종류인데 정상적으로 동작하는 사례를 찾아 끝까지 읽는다. 훑어보고 넘어가지 않는다 — 훑으면 비슷한 점만 보이고 다른 점은 안 보인다.

두 사례의 차이를 하나도 빠짐없이 적는다. "이건 상관없겠지"라고 미리 걸러내지 않는다. 그 차이를 바탕으로 정상 동작하는 코드가 무엇에 기대고 있는지 파악한다.

### 3단계: 가설 하나 세우고 검증

가설은 한 번에 하나만 세운다. "Y 때문에 X가 원인이라고 본다"처럼 명확한 문장으로 적는다.

가장 작은 변경으로 시험한다. 한 번에 한 가지만 바꾼다. 여러 곳을 한꺼번에 고치면 무엇이 실제로 문제를 해결했는지 알 수 없다.

- 가설이 맞았다 → 4단계로.
- 가설이 틀렸다 → 그 수정 위에 다른 수정을 덧대지 말고, 새로운 가설을 세운다 (3단계 반복).

**고친 횟수를 센다.** 같은 자리를 세 번째 고치려는 순간이라면 멈춘다. 그건 가설이 빗나간 게 아니라 구조 자체가 잘못된 것이다. 다음 신호가 있으면 구조 문제다: 고칠 때마다 다른 곳에서 새로운 문제가 생긴다, 제대로 고치려면 대공사가 필요해 보인다, 하나를 고치면 다른 곳에서 증상이 나타난다. 이럴 땐 네 번째 수정을 시도하기 전에 먼저 이 사실을 사람에게 알리고 논의한다.

### 4단계: 고치기 — 재발 방지 테스트를 먼저

고치기 전에, 이 문제를 재현하는 실패 테스트를 먼저 만든다. 테스트가 없으면 고쳤다는 걸 증명할 수 없고, 나중에 같은 문제가 돌아와도 알아챌 수 없다.

- 테스트를 쓴다.
- 돌린다 — 실패해야 한다.
- 방금 만든 수정을 잠깐 되돌린다.
- 다시 돌린다 — 반드시 실패해야 한다. (여기서 실패하지 않으면 이 테스트는 실제로 문제를 못 잡는 테스트다.)
- 수정을 되살린다.
- 다시 돌린다 — 이제 통과해야 한다.

한 번에 하나만 고친다. 온 김에 다른 것도 정리하거나 근처 코드를 손보지 않는다.

## 원인 없이 끝내도 되는 경우 (드물다)

정말로 타이밍이나 환경 문제일 수 있다. 다만 다음 네 가지를 모두 갖췄을 때만 "원인 불명"으로 결론 낸다.

- 위 조사 절차를 끝까지 마쳤다.
- 무엇을 확인했는지 기록으로 남겼다.
- 그 상황을 견디는 처리(재시도, 시간 제한, 안내 문구 등)를 넣었다.
- 다음에 다시 볼 수 있도록 로그를 남겨뒀다.

대부분의 "원인 불명"은 사실 조사가 덜 된 것이다.

## 흔한 변명과 현실

| 이런 생각이 든다면 | 현실은 이렇다 |
|---|---|
| "간단한 문제라 이 절차까지는 필요 없다" | 간단한 문제에도 원인은 있다. 절차를 밟는 게 간단한 버그일수록 오히려 더 빠르다 |
| "급하니까 절차 밟을 시간이 없다" | 체계적으로 접근하는 게 여기저기 찍어보며 헤매는 것보다 결국 빠르다 |
| "일단 이것부터 해보고 그다음에 조사하자" | 첫 번째 시도가 이후 방향을 정해버린다. 처음부터 제대로 조사한다 |
| "고쳐지는지 먼저 확인하고 테스트는 나중에 쓰겠다" | 확인 안 된 수정은 남지 않는다. 재발 방지 테스트를 먼저 써야 증명이 된다 |
| "여러 개를 한꺼번에 고치면 시간이 절약된다" | 무엇이 실제로 효과가 있었는지 가릴 수 없고, 새 버그를 만들 수도 있다 |
| "문제가 뭔지 눈에 보이니 바로 고치겠다" | 증상이 보이는 것과 원인을 아는 것은 다르다 |
| "한 번만 더 고쳐보자" (이미 두 번 이상 실패한 뒤) | 두 번 이상 실패했다면 구조 문제다. 또 고치지 말고 접근 방식 자체를 의심한다 |

## 위험 신호 — 이 생각이 들면 멈추고 1단계로 돌아간다

- "일단 빨리 고치고 조사는 나중에 하자"
- "이 값 한번 바꿔보고 되는지 보자"
- "여러 군데 고치고 한 번에 테스트를 돌리자"
- "테스트는 건너뛰고 내가 직접 확인해보겠다"
- "아마 이것 때문일 테니 일단 이것부터 고치자"
- "온전히 이해하진 못했지만 이러면 될 것 같다"
- 값이 어디서 왔는지 따라가기도 전에 해결책부터 내놓고 있다
- "한 번만 더 고쳐보자" (이미 두 번 이상 시도한 뒤)
- 고칠 때마다 엉뚱한 곳에서 새 문제가 나온다
- 왜 원래 문제가 생겼는지 아직 설명하지 못한다

이 중 하나라도 해당하면 하던 작업을 멈추고 1단계(근본 원인 조사)로 돌아간다. 같은 자리를 세 번째 고치는 중이라면 특히 구조 자체를 의심한다.

## 완료 전 점검

아래 질문에 전부 "그렇다"고 답할 수 있어야 "고쳤다"고 말할 수 있다. 하나라도 아니라면 해당 단계로 돌아간다.

- [ ] 왜 원래 문제가 발생했는지 근거를 가지고 설명할 수 있는가?
- [ ] 실패하는 테스트를 먼저 썼고, 그 테스트가 실패하는 것을 직접 봤는가?
- [ ] 수정을 되돌렸을 때 테스트가 실제로 다시 실패하는 것을 확인했는가?
- [ ] 수정을 되살린 뒤 테스트가 통과하는 것을 확인했는가?
- [ ] 관련된 다른 테스트도 전부 여전히 통과하는가?
- [ ] 이 자리를 세 번째 이상 고치는 게 아닌가? (맞다면 구조 문제를 먼저 논의했는가?)
- [ ] "될 것 같다", "아마 고쳐졌을 것" 같은 표현 없이, 실제로 돌려본 결과로 말하고 있는가?
