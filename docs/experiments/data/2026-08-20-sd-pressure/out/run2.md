# 근본 원인 디버깅

## 개요

**왜 고쳐졌는지 말할 수 없으면, 아직 고친 게 아니다.** 증상을 찍어서 없애는 것과 원인을 찾아 없애는 것은 다르다. 이 스킬은 추측으로 여기저기 건드리는 것을 막고, 근본 원인을 찾아 고치고, 고쳤다는 것을 증거로 증명하는 순서를 강제한다.

## 언제 적용하나

아래 상황이면 항상 적용한다:
- 테스트가 실패한다
- 운영 중인 코드에서 버그가 발견됐다
- 코드가 예상과 다르게 동작한다
- 성능이 이상하다
- 빌드나 연동이 실패한다

**특히 다음과 같은 생각이 들 때일수록 반드시 적용한다** — 이런 순간이 바로 건너뛰고 싶어지는 순간이기 때문이다:
- 시간이 없어서 빨리 고치고 싶을 때
- "이거 하나만 바꾸면 될 것 같다"는 느낌이 들 때
- 이미 여러 번 고쳐봤을 때
- 방금 한 수정이 안 먹혔을 때
- 문제를 아직 완전히 이해하지 못했을 때

## 절차

### 1단계 — 근본 원인 조사 (증거를 다 모으기 전에는 고칠 방법을 제안하지 않는다)

1. 에러 메시지를 끝까지 읽는다 — 줄 번호, 파일 경로, 에러 코드까지 전부.
2. 문제를 일관되게 재현해본다. 정확한 재현 단계는 무엇이고, 매번 똑같이 일어나는가?
   - 재현이 안 되면 추측하지 말고 자료를 더 모은다. (예: 로그, 실행 환경 차이)
3. 최근에 무엇이 바뀌었는지 확인한다 — 최근 커밋, 새로 추가된 의존성, 설정 변경.
4. 여러 컴포넌트를 거치는 문제라면, 각 경계(입력/출력이 넘어가는 지점)마다 실제로 어떤 값이 들어오고 나가는지 로그나 출력으로 확인한다. 어느 조각이 문제인지 증거 없이 "여기가 문제일 것 같다"고 짐작으로 고르지 않는다.
5. 잘못된 값이 어디서 처음 생겼는지, 에러가 터진 지점에서부터 거꾸로 한 단계씩 거슬러 올라간다. 에러가 보인 자리와 원인이 생긴 자리는 대개 다르다.

### 2단계 — 비슷한 사례와 비교한다

같은 종류의 코드 중 정상적으로 동작하는 사례를 찾아 끝까지 읽고, 문제가 있는 코드와의 차이를 하나도 빠짐없이 적는다. "이건 관련 없을 것 같다"고 미리 걸러내지 않는다 — 차이를 다 적어야 무엇이 진짜 원인인지 보인다.

### 3단계 — 가설을 하나만 세우고 검증한다

- 가설은 한 번에 하나만: "Y 때문에 X가 원인이라고 본다"처럼 분명한 문장으로 적는다.
- 가장 작은 변경 하나로 시험한다. 짚이는 곳 여러 개를 한꺼번에 고치지 않는다 — 그러면 무엇이 실제로 문제를 해결했는지 알 수 없게 된다.
- 가설이 틀렸으면 그 수정을 걷어내고, 위에 또 다른 수정을 얹지 않는다. 처음부터 새 가설을 세운다.
- 모르는 부분이 있으면 아는 척하지 말고 "이 부분은 아직 모르겠다"고 그대로 말한다.

**세 번째 시도부터는 구조를 의심한다:** 같은 자리를 두 번 고쳤는데도 안 됐다면, 세 번째 수정을 바로 시도하지 말고 멈춘다. 고칠 때마다 엉뚱한 곳에서 새 문제가 생기거나, 고치려면 큰 구조 변경이 필요해 보인다면 이것이 신호다.

### 4단계 — 고치기 전에 실패하는 테스트를 먼저 만든다

1. 문제를 가장 단순하게 재현하는 테스트(또는 재현 스크립트)를 만든다.
2. 그 테스트를 돌려 실제로 실패하는지 확인한다.
3. 딱 이 문제를 고치는 만큼만 수정한다 — 온 김에 다른 부분을 정리하거나 다른 기능을 손보지 않는다.
4. 테스트를 다시 돌려 통과하는지 확인한다.
5. 가능하면 고친 코드를 잠시 되돌려서 테스트가 실제로 다시 실패하는지도 확인한다. 되돌렸을 때 실패하지 않으면, 이 테스트는 애초에 이 문제를 잡지 못하는 테스트다.

### 5단계 — 여러 층에 방어를 추가한다 (선택, 원인 확정 후)

원인을 찾은 뒤에는 값이 지나가는 경로의 여러 지점에 검사를 추가하는 것이 좋다:
- 값이 들어오는 자리에서 잘못된 입력을 거른다
- 처리하는 자리에서 이 작업에 말이 되는 값인지 확인한다
- 위험한 동작을 하는 자리에 기록(로그)을 남긴다

## 흔한 변명과 현실

| 이런 생각이 들 때 | 현실 |
|---|---|
| "간단한 문제라 절차까지는 필요 없다" | 간단한 문제에도 원인은 있다. 절차를 따르는 쪽이 오히려 더 빠르다 |
| "급한 상황이라 시간이 없다" | 체계적으로 하는 것이 찍어보며 헤매는 것보다 결국 빠르다 |
| "일단 이것부터 해보고 나중에 조사하자" | 첫 수정이 이후 방향을 정한다. 처음부터 제대로 조사한다 |
| "고쳐지는지 확인하고 테스트는 나중에 쓰겠다" | 테스트 없이 확인한 수정은 남지 않는다. 재발해도 알 수 없다 |
| "여러 군데를 한꺼번에 고치면 빠르다" | 무엇이 실제로 문제를 해결했는지 알 수 없고, 새 버그를 만들 수 있다 |
| "문제가 보이니 바로 고치겠다" | 증상이 보이는 것과 원인을 아는 것은 다르다 |
| "한 번만 더 고쳐보자" | 이미 두 번 이상 실패했다면 구조 문제일 가능성이 높다. 또 고치지 말고 멈춰서 다시 본다 |

## 위험 신호

아래 생각이 떠오르면 하던 것을 멈추고 1단계로 돌아간다:

- "일단 빨리 고치고 조사는 나중에"
- "이거 한번 바꿔보고 되는지 보자"
- "여러 군데 고치고 한꺼번에 테스트해보자"
- "아마 이거일 테니 일단 이것부터 고치자"
- "온전히 이해하진 못했지만 이러면 될 것 같다"
- "이게 주요 문제들입니다" — 조사도 안 하고 고칠 것부터 나열한다
- 값이 어디서 왔는지 따라가기도 전에 해결책부터 내놓고 있다
- 이미 두 번 이상 고쳐봤는데 또 "이번엔 되겠지"라고 생각하고 있다
- 고칠 때마다 다른 곳에서 새 문제가 나온다

**하나라도 해당하면 멈추고 1단계(근본 원인 조사)로 돌아간다. 같은 자리를 세 번째 고치려는 참이라면 구조 자체를 의심한다.**

## 완료 전 점검

아래를 전부 과거형으로 확인한다. 하나라도 "아니오"면 완료로 넘어가지 않는다.

- [ ] 무엇이 원인인지 한 문장으로 설명할 수 있는가 — "왜 고쳐졌는지" 말할 수 있는가
- [ ] 이 문제를 재현하는 테스트를 실제로 실패하는 것을 눈으로 봤는가
- [ ] 코드를 고친 뒤 그 테스트가 통과하는 것을 확인했는가
- [ ] 고친 코드를 되돌렸을 때 테스트가 다시 실패하는 것을 확인했는가 (또는 확인이 어려운 이유를 알고 있는가)
- [ ] 다른 기존 테스트들도 여전히 통과하는가
- [ ] "아마 이래서 그런 것 같다" 같은 추측이 아니라, 실제 값·로그·재현 결과로 원인을 증명했는가

하나라도 못 채웠다면, "고쳐진 것 같습니다"라고 말하지 말고 1단계로 돌아가 조사를 이어간다.
