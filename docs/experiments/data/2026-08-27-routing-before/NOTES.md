# 코퍼스 라우팅 전환 전 기준값 (2026-08-27)

전체 코퍼스를 매번 보내는 **현재 방식**의 값이다. 라우팅으로 바꾼 뒤 **같은
시나리오를 같은 방법으로 다시 돌려** 이 값과 비교한다.

- 측정 커밋: `205d1c9` + 계측 한 줄(브랜치 `corpus-routing`)
- 실행기: `../2026-08-20-baseline-fill/run.mjs`
- 명령: `node run.mjs ../2026-08-27-routing-before 1 1 01-testing,05-design`
- 모델: `claude-sonnet-5`, `thinking: disabled`, `max_tokens: 8192`

## 비용 — 캐시를 빼고 계산한다

방문자가 없어 캐시가 걸린다고 가정하지 않는다(입력 $2/100만, 출력 $10/100만).

| 항목 | 토큰 | 비용 |
|---|---:|---:|
| 입력 | 65,808 | $0.132 |
| 출력(평균) | 3,625 | $0.036 |
| **1회 합계** | | **약 $0.168** |

실제로는 캐시가 켜져 있어 **첫 요청은 저장 값이 붙어 약 $0.20**, 5분 안의 다음
요청은 **약 $0.05**가 된다. 위 표는 캐시를 빼고 본 기준값이다.

## ⚠️ 3번 중 1번이 파서에서 실패했다

`01-testing` 1차에서 502가 났다. **모델은 문서를 다 썼는데 `</skill_md>`를 닫지
않았다** — 열린 태그와 본문은 정상이고 닫는 태그·`<review>`·`<questions>`가
통째로 없었다. `stop_reason`은 `end_turn`이었으므로 길이에 잘린 것이 아니다.

지금 파서는 여는 태그와 닫는 태그가 **둘 다** 있어야 본문을 꺼낸다
(`prompt.ts`의 `extractTag`). 그래서 다 쓴 문서를 통째로 버렸다.

**이것은 라우팅과 무관한 기존 결함이다.** 표본이 3건이라 빈도는 말할 수 없지만,
전환 뒤 비교할 때 **실패율도 함께 세야 한다** — 안 그러면 라우팅 탓으로
오해하거나, 반대로 라우팅이 고쳤다고 착각한다.
