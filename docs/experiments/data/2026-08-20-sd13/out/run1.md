# 근본 원인 디버깅

## 개요

**증상을 없애는 것과 원인을 찾는 것은 다르다.** 여기저기 고쳐보다 우연히 증상이 사라지면, 진짜 원인은 그대로 남아 있다가 다른 모습으로 다시 나타난다. 이 스킬은 "왜 고쳐졌는지 설명할 수 있을 때까지" 고치는 것을 미루는 절차입니다.

## 언제 적용하나

- 항상 적용: 버그 수정, 에러 해결, "왜 이게 안 되는지 모르겠다"는 상황 전부
- 예외: 급한 임시 조치가 필요해서 원인 규명 전에 증상만 먼저 막아야 한다면, 그렇게 할지 여부는 혼자 정하지 말고 사람에게 먼저 확인합니다. 임시 조치를 했더라도 원인 조사는 별도로 마쳐야 합니다.

## 절차

### 1단계 — 원인부터 조사한다 (고칠 방법을 먼저 말하지 않는다)

조사가 끝나기 전에는 "이렇게 고치면 될 것 같다"는 말을 하지 않습니다. 증상만 보고 짐작으로 고치면, 그 짐작이 맞았는지 틀렸는지조차 알 수 없게 됩니다.

- 에러 메시지를 끝까지 읽습니다 — 줄 번호, 파일 경로, 에러 코드까지 빠짐없이
- 문제를 일관되게 재현할 방법을 확인합니다 (정확한 재현 단계, 매번 똑같이 일어나는지)
  - 재현이 안 되면: 추측으로 넘어가지 말고 정보를 더 모읍니다
- 최근에 무엇이 바뀌었는지 확인합니다 — 코드 변경 이력, 새로 추가된 라이브러리(외부에서 가져온 코드 묶음), 설정 변경
- 여러 부분(컴포넌트)을 거쳐 일어나는 문제라면, 각 경계마다 무엇이 들어오고 나가는지 기록해 어느 지점에서 어긋나는지 좁혀갑니다
  - 예: 값이 A 단계까지는 정상으로 넘어오는데 B 단계에서 비어 있다면, 그 사이가 범인입니다
  - 하지 말 것: 증거 없이 "제일 그럴듯한 부분"부터 고쳐보는 것
- 잘못된 값이 어디서 처음 생겼는지 거슬러 올라갑니다. 에러가 "터진" 자리와 문제가 "시작된" 자리는 다른 경우가 많습니다. 터진 자리만 고치면 증상만 가려질 수 있습니다.

**같은 종류인데 정상 동작하는 사례가 있다면 반드시 비교합니다.** 문제가 난 코드만 들여다보면 무엇이 정상인지 기준이 없습니다.
- 참조할 만한 정상 동작 사례를 찾아 끝까지(훑지 말고) 읽습니다
- 두 코드의 차이를 하나도 빠짐없이 적습니다 — "이건 상관없겠지"라며 미리 거르지 않습니다
- 그 코드가 무엇에 의존하고 있는지 파악합니다

### 2단계 — 가설은 한 번에 하나만, 가장 작은 변경으로 검증한다

"~ 때문에 ~가 원인이라고 본다"는 형태로 가설을 명확히 말로 적습니다. 그다음 가장 작은 변경 하나로 시험합니다.

- 좋은 예: "설정값이 다음 단계로 안 넘어가서 실패한다고 본다" → 넘어가는 값 하나만 바꿔 확인
- 나쁜 예: 짚이는 곳 세 군데를 한꺼번에 고치고 돌려본다 (뭐가 원인이었는지 알 수 없게 됨)
- 나쁜 예: 가설이 틀렸는데 그 수정을 남겨둔 채 다음 가설을 또 시험한다 (코드가 누더기가 됨)

가설이 안 맞았으면 → 1단계로 돌아가 새로 알게 된 정보를 반영합니다.
가설이 맞았으면 → 3단계로 넘어갑니다.

**세 번 고쳐도 안 되면 멈추고 구조를 의심합니다.** 같은 자리를 세 번째 고치고 있다면, 그건 가설이 빗나간 게 아니라 접근 방식 자체가 잘못된 신호입니다. 이때는 네 번째 시도를 바로 하지 말고, 사람에게 "이 방향이 맞는지" 먼저 상의합니다.

### 3단계 — 고치기 전에 실패하는 테스트(검증 코드)를 먼저 만든다

테스트란 코드가 맞게 동작하는지 자동으로 확인해주는 작은 검증 코드입니다. 지금 겪는 문제를 재현하는 테스트를 먼저 만들고, 그 테스트가 실제로 실패하는 것을 눈으로 확인합니다.

- 테스트 틀이 있는 프로젝트면 테스트 코드로 자동화합니다
- 마땅한 테스트 틀이 없으면 문제를 재현하는 간단한 스크립트라도 만듭니다
- 고칠 때는 한 번에 하나만 고칩니다 — 겸사겸사 다른 부분을 정리하거나 손보지 않습니다

### 4단계 — 고친 뒤, 값이 지나는 모든 지점에 방어를 넣는다

원인을 찾아 고�친 뒤에는 그 값이 지나가는 여러 지점에 검사를 추가합니다. 한 곳만 막으면 다른 경로가 그 검사를 비켜갈 수 있습니다.

- 들어오는 자리: 딱 봐도 잘못된 입력을 여기서 거른다
- 처리하는 자리: 이 작업에 말이 되는 값인지 확인한다
- 특정 상황(환경): 위험한 동작을 막는 조건을 넣는다
- 기록: 나중에 다시 살펴볼 수 있도록 관련 정보를 로그로 남긴다

## "됐다"고 말하기 전에 반드시 확인할 것

아래 다섯 가지 중 하나라도 안 됐으면 "고쳐졌다"고 말하지 않습니다.

- [ ] 문제를 일으키는 원인을 한 문장으로 설명할 수 있는가 (설명 못 하면 아직 모르는 것)
- [ ] 그 원인을 뒷받침하는 증거(로그, 재현 결과, 비교 결과)가 있는가
- [ ] 재발 방지용 테스트를 만들었고, 그 테스트가 고치기 전에는 실패하는 것을 직접 봤는가
- [ ] 고친 뒤 그 테스트를 다시 돌려 통과하는 것을 직접 봤는가 (지난 실행 결과나 "이제 될 것 같다"는 근거로는 안 됨)
- [ ] 원래 있던 다른 테스트들도 여전히 통과하는가

하나라도 체크가 안 되면 1단계로 돌아갑니다.

## 흔한 변명과 현실

| 이런 생각이 들 때 | 현실 |
|---|---|
| "일단 이거 지우니까 되네, 왜인지는 나중에" | 나중은 오지 않습니다. 다음에 비슷한 문제가 나면 또 처음부터 헤매게 됩니다 |
| "시간이 없으니 증상만 빨리 없애자" | 증상만 없애면 원인은 남아있고, 다른 곳에서 다시 터집니다. 정말 급하면 임시 조치를 하되, 반드시 사람에게 알리고 원인 조사는 별도로 이어갑니다 |
| "테스트까지 만들 필요는 없을 것 같은데" | 테스트 없이 "고쳐졌다"는 건 눈으로 한 번 본 것뿐입니다. 같은 문제가 조용히 되돌아와도 알 방법이 없습니다 |
| "이 정도면 될 것 같다" | "될 것 같다"는 확인이 아닙니다. 실제로 돌려서 통과하는 걸 본 뒤에만 "됐다"고 말합니다 |
| "짚이는 데가 몇 군데 있으니 다 고쳐보자" | 여러 곳을 한꺼번에 고치면 정작 무엇이 원인이었는지 끝내 알 수 없습니다. 하나씩 검증합니다 |

## 위험 신호

아래 중 하나라도 해당하면 멈추고 1단계로 돌아갑니다.

- 코드를 먼저 고치고 나서 "왜 됐는지"를 생각하고 있다
- 왜 실패했는지 설명하지 못한다
- 짚이는 곳을 여러 군데 동시에 고치고 있다
- "이번엔 그냥 넘어가자"는 생각이 든다
- 같은 자리를 세 번째 고치고 있다
- 테스트 없이 "이제 될 것 같다"고 말하려는 참이다
