# 근본 원인 디버깅

## 개요

**증상을 가리는 것과 원인을 없애는 것은 다르다.** 코드를 이리저리 바꾸다 보면 우연히 증상이 사라질 때가 있다. 그런데 왜 사라졌는지 설명할 수 없다면, 그건 고친 게 아니라 운이 좋았던 것이다. 원인이 그대로 남아 있으면 다른 모습으로 반드시 다시 나타난다.

이 스킬은 버그를 만났을 때 "일단 아무거나 바꿔보기"로 새지 않도록, 네 단계(조사 → 가설 → 검증 → 수정)를 순서대로 밟게 하는 절차입니다. 각 단계를 다 마쳐야 다음 단계로 넘어갈 수 있고, 마지막에는 "왜 고쳐졌는지"를 말로 설명할 수 있어야 끝난 것으로 봅니다.

## 언제 적용하나

- 항상 적용: 에러가 나거나, 기대한 동작과 다르게 동작하거나, 테스트가 실패하는 모든 상황.
- 예외(사람에게 확인): 급한 장애 대응처럼 "일단 서비스부터 살려야 하는" 상황에서는 임시 조치(롤백, 재시작 등)를 먼저 취할 수 있습니다. 단, 이 경우에도 임시 조치 후에는 반드시 이 절차로 돌아와 근본 원인을 조사해야 합니다 — 임시 조치를 끝으로 치지 않을지는 사람에게 확인하세요.

## 절차

### 1단계 — 조사: 증거를 모으기 전에는 고칠 방법을 제안하지 않는다

아래를 순서대로 확인합니다. 하나라도 빠뜨리면 다음 단계로 넘어가지 않습니다.

1. **에러 메시지를 끝까지 읽는다** — 줄 번호, 파일 경로, 에러 코드까지 전부.
2. **일관되게 재현한다** — 정확히 어떤 단계를 거치면 재현되는지 적고, 여러 번 반복해도 매번 재현되는지 확인한다.
   - 재현이 안 되면 → 추측하지 말고 재현 조건을 더 좁혀본다. (예: 특정 입력값, 특정 순서, 특정 환경에서만 나는지)
3. **최근에 무엇이 바뀌었는지 본다** — 코드 변경 이력, 새로 추가된 의존성(라이브러리), 설정값 변경.
4. **여러 부분(모듈·서비스·함수)을 거치는 문제라면 경계마다 값을 찍어 확인한다** — 어디까지는 정상이고 어디서부터 잘못됐는지 좁혀나간다.
5. **잘못된 값이 처음 어디서 생겼는지 거슬러 올라간다** — 에러가 "터진" 자리와 값이 "잘못 생긴" 자리는 다를 수 있다. 터진 자리만 보고 있으면 진짜 원인을 놓친다.

이렇게: "설정 파일을 읽는 함수의 반환값을 출력해보니, A 단계까지는 정상 값이 넘어오고 B 단계에서 비어 있었다 — 그 사이가 원인이다."

이러지 말 것: "이 부분이 의심스러워 보이니 일단 고쳐보자" — 증거 없이 짐작으로 코드를 바꾸는 것.

### 2단계 — 비교: 정상 동작하는 사례와 비교한다 (있다면)

비슷한 기능인데 정상적으로 동작하는 코드나 사례가 있다면, 문제가 난 쪽과 나란히 놓고 차이를 전부 적습니다. "이건 상관없겠지"라며 미리 걸러내지 않습니다 — 훑어보면 비슷한 점만 보이고 진짜 다른 점은 놓치기 쉽습니다.

이 단계는 비교할 대상이 없으면 건너뛸 수 있습니다.

### 3단계 — 가설: 한 번에 하나씩 세우고 검증한다

1. 가설을 명확한 문장으로 적습니다. (예: "설정값이 다음 단계로 안 넘어가서 실패하는 것 같다")
2. 가장 작은 변경 하나로 그 가설을 시험합니다. 여러 곳을 한꺼번에 고치지 않습니다 — 그러면 무엇 때문에 되고 안 됐는지 알 수 없게 됩니다.
3. 결과를 확인합니다.
   - 가설이 맞았다 → 4단계(수정)로 이동.
   - 가설이 빗나갔다 → 방금 한 변경을 되돌리고, 1단계로 돌아가 새로 알게 된 정보를 반영해 조사를 다시 합니다. (이미 한 수정 위에 새 수정을 얹지 않습니다)

**세 번 규칙**: 같은 부분을 세 번째 고치는데도 안 되면, 가설이 틀린 게 아니라 구조 자체가 문제일 가능성이 큽니다. 이 경우 네 번째 시도를 바로 하지 말고 일단 멈춘 뒤 사람에게 "이 부분 구조를 다시 봐야 할 것 같다"고 알립니다.

### 4단계 — 수정: 원인을 고치고, 재현 테스트로 증명한다

1. 원인이 되는 지점을 정확히 고칩니다. 한 번에 하나만 고치고, 지나가는 김에 다른 것을 같이 정리하지 않습니다.
2. 가능하면 이 버그를 재현하는 테스트(자동화된 테스트가 어려우면 재현 스크립트라도)를 만듭니다.
3. **되돌려서 확인**: 방금 고친 부분을 잠시 되돌려서 정말로 다시 실패하는지 확인합니다. 실패하지 않으면 그 테스트는 이 버그를 잡지 못하는 것이므로 테스트를 다시 손봅니다.
4. 고친 것을 되살리고, 다시 통과하는지 확인합니다.

## 원인 없음으로 결론 내릴 때

"환경 문제였다", "타이밍 문제였다"로 끝내려면 아래를 모두 확인해야 합니다. 그냥 포기하고 던지는 결론이 아니라는 것을 증명해야 합니다.

- 위 조사 단계를 끝까지 마쳤는가
- 무엇을 확인했는지 기록으로 남겼는가
- 그 상황을 견디는 처리(재시도, 시간 제한, 안내 메시지 등)를 넣었는가
- 다음에 다시 볼 수 있도록 로그나 기록을 남겨두었는가

## 흔한 변명과 현실

| 이런 생각이 든다면 | 현실은 이렇다 |
|---|---|
| "일단 이거 바꿔보고 되면 그걸로 끝내자" | 왜 됐는지 모르면 다음에 비슷한 문제가 다른 모습으로 또 나온다. 그때는 이 지식조차 없이 처음부터 다시 시작해야 한다. |
| "시간이 없으니 원인 찾기는 나중에" | 원인을 모르고 넘어간 버그는 대개 더 안 좋은 시점에 다시 터진다. 지금 쓰는 시간이 나중에 쓸 시간보다 항상 적다. |
| "여러 군데 한꺼번에 고치면 더 빠르지 않을까" | 여러 곳을 동시에 바꾸면 무엇 때문에 고쳐졌는지 알 수 없다. 다음에 비슷한 문제가 나도 무엇을 봐야 할지 모른다. |
| "테스트로 재현할 필요까지야" | 재현하지 못하면 정말 고쳐졌는지 증명할 방법이 없다. "느낌상 됐다"는 증거가 아니다. |
| "이 정도 증상이면 뻔한 원인이겠지" | 뻔해 보이는 원인이 진짜 원인이 아닌 경우가 많다. 조사 없이 짐작으로 넘어가면 결국 다시 돌아온다. |

## 위험 신호

아래 중 하나라도 해당하면 멈추고 조사 단계(1단계)로 돌아갑니다.

- 왜 고쳐졌는지 한 문장으로 설명할 수 없다
- "이렇게 하니까 됐다"만 있고 "왜 이게 문제였다"가 없다
- 여러 곳을 동시에 고쳤는데 어느 것 때문인지 모른다
- 같은 자리를 세 번 넘게 고치고 있다
- 재현을 시도하지 않고 넘어가려 한다
- "이번엔 급하니까 나중에 제대로 보자"고 생각하고 있다

## 완료 전 점검

- [ ] 증상을 재현했는가
- [ ] 원인이 어디서 시작됐는지 거슬러 올라가 확인했는가
- [ ] 가설을 세우고 최소한의 변경으로 검증했는가
- [ ] 원인을 고쳤고, 그 원인을 한 문장으로 설명할 수 있는가
- [ ] 고친 부분을 되돌리면 다시 실패하는 것을 확인했는가 (재발 방지 검증)
- [ ] 관련된 다른 부분이 여전히 정상 동작하는 것을 확인했는가

위 항목을 다 채우지 못했다면 "고쳐졌다"고 말하지 않습니다.
