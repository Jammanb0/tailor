# 8단계 — 전체 주입과 선택 주입 비교 사전 등록

> **8단계 생성 결과를 만들기 전에 쓴 초안이다.** 6단계에서 이미 확인한 선택
> 결과와 생성 결과는 알고 있으므로, 이 문서를 새 자료를 전혀 모르는 상태의
> 사전등록이라고 부풀리지 않는다. 여기서 고정하는 것은 8단계의 시나리오, 호출 수,
> 품질 판정선, 비용 계산법, 응답 시간 기록법과 위험 처리 규칙이다.
>
> 작성일: 2026-08-28 · 대상 커밋
> `fd43bfb32b685421661ade4ab9e9d833fae62803`(브랜치 `corpus-routing`).
>
> 이 초안은 실행 전에 사용자 검토를 받는다. 승인 뒤 고정한 항목은 8단계 결과를
> 본 다음 고치지 않는다. 바꿔야 하면 기존 문구와 변경 이유를 남기고 새 실험으로
> 구분한다.

## 이번 단계가 답할 것

6단계는 선택 정확도 14건과 3개 시나리오의 품질 생성 12건으로 선택 주입이
작동할 가능성을 확인했다. 8단계는 같은 선택 구현을 바로 고치지 않고 다음 세
질문에 답한다.

1. **품질** — 시나리오를 6개로 늘려도 선택 주입 결과가 전체 주입보다 나빠지지
   않는가?
2. **비용** — 선택 호출까지 포함하고 캐시 조건을 분리했을 때 어느 방식이 싼가?
3. **응답 시간** — 선택부터 생성 완료까지 실제로 이어서 재면 얼마나 걸리는가?

선택 정확도를 다시 대표 표본처럼 추정하는 단계는 아니다. 여섯 시나리오는
6단계에서 이미 선택 결과를 본 사례이며, 알려진 오선택의 영향을 보기 위해
의도적으로 위험 사례를 많이 넣었다. 실제 요청에서 오선택이 얼마나 흔한지는
트래픽이 생긴 뒤 7단계가 답한다.

## 비교 조건

### 전체 주입(`full`)

- `claude-sonnet-5`
- `max_tokens: 8192`
- `thinking: disabled`
- system 첫 블록에 `CORPUS_SECTION`, 둘째 블록에 `SYSTEM_PROMPT`
- user 메시지는 `buildUserContent(answers, false)`
- 코퍼스 system 블록에 5분 ephemeral cache

개발 전용 `/api/route-preview`에 평가용 `mode: "full"`을 추가해 응답에
`usage`, 모델 처리 시간, `stopReason`을 함께 담는다. 프로덕션
`/api/generate-skill`은 바꾸지 않는다. 실행 전 정적 검사에서 위 호출 설정이 실제
create 경로와 같은지 확인한다.

### 선택 주입(`routed`)

생성 설정은 full과 같고 system 첫 블록만 `buildRoutedCorpusSection(patternIds)`로
바뀐다. 품질 비교에서는 선택 모델을 다시 호출하지 않고 6단계에서 한 번 뽑아 둔
묶음 id를 고정해 쓴다. 회차마다 선택 결과가 달라지면 선택 변동과 생성 변동을
가를 수 없기 때문이다.

| 시나리오 | 품질 비교에 고정할 묶음 |
|---|---|
| `01-testing` | `tdd-cycle`, `test-discipline`, `skill-decision-aid` |
| `05-design` | `visual-direction`, `visual-typography`, `design-tokens`, `interface-copy` |
| `09-mismatch-office` | `request-framing`, `implementation-plan-structure`, `implementation-plan-handoff`, `skill-decision-aid`, `completion-evidence` |
| `10-mismatch-setup` | `tdd-cycle`, `implementation-plan-structure`, `implementation-plan-handoff`, `skill-decision-aid`, `completion-evidence`, `frequent-skill-budget` |
| `13-always-on` | `request-framing`, `frequent-skill-budget`, `skill-decision-aid` |
| `14-three-line-memo` | `interface-copy`, `frequent-skill-budget`, `skill-example` |

이 목록은 `2026-08-28-routing-eval/selection-results.json`의 성공한 6단계 결과를
옮긴 것이다. 8단계 결과를 보고 묶음을 빼거나 더하지 않는다.

## 시나리오 6개와 역할

| id | 포함 이유 | 6단계에서 이미 아는 것 |
|---|---|---|
| `01-testing` | 코드·절차형 대표 | 품질 비교에 포함, 선택 문제 없음 |
| `05-design` | 비코드 제작형 대표 | 품질 비교에 포함, 선택 문제 없음 |
| `09-mismatch-office` | 비코드 순서형 위험 | 구현 계획 묶음 2개 오선택, 품질 비교에는 포함 |
| `10-mismatch-setup` | 가장 큰 선택 코퍼스와 복합 위험 | TDD·구현 계획·빈도 묶음 오선택, 품질은 아직 비교하지 않음 |
| `13-always-on` | 빈도 대체 추론 양성 | `frequent-skill-budget`을 올바르게 선택, 품질은 아직 비교하지 않음 |
| `14-three-line-memo` | 가장 작은 선택 코퍼스와 복합 위험 | UI 문구·빈도 묶음 오선택, 바닥 생성만 했고 선택 결과의 품질은 아직 비교하지 않음 |

이 구성은 일반 요청의 분포가 아니다. 정상 사례, 양성 사례, 이미 알려진 위험
사례에서 선택 주입의 결과가 어떻게 달라지는지 보는 스트레스 표본이다.

## 품질 비교 — 24건

- 시나리오 6 × 조건 2 × 회차 2 = **24건**
- 같은 시나리오·회차의 full과 routed는 가능한 한 동시에 시작한다.
- 두 회차 모두 위 표의 같은 묶음 id를 사용한다.
- 모든 결과에서 조건 라벨을 지우고 섞은 뒤 채점한다.
- 같은 시나리오의 문서가 이웃하지 않게 배치한다.
- 채점자는 조건표를 열기 전에 24건의 점수와 근거를 먼저 고정한다.
- 결과 문서에는 채점자와 실행·도구 구현 담당이 같은지 다른지 기록한다. 가능하면
  두 역할을 분리하고, 분리하지 못하면 같은 사람이 맡았다는 한계를 밝힌다.

### 채점 기준과 통과선

6단계와 같은 A~F 앵커인
`../2026-08-19-expand3/GRADING-REPORT.md` §0을 쓴다. **B와 E는 정정판 앵커만
쓴다** — 용어가 있다는 이유로 감점하지 않고, 역할이 다른 반복은 감점하지 않는다.
새 축을 만들어 결정 직전에 자를 바꾸지 않는다.

| 역할 | 축 | 통과선(`routed 평균 - full 평균`) |
|---|---|---:|
| 주 지표 | F 절차 무결성 | **-0.33 이상** |
| 안전 지표 | A 구체성 | **하락 폭 0.67 미만** |
| 안전 지표 | B 용어 해소도 | **하락 폭 0.67 미만** |
| 안전 지표 | C 이식 저항성 | **하락 폭 0.67 미만** |
| 안전 지표 | D 금지의 판정 가능성 | **하락 폭 0.67 미만** |
| 안전 지표 | E 반복·모순 | **하락 폭 0.67 미만** |

A는 3차 확장 회차에서 60건 중 59건이 4점이었고, 6단계에서도 12건 모두 4점이라
두 회차 연속으로 변별력이 없었다. 그래서 주 지표에서 내린다. C도 3차 확장
회차에서 60건 중 57건이 3점으로 거의 고정이었다. A~E는 결과가 크게 나빠지는지를
막는 안전 지표로 유지하되, 특히 A와 C가 움직이지 않았다는 사실만으로 품질이
유지됐다고 해석하지 않는다. 시나리오별 평균도 함께 공개하지만 각 조건 2건뿐이므로
별도의 일반화된 통과선은 두지 않는다.

### 알려진 오선택의 결과물 감사

A~F 점수를 고정하고 조건을 공개한 뒤, 아래 세 시나리오는 별도 체크리스트로
직접 읽는다. 새 범용 품질 축을 만드는 것이 아니라 6단계에서 남긴 두 위험이 실제
문서에 나타났는지 확인하는 한정 감사다.

- `09-mismatch-office`: 코드 파일·구현 계획서 작성 절차가 불필요하게 붙었는가?
- `10-mismatch-setup`: 코드 동작을 위한 TDD 절차나 구현 계획 산출물을 요구하는가?
- `14-three-line-memo`: UI 문구 작성 절차나 상시 로드용 분량 규칙 때문에 요청한
  세 줄 형식을 벗어났는가?

routed 2건 중 하나라도 위 행동이 나타나고 같은 시나리오의 full 2건에는 나타나지
않으면, 그 위험은 결과물까지 전달된 것으로 판정한다. 이 경우 전체 품질 평균이
통과해도 9단계로 바로 가지 않고 카드 문구나 선택 프롬프트를 고친 뒤 해당
시나리오를 다시 비교한다.

### 실패 호출 처리

- 24건이 모두 성공해야 블라인드 묶음을 만든다.
- 한 조건이 API·네트워크·파서 오류로 실패하면 같은 시나리오·회차의 쌍을 모두
  버리고 그 쌍을 한 번만 다시 실행한다. 실패 자체와 사용량은 운영 기록에 남긴다.
- 재시도에서도 실패하면 부분 자료로 품질 점수를 내지 않고 실행을 멈춘다.
- 점수가 낮다는 이유로 다시 생성하지 않는다.

## 비용 비교

가격은 실행일의 Anthropic 공식 가격표와 저장소의 계산값을 함께 확인한다.
2026-08-28 현재 저장소가 쓰는 단가는 다음과 같다.

| 모델 | 일반 입력 | 출력 | 5분 캐시 생성 | 캐시 읽기 |
|---|---:|---:|---:|---:|
| Sonnet 5 | $2/MTok | $10/MTok | 입력의 1.25배 | 입력의 0.1배 |
| Haiku 4.5 | $1/MTok | $5/MTok | 사용하지 않음 | 사용하지 않음 |

공식 가격표(2026-08-28 확인):
<https://platform.claude.com/docs/en/about-claude/pricing>

Sonnet 5의 $2/$10은 출시 때 2026-08-31까지의 도입가로 발표됐지만, Anthropic은
이를 표준 가격으로 유지하고 2026-09-01에 예정했던 $3/$15 인상을 시행하지 않는다고
위 가격표에 명시했다.

다음 값을 모두 남긴다.

1. **관측 실행 비용** — API usage에 실제로 기록된 일반 입력·캐시 생성·캐시
   읽기·출력 토큰으로 계산한다.
2. **캐시 미적중 환산 비용** — 캐시 생성·읽기 토큰도 일반 입력으로 보아 두
   조건을 같은 0% 적중 가정에서 비교한다.
3. **선택 포함 routed 비용** — end-to-end 3건의 선택 usage 평균을 routed 요청
   한 건마다 더한다.
4. **손익분기 캐시 적중률** — full의 코퍼스 캐시 적중률이 얼마일 때 선택 포함
   routed 비용과 같아지는지 8단계 실측 평균으로 다시 계산한다.

손익분기 계산에서는 요청마다 조합이 달라지는 routed 코퍼스 블록의 캐시 적중률을
0%로 둔다. `design.md`가 정한 운영 초안도 선택 묶음 전체를 처음부터 캐시하지
않는다. 나중에 항상 같은 골격·기본 규칙만 별도 캐시하는 구현을 만들면 그 비용은
9단계에서 다시 계산한다.

품질 실행에서 우연히 캐시가 많이 맞은 값만으로 운영 비용을 결론내리지 않는다.
라우팅 채택의 비용 조건은 **캐시 적중률 0% 환산에서 선택 비용을 포함한 routed
평균이 full 평균보다 낮을 것**이다. 실제 요청이 거의 없다는 운영 가정과 함께
10단계 결정문에 적는다.

### 실행 예산

기존 usage로 예상한 실제 실행 비용은 품질 비교 약 $1.4~2, end-to-end 확인 약
$0.2다. 캐시가 전혀 없다고 환산한 비용은 약 $3이지만, 이는 실제 청구 상한이
아니다. 출력 길이와 캐시 상태에 따라 달라질 수 있다.

실행 중에는 완료된 호출의 usage로 **관측 실행 비용**을 누적한다. **관측 실행
비용이 $2.80을 넘으면 다음 호출을 시작하지 않고**, 남은 호출 수와 예상 추가 비용을
사용자에게 보고해 다시 승인받는다. 한 호출의 비용은 응답 뒤에야 확정되므로
$2.80이 절대적인 청구 상한은 아니다.

## end-to-end 응답 시간 — 별도 3건

품질 비교에 선택 호출을 섞지 않는다. 아래 세 시나리오는 품질 24건과 별도로
routed를 한 번씩 실행하며, 실제 선택 모델을 거쳐 생성한다.

| 시나리오 | 고른 이유 | 6단계 선택 코퍼스 크기 |
|---|---|---:|
| `14-three-line-memo` | 작은 선택 코퍼스·오선택 위험 | 17,431B |
| `01-testing` | 중간 크기·정상 코드 사례 | 27,683B |
| `10-mismatch-setup` | 큰 선택 코퍼스·복합 오선택 위험 | 41,406B |

각 호출에서 다음을 기록한다.

- 클라이언트가 POST 직전부터 응답 전문을 받을 때까지 잰 전체 시간
- 선택 모델 시간과 usage
- 생성 모델 시간과 usage
- 전체 시간과 `선택 시간 + 생성 시간`의 차이
- 6단계에서 고정한 묶음과 이번에 다시 고른 묶음의 차이

세 건은 선택과 생성 시간을 한 번에 잰 값이 기존 조각 합산치와 맞는지 확인하는
용도다. 생성 자체의 변동이 크고 표본도 3건뿐이므로 “routed가 더 빠르다”는 결론은
내리지 않는다. 별도의 제품 SLA가 정해져 있지 않아 임의의 속도 통과선을 만들지
않고, 평균·중앙값·범위와 full 품질 생성 시간 대비 차이를 그대로 보고한다.

end-to-end에서 묶음이 다르게 선택돼도 품질 비교의 고정 묶음은 바꾸지 않는다.
