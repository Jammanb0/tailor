# 6단계 — 선택 정확도와 생성 품질의 판정선 사전 등록

> **아무것도 돌리기 전에 썼다.** 선택 모델을 한 번도 호출하지 않았고 생성도
> 돌리지 않은 상태에서 정답지와 통과선을 먼저 적었다.
>
> **고정 대상은 셋이다** — 통과선, 정답지(`bundle-answer-key.json`),
> 「미리 적어두는 예측」. 자료를 한 줄이라도 본 뒤에는 이 셋을 고치지 않는다.
> 나머지 절은 사실이 달라지면 고친다.
>
> 작성 시각: 2026-08-28 · 대상 커밋 `f9bea55`(브랜치 `corpus-routing`).
>
> 왜 먼저 쓰는가: 자료를 본 뒤에 기준을 정하면 나온 결과가 그대로 통과선이 된다.
> 3차 확장 회차에서 같은 이유로 판정선을 먼저 등록했고, 그 자리에서 실제로
> "판정선 밖의 회귀"를 잡았다(`../2026-08-19-expand3/PRE-REGISTRATION.md`).

## 무엇을 재는가

5단계에서 만든 선택 경로가 **요청에 맞는 묶음을 고르는지**, 그리고 그렇게 고른
묶음만으로 만든 SKILL.md가 **전체 코퍼스를 넣은 결과보다 나빠지지 않는지**를
본다. 선택 경로는 아직 `/api/generate-skill`에 붙어 있지 않다. 선택 정확도는
`/api/route-preview`로 재고, 생성 품질은 현재 전체 주입 경로인
`/api/generate-skill`과 개발 전용 선택 주입 생성 경로를 같은 시점에 비교한다.
제품의 실제 생성 동작은 바꾸지 않는다.

## 선택 정확도와 바닥 규칙을 네 축으로 나눈다 — 한 평균으로 합치지 않는다

`design.md`의 「조건 종류를 나눠 평가한다」를 따른다. 직접 신호는 코드가 결정적으로
판정하고, 예측형 조건은 모델이 아직 만들어지지 않은 결과물의 형태를 예측해야
한다. 성격이 다른 두 정확도를 한 숫자로 합치면 코드가 맞힌 몫이 모델의 성적을
가린다.

| 축 | 대상 | 판정 주체 |
|---|---|---|
| 1. 직접 신호 | `token-budget` × 빈도 답이 있는 요청 3건 | 코드 (결정적) |
| 2. 예측형 조건 | 온라인 묶음 35개 × 시나리오 14건 | 모델, 사람이 채점 |
| 3. 대체 추론 | `frequent-skill-budget` × 빈도 답이 없는 14건 | 모델, 사람이 채점 |
| 4. 완료 전 확인의 바닥 | 상세 검증 패턴 0개로 만든 생성물 | 사람이 문서를 열어 판정 |

`frequent-skill-budget`은 축 2에서 세지 않는다. 이 묶음의 유일한 중심 패턴이
`token-budget`이고, 빈도 답이 있으면 축 1이, 없으면 축 3이 맡는다. 양쪽에서
세면 같은 판정을 두 번 세게 된다.

생성 품질 블라인드 비교는 성격이 다른 별도 축 5로 둔다.

## 정답지의 세 칸 — 필수·허용·불필요

정답지는 `bundle-answer-key.json`에 있다. 시나리오마다 온라인 묶음 36개를 세
칸으로 가른다.

- **필수** — 요청이 명시적으로 시킨 일을 담은 묶음. 빠지면 결과물이 요청을 안
  지킨 것이 된다. 안 고르면 **누락 1건**.
- **허용** — 요청과 어긋나지 않고, 골랐다면 근거를 댈 수 있는 묶음. 골라도 안
  골라도 세지 않는다.
- **불필요** — 요청이 시키지 않은 일. 고르면 **오선택 1건**.

애매하면 허용에 넣었다. 허용 칸이 있는 이유가 그것이다 — 판정이 갈리는 자리를
억지로 감점이나 가점으로 밀어 넣으면 통과선이 정답지 설계의 결과가 된다.

`requiredAnyOf`는 「이 중 최소 하나」다. 05-design에서만 썼다 — 색과 폰트를
정하는 자리를 `visual-typography`와 `design-tokens`가 나눠 맡고 있어 어느 쪽을
골라도 요청을 만족한다.

### 시나리오 14건

기존 12건(`../2026-08-19-expand3/scenarios.json` 10건 +
`../2026-08-20-baseline-fill/scenarios-extra.json` 2건)에 두 건을 보탰다.
새 두 건은 `scenarios-routing.json`에 있다.

| id | 왜 보탰나 |
|---|---|
| `13-always-on` | 대체 추론의 **양성 사례가 하나도 없었다.** 기존 12건은 전부 상시 로드가 아니어서, 축 3이 "안 고르면 만점"인 시험이 된다 |
| `14-three-line-memo` | `design.md`가 요구한 **상세 검증 묶음 0개 사례.** 골격의 「완료 전 확인」 바닥 규칙만으로 구체적인 확인 절이 나오는지 본다 |

축 1용으로 기존 시나리오에 빈도 답만 붙인 변형 3건을 따로 둔다. 상황 글을
복사하지 않고 `basedOn`으로 가리킨다 — 복사하면 원본을 고쳤을 때 조용히 갈라진다.

## 통과선

### 축 1 — 직접 신호: 3/3

`frequency=often`이면 `token-budget`이 켜지고 전달 목록에 있어야 한다.
`rarely`·`sometimes`면 꺼지고 전달 목록에 없어야 한다(`requires`로 다시 들어오면
`addedByRequires`에 남아야 한다).

**부분 점수를 두지 않는다.** 결정적 코드 판정이므로 1건이라도 어긋나면 실패로
보고 코드를 고친다.

### 축 2 — 예측형 조건

| 항목 | 통과선 |
|---|---|
| 필수 누락 | 전체 19개 판정 단위 중 **1건 이하** |
| 필수를 하나도 못 고른 시나리오 | **0건** |
| 시나리오당 평균 오선택 | **1.5개 이하**(14건 합계 21개 이하) |
| 오선택 5개 이상인 시나리오 | **0건** |
| 목록에 없는 id(`unknownBundleIds`) | **0건** |
| 평가 전용 묶음 선택(`rejectedBundleIds`) | **0건** |

필수를 빡세게 잡은 이유: 필수 칸에는 요청이 글로 시킨 것만 넣었다. 여기를
놓치면 비용이 얼마나 줄었든 의미가 없다.

**누락이나 오선택이 나오면 수치로 끝내지 않는다.** 그 시나리오의 선택 응답
원문과 묶음 카드를 열어 원인이 카드 문구인지 선택 능력인지 가른다. 통과선을
못 넘는다고 곧바로 라우팅을 접는 것이 아니라, 카드를 고쳐 다시 재는 것이 다음
수순이다.

### 축 3 — 대체 추론

빈도 답이 없는 14건에서 `frequent-skill-budget` 선택 여부를 본다.

- 양성 1건(`13-always-on`): **골라야 한다.** 못 고르면 실패.
- 음성 12건: 오선택 **2건 이하**.
- 보류 1건(`01-testing`): 세지 않는다. TDD 스킬은 코딩할 때마다 걸릴 수 있어
  어느 쪽도 틀렸다고 하기 어렵다.

### 축 4 — 완료 전 확인의 바닥 규칙

`14-three-line-memo`의 전달 목록에 `bundle-answer-key.json`의
`verificationPatternIds`가 **하나도 없는 상태**로 3회 생성한다. 선택 능력과
분리하기 위해 **언제나 `bundleIds: []`로 실행한다** — 선택 모델이 무엇을 골랐든
머리말·골격·always 5개만 남는다. 여기서 보려는 것은 무엇을 골랐는지가 아니라
**골격이 만든 자리가 혼자 버티는지**다. 검증이 아닌 다른 조건부 묶음이 바닥
규칙을 대신 살리는 경우도 섞지 않는다.

생성물 3건 모두에서 「완료 전 확인」 절이

1. 있고,
2. 비어 있지 않고,
3. 그 결과물에 맞는 **구체적인 확인 행동**을 최소 하나 지시해야 한다.
   ("확인한다", "검토한다" 같은 일반론만 있으면 실패.)

**3/3이어야 통과한다.** 실패하면 최소 검증 묶음 강제를 다시 안건으로 올린다
(`decisions.md` 2026-08-27).

판정은 낱말 검색으로 하지 않는다 — 문서를 열어 읽는다. 생성물 확인을 낱말
검색으로 했다가 네 번 오판한 기록이 있다(`handoff.md`의 「손대기 전에 읽을 다섯」 2번).

### 축 5 — 생성 품질 블라인드 비교

선택 주입으로 만든 SKILL.md가 전체 주입 결과보다 나빠지지 않았는지 본다.

- 시나리오 3종: `01-testing`, `05-design`, `09-mismatch-office`
  (앞의 둘은 2026-08-27 기준값과 같은 시나리오이고, 09는 계획 묶음이 딸려올
  여지가 커 오선택의 영향을 보기 좋다)
- 조건 2 × 시나리오 3 × 2회 = **12건**
- 두 조건을 **같은 시점에** 돌린다. 옛 값을 꺼내 쓰지 않는다
  (`decisions.md` 2026-08-27).
- 선택 주입 2회는 축 2에서 그 시나리오가 고른 `bundleIds`를 그대로 재사용한다.
  회차마다 선택을 다시 뽑으면 묶음 차이와 생성 변동을 가를 수 없기 때문이다.
- 같은 시나리오·회차의 전체 주입과 선택 주입 호출은 한 쌍으로 동시에 시작한다.

채점 축은 `A 구체성 / B 용어 해소도 / C 이식 저항성 / D 금지의 판정 가능성 /
E 반복·모순 / F 절차 무결성`이고, 앵커는
`../2026-08-19-expand3/GRADING-REPORT.md` §0을 쓴다. **B와 E는 정정판 앵커만
쓴다** — 용어가 있다는 이유로 감점하지 않고, 역할이 다른 반복은 감점하지 않는다.

| 항목 | 통과선 |
|---|---|
| F축(절차 무결성) 평균 | 전체 주입 대비 **-0.33 이내** |
| A축(구체성) 평균 | 전체 주입 대비 **-0.33 이내** |
| 나머지 축 | 어느 축도 **-0.67 이상 하락하지 않음** |

±0.33은 과거 회차가 쓴 폭과 같다. 새로 만든 기준이 아니다.

**실패(502·파서) 건수는 두 조건 각각 세되 비교하지 않는다.** 기준값 측정 이후
파서 되돌림 경로가 들어갔으므로(`00074ee`), 실패율 차이는 라우팅의 성과가 아니다
(`../2026-08-27-routing-before/NOTES.md` 맨 위 정정).

## 미리 적어두는 예측

빗나가면 빗나간 대로 남긴다.

- **필수 재현율은 통과할 것 같다.** 5단계 미리보기에서 `01-testing`은
  `tdd-cycle`을, `05-design`은 `visual-direction`·`visual-typography`·`design-tokens`를
  골랐다. 필수 칸에 넣은 것들이다.
- **오선택이 통과선을 흔든다면 `09-mismatch-office`다.** 5단계 미리보기에서 7개를
  골랐고 그중 계획 묶음 둘과 `interface-copy`는 요청에 없는 일이다. 이 한 건만
  4개를 넘기면 평균이 아니라 "5개 이상 0건" 쪽이 먼저 걸린다.
- **`frequent-skill-budget`의 음성 오선택이 나올 것 같다.** 5단계 미리보기에서
  `01-testing`이 이미 골랐다. 보류로 뒀으니 그 한 건은 안 세지만, 같은 성향이면
  다른 시나리오에서도 나온다.
- **품질 축에서는 F축이 가장 위험하다.** 과거 회차에서 F축은 골격보다 카테고리
  내용에 크게 반응했다. 코퍼스가 4분의 1로 줄면 여기가 먼저 움직인다.

**반복하지 않을 예측**: 「분량이 줄어 사용자 상황이 더 잘 반영된다」는 예측은
세우지 않는다. 2차 확장에서 반대 방향의 같은 예측(분량 때문에 상황이 묻힌다)이
빗나갔고, C축은 한 칸도 움직이지 않았다.

## 자료 취급 규칙

- **성공 건수를 먼저 확인한 뒤에 수치를 낸다.** 과거 한도 소진으로 30건 중 8건만
  성공한 자료로 수치를 낸 사고가 있었다.
- **점수나 선택이 예상과 다르면 그 문서를 직접 연다.** 수치만 보고 원인을 판정하지
  않는다.
- **채점은 조건 라벨을 지우고 섞어서 한다.** 조건별 목록을 따로 섞은 뒤 지퍼로
  엮어, 어느 구간을 잘라도 두 조건이 반반이 되게 배치한다
  (`../2026-08-19-expand3/make-blind.mjs` 방식). **같은 시나리오의 결과물을
  나란히 놓지 않는다** — 붙여 놓으면 축별 절대 채점이 아니라 머리를 맞댄 비교가
  되고, 길이 차이 같은 단서가 12건 내내 같은 방향으로 작용한다. 회차가 달라도
  상황 글은 같으므로 짝 안뿐 아니라 **인접한 모든 자리**를 본다.
- **선택 모델의 원시 응답과 호출별 usage를 함께 저장한다.** 5단계에서는 남기지
  않아 그때의 선택 호출 수치가 재현되지 않는다(`design.md` 5단계 실측 표 아래 주석).
- **최종 전달량은 `patternIds`, 묶음이 데려온 후보는 `bundlePatternIds`다.**
  둘을 섞어 세지 않는다.
- **사용자 원문은 여기 없다.** 14건 전부 우리가 만든 시나리오다.

## 이 단계에서 손대지 않는 것

- **코퍼스 내용**(`src/data/reference-corpus.ts`의 패턴 본문). 고치면 전체 주입
  조건과 선택 주입 조건이 같은 코퍼스를 쓰지 않게 되어 비교가 깨진다.
- **묶음 구성과 카드 문구.** 축 2가 재려는 대상이다. 결과를 본 뒤에 고친다.
- **`/api/generate-skill`.** 그대로 전체 코퍼스를 보낸다(`decisions.md` 2026-08-28).

## 사전등록 시점에 없었던 실행 준비물

**기준을 고정한 뒤에 구현한다.** 순서를 뒤집으면 도구가 낼 수 있는 수치에 맞춰
통과선을 정하게 된다.

아래는 이 문서를 쓴 시점의 상태다. 나중에 갱신하지 않는다 — 무엇이 없는 상태에서
기준을 정했는지가 남아야 이 문서가 사전등록 구실을 한다.

1. **정답지 채점기** — `route-preview` 응답과 `bundle-answer-key.json`을 맞춰
   축 1~3을 세는 도구. 지금은 `tools/route-preview.mjs`가 무엇을 골랐는지만
   찍는다(그 파일도 "이것은 채점이 아니다"라고 적고 있다).
2. **선택 주입으로 생성하는 평가용 경로** — 축 5에 필요하다. `/api/generate-skill`은
   라우팅을 쓰지 않고, `/api/route-preview`는 생성을 하지 않는다.
3. **빈도 답과 `wantsAdvanced`를 넘기는 실행기 지원** — 축 1의 변형 3건에 필요하다.
   현재 `route-preview.mjs`는 `wantsAdvanced: false`로 고정해 보낸다.
