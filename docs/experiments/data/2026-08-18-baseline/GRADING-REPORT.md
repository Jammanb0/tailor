## 2. 문서별 상세 (최강/최약 지시문 인용 + 구체성 요소 + 누수)

구체성 요소 표기: `#`=구체 숫자/개수, `"`=그대로 복사할 문자열, `F`=명명된 출력 포맷, `E`=완결된 워크드 예제.

### 01-testing (TDD)

**run1** — 요소: `#` `"` `F` `E`
- 최강: "테스트를 실제로 **실행해서 실패하는 것을 눈으로 확인**한다. (아직 기능이 없어서 실패해야 한다 — 문법 오류로 실패하는 건 안 된다)" — 실패의 *종류*까지 판정 기준을 준다.
- 최약: "중복 제거, 이름 정리, 구조 개선을 하되" — 무엇이 중복/나쁜 이름인지 기준 없음.
- 근거: Cart 클래스 Good/Bad 코드블록, 리터럴 실패 메시지 `FAIL: Cart is not defined`, "이름에 and가 들어가면 쪼갠다".

**run2** — 요소: `"` `#`
- 최강: "**Good**: `test_creates_user_with_valid_email()` / `test_rejects_invalid_email()`" — 복사 가능한 이름 형태.
- 최약: "테스트하기 어렵다는 건 설계 신호일 수 있다. 지금 구조를 다시 보는 게 낫다" — 태도 문장.

**run3** — 요소: `"` `#`
- 최강: "Good: 테스트 실행 → `ReferenceError: loginUser is not defined` 확인 → 의도한 실패임을 확인"
- 최약: "코드를 깔끔하게 정리할 필요가 있으면 이 단계에서 정리합니다" — 판단 기준 전무.
- 누수 의심: "이것이 바로 **사용자가 이 스킬을 만든 이유**입니다", "이미 사용자가 겪은 문제입니다" — 독자(AI 어시스턴트)에게 주는 지시가 아니라 생성 맥락에 대한 메타 코멘트.

### 02-debugging (근본원인)

**run1** — 요소: `#` `"` `E`
- 최강: "**Good**: \"TypeError: Cannot read property 'id' of undefined, at UserCard.tsx:42\" — 정확한 위치와 메시지를 그대로 인용"
- 최약: "해결책을 먼저 제시하지 않습니다. 원인 지점을 먼저 특정합니다." — 방향은 맞으나 "특정했다"의 판정은 4단계로 미뤄진다(4단계가 이를 구제).
- 특기: "원인을 한 문장으로 설명할 수 없으면 3단계로 돌아간다"는 이 코퍼스 전체에서 가장 잘 설계된 **되돌림 조건**이다.

**run2** — 요소: `#` `"`
- 최강: "`git log`, `git diff`, 최근 커밋을 보고 문제가 언제부터 생겼는지 좁힙니다. … 문제가 없던 마지막 커밋과 문제가 생긴 첫 커밋을 찾아 그 사이의 diff를 살펴본다."
- 최약: "김에 다른 것도 손보거나 방어 코드를 잔뜩 추가하지 않습니다" — "잔뜩"의 기준 없음.

**run3** — 요소: `#`
- 최강: "같은 문제를 세 번 넘게 수정 시도했는데도 재현된다면 … 멈춰서 구조를 다시 살펴봅니다." — 셀 수 있는 임계값.
- 최약: "3단계: 최근 변경 사항을 확인한다 — 언제부터 문제가 생겼는지 … 확인합니다." (run2와 달리 명령어도 판정 기준도 없음)

- 최약: "각 단위는 독립적으로 완료·확인 가능한 크기여야 한다." — 크기 기준 없음.

### 04-code-review — A축 최고점 카테고리

**run1** — 요소: `"` `F` `E`
- 최강: "### 🐞 버그 … ### ⚠️ 취향/스타일 … - [파일:줄번호] 무엇이 문제인지 + 어떤 상황에서 어떻게 깨지는지" — 출력 형식을 헤딩·이모지·필드 단위로 못박음. 위반 판정이 자동으로 된다.
- 최약: "확신이 안 서는 지점은 \"아마도\"라고 흐리지 말고, 왜 의심스러운지와 확인이 필요한 부분을 명확히 짚는다." (그래도 금지어 "아마도"가 리터럴로 박혀 있어 검증 가능)
- 특기: "버그가 없으면 \"버그는 안 보입니다\"라고 명확히 말하고, 억지로 지적거리를 만들지 않습니다" — **빈 결과의 처리 규칙**을 명시한 몇 안 되는 문서.

**run2** — 요소: `"` `F` `E`
- 최강: 🔴/🟡/🟢 3단 분류 + 각 등급의 예시 문장("이 함수는 `items`가 빈 배열일 때 `items[0]`에 접근해서 죽습니다.")
- 최약: "🟡 주의 (애매한 것): 지금은 동작하지만 나중에 문제가 될 수 있는 것" — 경계가 🟢 취향과 겹친다.

**run3** — 요소: `"` `F`
- 최강: 코드펜스로 제시한 출력 템플릿 전체(섹션 2개, 라인 표기 형식 포함).
- 최약: "2. **버그 관점**: 로직 오류, 엣지 케이스(빈 값·null·경계값·에러 경로) … 확인합니다." — 점검 목록이지 절차는 아님(열거되어 있어 체크는 가능).

- 최약: "아무 프로젝트에나 쓰는 무난한 산세리프 폰트 하나로 전체 통일" — 클리셰 목록조차 이름을 대지 않아 판정 불가.

## 4. A축(구체성) 시나리오 순위

1. **04-code-review (4.00)** — 압도적. 이유가 분명하다: 산출물이 *문서 형태*라 출력 포맷(🔴/🟡 섹션, `[파일:줄번호]`)을 강제할 수 있었고, `git diff`라는 리터럴 명령이 존재한다. 3런 전부 A=4.
2. **02-debugging (3.67)** — "세 번 규칙", "원인을 한 문장으로", 리터럴 에러 문자열, git 명령. 되돌림 조건이 명시된 유일한 절차.
3. **07-documentation (3.67)** — 명명된 섹션 7~8개, 결손 조건별 되묻는 질문 리터럴.
4. **01-testing (3.33)** — Red/Green/Refactor 단계명, 실패 원인 판별 기준, 실행 코드 예제.
5. **06-voice (3.33)** — 리터럴 금지어 목록이 점수를 견인. 그 외는 태도.
6. **08-explanation (3.00)** — 편차가 커서 평균의 의미가 약함.
7. **05-design (2.67)** — 클리셰 목록만 구체적이고, 정작 지시해야 할 색·폰트·대비는 전부 형용사.
8. **03-planning (2.67)** — 최하위.

**태도만 나온 영역 vs 지시가 나온 영역**

- **지시가 나온 영역**: 코드 리뷰, 디버깅, 기획 문서. 공통점은 *절차가 이미 세상에 이름으로 존재*하고(diff, 스택 트레이스, 목차) 산출물에 형식이 있다는 것.
- **태도만 나온 영역**: 디자인, 설계-먼저. 디자인 문서는 "이 주제만의", "절제한다", "충분한 대비", "반사적으로 고르지 말 것" 같은 문장이 조작적 지시 자리를 차지한다. 색상값 하나, 추천 폰트 하나, 대비 수치 하나가 문서 전체에 없다 — 정작 사용자가 "색이랑 폰트를 정해달라"고 요청한 시나리오에서. 설계-먼저 문서는 "애매한 부분을 질문한다"를 세 가지 다른 표현으로 반복할 뿐, "무엇이 애매한가"의 판별식이 없다.

**이 시스템은 "구체적으로 쓰는 법"을 아는 것이 아니라, 주제가 이미 구체적인 어휘를 갖고 있을 때만 구체적으로 쓴다.** `git diff`, 스택 트레이스, "5~10줄" 같은 재료가 주제 안에 준비된 시나리오(04/02/07)에서는 A=4를 안정적으로 낸다. 재료를 스스로 만들어야 하는 시나리오(05 디자인, 03 설계)에서는 즉시 "절제한다 / 충분한 대비 / 반사적으로 고르지 말 것"으로 후퇴한다. 사용자가 명시적으로 "색이랑 폰트를 정해달라"고 요청한 05에서 색상값도, 폰트 추천도, 대비 수치도 끝내 나오지 않고 대신 *금지 목록*(Inter 쓰지 마라, 보라 그라디언트 쓰지 마라)만 나온 것이 이 실패의 결정적 증거다. 무엇을 하지 말지는 말할 수 있지만 무엇을 할지는 말하지 못한다. 08-run3에서 "5~10줄"이 이유 없이 증발한 것도 같은 병증의 다른 얼굴이다 — 임계값이 규칙으로 관리되지 않고 그때그때 운으로 나온다.

부수적으로: 01/02의 4단 반복 구조는 "충실해 보이는 분량"을 만들지만 실제 검증 가능한 지시는 문서당 9~13개로, 절반 길이인 04(14~15개)보다 적다. **분량이 품질의 대리 지표가 되고 있다.**

## 8. 문서만으로는 판단할 수 없었던 것 (명시)

1. **실제 효과**: 이 SKILL.md들을 실제 코딩 어시스턴트에 적용했을 때 행동이 바뀌는지. 나는 지시가 *검증 가능한 형태인지*만 봤고 *작동하는지*는 보지 않았다.
2. **트리거 정확도**: frontmatter `description`이 의도한 상황에서만 발동하는지, 과발동/미발동 하는지.
3. **사실 정확성**: 08-run1의 React 설명, 05의 클리셰 목록이 현재 기준으로 맞는 조언인지 검증하지 않았다(채점 축이 아니다).
4. **템플릿의 출처**: `Overview`/`Red Flags`/`Rationalizations` 골격이 시스템 프롬프트에서 온 것인지, 참조 코퍼스에서 온 것인지, 모델의 사전지식인지. 소스를 열지 않았으므로 "주제와 무관하게 반복된다"는 관측만 보고했고 원인은 단정하지 않았다.
5. **파일명·frontmatter의 적법성**: 한글 파일명(`테스트-먼저-작성하기`)과 영문 파일명이 섞여 있는데 해당 형식이 유효한지 판단할 근거가 문서에 없다. 다만 **같은 시나리오 3런에서 name이 서로 다르게 나오는 것**(04가 `코드-변경-리뷰`/`diff-code-review`/`방금-변경-코드-리뷰`, 05·06도 한/영 혼재)은 관측 사실로 기록해 둔다.
6. **사용자 상황의 정보량**: C축이 3에 갇힌 것이 시스템의 한계인지, 애초에 입력에 프로젝트 정보가 없어서인지 분리할 수 없다. 개선판 비교 시 이 축의 상승은 "입력을 더 캐물었는가"와 함께 해석해야 한다.

## 9. 채점 규칙과 판단 기준 (개선판에 동일 적용할 것)

**9.1 "검증 가능한 지시" 계수 규칙**

- 1개로 세는 것: *고유한* 규범 명제 하나(X를 하라 / X를 하지 마라 / X가 참이어야 한다) 중, 제3자가 대화 기록이나 산출물을 보고 준수 여부를 판정할 수 있는 것.
- 세지 않는 것:
  - (a) 이미 센 규칙을 다른 섹션에서 재기술한 것 — Verification Checklist, Red Flags, Rationalizations 표, Done 기준의 항목은 **원칙적으로 0으로 계산**한다. 그 섹션에서 *새 규칙*이 처음 등장할 때만 센다.
  - (b) 이미 센 규칙을 예시하는 Good/Bad 쌍.
  - (c) 근거·이유·동기 설명 문장("~하면 버그를 놓치기 쉽습니다").
  - (d) 헤딩, 개요, 자기소개 문장.
  - (e) 채워 넣을 빈 템플릿 항목(예: "**어조**: (예: …)") — 지시가 아니라 슬롯.
- 한 문장에 독립적으로 위반 가능한 규범이 둘 이상이면 나눠 센다("5~10줄 이내 / 주석을 단다 / 실행 결과를 말한다" = 3).

**9.2 축별 앵커(이 코퍼스에서 실제로 쓴 기준)**

- **A**: 4 = 숫자·임계값·리터럴 문자열·명명된 포맷·워크드 예제 중 2종 이상이 *핵심 지시 자리*에 있다. 3 = 그런 요소가 있으나 일부 핵심 지시는 여전히 형용사. 2 = 구체 요소가 주변부(예시 목록)에만 있고 조작적 지시는 태도 문장. 1 = 리터럴이 한두 개. 0 = 전무.
- **B**: 4 = 미정의 용어 0, 그대로 따라 하면 된다. 3 = 일반적 개발 용어(git, 스택 트레이스, 종료코드) 정도만 전제. 2 = 번역 안 된 골격 용어(Handoff, 게이트) 또는 판정 불가 기준("충분한 대비")이 실행을 막는다.
- **C**: 4 = 사용자의 구체 프로젝트/도구/제약이 문서에 박혀 있어 이식 불가. 3 = 주제 카테고리에 묶여 있어 주제 교체 시 깨짐. 2 = 주제어만 갈아끼우면 그대로 재사용 가능. **입력에 프로젝트 정보가 없었다는 사정은 감안하지 않았다** — 오직 페이지 위의 것만 봤다(과제 규칙).
- **D**: 4 = 위반 판정이 명확한 금지가 복수 + 최소 하나에 명시적 예외/탈출 조건. 3 = 명확한 금지 복수, 예외는 약하거나 없음. 2 = 금지가 얇거나 승인 게이트의 뒷면일 뿐. 1 = "나쁜 관행 피하기" 수준.
- **E**: 4 = 반복·패딩 없음. 3 = 마무리 체크리스트 정도의 경미한 재기술. 2 = 동일 규칙이 3개 이상 섹션에 재등장하거나 두 섹션이 사실상 같은 목록. 1 = 상호 모순 존재. **모순은 이 코퍼스에서 발견되지 않았다** — E 점수는 전부 *반복/패딩* 사유다. 개선판에서 진짜 모순이 나오면 1 이하로 내려야 한다.

**9.3 내린 판단(논쟁 가능, 기록해 둠)**

- 반복을 E에서만 감점하고 A는 깎지 않았다. 반복된 규칙도 여전히 검증 가능하기 때문이다.
- 03-planning-run1의 "별다른 이견이 없다는 신호를 주면"은 승인 게이트를 무력화하지만 *모순*으로 보지 않고 A의 최약 문장으로 처리했다(같은 문서 안에 반대 규칙이 없으므로).

- 길이는 점수에 직접 반영하지 않았고 밀도 지표로만 기록했다.
- 이모지 사용(🔴🟡🟢)은 포맷 명세의 일부로 보아 A에 가산했다. 미적 판단은 하지 않았다.
