# 패턴 카탈로그 (채점용)

총 35개 패턴.

## 테스트

### `test-first`
- 요약: 구현 코드보다 실패하는 테스트를 먼저 쓴다
- 내용: 새 기능·버그픽스·리팩터링 전에 실패하는 테스트를 먼저 작성하고, 그 테스트가 '기능이 없어서' 실패하는지 눈으로 확인한 뒤 통과할 최소 코드를 쓴다(Red-Green-Refactor). 테스트를 나중에 쓰면 이미 짠 코드에 편향돼 '무엇을 하는가'만 검증하게 된다.

### `one-behavior-per-test`
- 요약: 테스트 하나는 한 가지 행동만 검증한다
- 내용: 테스트 이름에 'and'가 들어가면 쪼갠다. 이름은 동작을 설명하고, mock의 동작이 아니라 실제 코드의 동작을 단언한다.

### `minimal-green`
- 요약: 테스트를 통과시킬 최소 코드만 쓴다
- 내용: 아직 필요 없는 옵션·추상화·에러 처리를 미리 넣지 않는다(YAGNI). 통과 후 리팩터 단계에서만 정리한다.

## 디버깅

### `root-cause-first`
- 요약: 증상이 아니라 근본 원인부터 조사한다
- 내용: 에러 메시지 정독 → 일관되게 재현 → 최근 변경 확인 → 컴포넌트 경계마다 진단 로그로 데이터 흐름을 추적한다. 데이터 흐름을 추적하기 전에 해결책부터 제안하면 안 된다.

### `three-fix-rule`
- 요약: 3번 이상 고쳐도 안 되면 설계 문제 신호
- 내용: 같은 문제에 세 번 넘게 고쳐도 안 되면 구현이 아니라 아키텍처 문제일 가능성이 크다. 계속 찔러보지 말고 구조를 의심한다.

### `verify-before-done`
- 요약: '됐다'고 말하기 전에 명령을 실행해 증거를 확인한다
- 내용: 완료·수정·통과를 주장하기 전에 그것을 증명하는 명령을 새로 실행하고 출력과 종료코드를 직접 읽는다. 'should/probably/seems' 같은 표현이나 실행 없는 성공 주장은 금지.

## 계획·설계

### `design-before-code`
- 요약: 구현 전에 설계를 먼저 합의한다
- 내용: 맥락 파악 → 한 번에 하나씩 질문 → 2~3개 접근안을 트레이드오프와 함께 제시 → 승인 후 진행. '간단한' 작업일수록 검증 안 된 가정이 낭비를 만든다.

### `bite-sized-tasks`
- 요약: 계획은 2~5분짜리 독립 작업 단위로 쪼갠다
- 내용: 실패 테스트 작성→실패 확인→구현→통과 확인→커밋 흐름으로 잘게 나눈다. 'TBD'·'검증 추가' 같은 자리표시자 대신 실제 파일 경로·인터페이스를 적는다.

### `assume-low-context-reader`
- 요약: '도메인을 거의 모르는 유능한 개발자'가 읽는다고 가정
- 내용: 계획은 추상적 표현 대신 구체적 구현 정보를 담는다. 읽는 사람이 이 코드베이스·도구를 모른다고 가정하고 실제 세부를 적는다.

## 코드 리뷰

### `review-early-often`
- 요약: 자주, 일찍 리뷰한다
- 내용: 작업·주요 기능 후, main 병합 전에 리뷰한다. '간단한' 변경이라고 건너뛰지 않는다.

### `severity-ordered-fixes`
- 요약: 피드백은 심각도 순으로 처리한다
- 내용: 치명적→중요→사소 순으로 고친다. 근거 없는 지적에는 기술적 근거를 들어 반박할 수 있다.

### `isolated-reviewer-context`
- 요약: 리뷰어에겐 변경 diff와 요구사항만 준다
- 내용: 세션 전체가 아니라 base·head 커밋의 diff와 요구사항만 전달해 리뷰어의 맥락을 격리하고 판단을 독립시킨다.

## 공통 기본 (모든 스킬)

### `trigger-first-description`
- 요약: description은 'Use when...' 트리거 조건 중심으로
- 내용: 워크플로 요약이 아니라 '언제 쓰는지'(어떤 요청·상황·에러·도구에서 호출되는지)를 구체적으로 쓴다. 에이전트가 검색할 키워드를 넣는다. description은 에이전트가 스킬 호출 여부를 판단하는 가장 중요한 필드다.

### `form-matches-failure`
- 요약: 가이드 형태를 실패 유형에 맞춘다(→ 구조 원형 선택)
- 내용: 규칙 위반엔 금지문, 출력 형태 문제엔 레시피/예시를 쓴다. 규율형 스킬엔 합리화 표와 red flag 목록을 넣는다. 이 원칙이 곧 어떤 구조 원형(규율형/절차형/참조형)을 쓸지 결정한다.

### `skills-are-reusable-techniques`
- 요약: 스킬은 재사용 가능한 검증된 기법이지 일회성 서사가 아니다
- 내용: 한 번의 문제 해결 이야기가 아니라 반복해서 쓸 기법의 참고 자료로 만든다. 일회성 작업은 스킬로 만들지 않는다.

## 디자인·프론트엔드

### `ground-in-subject`
- 요약: 주제 고유의 세계에서 디자인 선택을 끌어낸다
- 내용: 어떤 프로젝트에나 쓸 법한 일반 패턴을 피하고, 주제의 소재·도구·용어에서 특징적인 선택을 뽑아낸다. 히어로는 주제의 가장 특징적인 요소로 열고, 큰 숫자+그라데이션 같은 기본값을 지양한다.

### `one-signature-element`
- 요약: 대담함은 한 곳에 집중하고 나머지는 절제한다
- 내용: 시그니처 요소 하나에 힘을 주고 나머지는 규율 있게 절제한다. 구조적 장치(번호 마커 등)는 순서가 실제로 의미를 가질 때만 쓰고 장식으로 쓰지 않는다.

### `deliberate-typography`
- 요약: 디스플레이·본문 폰트를 의도적으로 짝짓는다
- 내용: 아무 프로젝트에나 반사적으로 쓰는 폰트 대신, 주제에 맞게 디스플레이와 본문 서체를 의도적으로 고른다.

### `purposeful-motion`
- 요약: 모션은 목적을 갖고 절제한다
- 내용: 흩뿌린 효과보다 하나의 연출된 순간이 더 강하게 남는다. 애니메이션이 과하면 'AI가 만든' 느낌이 나니 목적을 갖고 쓴다.

### `plan-then-critique`
- 요약: 만들기 전에 계획→클리셰 자기비판→구현(2패스)
- 내용: 바로 만들지 말고 디자인 계획을 먼저 세우고 흔한 클리셰에 비춰 자기비판한 뒤, 고유성을 확인하고 나서 구현한다.

### `cohesive-palette-and-fonts`
- 요약: 색 팔레트와 폰트 짝을 하나의 시각 정체성으로 묶는다
- 내용: 색과 폰트 조합을 하나의 정체성으로 정해 슬라이드·문서·랜딩 등 여러 콘텐츠에 일관되게 적용한다.

### `show-options-then-apply`
- 요약: 옵션을 먼저 보여주고 승인 후 일관 적용
- 내용: 테마 옵션을 먼저 제시해 사용자 승인을 받은 뒤, 대비·가독성을 지키며 전체에 체계적으로 적용한다.

### `context-appropriate-theme`
- 요약: 맥락·청중에 맞는 시각 정체성을 고른다
- 내용: 미니멀부터 드라마틱까지, 맥락과 청중에 맞는 시각 정체성을 고른다. 스타일은 미학이자 전달 수단이다.

## 말투·보이스

### `define-voice-profile`
- 요약: 말투를 먼저 '프로필'로 정의하고 일관 적용한다
- 내용: 정체성·핵심 신념·독자·보이스 특성(3~5개)·핵심 주제·선호/거부 어휘·금지 문구·채널별 규칙·예시 문단을 프로필로 정의하고, 그 기준으로 일관되게 쓴다.

### `banned-phrases`
- 요약: 쓰지 말 표현을 명시적으로 목록화해 제거한다
- 내용: 진부하거나 'AI스러운' 문구를 금지 목록으로 만들고, 선호 어휘 대 거부 어휘를 구분해 걸러낸다.

### `open-with-punch`
- 요약: 빌드업 없이 핵심으로 열고, 짧게 쓴다
- 내용: 숫자·대담한 주장·의외의 관점으로 시작한다. 짧은 문장, 짧은 문단, 여백을 둔다.

### `substance-over-performance`
- 요약: 태도가 아니라 근거로 뒷받침된 의견을 낸다
- 내용: 데이터·경험으로 뒷받침한다. 과시성 글쓰기·허수아비·아랫사람 깔보기·선언문식 수사를 금지하고, 모든 문장이 값을 하게 한다.

## 문서 작성

### `context-gathering-first`
- 요약: 쓰기 전에 배경·엣지케이스·트레이드오프를 질문으로 채운다
- 내용: 초기 질문·정보 덤프·후속 질문으로 지식 공백을 메운다. 모르는 게 가장 많은 섹션부터 시작한다.

### `section-by-section`
- 요약: 섹션 단위로 브레인스토밍→선별→초안→반복
- 내용: 섹션마다 5~20개 옵션을 브레인스토밍하고 선별해 초안을 쓴 뒤 피드백을 반영한다. 전체 재작성 대신 타깃 편집(str_replace)을 쓴다.

### `fresh-reader-test`
- 요약: 맥락 없는 새 인스턴스로 읽혀 맹점을 찾는다
- 내용: 저자는 알지만 독자는 모를 지점을, 맥락이 섞이지 않은 새 Claude로 문서를 읽혀 찾아낸다.

### `trim-filler`
- 요약: 군더더기를 덜어내며 마무리한다
- 내용: 세 번 반복해도 변화가 적으면 무엇을 뺄지 묻는다. 마무리에 전체 흐름·일관성·군더더기를 점검한다.

## 설명형 (쉽게 설명)

### `everyday-analogy`
- 요약: 추상 개념을 일상의 구체적 장면에 빗댄다
- 내용: 카페·알바생·메모처럼 누구나 아는 일상 상황으로 치환해 설명한다. (예: '스크립트 = 알바생에게 남긴 할 일 메모')

### `plain-words-first`
- 요약: 전문용어를 먼저 꺼내지 않는다
- 내용: 쉬운 말로 먼저 풀고, 전문용어는 필요할 때 뒤에 괄호로 곁들인다. 용어로 시작해 겁주지 않는다.

### `summary-then-detail`
- 요약: 한 줄 요약 먼저, 그다음 풀이
- 내용: 짧은 한 줄로 감을 준 뒤 자세히 풀이한다. 처음부터 길게 늘어놓지 않는다.

### `include-why`
- 요약: 무엇이 좋은지·왜 쓰는지를 곁들인다
- 내용: 개념이 왜 필요한지, 쓰면 무엇이 편해지는지를 함께 알려준다. (예: '한 번 써두면 매번 사람이 시키지 않아도 알아서 처리')

# 문서 구조 골격 (4종)

각 SKILL.md가 아래 넷 중 어느 형태에 가장 가까운지 판정할 때 쓴다.

## `discipline` — 규율형 (지켜야 할 원칙)
지켜야 할 원칙·규율이 핵심이고, AI가 "이번만 건너뛰자"며 합리화하기 쉬운 스킬.
전형적 섹션: Overview(핵심 원칙 한 줄) / When to Use / 단계별 규칙 + Good·Bad 예시 쌍 /
Rationalizations(변명 → 현실 표) / Red Flags(STOP 신호) / Verification Checklist.

## `workflow` — 절차형 (순서 있는 워크플로)
순서 있는 여러 단계를 거쳐 산출물을 만드는 스킬.
전형적 섹션: Overview(무엇을 만들어내는지) / 번호 있는 Stages(각 단계에 게이트) /
Self-Review / Handoff·Done(완료 기준).

## `reference` — 참조형 (옵션 제공·적용)
옵션/프로필을 정의하고 일관되게 적용하는 스킬.
전형적 섹션: Overview / Profile·Options(선택지 목록) / Apply(승인 후 전체 적용) /
Constraints(금지 조건).

## `explanation` — 설명형 (개념을 쉽게 설명)
개념·라이브러리·도구가 무엇인지 초보에게 쉽게 설명하는 스킬.
전형적 섹션: 한 줄 요약 / 비유 / 풀이 / (용어).
