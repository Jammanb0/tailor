# routed 운영 관찰 사전 등록

> **실제 요청 자료를 하나도 보기 전에 쓴 초안이다.** 여기서 고정하는 것은
> 100건의 단위와 시작점, 저장할 값, 비용·시간·전환 판정선, 그리고 결과에
> 따라 무엇을 할지다.
>
> 작성일: 2026-08-31 · 대상 커밋 `aa8cf46`(브랜치 `corpus-routing`).
>
> 이 초안은 계측 구현 전에 사용자 검토를 받는다. 승인 뒤 고정한 항목은 운영
> 자료를 본 다음 고치지 않는다. 바꿔야 하면 기존 문구와 변경 이유를 남기고
> 새 관찰로 구분한다.
>
> 앞선 실험과 다른 점이 하나 있다. 8·9단계는 우리가 표본을 골라 실행했지만
> 이번에는 실제 사용자가 보내는 요청을 그대로 받는다. 표본을 설계할 수 없으니
> **무엇을 셀지와 어디서 끊을지를 미리 정하는 것**이 이 문서의 목적이다.

## 이 관찰이 답할 것

8단계는 통제된 6개 시나리오에서 routed가 품질을 지키면서 더 싸다는 것을
보였다. 9단계는 F1~F7 전환이 정확히 작동하는 것을 보였다. 둘 다 우리가 만든
입력이었다. 이번에는 실제 요청에서 다음 세 가지에 답한다.

1. **비용** — 8단계가 계산한 손익분기 캐시 적중률 87.2%를 실제 요청 도착
   간격이 넘는가? 즉 **8단계 비용 모형에서 실제 트래픽에도 routed가 유리한가?**
2. **전환** — F1~F6 전환이 실제로 얼마나 자주 일어나는가? 원인은 무엇인가?
3. **안정성** — 사용자에게 실패가 전달되는 비율과 응답 시간이 감당할 수준인가?

**생성 품질은 이 관찰이 답하지 않는다.** 아래 「이 계측으로 답할 수 없는 것」에
따로 적는다.

## 8·9단계에서 가져오는 기준값

전환율 10%나 응답 시간 60초처럼 어디에서도 측정된 적 없는 값을 우리가 미리
긋는 정책선이다. 둘을 같은 말로 부르지 않는다. 표는 기준값이고, 「판정선」
절의 숫자는 그 기준에서 정한 사전 정책이다.

## 100건의 정의

### 단위

**최초 생성 요청 한 번이 1건이다.** `kind=create`이고 생성 경로에 실제로
들어간 요청만 센다.

정제(`kind=refine`)는 설정과 무관하게 늘 full이므로 100건에 넣지 않는다. 다만
같은 표에 저장하고 따로 집계한다 — full 경로의 캐시 usage를 실제로 관측할 수
있는 몇 안 되는 자료다.

### 시작점

배포 뒤 synthetic smoke를 마친 시각 **이후**에 도착한 요청부터 센다.

smoke와 실제 요청은 `deployment_id`와 `started_at`으로 가른다.

**smoke는 smoke로 돌린 `operation_id`를 이 문서에 수동으로 적어 구분한다.**
`is_smoke` 열은 그 수동 목록을 반영하는 자리로만 두고, 요청에서 값을 받지
않는다.

두 가지 대안을 다 버렸다. `/api/generate-skill`은 공개 엔드포인트이므로
**요청 body에서 받으면** 아무나 `is_smoke: true`를 붙여 자기 요청을 표본에서
빼거나 남의 요청을 오염시킬 수 있다. **서버 환경변수로 배포 단위에 걸면**
smoke를 도는 동안 그 배포에 들어온 실제 사용자 요청까지 전부 smoke로 표시된다.
수동 기록이 가장 단순하고, 틀려도 티가 난다.

표시 실패에 대비해 smoke 종료 시각도 이 문서에 적어, 시각으로도 자를 수 있게
한다.

### 포함하는 것

- 성공한 요청
- 되물음(`needsMoreInfo`)으로 끝난 요청
- 생성 실패·파싱 실패로 끝난 요청
- 선택 실패 뒤 full로 전환해 성공한 요청
- 결제·인증·429로 중단된 요청

**실패도 100건에 넣는다.** 실패율 자체가 관측 대상이다. 실패를 빼고 세면 가장
보고 싶은 값이 표본에서 사라진다.

### 제외하는 것

- `is_smoke=true`인 요청
- 입력 검사에서 막힌 요청 — 생성 호출에 들어가지 않았으므로 100건 밖이다.
  차단 건수는 따로 센다.
- `configured_mode != 'routed'`인 create 요청 — 환경변수가 잘못됐다는 뜻이므로
  설정을 고치고 그 시점 이후부터 다시 센다.

> **주의: 전달된 코퍼스로 제외하면 안 된다.** F1~F6으로 전환한 요청은
> `resolveCorpusDeliveryPolicy`가 `mode: "full"`을 돌려주므로 실제 전달
> 코퍼스가 full이다. 전달 코퍼스가 full이라는 이유로 걸러내면 이 관찰이 가장
> 보고 싶어 하는 전환 요청이 통째로 표본에서 사라지고, 전환율 `f`는 언제나
> 0%로 나온다. 제외 기준은 **배포 설정**(`configured_mode`)이지 전달
> 결과(`delivered_mode`)가 아니다.

### 재시도

1단계에서 넣은 수동 재시도는 같은 입력을 그대로 다시 보낸다. 서버는 이것을
새 요청과 구분하지 못한다.

**재시도도 별개의 1건으로 센다.** 서버가 실제로 처리한 요청 수가 비용과
전환율의 분모이기 때문이다. 대신 한계를 적어 둔다 — 한 사람이 세 번 눌러 만든
3건과 세 사람이 한 번씩 만든 3건을 이 자료로는 가르지 못한다. 실패가 몰려
있으면 도착 시각 간격으로 사후에 짐작만 한다.

### 계측이 유실된 요청

`after()`는 함수 실행 시간 예산을 응답과 나눠 쓴다. 하드 타임아웃이 나면 최종
갱신이 실행되지 않고 `status=pending` 행만 남는다.

**pending 행만으로는 유실을 다 잡지 못한다.** 저장이 fail-open이므로 pending
insert 자체가 실패하면 행이 아예 생기지 않고, 그 요청은 표에서 보이지도 않는다.
없는 행은 셀 수 없으므로 로그와 표를 함께 대조해야 한다.

**저장 오류 로그를 유실로 세면 안 된다.** `fetch`가 타임아웃되거나 연결이
끊겨도 Supabase 쪽에서는 insert나 update가 이미 성공했을 수 있다. 오류 로그는
"우리가 결과를 못 봤다"는 뜻이지 "행이 없다"는 뜻이 아니다. 로그만 세면 유실이
실제보다 높게 나온다.

**판정할 때 DB와 대조한다.**

| 집합 | 정의 |
|---|---|
| `missing_row` | `stage=pending-insert` 오류가 난 `operation_id` 중, `generations`에 행이 **실제로 없는** 것 |
| `stale_pending` | 마지막 요청 뒤 300초가 지나도 `status=pending`인 행 |

> 계측 유실률 = `distinct(missing_row ∪ stale_pending)`
> ÷ (표의 대상 행 수 + `missing_row` 수)

`stage=final-update` 오류 로그는 **진단용으로만 남긴다.** 최종 행이 정상
상태로 끝났다면 유실이 아니다. 정말 갱신되지 않았다면 그 행은 여전히
`status=pending`이므로 `stale_pending`이 이미 잡는다. 따로 더하면 같은 요청을
두 번 센다.

pending insert가 실패한 요청은 표에 흔적이 없으므로, 그 로그만으로 「첫 100건에
속하는지」를 복원할 수 있어야 한다. `generate-skill-persistence-error`에 아래
필드를 싣는다. 전부 우리가 만든 값이라 요청 내용이 섞이지 않는다.

`operation_id` · `started_at` · `stage` · `kind` · `configured_mode` ·
`deployment_id` · `is_smoke`

순서를 복원하는 값은 오류가 난 시각이 아니라 **요청이 시작된 시각**이다.
`started_at`은 요청 시작에서 한 번 만들어 pending 행과 로그에 **같은 값**으로
쓴다. 행은 DB의 `DEFAULT now()`를 쓰지 않는다 — 그러면 저장 지연만큼 로그와
어긋나 대조가 안 맞는다.

- pending으로 남은 행도 100건에 넣고 따로 표시한다.
- **stale pending은 마지막(100번째) 요청이 끝나고 최소 300초를 기다린 뒤에
  센다.** Vercel 함수 예산이 300초이므로 그 전에 세면 아직 정상 실행 중인
  요청을 유실로 오인한다.
- **계측 유실률이 10%를 넘으면 판정을 멈춘다.** 계측의 10분의 1이 비어 있는데
  비용과 전환율을 결론내는 것은 자료가 아니라 인상이다. 이때는 원인을 고치고
  100건을 다시 센다.

## 저장 설계

### 원칙

`telemetry.ts`가 콘솔 로그에 쓰는 것과 같은 **허용 목록 방식**이다. 객체를
통째로 넘기지 않고 필요한 필드만 골라 새로 만든다.

### 저장하지 않는 것

1. 사용자가 쓴 답변 원문
2. 생성된 SKILL.md 전문과 제안 파일명
3. 되물음 질문과 검토 노트 본문
4. 오류 객체의 `message`, Supabase 응답 본문
5. IP 주소, User-Agent, 쿠키, 사용자 식별자
6. **선택된 묶음 id와 패턴 id** — 아래 참조

묶음 id를 빼는 이유는 그것이 요청의 주제를 상당히 드러내기 때문이다.
`tdd-cycle`과 `test-discipline`이 뽑혔다면 그 사람이 무엇을 만들려 했는지가
거의 그대로 남는다. 원문을 저장하지 않기로 한 결정과 어긋난다. 대신 개수와
바이트만 남긴다.

**이 선택의 대가는 분명하다** — 유효한 id를 엉뚱하게 고른 의미상 오선택을
이 자료로는 찾을 수 없다. 이미 알고 받아들인 한계이고, 아래에 다시 적는다.

### 표 구성

`generations` 한 개다. pending으로 넣고 최종에 갱신한다.

| 열 | 형 | 언제 채우나 | 비고 |
|---|---|---|---|
| `operation_id` | uuid PK | pending | `crypto.randomUUID()` |
| `started_at` | timestamptz | pending | 요청 시작 시각. 서버가 만들어 로그와 같은 값을 쓴다. `DEFAULT now()`를 쓰지 않는다 |
| `deployment_id` | text | pending | Vercel 배포 식별자 |
| `is_smoke` | bool | pending | 기본 false |
| `kind` | text | pending | `create` / `refine` |
| `configured_mode` | text | pending | 배포 설정. `full` / `routed` |
| `delivered_mode` | text | 최종 | Sonnet에 실제 전달한 코퍼스. `full` / `routed` / null |
| `generation_attempted` | bool | 최종 | Sonnet을 불렀는가 |
| `status` | text | pending→최종 | `pending` / `success` / `needs_more_info` / `error` |
| `error_code` | text | 최종 | `generation-errors.ts`의 고정 집합 |
| `selection_status` | text | 최종 | `success` / `ambiguous` / `failure` / null |
| `selection_fallback` | bool | 최종 | full로 돌아갔는가 |
| `fallback_reason_ids` | text[] | 최종 | F1~F6 |
| `ambiguity_ids` | text[] | 최종 | F7 |
| `selection_error_stage` | text | 최종 | `selection` / `selection-processing` |
| `selection_error_category` | text | 최종 | 허용 목록 |
| `selection_ms` | int | 최종 | |
| `selection_usage_*` | int ×4 | 최종 | `USAGE_LOG_FIELDS`와 같은 이름 |
| `generation_ms` | int | 최종 | |
| `generation_stop_reason` | text | 최종 | |
| `generation_usage_*` | int ×4 | 최종 | |
| `delivered_pattern_count` | int | 최종 | id가 아니라 개수 |
| `injected_bytes` | int | 최종 | 실제 주입한 코퍼스 크기 |
| `total_ms` | int | 최종 | 요청 시작부터 응답까지 |

`selection_usage_*`와 `generation_usage_*`의 이름은 `USAGE_LOG_FIELDS`를
그대로 따른다. 2026-08-28 실험 자료가 같은 이름으로 남아 있어, 이름을 바꾸면
옛 자료와 새 자료를 함께 집계할 수 없다.

`selection_status`의 값은 `SelectionDecision["status"]`를 그대로 쓴다. 실제
코드의 리터럴은 `"success" | "ambiguous" | "failure"`다. 선택이 아예 돌지 않은
요청(정제, `configured_mode=full`)은 null이다.

모드를 세 열로 가른 이유는 하나로 합치면 아무것도 구분하지 못하기 때문이다.
`configured_mode`는 표본을 자르는 기준이고, `delivered_mode`는 전환이
일어났는지 말하고, `generation_attempted`는 결제·인증·429로 Sonnet을 아예
부르지 않고 끝난 요청을 가른다. 마지막 값이 없으면 「전환해서 full로 성공한
요청」과 「선택 실패로 중단한 요청」이 비용 집계에서 같은 칸에 들어간다.

**`generation_attempted=false`면 `delivered_mode`는 null이다.** 전달한 코퍼스가
없는데 `full`이라고 적으면 이름과 값이 어긋나고, 나중에 전환율을 세는 질의가
중단된 요청까지 끌어온다. 즉 `generation_attempted = (delivered_mode IS NOT
NULL)`이 성립해야 한다.

### 저장 시점

- **pending insert는 동기다.** 요청 검사가 끝난 직후, 생성 경로에 들어가기
  전에 넣는다. 하드 타임아웃이 나도 행이 남게 하려는 것이므로 `after()`에
  넣으면 목적이 사라진다.
- **최종 갱신만 `after()`로 보낸다.** 응답을 붙잡지 않는다.
- **저장 실패는 생성을 막지 않는다(fail-open).** Supabase가 죽어도 스킬은
  나가야 한다. 실패는 `generate-skill-persistence-error`로 콘솔에 남기고,
  Vercel 로그와 pending 행을 맞춰 누락을 찾는다.

### 로그와 행 연결

`operation_id`를 기존 콘솔 로그 세 종류(`generate-skill`,
`generate-skill-routing`, `generate-skill-error`)에도 넣는다. 그래야 Vercel
로그와 Supabase 행을 맞출 수 있다. 이 값은 우리가 만든 uuid라 요청 내용이
섞이지 않는다.

## 판정선

100건을 다 센 뒤 아래 순서로 판정한다. 순서를 지키는 이유는 계측을 믿을 수
없으면 나머지가 의미 없기 때문이다.

### 0. 계측 신뢰성 (먼저 본다)

위 「계측이 유실된 요청」의 합집합으로 판정한다. 마지막 요청 뒤 300초를 기다린
다음, DB와 대조해서 센다.

| 조건 | 판정 |
|---|---|
| 계측 유실률 ≤ 10% | 판정을 진행한다 |
| 계측 유실률 > 10% | **판정 중단.** 원인을 고치고 100건을 다시 센다 |

### 1. 비용

실제 요청에서 full의 캐시 적중률을 직접 잴 수는 없다. routed로 돌리고 있으니
full 경로가 대부분 실행되지 않기 때문이다. 대신 **도착 시각으로 추정한다.**

> `p̂` = 100건의 create 중, **직전 5분 안에 입력 검사를 통과한 create 또는
> refine 요청이 있었던** 요청의 비율

**`delivered_mode`는 보지 않는다.** 이 값이 답해야 하는 질문은 "처음부터 full로
배포했다면 캐시가 얼마나 맞았을까"라는 반사실이고, 그 세계에서는 입력 검사를
통과한 create와 refine이 **전부** 같은 `CORPUS_SECTION` 접두사를 같은
`cache_control`로 보낸다. 실제로 무엇이 전달됐는지는 그 계산과 무관하다.

실제 전달 모드로 재면 값이 반대로 망가진다. routed create 100건이 1분 간격으로
모두 성공하고 정제와 전환이 하나도 없으면, full 블록을 쓴 요청이 없으므로
`p̂ = 0%`가 나온다. 그런데 같은 트래픽을 full로 배포했다면 첫 건 뒤 99건이
캐시를 맞았을 테니 실제 반사실 값은 약 99%다. **routed가 잘 돌수록 `p̂`가 0에
가까워지고, 규칙은 언제나 「routed 유지」로 떨어진다.** 한쪽으로만 틀리는
편향이라 상한이라고 부를 수 없다.

입력 검사를 통과한 요청까지 세는 이유는, full 세계에는 선택 호출이 없어
결제·인증·429로 중단됐을 요청도 곧장 Sonnet을 불렀을 것이기 때문이다. 반대로
입력 검사에서 막힌 요청은 어느 세계에서도 API를 부르지 않으므로 뺀다.

이 값은 **상한이다.** 캐시는 Vercel 배포가 아니라 **같은 프롬프트 접두사와
Anthropic workspace** 단위로 갈리고, 5분 창은 쓸 때마다 갱신되며, 동시에 들어온
요청은 앞 요청의 응답이 시작된 뒤에야 캐시를 쓸 수 있다. 도착 간격은 이 조건을
전부 무시한 낙관값이므로 진짜 적중률은 이보다 낮다. 상한이 손익분기를 못 넘으면
실제도 못 넘는다.

근거: [prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching),
[workspace 격리](https://platform.claude.com/docs/en/manage-claude/workspaces)

| 조건 | 판정 |
|---|---|
| `p̂` ≤ 87.2% | 8단계 비용 모형에서 routed가 유리하다 — **유지** |
| `p̂` > 87.2% | full이 쌀 수 있다 — 실제 full usage와 함께 다시 계산하고 **복귀 검토** |
| routed 요청당 실측 평균이 $0.0928(= $0.0619 × 1.5)을 넘음 | **조정** — 원인을 분해한다 |

87.2%는 8단계 6개 시나리오에서 나온 손익분기점이지, 실제 사용자 요청 분포에서도
그대로 성립하는 보편값이 아니다. 결론을 쓸 때 「routed가 싸다」가 아니라
**「8단계 비용 모형에서는 routed가 유리하다」**라고 적는다.

세 번째 줄이 있는 이유는 8단계의 6개 시나리오가 실제 요청 분포가 아니기
때문이다. 실제 입력이 훨씬 길거나 출력이 길면 요청당 비용이 실측을 크게 넘을
수 있고, 그때는 손익분기와 별개로 원인을 봐야 한다.

### 요청당 비용의 분모

> 요청당 비용 = 기록된 usage로 계산한 비용 총합 ÷ 100

분모는 **요청 수 100**이지 성공 건수가 아니다. 실패한 요청도 선택 호출 비용은
이미 썼으므로, 성공 건수로 나누면 실패가 잦을수록 요청당 비용이 싸 보인다.

usage가 없는 실패(연결 오류, 응답 전 중단)의 비용은 잡지 못한다. 따라서 이
값은 실제 청구액이 아니라 **관측 가능한 비용의 하한**이다. 결론에 그렇게 적는다.

### 총액 점검선

100건 예상 비용은 캐시 0% 환산으로 약 **$6.2**다($0.0619 × 100). 요청당 조정선
$0.0928로 100건을 채우면 $9.28이다.

**누적 $10 초과를 확인하는 즉시 routed 관찰을 끝내고 full 복귀를 검토한다.**

이것은 **자동 상한이 아니다.** 호출 제한을 두지 않았으므로 코드가 요청을 막지
않고, 점검과 점검 사이에 이 금액을 넘어설 수 있다. $10은 "여기서 자동으로
멈춘다"가 아니라 "여기를 넘은 것을 보면 사람이 끝낸다"는 선이다.

100건에 이르기 전에 $10을 넘었다면 요청당 비용이 예상의 1.6배를 넘었다는
뜻이고, 그 자체가 조사할 사건이다. 실제 계정 잔액과 월 지출 한도는 이 문서에
적지 않는다 — 공개 저장소다.

### 2. 전환율

> `f` = 100건 중 F1~F6으로 full에 **전환해 생성까지 간** 요청의 비율
> (`delivered_mode='full' AND generation_attempted`)

결제·인증·429로 **중단된 요청은 `f`에 넣지 않는다.** 그것은 Sonnet을 아예
부르지 않으므로 「전환」이 아니다. 아래 3번에서 따로 센다.

| 조건 | 판정 |
|---|---|
| `f` ≤ 10% | **유지** |
| 10% < `f` ≤ 25% | **조정** — 원인별로 분해해 카드 문구나 선택 프롬프트를 고친다 |
| `f` > 25% | **복귀 검토** |

**이 선은 비용이 아니라 운영 정책이다.** 비용만 보면 전환이 잦아도 routed가
한참 유리하다. 8단계 캐시 0% 환산으로 다시 계산한 값은 이렇다.

| `f` | routed 요청당 (선택 포함) | full 요청당 |
|---:|---:|---:|
| 0% | $0.0619 | $0.1583 |
| 10% | $0.0720 | $0.1583 |
| 25% | $0.0870 | $0.1583 |
| 50% | $0.1121 | $0.1583 |
| 75% | $0.1372 | $0.1583 |

비용 이득이 실제로 사라지는 지점은 **`f` ≈ 96%**다. 그러니 25%를 복귀
검토선으로 두는 근거는 비용이 아니라, 전환이 그만큼 잦다면 선택이 제 역할을
못 하고 있고 원인을 모른 채 운영하고 싶지 않다는 판단이다. 근거를 비용으로
적으면 나중에 계산이 맞지 않는다.

F1은 따로 본다. **F1이 5%를 넘으면 `f`와 무관하게 원인을 조사한다.**
`selection_error_stage`로 업스트림 실패와 우리 코드의 후처리 실패를 가른다.
후처리 실패가 하나라도 나오면 그것은 버그이므로 비율과 관계없이 고친다.

F7은 전환하지 않으므로 판정선을 두지 않는다. 발생하면 **건수를 세고, 허용된
계측값을 행 단위로 확인한다.** 묶음 id와 원문을 저장하지 않으므로 「그 판정이
타당했는가」는 이 자료로 알 수 없다 — 언제 몇 번 일어났고 그 요청이 어떻게
끝났는지까지다. 9단계까지 합성 fixture로만 본 분기라 실제 사례가 처음이면 그
자체가 자료다.

### 3. 사용자에게 전달된 실패

| 조건 | 판정 |
|---|---|
| `status=error` ≤ 5% | **유지** |
| 5% < `status=error` ≤ 15% | **조정** — `error_code`별로 분해한다 |
| `status=error` > 15% | **복귀 검토** |

결제·인증·사용량 상한으로 중단된 요청은 별도로 센다. **3건을 넘으면 비율과
무관하게 즉시 알린다** — routed의 문제가 아니라 계정 상태의 문제이고, 방치하면
남은 관찰이 전부 오염된다.

### 4. 시간

별도의 제품 SLA가 없으므로 8단계 실측 대비로만 판정한다.

**판정선의 중앙값은 최종 갱신이 끝나고 `status=success`인 요청에만 매긴다.**

`generation_attempted=true`만으로는 부족하다. 그것은 Sonnet 호출을 시작했다는
뜻일 뿐이라, Sonnet에서 곧바로 401·429·연결 오류가 나도 참이다. 그런 요청은
몇 초 만에 끝나므로 섞이면 중앙값이 끌려 내려가 응답이 실제보다 빨라 보인다.

비교 대상인 8단계 end-to-end 35.1초는 **문서가 실제로 나온 생성 3건**의
시간이다. 자를 맞추려면 이쪽도 사용자에게 결과가 전달된 요청이어야 한다.

아래 셋은 판정에 넣지 않고 분포를 따로 보고한다.

- 되물음(`needs_more_info`) — 생성은 정상이지만 산출물이 다르다
- 파싱 실패 — `generation_ms`는 있지만 사용자는 결과를 못 받았다
- Sonnet 오류와 선택 단계 중단 — 대부분 몇 초짜리 빠른 실패다

`generation_ms IS NOT NULL`인 요청의 중앙값도 함께 적는다. 모델 호출 자체가
느려진 것과 우리 경로가 느려진 것을 가르는 데 쓴다.

| 조건 | 판정 |
|---|---|
| end-to-end 중앙값 ≤ 60초 | **유지** (8단계 35.1초의 약 1.7배) |
| 60초 < 중앙값 ≤ 90초 | **조정** |
| 중앙값 > 90초 | **복귀 검토** |
| 단일 요청이 240초를 넘음 | **즉시 조사** — Vercel 300초 예산의 80%다. 하드 타임아웃과 계측 유실이 임박했다 |
| 선택 시간 p90 > 3초 | **조사** — 실측 1.10초의 약 3배. 10초 deadline에 가까워지면 F2가 늘어난다 |

## 결과에 따른 다음 행동

| 결과 | 다음 행동 |
|---|---|
| 네 축 모두 유지 | routed를 운영 기본으로 확정하고 이 워크스트림을 닫는다 |
| 한 축이 조정 | 그 축의 원인만 고치고, 고친 시점부터 100건을 다시 센다 |
| 두 축 이상이 조정 | 고치기 전에 full로 되돌리고, 압박 없이 원인을 본다 |
| 어느 축이든 복귀 검토 | `CORPUS_ROUTING_MODE=full`로 되돌린 뒤 판단한다 |
| 계측 신뢰성 실패 | 판정하지 않는다. 계측을 고치고 다시 센다 |

**점수가 아쉽다는 이유로 100건을 더 세지 않는다.** 100건에서 끊고 판정한다.
표본을 늘려야 한다는 판단이 서면 그것을 새 관찰로 사전등록한다.

## 이 계측으로 답할 수 없는 것

내용을 저장하지 않기로 했으므로 아래는 이 자료로 판정할 수 없다. 결론을 쓸 때
답한 것처럼 쓰지 않는다.

1. **생성된 문서의 품질.** 8단계의 A~F 채점 같은 것을 운영 자료로는 하지
   못한다.
2. **의미상 오선택.** 유효한 묶음 id를 골랐지만 그 요청에 맞지 않는 경우다.
   묶음 id를 저장하지 않으므로 흔적이 남지 않는다.
3. **사용자가 결과에 만족했는가.** 되물음 비율과 정제 요청 비율이 간접
   신호이지만 만족도가 아니다.
4. **한 사람이 몇 번 시도했는가.** 식별자를 저장하지 않는다.

품질을 다시 봐야 한다면 운영 자료가 아니라 8단계 같은 통제된 비교를 새로
사전등록해서 한다.

## 구현 전에 정할 것

이 문서를 승인해 고정한 다음에 구현한다.

1. Supabase 프로젝트와 `generations` 표
2. REST 저장 모듈과 `operation_id` 배선

   저장은 **서버 전용 native `fetch`로 구현하고 `supabase-js`는 넣지 않는다.**
   쓰는 곳이 insert 한 번과 update 한 번뿐이라 **현재 범위에서 클라이언트
   라이브러리로 얻는 편익이 작고**, 의존성이 늘면 공개 저장소의 공급망 표면도
   늘어난다. 나중에 질의가 복잡해지면 다시 판단한다.

   pending insert와 최종 update에 각각 짧은 타임아웃을 건다. 계측이 생성을
   붙잡으면 fail-open의 의미가 사라진다. 시크릿 키는 서버 환경변수에서만
   읽는다 — 클라이언트 번들에 들어가는 이름을 쓰지 않는다. 정확한 키 이름과
   형식은 프로젝트를 만들 때 Supabase 문서에서 확인해 적는다.
3. `generate-skill-persistence-error` 이벤트와 `check:logging` 확장
4. 모든 조기 반환 경로가 observation을 만드는지 검사하는 회귀 시험
5. synthetic smoke 절차와 종료 시각 기록

프로덕션 생성 경로의 동작, 코퍼스 내용, 묶음 구성, 선택 프롬프트는 이 관찰
중에 바꾸지 않는다. 바꾸면 그 시점에서 100건을 다시 센다.
