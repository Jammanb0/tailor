# 커밋 전 비밀정보 검사

## 개요
커밋하기 직전에 스테이징된 변경사항(git add로 올린 내용)을 살펴 API 키, 비밀번호, 토큰, `.env` 파일 등 민감 정보가 섞여 들어가지 않았는지 확인한다. 한 번 커밋되어 git 기록(history)에 남으면 나중에 그 줄을 지워도 과거 기록에는 그대로 남아있으므로, **커밋되기 전에** 잡는 것이 유일하게 확실한 시점이다.

## 언제 쓰나
- `git commit` 실행 직전
- `git add`로 파일을 스테이징한 직후, 커밋하기 전
- `git push`로 원격 저장소에 올리기 직전
- 사용자가 "커밋해줘", "커밋하고 푸시해줘"라고 요청했을 때
- 새 `.env` 파일이나 설정 파일을 만들거나 수정한 직후

쓰지 않을 때: 이미 공개 저장소에 커밋되어 버린 뒤의 뒤처리(이 경우는 git 기록 자체를 지우는 별도 작업이 필요하며, 단순 재검사로는 해결되지 않는다는 점을 사용자에게 알린다).

## 검사 절차

1. **스테이징된 변경사항을 실제로 연다**
   `git diff --staged`로 커밋될 내용 전체를 확인한다. `git status`만 보고 파일 이름으로 짐작하지 않는다 — 비밀정보는 파일 이름이 아니라 내용에 들어있다.

2. **아래 패턴이 있는지 줄 단위로 확인한다**

   | 분류 | 찾아볼 것 |
   |---|---|
   | 환경 파일 | `.env`, `.env.local`, `.env.production` 등 `.env`로 시작하는 모든 파일이 스테이징됐는지 |
   | API 키 | `api_key`, `apiKey`, `API_KEY` 등의 변수에 실제 값(따옴표 안에 길고 무작위한 문자열)이 들어있는지 |
   | 토큰 | `token`, `access_token`, `bearer` 뒤에 실제 값이 있는지, `ghp_`, `sk-`, `AKIA` 같은 알려진 접두사 |
   | 비밀번호 | `password`, `passwd`, `pwd`, `secret` 변수에 평문 값이 있는지 |
   | 개인 키 파일 | `.pem`, `.key`, `id_rsa`, `id_ed25519` 등 |
   | 연결 문자열 | `mongodb://user:pass@...`, `postgres://user:pass@...`처럼 URL 안에 인증정보가 박힌 경우 |

3. **발견되면 커밋을 진행하지 않는다**
   무엇을, 어느 파일 몇 번째 줄에서 발견했는지 사용자에게 구체적으로 알리고 아래 중 하나를 제안한다:
   - 해당 값을 `.env` 파일로 옮기고 `.gitignore`에 `.env`를 추가한다
   - 이미 `.gitignore`에 있는데도 스테이징됐다면 `git rm --cached <파일>`로 스테이징에서 뺀다
   - 값 자체를 `os.environ`, `process.env` 같은 환경변수 참조로 바꾸고 실제 값은 코드에서 제거한다

4. **아무것도 발견되지 않으면 그 사실을 짧게 보고하고 커밋을 진행한다**
   "스테이징된 N개 파일을 확인했고 비밀정보로 보이는 패턴은 없었습니다"처럼 무엇을 확인했는지 한 줄로 밝힌다.

## 지켜야 할 것

- **의심스러우면 보수적으로 판단한다.** 변수 이름에 `secret`, `key`, `password`가 들어가 있으면 값이 가짜처럼 보여도(`"test123"`, `"xxx"`) 일단 알린다 — 실수로 진짜 값을 남겨둔 것인지 사용자가 직접 확인하게 한다.
- **`.env.example`, `.env.sample`처럼 값이 비어있거나 플레이스홀더(`YOUR_API_KEY_HERE`)만 있는 템플릿 파일은 구분한다.** 이런 파일은 보통 커밋해도 안전하므로 실제 값 여부를 보고 판단한다.
- **이미 git 기록에 비밀정보가 들어가 있는 것 같다면 별도로 알린다.** 이번 커밋만 막는 것으로는 과거 기록이 지워지지 않는다. `git log -p`로 과거 커밋까지 뒤져야 하는 작업이라는 점과, `git filter-repo` 같은 별도 도구가 필요하다는 점을 설명하고 사용자 확인 없이 임의로 기록을 재작성하지 않는다.
- **검사를 건너뛰고 싶은 유혹이 들어도 건너뛰지 않는다.** "급하다", "이번 건 별거 아니다", "로컬 전용 브랜치다" 같은 이유는 검사를 생략할 근거가 되지 않는다 — 로컬 브랜치도 나중에 푸시되거나 병합될 수 있다.

## 완료 전 확인
- `git diff --staged`를 실제로 열어 읽었는가 (파일 목록만 보고 추측하지 않았는가)
- 위 표의 패턴을 한 줄씩 짚어봤는가
- 발견된 것이 있다면 사용자에게 구체적 위치(파일명, 줄)와 함께 알렸는가
- 발견된 게 없다면 "무엇을 확인했는지"를 말로 보고했는가 (말없이 그냥 커밋 진행하지 않았는가)

## 흔한 실수

| 실수 | 왜 문제인가 | 고치는 법 |
|---|---|---|
| `git status`만 보고 파일 이름으로 안전 여부를 판단 | 비밀정보는 내용에 있지 이름에 없다 | 반드시 `git diff --staged`로 실제 변경 내용을 읽는다 |
| `.gitignore`에 `.env`가 있으니 안전하다고 가정 | 이미 한 번 커밋됐던 파일은 `.gitignore`에 추가해도 계속 추적된다 | `git status`에 해당 파일이 스테이징되어 뜨는지 다시 확인한다 |
| 값을 지웠다고 끝났다고 생각 | 과거 커밋 기록에는 여전히 남아있다 | 이미 커밋된 적이 있다면 기록 재작성이 필요하다는 것을 알린다 |
| 플레이스홀더와 실제 값을 구분하지 않고 전부 통과시킴 | `"YOUR_KEY_HERE"`와 실제 32자리 랜덤 문자열을 같은 것으로 취급 | 값의 형태(길이, 무작위성)를 보고 실제 값인지 판단한다 |
