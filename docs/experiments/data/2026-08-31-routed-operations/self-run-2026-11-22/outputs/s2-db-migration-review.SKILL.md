# PostgreSQL 마이그레이션 안전 점검

## 개요
새로 작성되거나 변경된 PostgreSQL 마이그레이션 파일을 적용하기 전에 읽고, 데이터 유실·긴 락(lock, 다른 요청이 테이블 작업을 기다리게 만드는 잠금 상태)·롤백(down 마이그레이션, 변경을 되돌리는 절차) 누락 위험을 찾아 보고합니다. **마이그레이션 파일을 직접 고치지 않고, 적용 명령도 직접 실행하지 않습니다** — 점검 결과와 고칠 방법만 제안하고, 실제 적용은 항상 사람이 합니다.

## 언제 쓰나
- 새 마이그레이션 파일(up/down, migrate 등)을 작성한 직후
- 기존 마이그레이션 파일을 수정한 직후
- "이 마이그레이션 적용해도 돼?", "위험한 거 있어?" 같은 질문을 받았을 때
- 마이그레이션을 병합(merge)하거나 배포 전 체크리스트를 돌 때

쓰지 않을 때: 이미 운영 DB에 적용 완료된 마이그레이션의 이력 조회, 스키마 설계 자체에 대한 자유 토론(이건 점검이 아니라 설계 논의이므로 범위 밖)

## 점검 절차

### 1단계 — 대상 파일 확인
어떤 마이그레이션 파일(들)을 점검할지 확인합니다. 사용자가 특정 파일을 지목하지 않았다면, 최근에 추가/수정된 마이그레이션 파일을 찾아 확인합니다. 파일은 **읽기만** 하고 내용을 바꾸지 않습니다.

### 2단계 — 위험 유형별로 훑기
아래 네 가지 관점으로 파일을 읽습니다. 하나라도 걸리면 이슈로 기록합니다.

**가. 데이터 유실 위험**
- `DROP COLUMN`, `DROP TABLE` — 컬럼/테이블 자체가 사라짐
- 타입 변경(`ALTER COLUMN ... TYPE`) 중 정보 손실이 생기는 방향 (예: `text` → `varchar(10)`, `numeric` → `integer`)
- `NOT NULL` 제약을 기존 데이터 백필(backfill, 빈 값을 미리 채워 넣는 작업) 없이 추가
- 컬럼 이름 변경을 `DROP` + `ADD`로 구현해서 실제로는 데이터가 날아가는 경우

**나. 긴 락 위험**
- 큰 테이블에 대한 `ALTER TABLE ... ADD COLUMN`에 `DEFAULT` 값과 `NOT NULL`을 동시에 지정 (옛 PostgreSQL 버전에서는 테이블 전체를 다시 씀)
- 기존 컬럼에 인덱스를 `CREATE INDEX`로 생성 (쓰기 작업을 막음) — `CREATE INDEX CONCURRENTLY`(테이블을 잠그지 않고 인덱스를 만드는 방식) 사용 여부 확인
- `ALTER TABLE`로 타입 변경 시 테이블 전체 재작성이 필요한 경우
- 트랜잭션(transaction, 여러 작업을 하나로 묶어 처리하는 단위) 안에서 `CREATE INDEX CONCURRENTLY`를 쓰는 실수 (PostgreSQL에서는 이게 안 됨 — 에러가 나거나 무시됨)
- 큰 테이블에 외래 키(foreign key) 제약을 추가할 때 `NOT VALID` 옵션 없이 추가 (기존 데이터 전체를 검증하느라 오래 락을 잡음)

**다. 롤백(down 마이그레이션) 점검**
- down 마이그레이션 자체가 없음
- down이 있어도 up의 변경을 완전히 되돌리지 못함 (예: 컬럼 삭제의 down이 컬럼만 복구하고 데이터는 복구 못 함 — 이 경우는 원래 되돌릴 수 없는 변경이므로 문서화가 필요하다는 점을 지적)
- down에서 참조하는 테이블/컬럼 이름이 up과 안 맞음

**라. 기타**
- 마이그레이션 파일 안에서 여러 무관한 변경을 한 파일에 몰아넣음 (리뷰·롤백 단위가 커짐)
- 운영 데이터에 의존하는 조건문이 들어 있어 실행 환경에 따라 결과가 달라짐

### 3단계 — 결과 보고
아래 형식으로 정리해 보고합니다. 코드를 직접 고치지 않고 **제안만** 적습니다.

```
## 점검 대상
- 파일: (경로)

## 발견된 이슈
### [위험도: 높음/중간/낮음] 이슈 제목
- 위치: (파일:줄 또는 구문)
- 무엇이 문제인가: (한두 문장)
- 왜 위험한가: (데이터 유실 / 긴 락 / 롤백 불가 중 해당하는 것과 근거)
- 고치는 방법 제안: (구체적인 대안 SQL 또는 접근 — 코드 블록으로 제시하되 파일에 직접 적용하지 않음)

## 요약
- 치명적 이슈: N건 (적용 전 반드시 수정 필요)
- 주의 이슈: N건 (적용 가능하나 운영 환경에서 주의 필요)
- 판정: 바로 적용 가능 / 수정 후 적용 권장 / 적용 보류 권장
```

위험도 기준:
- **높음**: 데이터가 영구적으로 사라질 수 있거나, 운영 트래픽 중 테이블 전체가 잠겨 서비스가 멈출 수 있음
- **중간**: 롤백이 불완전하거나, 큰 테이블에서 짧지 않은 락이 걸릴 수 있음
- **낮음**: 스타일/구조상 개선 여지 (파일 분리, 네이밍 등)

### 4단계 — 적용은 사람에게 맡기기
점검이 끝나면 **절대로 마이그레이션 적용 명령(`migrate up`, `psql`로 직접 DDL 실행, ORM의 migrate 명령 등)을 실행하지 않습니다.** "위 이슈를 확인하신 뒤 직접 적용해 주세요"라고 안내하고 끝냅니다. 사용자가 "그냥 적용해줘"라고 요청해도, 실제 DB 적용 명령 실행은 거절하고 점검 결과만 다시 안내합니다.

## 하지 말아야 할 것
- 운영 DB(production database)에 접속하거나 접속을 시도하는 것 — 점검은 파일만 읽고 끝낸다
- 마이그레이션 파일 내용을 직접 수정하는 것 — 고칠 내용은 제안으로만 제시한다
- 마이그레이션 적용 명령을 대신 실행하는 것 — 높음 위험이 없어 보여도 실행은 항상 사람 몫이다
- 확인 안 된 "괜찮아 보입니다" 같은 두루뭉술한 결론 — 반드시 위 네 가지 위험 유형을 각각 짚었는지 확인한 뒤 판정을 내린다

## 완료 전 확인
- [ ] 데이터 유실 / 긴 락 / 롤백 누락 네 가지 관점을 모두 짚었는가
- [ ] 발견한 이슈마다 위치·이유·고치는 방법이 다 채워져 있는가
- [ ] 파일을 수정하지 않았는가 (읽기만 했는가)
- [ ] 적용 명령을 실행하지 않았는가
- [ ] 마지막에 판정(바로 적용 가능 / 수정 후 적용 권장 / 적용 보류 권장)을 명시했는가

## 빠른 참조

| 위험 유형 | 주로 찾는 패턴 |
|---|---|
| 데이터 유실 | `DROP COLUMN`, `DROP TABLE`, 축소 방향 타입 변경, 백필 없는 `NOT NULL` |
| 긴 락 | `DEFAULT`+`NOT NULL` 동시 추가, `CREATE INDEX`(CONCURRENTLY 아님), `NOT VALID` 없는 FK |
| 롤백 누락 | down 없음, down이 불완전, up/down 이름 불일치 |
