# 릴리스 노트 초안 작성

## 개요
배포 시점에 마지막 태그(이전 릴리스 지점을 표시해 둔 이름표) 이후의 git 커밋 기록을 읽어, 개발자 말투로 적힌 커밋 메시지를 사용자가 이해할 수 있는 문장으로 바꾸고, "새 기능 / 고친 문제 / 주의할 변경"으로 나눈 릴리스 노트 초안을 만든다. 커밋 메시지를 그대로 옮기지 않는다 — 무엇이 바뀌었고 사용자에게 왜 중요한지를 새로 쓴다.

## 언제 쓰나
- 배포 직전, 지난 태그 이후의 변경 사항을 사용자 공지용으로 정리해야 할 때
- "릴리스 노트 써줘", "체인지로그 정리해줘", "이번 배포 뭐 바뀌었는지 요약해줘" 같은 요청을 받았을 때
- 커밋 메시지가 `fix: null pointer in auth middleware`처럼 기술 용어 위주라 그대로는 못 쓸 때

쓰지 말아야 할 때:
- 내부 개발팀용 기술 체인지로그를 원할 때 (커밋 메시지를 그대로 정리하는 편이 낫다)
- 아직 태그를 찍지 않아 "마지막 릴리스 지점"이 불명확할 때 — 먼저 범위를 사용자에게 확인한다

## 절차

### 1단계 — 커밋 범위 확정
마지막 태그를 확인한다.
```
git describe --tags --abbrev=0
```
이 태그와 현재 `HEAD`(지금 작업 중인 지점) 사이의 커밋 로그를 가져온다.
```
git log <마지막-태그>..HEAD --pretty=format:"%h %s"
```
- 태그가 하나도 없다면(첫 릴리스라면) 사용자에게 범위를 확인한다 — 전체 로그를 쓸지, 특정 날짜 이후로 자를지.
- 커밋이 너무 많아(대략 50개 이상) 한눈에 파악하기 어렵다면, 머지 커밋이나 사소한 수정(`chore`, `docs`, 오타 수정 등)은 먼저 걸러내고 본다.

### 2단계 — 커밋을 세 갈래로 분류
각 커밋을 다음 세 범주 중 하나로 분류한다. 애매하면 커밋에 연결된 PR(변경 사항 제안서) 설명이나 diff(실제 코드 변경 내용)를 열어 실제로 사용자가 체감할 변화인지 확인한다.

| 범주 | 기준 | 흔한 커밋 접두사 |
|---|---|---|
| 새 기능 | 사용자가 할 수 있는 일이 늘어남 | `feat:`, `add:` |
| 고친 문제 | 전에 안 되던 것이 되게 함, 버그 수정 | `fix:`, `bugfix:` |
| 주의할 변경 | 사용자의 기존 사용 방식이 달라지거나 깨짐 | `BREAKING CHANGE`, `refactor:`(동작이 바뀐 경우), `remove:` |

- 내부 리팩토링, 테스트 추가, 빌드 설정 변경처럼 **사용자가 전혀 체감할 수 없는 커밋은 세 범주 어디에도 넣지 않고 제외한다.**
- 하나의 커밋이 여러 범주에 걸치면(예: 기능 추가이면서 동시에 기존 API를 깨뜨림) 두 범주에 각각 넣되 같은 설명을 반복하지 않고 관점만 다르게 쓴다.

### 3단계 — 사용자 말투로 다시 쓰기
분류한 각 항목을 아래 기준으로 바꿔 쓴다.

- 커밋 메시지의 기술 용어(함수명, 변수명, 내부 모듈명, 에러 코드)를 그대로 쓰지 않는다. 사용자가 화면에서 보는 용어로 바꾼다.
- "무엇을 고쳤는가"가 아니라 "사용자에게 무엇이 달라지는가"로 문장을 쓴다.
- 한 항목은 한 문장, 되도록 한 줄로 끝낸다. 꼭 필요할 때만 한 문장을 더해 영향 범위를 덧붙인다.

이러지 말 것: `fix: resolve race condition in session token refresh` → "세션 토큰 리프레시 레이스 컨디션을 수정했습니다"
이렇게: "로그인이 간헐적으로 끊기던 문제를 고쳤습니다"

이러지 말 것: `feat: add debounce to search input handler` → "검색 입력 핸들러에 디바운스를 추가했습니다"
이렇게: "검색창에 입력할 때 화면이 버벅이던 현상이 사라졌습니다"

**주의할 변경**은 특히 신중히 쓴다. 무엇이 어떻게 달라지는지, 사용자가 무엇을 해야 하는지(설정 변경, 재로그인 등 필요한 조치가 있다면)까지 적는다. 조치가 필요 없다면 "별도 조치는 필요 없습니다"라고 명시한다.

### 4단계 — 초안 조립
세 범주를 아래 순서로 배치한다. 범주에 해당 항목이 없으면 그 섹션 자체를 통째로 뺀다 — 빈 섹션을 "해당 없음"으로 남기지 않는다.

```
## 새 기능
- (항목)

## 고친 문제
- (항목)

## 주의할 변경
- (항목, 필요 시 조치 안내 포함)
```

## 완료 전 확인
- 모든 항목이 사용자 관점 문장으로 바뀌었고, 함수명·내부 모듈명·에러 코드 등 개발 용어가 남아 있지 않은가
- 사용자가 전혀 체감할 수 없는 내부 변경(리팩토링, 테스트, 빌드 설정)이 섞여 들어가지 않았는가
- "주의할 변경" 항목에 필요한 조치가 있다면 안내가 빠지지 않았는가
- 커밋이 중복 집계되거나(여러 범주에 같은 문장이 그대로 반복) 누락되지 않았는가
- 완성된 초안을 바로 배포하지 않고, 사용자에게 보여준 뒤 확인을 받는다 — 이 스킬은 "초안"을 만드는 것이지 최종본을 확정하는 것이 아니다

## 빠른 참조

| 커밋 메시지 예시 | 분류 | 사용자용 문장 |
|---|---|---|
| `fix: null check in payment webhook` | 고친 문제 | "특정 상황에서 결제 완료 알림이 누락되던 문제를 고쳤습니다" |
| `feat: add CSV export to dashboard` | 새 기능 | "대시보드에서 데이터를 CSV로 내려받을 수 있습니다" |
| `BREAKING CHANGE: remove legacy API v1 endpoint` | 주의할 변경 | "기존 v1 연동 방식이 더 이상 지원되지 않습니다. v2로 전환이 필요합니다" |
| `chore: bump lodash version` | 제외 | (사용자가 체감할 수 없음) |
