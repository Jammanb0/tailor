# baseline 1차 채우기 후 확인 (2026-08-20)

> 회차식 실험이 아니다. `baseline`을 채운 뒤 눈으로 보기 위한 소량 실행 기록.

## 조건

- 코퍼스 렌더 **84,980 → 93,845바이트** (직전 커밋 `5983f13` → 이번 `52991c1`)
- `baseline` 섹션만 **1,082 → 9,947바이트**. 섹션별 대조로 다른 카테고리 무변화 확인
- 시나리오는 3차 회차 것(`../2026-08-19-expand3/scenarios.json`)을 그대로 씀
- **10종 × 1회 = 10건.** 표본이 작다 — 아래 관찰을 효과로 읽지 말 것

## 왜 이 폴더를 따로 만들었나

3차 회차의 `run.mjs`를 그대로 돌리면 그 폴더의 `for-grader`·`answer-key`를
덮어쓴다. 실험 자료를 보존하려고 실행기를 복사해 출력 경로만 여기로 돌렸다.

## 결과

- **10/10 성공.** 생성물 1,087~3,324자
- **상황 밀착도(C축)가 살아 있다.** 분량이 늘어난 뒤 가장 걱정한 지점이었다.
  `09-mismatch-office`(엑셀 매출 정리)는 거래처명·전월 대비 증감률·급감 임계값
  50%까지 사용자 상황 그대로 나왔고, 스킬 작성 메타 내용은 섞이지 않았다
- **메타 누출 0건.** 10건 전부에서 `SKILL.md`·`frontmatter`·`RED/GREEN`·
  `변명 표`·단어 수 규정 같은 baseline 원문 어휘가 본문에 나오지 않았다
  (`05-design`의 "토큰"은 디자인 토큰이라 해당 없음)

## ⚠️ 관찰 — 단정하지 않는다

**`description`이 워크플로를 요약한 건이 있다.** `06-voice`가
"…말투 프로필이 저장되어 있는지 **먼저 확인하고, 없으면** …"으로 절차를
요약했다. 이번에 넣은 W-03이 정확히 금지하는 형태인데 걸리지 않았다.
`03-planning`도 경계선이다.

**10건 중 2건이고 대조군이 없다.** 이 프로젝트가 두 번 속은 함정이므로
(handoff 「판정 규칙」 절) 효과로 읽지 않는다. 다음에 baseline을 손댈 때
같은 자리를 다시 볼 것.

**한국어 생성이라 `Use when` 리터럴 대신 "~할 때 사용"으로 나오는 것은
위반이 아니다.** 10건 중 7건이 그 형태다. 규정의 알맹이는 "트리거 조건으로
시작한다"이지 영어 문구가 아니다.

## 분량 예상이 어긋났다

감사 9-3(`docs/corpus/superpowers-writing-skills.md`)은 **신규 15개를 다 넣으면
8,000바이트 안팎**으로 봤다. 실제로는 **5개만으로 9,947바이트**다.

남은 10개를 같은 밀도로 넣으면 25,000바이트를 넘길 수 있고, 그 증가분은
조건과 무관하게 모든 생성에 실린다. **2차에 들어가기 전에 밀도를 낮출지
결정할 것.**

## 재현

```
pnpm dev                      # 3000 포트
node run.mjs 1 3              # 10종 × 1회, 동시 3건
```

# 2차 — 잔여분 채운 뒤 확인 (2026-08-20)

> `round2/`에 자료가 있다. 실행기는 `run2.mjs`(출력 경로만 다르다).

## 조건

- 코퍼스 렌더 **93,845 → 106,458바이트** (커밋 `57a3624`)
- `baseline` 섹션 **9,947 → 22,560바이트**. 섹션별 대조로 다른 카테고리 무변화 확인
- 같은 시나리오 10종 × 1회

## 결과

- **10/10 성공.** 메타 누출 **0건**(1차와 같은 검사)
- **상황 밀착도 유지.** `09-mismatch-office`는 1차와 다른 고정 항목 구성이
  나왔지만(수량·단가가 들어갔다) 둘 다 사용자 상황에 맞는 답이고, 항목 이름을
  임의로 짐작하지 말고 물어보라는 지시까지 살아 있다
- **생성물이 길어지지 않았다.** 코퍼스가 13% 커졌는데 결과물 길이는 오히려
  뒤섞였다(+613 ~ -996자, 합계 -586자). **분량 증가가 결과물 비대화로
  이어지지는 않는다**는 첫 관측이다 — 다만 1회씩이라 잡음과 못 가른다

| 시나리오 | 1차 | 2차 |
|---|---|---|
| 01-testing | 3,037 | 3,216 |
| 02-debugging | 3,324 | 3,180 |
| 03-planning | 2,082 | 2,695 |
| 04-code-review | 1,394 | 1,697 |
| 05-design | 3,278 | 2,282 |
| 06-voice | 2,319 | 2,015 |
| 07-documentation | 1,903 | 1,721 |
| 08-explanation | 1,087 | 1,011 |
| 09-mismatch-office | 1,751 | 1,726 |

## 최종 분량

`baseline` **1,082 → 22,560바이트(약 21배)**. 감사 9-3의 예상(8,000)의 **2.8배**다.
분량을 줄이지 않고 같은 밀도로 가기로 한 것은 기록된 결정이다. 여기까지의
확인으로는 부작용이 관측되지 않았으나, **10건 × 1회는 부작용을 찾기에 충분한
표본이 아니다.** 다음에 생성 품질이 흔들리면 이 증가분을 첫 용의자로 볼 것.

# 3차 — 골격 구조 개편 뒤 확인 (2026-08-20)

> `round3/`에 자료가 있다. 실행기는 `run3.mjs`.

## 무엇을 바꿨나

골격 4종의 `sectionFlow`를 **공통 뼈대(`commonSpine`) + 타입별 본문
(`bodySections`)**으로 쪼갰다(커밋 `422909d`). 렌더 106,458 → **106,843바이트**.
바뀐 곳은 골격 절 하나뿐이다.

**W-06을 담기 위한 변경이다.** 원문의 표준 섹션 순서는 "스킬 종류 하나"가 아니라
종류와 무관한 한 벌이라, 4종에 5번째로 넣으면 종류로 오해된다. 공통/변형으로
쪼개야 자리가 생긴다.

## 세 회차 대조 — 이번 작업의 핵심 자료

| 시나리오 | 1차 | 2차 | 3차 |
|---|---|---|---|
| 01-testing | 3,037 | 3,216 | 2,824 |
| 02-debugging | 3,324 | 3,180 | 2,980 |
| 03-planning | 2,082 | 2,695 | 2,024 |
| 04-code-review | 1,394 | 1,697 | 2,099 |
| 05-design | 3,278 | 2,282 | 2,697 |
| 06-voice | 2,319 | 2,015 | 2,941 |
| 07-documentation | 1,903 | 1,721 | 2,255 |
| 08-explanation | 1,087 | 1,011 | 1,884 |
| 09-mismatch-office | 1,751 | 1,726 | 1,998 |
| 10-mismatch-setup | 1,730 | 1,776 | 2,245 |
| **합계** | **21,905** | **21,319** | **23,947** |

## 새 섹션이 실제로 나왔다

| 새 공통 섹션 | 10건 중 |
|---|---|
| 언제 쓰나 (쓰지 말아야 할 때 포함) | **10** |
| 흔한 실수 | **8** |
| 빠른 참조 | **1** |

**「빠른 참조」가 1건뿐인 것은 의도한 대로일 수 있다** — "항목이 여럿일 때만"이라는
조건을 붙였고, 이번 시나리오 대부분이 표를 만들 만큼 항목이 많지 않다. 조건이
너무 빡빡한 것인지 시나리오 탓인지는 이 자료로 못 가른다.

## 관측

- **10/10 성공 · 메타 누출 0건**(골격 어휘 `{{본문}}`·`공통 뼈대`·`규율형` 등도 검사)
- **생성물이 12% 길어졌다**(21,319 → 23,947자). 새 섹션 둘이 들어간 만큼이다.
  baseline을 21배로 늘렸을 때는 길이가 안 늘었는데 **골격을 바꾸니 늘었다** —
  분량이 아니라 **골격이 결과물 구성을 좌우한다**는 쪽을 가리키는 관측이다.
  다만 회차당 1회씩이라 단정하지 않는다
- 가장 크게 는 것은 `08-explanation`(1,011 → 1,884자). 「언제 쓰나」에
  **쓰지 말아야 할 때**가 들어갔고 「흔한 실수」 절이 새로 생겼다. 둘 다 이번에
  공통 뼈대에 넣은 것이다

## ⚠️ 이 세 회차는 A/B가 아니다

**대조군이 없고 회차마다 1회씩이다.** 1차·2차·3차 사이에 바뀐 것이 각각 하나씩
있었을 뿐, 같은 조건을 반복하지 않았다. 위 수치는 **방향을 보는 자료이지 판정이
아니다.** 이 프로젝트가 두 번 속은 함정이므로(handoff 「판정 규칙」 절)
"골격 개편이 결과물을 좋게 했다"고 적지 않는다.
