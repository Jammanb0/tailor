# baseline 1차 채우기 후 확인 (2026-08-20)

> 회차식 실험이 아니다. `baseline`을 채운 뒤 눈으로 보기 위한 소량 실행 기록.

## 조건

- 코퍼스 렌더 **84,980 → 93,845바이트** (직전 커밋 `5983f13` → 이번 `52991c1`)
- `baseline` 섹션만 **1,082 → 9,947바이트**. 섹션별 대조로 다른 카테고리 무변화 확인
- 시나리오는 3차 회차 것(`../2026-08-19-expand3/scenarios.json`)을 그대로 씀
- **10종 × 1회 = 10건.** 표본이 작다 — 아래 관찰을 효과로 읽지 말 것

## 왜 이 폴더를 따로 만들었나

3차 회차의 `run.mjs`를 그대로 돌리면 그 폴더의 `for-grader`·`answer-key`를
덮어쓴다. 실험 자료를 보존하려고 실행기를 복사해 출력 경로만 여기로 돌렸다.

## 결과

- **10/10 성공.** 생성물 1,087~3,324자
- **상황 밀착도(C축)가 살아 있다.** 분량이 늘어난 뒤 가장 걱정한 지점이었다.
  `09-mismatch-office`(엑셀 매출 정리)는 거래처명·전월 대비 증감률·급감 임계값
  50%까지 사용자 상황 그대로 나왔고, 스킬 작성 메타 내용은 섞이지 않았다
- **메타 누출 0건.** 10건 전부에서 `SKILL.md`·`frontmatter`·`RED/GREEN`·
  `변명 표`·단어 수 규정 같은 baseline 원문 어휘가 본문에 나오지 않았다
  (`05-design`의 "토큰"은 디자인 토큰이라 해당 없음)

## ⚠️ 관찰 — 단정하지 않는다

**`description`이 워크플로를 요약한 건이 있다.** `06-voice`가
"…말투 프로필이 저장되어 있는지 **먼저 확인하고, 없으면** …"으로 절차를
요약했다. 이번에 넣은 W-03이 정확히 금지하는 형태인데 걸리지 않았다.
`03-planning`도 경계선이다.

**10건 중 2건이고 대조군이 없다.** 이 프로젝트가 두 번 속은 함정이므로
(handoff 「판정 규칙」 절) 효과로 읽지 않는다. 다음에 baseline을 손댈 때
같은 자리를 다시 볼 것.

**한국어 생성이라 `Use when` 리터럴 대신 "~할 때 사용"으로 나오는 것은
위반이 아니다.** 10건 중 7건이 그 형태다. 규정의 알맹이는 "트리거 조건으로
시작한다"이지 영어 문구가 아니다.

## 분량 예상이 어긋났다

감사 9-3(`docs/corpus/superpowers-writing-skills.md`)은 **신규 15개를 다 넣으면
8,000바이트 안팎**으로 봤다. 실제로는 **5개만으로 9,947바이트**다.

남은 10개를 같은 밀도로 넣으면 25,000바이트를 넘길 수 있고, 그 증가분은
조건과 무관하게 모든 생성에 실린다. **2차에 들어가기 전에 밀도를 낮출지
결정할 것.**

## 재현

```
pnpm dev                      # 3000 포트
node run.mjs 1 3              # 10종 × 1회, 동시 3건
```

# 3차 — 골격 구조 개편 뒤 확인 (2026-08-20)

> `round3/`에 자료가 있다. 실행기는 `run3.mjs`.

## 무엇을 바꿨나

골격 4종의 `sectionFlow`를 **공통 뼈대(`commonSpine`) + 타입별 본문
(`bodySections`)**으로 쪼갰다(커밋 `422909d`). 렌더 106,458 → **106,843바이트**.

## 새 섹션이 실제로 나왔다

| 새 공통 섹션 | 10건 중 |
|---|---|
| 언제 쓰나 (쓰지 말아야 할 때 포함) | **10** |

| 빠른 참조 | **1** |

**「빠른 참조」가 1건뿐인 것은 의도한 대로일 수 있다** — "항목이 여럿일 때만"이라는
조건을 붙였고, 이번 시나리오 대부분이 표를 만들 만큼 항목이 많지 않다. 조건이
너무 빡빡한 것인지 시나리오 탓인지는 이 자료로 못 가른다.

## 관측

- **10/10 성공 · 메타 누출 0건**(골격 어휘 `{{본문}}`·`공통 뼈대`·`규율형` 등도 검사)
- **생성물이 12% 길어졌다**(21,319 → 23,947자). 새 섹션 둘이 들어간 만큼이다.
  baseline을 21배로 늘렸을 때는 길이가 안 늘었는데 **골격을 바꾸니 늘었다** —
  분량이 아니라 **골격이 결과물 구성을 좌우한다**는 쪽을 가리키는 관측이다.
  다만 회차당 1회씩이라 단정하지 않는다
- 가장 크게 는 것은 `08-explanation`(1,011 → 1,884자). 「언제 쓰나」에
  **쓰지 말아야 할 때**가 들어갔고 「흔한 실수」 절이 새로 생겼다. 둘 다 이번에
  공통 뼈대에 넣은 것이다

## ⚠️ 이 세 회차는 A/B가 아니다

**대조군이 없고 회차마다 1회씩이다.** 1차·2차·3차 사이에 바뀐 것이 각각 하나씩
있었을 뿐, 같은 조건을 반복하지 않았다. 위 수치는 **방향을 보는 자료이지 판정이
아니다.** 이 프로젝트가 두 번 속은 함정이므로(handoff 「판정 규칙」 절)
"골격 개편이 결과물을 좋게 했다"고 적지 않는다.

# 4·5·6차 — 카테고리 채우기와 축 1 확인 (2026-08-21)

각 회차는 **변경 하나 뒤의 스냅샷**이지 A/B가 아니다. 시나리오당 1회씩이고
대조군이 없다. **판정으로 쓰지 말 것.**

| 회차 | 무엇을 바꿨나 | 렌더 | 폴더 |
|---|---|---|---|
| 4차 | `explanation` 채우기 | 106,843 → 112,406 | `round4/` |
| 5차 | `documentation` 채우기 | 112,406 → 118,412 | `round5/` |
| 6차 | 축 1 — TDD 주기와 리뷰 절차를 흐름으로 | 118,412 → 121,033 | `round6/` |

세 번 다 **10/10 성공**이고 섹션별 대조에서 의도한 카테고리만 움직였다.

## 회차별로 확인한 것

- **4차** — 설명형 신규 3개가 생성물에 다 나왔다(지금 보는 것으로 착지 / 낯섦을
  인정하고 문턱 좁히기 / 더 맞는 대안 알려주기). 억지로 연결할 게 없으면
  생략하라는 예외 조항까지 살아서 나왔다
- **5차** — 문서 작성의 수치가 그대로 나왔다("질문 5~10개", "섹션 3~6개").
  **정책 B 2등급 조항을 정정하지 않았으면 "여러 개 물어본다"가 됐을 것이다**
- **6차** — TDD의 **되돌아가는 길 세 개가 전부 나왔다.** `test-first`의
  `verifyHint`가 정확히 그것을 재도록 적혀 있었고 통과했다

## ⚠️ 5차에서 한 번 실패했다

첫 실행이 502로 9/10이었다. 실행기가 "부분 자료로 수치를 내지 말 것"을 찍는다.
**다시 받아 10/10으로 확인했고, 저장된 자료는 재실행분이다.**

## 실행기 사본이 늘어나고 있다

`run.mjs`(3차 회차 것) → `run2~6.mjs`. 출력 경로만 다르고 나머지는 같다.
**다음에 또 필요하면 출력 폴더를 인자로 받게 고칠 것** — 사본이 여섯 개가 되면
어느 것이 기준인지 흐려진다.

# 7차 — 축 1 두 번째 묶음 (2026-08-21)

`planning`과 `voice`를 흐름으로 이었다(커밋 `a9d93cf`). 렌더 121,033 →
**123,913바이트**. 두 섹션만 움직였다. 10/10 성공.

## 확인된 것

- **말투** — 프로필 유무 분기가 생성물에 나왔고, "찾기 전에는 묻지 않는다"까지
  살아 있다

## ⚠️ 확인 못 한 것 — 시나리오가 없다

**`plan-writing-flow`는 이 시나리오 묶음으로 확인할 수 없다.**

`03-planning` 시나리오는 *"바로 코드부터 써서 갈아엎는다. 먼저 정리하고
애매한 건 물어봐 달라"*이다. 이것은 **코드 전에 설계를 합의하는** 스킬이지
**계획 문서를 쓰는** 스킬이 아니다. 모델은 `design-before-code`와 승인 게이트를
골랐고 그게 맞는 판단이다.

**처음에는 이것을 실패로 읽을 뻔했다.** 검사식이 "파일 구조가 작업 쪼개기보다
먼저 나오는가"를 봤는데, 애초에 둘 다 나올 이유가 없는 시나리오였다.
**검사가 재는 것이 시나리오와 맞는지 먼저 볼 것.**

**시나리오 10종에 「계획 문서를 쓰게 하는 스킬」이 없다.** `planning`을 다시
손대면 시나리오를 하나 보태야 확인이 가능하다.

# 8차 — 축 1 마지막 묶음 (2026-08-21)

커밋 `d5cf0bd`. 렌더 123,913 → **125,594바이트**. 디버깅·디자인·공통기본만 움직였다.
10/10 성공.

## 확인 결과 — 4개 중 1개만 나왔다

| 넣은 것 | 생성물에 나왔나 |
|---|---|
| 디자인 — 맞는 선택지가 없으면 새로 만든다 | ✅ |
| 디자인 — 만든 뒤 다시 승인 절차 | ❌ |
| 디버깅 — 원인을 못 찾을 때의 출구 | ❌ |
| 디버깅 — 고친 뒤 모든 층에 검사 | ❌ |

**이것을 실패로 읽지 않는다.** ⓐ 시나리오당 1회다. ⓑ 디버깅 생성물은 이미
3,328자로 조밀했고, 넣지 않은 것을 고른 것이지 모르고 빠뜨린 것인지 알 수 없다.
ⓒ **반대 방향의 관측도 있다** — 흐름에 없는 `trace-backward-to-source`와
`instrument-component-boundaries`는 생성물에 들어갔다. 모델은 흐름 밖의 패턴도
끌어다 쓴다.

**다음에 디버깅이나 디자인을 손대면 같은 자리를 다시 볼 것.** 세 번 연속으로
안 나오면 그때는 신호로 본다.

## 축 1 정리 — 무엇이었나

시작은 "게이트가 없다"는 진단이었는데 **틀렸다.** 게이트 내용은 `explanation`을
빼고 모든 카테고리에 이미 있었다. 빠진 것은 **그 게이트가 어느 단계 뒤에
오는지**였다.

`flow`를 쓰는 패턴이 **14 → 20개**가 됐다(6·7·8차 합계). 새로 이은 것:

- TDD 주기와 되돌아가는 길 셋 (testing)
- 리뷰 절차 — 넘길 것을 닫고 → 훑고 → 판정 → 심각도 순 처리 (code-review)
- 계획 한 벌 — 범위 → 파일 구조 → 작업 → 자기 점검 → 사용자 게이트 (planning)
- 프로필 유무 갈림길 (voice)
- 스킬 만들기 5단계와 재시험 루프 (baseline)
- 선택지 되만들기 / 조사 출구 / 층 방어 (design · debugging)

**`explanation`에는 넣지 않았다.** 그 방식에는 순서 있는 절차 자체가 없다 —
게이트를 만들어 넣으면 지어내는 것이 된다.

| 07-documentation | 기획-문서-공동작성 | planning-doc-coauthoring | planning-doc-coauthoring | **기획-문서-공동작성** |

**한국어 이름 3개 → 1개**로 줄었고 `systematic-debugging`은 **2회 다 정확히
일치**했다. 프롬프트에 "출처 이름을 결과물에 적지 마세요"를 넣어뒀는데도
걸리지 않았다 — 모델은 인용이 아니라 **작명**을 한 것이라 그 금지가 안 걸린다.

## 고친 방법 — 이름을 빼고 번호만

**필요한 신호는 "이 항목들이 한 스킬에서 함께 나왔다"까지이지 "어느 스킬인가"가
아니다.** 머리말을 「N번째 묶음」으로 바꾸자 **누출 0/10**이 됐고 한국어 이름도
돌아왔다(`근본원인-디버깅`, `기획-문서-공동작성`).

## 배운 것

**프롬프트에 넣은 값은 모델이 그 용도로만 쓰지 않는다.** 출처 이름은 "출신을
알려주려고" 넣었는데 **작명 재료로 쓰였다.** 금지 문구로 막으려 했으나 안 걸렸다
— 금지가 겨냥한 행동(인용)과 실제 행동(작명)이 달랐기 때문이다.
`form-matches-failure`가 말하는 것과 같다: **막을 실패의 형태를 잘못 잡으면
금지문은 헛돈다.** 값을 아예 안 주는 쪽이 확실했다.

## 짝 패턴 확인

금지 문구 원칙(`banned-phrases`)과 값(`banned-phrase-defaults`)이 한 묶음 안에
같이 읽히는지 봤고, 생성물에 둘 다 반영됐다. 다만 **그룹핑 전에도 우연히 붙어
있었으므로 이 확인만으로는 그룹핑의 효과라고 말할 수 없다.**

# 14·15차 — 완료 검증 승격 (2026-08-21)

## 먼저 세고 나서 옮겼다

승격 전 실측: **22건 중 완료 확인 절이 붙은 것은 8건(36%)**. 붙은 쪽은
테스트·디버깅 계열이고 **계획·코드리뷰·디자인·문서·설명·엑셀 정리는 두 번 다
없었다.**

## 14차 — 패턴을 옮겼는데 수치가 안 움직였다

`debugging`에 있던 넷을 `baseline`으로 옮기고 `evidence-matches-the-claim`을
새로 넣었다(커밋 `a23291c`). 렌더 128,583 → 130,640.

**결과: 36% → 32%.** 오르지 않았다.

### 원인 — 자리는 골격이 만든다

확인 절이 붙은 문서와 그 문서가 고른 골격을 대조하니 갈렸다.

| 골격 | `bodySections`에 완료 점검이 | 결과 |
|---|---|---|
| discipline | **있다** | 항상 붙음(테스트·디버깅) |
| workflow · reference · explanation | **없다** | 안 붙음 |

**패턴은 무엇을 확인할지 알려주지만 확인할 자리를 만들지는 못한다.**
자리가 없는 골격에서는 아무리 패턴을 실어도 절이 생기지 않는다.

이번 세션에서 「분량을 늘려도 결과물이 안 변한다」는 관측이 몇 번 있었는데,
**그중 일부가 이것으로 설명될 수 있다** — 자리가 없으면 내용을 줘도 안 들어간다.
골격 개편 때 생성물이 12% 길어진 것과도 이어진다.

## 15차 — 뼈대에 자리를 만들었다 (커밋 `c1872c2`)

`commonSpine`에 「완료 전 확인」을 넣고, `discipline`에만 있던 같은 줄은 뺐다
(같은 줄이 두 곳에 살면 한쪽만 고쳐진다).

### 확인 결과 — 100% (2026-08-21, API 복구 후 재실행)

| | 완료 확인 절 |
|---|---|
| 승격 전 | 8/22 (36%) |
| 패턴만 옮김 | 7/22 (32%) |
| **뼈대에 자리를 만듦** | **22/22 (100%)** |

**열한 종 전부, 두 번 다 붙었다.** 이번 세션에서 전후 비교가 되는 유일한
변경이고 결과가 가장 뚜렷하다.

#### 우려했던 실패 모드는 안 나왔다

"돌릴 명령이 없는 스킬에 「명령을 실행해 확인하라」가 박힌다"를 걱정했는데,
돌릴 것이 없는 다섯 종(설명·말투·문서·계획·계획문서) × 2회 = **10건 전부
내용 기준으로 확인**한다. 실행 지시가 박힌 건 **0건**이다.

실물 — 설명형 스킬의 완료 확인:

```
## 완료 전 확인
- 어려운 용어로 문장을 시작하지 않았는가
- 비유를 들었다면 그 비유의 각 부분이 실제로 무엇인지 짚어줬는가
- "왜 필요한지"가 들어갔는가
- 지금 사용자가 보고 있는 상황과 연결되는 문장이 하나라도 있는가
```

**그 스킬이 스스로 적어둔 조건이 그대로 점검표가 됐다.**
`evidence-matches-the-claim`이 겨냥한 동작이고, 원문 증거 표의
「요구사항을 다 채웠다」 줄과 같다.

#### 낱말 검색으로 끝내지 않았다

22/22가 나온 뒤 **세 건을 직접 열어 읽었고**(설명·디자인·엑셀), 실행 지시
여부도 따로 셌다. 이번 세션에 낱말 검색으로 세 번 틀렸기 때문이다.
