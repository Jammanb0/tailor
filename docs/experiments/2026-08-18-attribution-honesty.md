# 출처 표기 정직성 실험 — 자가 보고는 사실인가 (2026-08-18)

Tailor는 생성 결과 화면에 "이 스킬을 만들 때 아래 스킬들에서 정리한 패턴을
참고했어요"라고 표기한다. 이 표기가 사실인지 **한 번도 검증한 적이 없었다.**
이 문서는 그 첫 측정이다.

**결론부터.** 모델이 "이 패턴을 참고했다"고 신고한 항목 중 **문서에서 근거를
짚을 수 있는 것은 77.1%**였다(판정 가능한 35건 기준). 반대로 **쓴 것을 숨긴
경우는 0건**이다 — 오류는 전부 "부풀리는" 방향 한쪽이다.

단, 두 가지를 혼동하지 말 것.

- **화면에 뜬 출처 목록이 틀렸다는 뜻이 아니다.** 12건 전부에서 출처 목록 자체는
  검증 가능한 근거로 뒷받침됐다(아래 「후속 조치」 참조).
- **근거 없는 신고의 상당수는 모델의 거짓말이 아니다.** 애초에 완성된 문서로는
  판정할 수 없는 항목을 판정 대상에 넣어둔 **코퍼스 설계의 결함**이었다 — 아래
  「거짓 크레딧은 한 패턴에 몰려 있다」 참조.

## 왜 했나

"정직한 출처 표시"는 이 프로젝트가 내세우는 핵심 주장이다. 그런데 그 주장을
떠받치는 검증은 **"모델이 보고한 id가 코퍼스에 실존하는가"** 하나뿐이었다.
실존하는 id를 보고했다는 것과, 그 패턴을 **실제로 결과물에 반영했다는 것**은
전혀 다른 명제다. 후자는 아무도 확인한 적이 없었다.

## 출처 표기가 만들어지는 경로

측정 대상을 정확히 하기 위해 먼저 전체 경로를 추적했다.

| 단계 | 무엇이 일어나는가 | 검증 가능성 |
|---|---|---|
| ① 코퍼스 저술 | 사람이 원문 스킬을 읽고 패턴을 쓰고 `sourceIds`를 태그 | **기록 없음** |
| ② 프롬프트 주입 | `buildCorpusSection()`이 `- [id] (role) summary: detail` 형태로 렌더 | 코드로 확인됨 |
| ③ 모델 자가 보고 | `<used_patterns>`에 쓴 패턴 id를 스스로 적음 | **이 실험의 대상** |
| ④ id → 출처 역매핑 | `sourcesForUsedPatterns()`가 id로 패턴을 찾아 `sourceIds` 수집 | 결정론적, 틀릴 수 없음 |
| ⑤ 화면 표기 | `SourcesSection`이 "참고한 자료"로 렌더 | 코드로 확인됨 |

②에서 **`sourceIds`는 렌더되지 않는다.** 모델은 각 패턴이 어느 스킬에서 왔는지
전혀 모른다 — 모델이 출처를 지어낼 수 없다는 뜻이라 이 부분 설계는 견고하다.
따라서 신뢰가 걸린 지점은 ③ 하나뿐이고, ①은 애초에 기록이 없어 검증 대상조차
되지 못한다.

## 무엇을 알아냈나 (요약)

| 항목 | 결과 | 신뢰도 |
|---|---|---|
| **정밀도 — 검증 가능한 보고만** | **77.1% ~ 85.7%** | 중간 — 12건, 채점자 1명 |
| 정밀도 — 전체 보고 기준(참고) | 62.8% ~ 76.7% | 〃 |
| **재현율** (실제 반영된 것 중 보고) | **100% (엄격) / 89.2% (관대)** | 중간 |
| **구조 골격 일치** | **12/12 (100%)** | 높음 — 판정이 명확한 항목 |
| 거짓 크레딧의 집중 | 16건 중 **7건이 `form-matches-failure` 하나** | 높음 |
| 코퍼스 활용 범위 | 35개 중 보고 10개 / 실제 인정 8개 | **낮음 — 아래 한계 참조** |
| 자가 보고의 재현성 | `04-explanation`은 3회 모두 동일한 5개 보고 | 높음 |

**정밀도를 두 줄로 적는 이유.** 보고 43건 중 8건은 완성된 문서만 보고는
원리상 판정할 수 없는 항목이었다(`form-matches-failure`,
`skills-are-reusable-techniques` — 아래 「거짓 크레딧은 한 패턴에 몰려 있다」
참조). 전체 기준 62.8%는 **채점 자체가 불가능한 문항을 오답으로 센 값**이라
모델의 자가 보고를 실제보다 나쁘게 보이게 한다. 판정 가능한 35건만 세면
27/35 = 77.1%다.

이 구분은 실험을 설계할 때는 없었고 **채점 결과에서 발견된 것**이라, 처음부터
이렇게 재지는 못했다. 62.8%도 남겨두는 이유는 이후 실험과 기준을 비교할 때
어떤 분모로 잰 값인지 헷갈리지 않게 하기 위해서다.

각 값에 다시 범위가 있는 이유(엄격/관대)는 「채점 기준」 항목에 적었다. 하나의
숫자로 적으면 과장이거나 과소평가가 된다.

## 측정 방법

### 생성

`POST /api/eval-ab { "experiment": "attribution", "runs": 3 }`

설정 비교 실험이 아니라 **"지금 앱이 실제로 내는 결과"의 기준선**을 재는
것이므로, `generate-skill/route.ts`와 동일 조건으로 맞췄다 — `claude-sonnet-5`,
`thinking: disabled`, **`effort` 파라미터를 넘기지 않음**(= 기본값).

> 주의: `2026-08-13-generation-quality.md`는 "effort low 잠정 채택"이라고
> 적었지만, 생성 라우트에는 `output_config`가 **지금도 없다**. 채택이 문서에만
> 있고 구현되지 않았다. 이 실험은 실제 앱 동작(파라미터 미전달)에 맞췄으므로
> 기준선으로서는 유효하다. 불일치 자체는 별건으로 정리해야 한다.

기존 하네스의 4개 시나리오(discipline/workflow/reference/explanation를 각각
유도하도록 설계된 것) × 3회 = **12건**. 워밍업 1회는 버렸다.

### 채점 기준

**채점자는 모델이 무엇을 보고했는지 보지 못한다.** 보고 내용을 보면 그대로 따라
읽게 되고, 그 순간 이 측정이 재려던 것이 사라진다. 그래서 결과를 두 파일로
분리해, 채점자에게는 SKILL.md 본문 12개와 패턴 카탈로그 35개만 주고 정답지는
다른 디렉터리로 옮겼다. 채점 주체도 실험 설계자와 분리했다(별도 에이전트).

인정 조건은 엄격하게 뒀다 — **문서에서 근거 구절을 인용할 수 있어야** 반영으로
인정하고, 주제가 비슷하기만 한 것은 인정하지 않는다. 애매하면 미반영으로
판정하되 `borderline`에 따로 남기게 했다.

이 지시 때문에 엄격 판정은 **정밀도의 하한**이다. borderline을 전부 인정한
관대 판정이 상한이고, 실제 값은 두 수 사이에 있다. 그래서 범위로 적는다
(판정 가능한 35건 기준 77.1%~85.7%, 전체 43건 기준 62.8%~76.7%).

## 결과

### 문서별

| 문서 | 시나리오 | 보고 | 실제 인정 | 일치 | 골격 |
|---|---|---|---|---|---|
| doc-01~03 | discipline | 4/3/3 | 2 | 2 | 3/3 일치 |
| doc-04~06 | workflow | 3/4/3 | 1 | 1 | 3/3 일치 |
| doc-07~09 | reference | 2/3/3 | 1 | 1 | 3/3 일치 |
| doc-10~12 | explanation | 5/5/5 | 5 | **5** | 3/3 일치 |

**재현율이 100%라는 건 모델이 쓴 것을 숨기지 않는다는 뜻이다.** 문제는 전부
반대 방향 — **안 쓴 것을 썼다고 보고하는 쪽**이다.

### 거짓 크레딧은 한 패턴에 몰려 있다

거짓 크레딧 16건의 분포:

| 패턴 | 거짓 크레딧 | borderline |
|---|---|---|
| `form-matches-failure` | **7회** | 4회 |
| `trigger-first-description` | 3회 | 3회 |
| `bite-sized-tasks` | 3회 | - |
| `show-options-then-apply` | 2회 | - |
| `skills-are-reusable-techniques` | 1회 | - |

`form-matches-failure`는 9번 보고돼 **7번이 거짓**이었다. 그런데 이 패턴의
정의를 보면 이유가 분명하다:

```
summary: "가이드 형태를 실패 유형에 맞춘다(→ 구조 원형 선택)"
detail:  "… 이 원칙이 곧 어떤 구조 원형을 쓸지 결정한다."
```

이건 **결과물에 나타나는 행동 패턴이 아니라, 문서 형태를 고르는 과정 원칙**이다.
문서 안에서 인용할 구절이 존재할 수 없다. 모델은 실제로 이 원칙에 따라 골격을
골랐고(골격 일치 12/12가 그 증거다) 그래서 정직하게 보고했는데, 채점자는
문서에서 근거를 찾을 수 없어 미반영으로 판정한 것이다.

**즉 이건 모델의 부정직이 아니라 코퍼스의 분류 오류다.** 코퍼스가 두 종류를
같은 목록에 섞어 놓았다:

- **산출물 패턴** — 결과 문서에 나타남. 검증 가능. (예: `everyday-analogy`)
- **과정 패턴** — 생성 과정을 지배함. 문서에서 검증 불가능. (예: `form-matches-failure`)

그런데 ④ 역매핑은 둘을 구분하지 않고 똑같이 출처 크레딧을 준다. 과정 패턴에
대한 크레딧은 **원리상 검증할 수 없는 표기**다.

`trigger-first-description`(description을 트리거 중심으로 쓴다)도 비슷한
경계에 있다. 채점자는 PR 체크리스트 문서 3건에서 description이 트리거 서술과
워크플로 요약을 겸하고 있어 borderline으로 뒀다.

### 유일하게 완벽했던 카테고리

`04-explanation`만 12건 중 유일하게 **보고 5 = 실제 5, 3회 모두 동일**이었다.
이 카테고리 패턴들의 `detail`을 보면:

```
everyday-analogy: "카페·알바생·메모처럼 누구나 아는 일상 상황으로 치환해
설명한다. (예: '스크립트 = 알바생에게 남긴 할 일 메모')"
```

**구체적 예시가 본문에 들어 있다.** 다른 카테고리의 추상적 한 줄과 대조된다.
표본이 한 카테고리뿐이라 인과로 단정할 수는 없지만, "구체적 예시가 담긴 패턴은
충실히 반영되고 검증도 된다"는 가설과 정합적이다. 이 가설은 `detail` 압축 방식
재설계(open-questions의 별도 항목)에서 다룰 문제와 정확히 같은 것을 가리킨다.

## 이 실험의 한계

**한계가 결론보다 중요하다.**

1. **커버리지 결론을 낼 수 없다.** 35개 중 27개가 한 번도 등장하지 않았지만,
   시나리오가 4개 도메인(커밋 전 검사 / PR 체크리스트 / 디자인 토큰 조회 /
   라이브러리 설명)뿐이라 테스트·디버깅·코드리뷰·디자인 패턴은 **애초에 적용될
   여지가 없었다.** "코퍼스 대부분이 놀고 있다"는 인상은 이 실험으로 뒷받침되지
   않는다. 확인하려면 각 카테고리를 겨냥한 시나리오가 필요하다.
2. **채점자가 1명이다.** 판정 기준(특히 borderline 경계)이 그 한 명의 해석에
   달려 있다. 두 번째 채점자를 붙여 일치율을 봐야 판정 자체를 신뢰할 수 있다.
3. **12건은 적다.** 시나리오당 3회로 재현성은 확인했지만, 정밀도 77.1%의
   신뢰구간은 넓다(판정 가능한 보고가 35건뿐이다).
4. **`effort` 기본값 조건에서만 유효하다.** 설정이 바뀌면 다시 재야 한다.
5. **골격 출처의 정밀도는 재지 않았다.** `sourcesForArchetype("discipline")`은
   어느 스킬이 실제로 그 형태를 만들었는지와 무관하게 **항상 같은 3개**를
   크레딧한다. 골격 일치 12/12는 "골격 선택이 맞았다"는 뜻이지 "그 3개 스킬이
   이 문서에 기여했다"는 뜻이 아니다. 패턴 출처보다 한 단계 거친 주장이다.

## 부수 관측

- **12건 전부 정상 생성.** 오류 0, 존재하지 않는 패턴 id 보고 0건, review/
  questions 한국어 규칙 위반 0건.
- **되물음(`needsMoreInfo`) 0건.** 같은 날 추가한 `INSUFFICIENT_INPUT_RULE`이
  멀쩡한 입력에서 과잉 발동하지 않는다는 첫 근거다(부실한 입력에서 의도대로
  발동하는 것은 별도 확인됨). 다만 "멀쩡한 입력 4종"이라 경계 케이스는 미측정.
- 평균 1,625자 / 출력 1,985토큰 / 24.4초 / **12건 총 $0.29**.

## 후속 조치 (같은 날 반영됨)

**과정 패턴을 출처 크레딧에서 분리했다.** `ReferencePattern.kind`
(`"artifact" | "process"`, 생략 시 artifact)를 두고 위 2개를 process로 표시한
뒤, `sourcesForUsedPatterns()`가 이를 크레딧에서 제외하도록 고쳤다.

**중요: 이 수정은 사용자 화면을 바꾸지 않는다.** 측정한 12건 전부에 대해
변경 전/후 크레딧 목록을 비교한 결과 **0/12 변화**였다. process 패턴의 출처인
`sp-writing-skills`는 `trigger-first-description`(검증 가능한 산출물 패턴)으로
12건 모두에서 어차피 크레딧되기 때문이다.

**즉 화면에 뜨던 출처가 틀렸던 적은 없다.** 틀린 것은 그 출처가 크레딧되는
근거 중 일부가 검증 불가능했다는 점이다. 이 커밋을 "출처 표시 버그 수정"으로
읽으면 오해다 — 원리를 바로잡은 것이고, 실질적 이득은 ① 앞으로 process 패턴만
단독 보고되는 생성에서 검증 불가능한 표기가 나가지 않는다는 것과 ② 채점 분모가
정확해진다는 것(위 요약표의 두 줄) 두 가지다.

## 재현 방법

```bash
# 1. 12건 생성 (dev 서버 필요, 약 5분 30초)
curl -X POST http://localhost:3000/api/eval-ab \
  -H "Content-Type: application/json" \
  -d '{"experiment":"attribution","runs":3}' -o attribution-raw.json
```
