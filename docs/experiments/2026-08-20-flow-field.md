## 1. 무엇을 바꿨나

원문 systematic-debugging은 4단계 순서와 "각 단계를 끝내야 다음"을 규정한다
(감사 `SD-07`, 원문 L44–47). 각 단계는 패턴으로 남았는데 **그 규정만 어디에도
없었다** — 감사 문서 「잃은 것」 표에 5번 항목 "부분" 복원으로 적혀 있고,
`SD-07`을 참조하는 패턴이 코퍼스에 0개였다.

`flow` 필드는 그것을 담는다. 목록(`string[]`)을 쓰지 않은 이유는 원문에 분기
(`SD-16`)가 있어서다. 설계 근거와 lint 규칙은 `.agents/plans/handoff.md` 3번 절.

**두 조건의 차이는 렌더 9줄뿐이다.**

```
off : 75,687바이트 — 직전 골든과 바이트 단위 동일
on  : 76,525바이트 — 디버깅 섹션에만 +838
```

`off`는 흐름 블록만 빼는 것이 아니라 **`flow`를 가진 패턴을 통째로 뺀다.**
처음에는 블록만 뺐는데, 그러면 요약 줄("디버깅은 네 단계이고, 각 단계를 끝내야
다음으로 간다")이 남아 **재려던 답이 대조군에 실렸다.** 이 실수는 렌더 확인
단계에서 잡혔다.

## 2. 결과 — 주 항목

원문 Phase 2(Pattern Analysis, "정상 동작하는 사례를 찾아 차이를 나열").
**코퍼스에 대응 패턴이 없고**, 존재하는 곳은 흐름의 `label` 한 줄뿐이다.

| | on | off |
|---|---|---|
| 1차 (사후 발견) | 5 / 6 | 0 / 6 |
| **2차 (사전 등록)** | **6 / 6** | **0 / 6** |

```
item-020  2단계 — 비슷하게 동작하는 사례와 비교한다
item-022  2단계 — 비슷한데 잘 되는 경우와 비교한다
item-024  2단계 — 패턴 분석 / 같은 종류의 코드 중 잘 작동하는 예를 찾아…
```

### 보조 항목 — 절차 전체에 걸린 게이트

| | on | off |
|---|---|---|
| 1차 | 2 / 6 | 0 / 6 |
| 2차 | 3 / 6 | 0 / 6 |

2차에서 `item-022`를 **탈락시켰다.** "이 단계를 끝내기 전에는…"이 1단계 **안에**
있어서, 사전 등록한 "특정 단계에만 걸린 조건은 아니오" 규정에 걸린다.
**정답지를 열기 전에 내린 판정이다.**

### 판정에서 뺀 두 항목

1차에서 A(순서)와 C(되돌아감)가 **양쪽 다 6/6**이었다. 2차에서는 판정 항목에서
뺐다. 원인은 사전에 적어둔 예측과 같다 — `root-cause-first`의 요약이 이미 순서를
함의하고, `three-fix-rule`이 되돌아감을 산문으로 담고 있다.

**두 예측이 다 맞았다.** 1·2차에서 빗나간 예측은 없다.

## 3. 문제 서술이 틀렸다는 것

이 실험의 가장 큰 소득이다.

| 처음 세운 걱정 | 실제 |
|---|---|
| 조각으로 쪼개서 **순서가 뒤섞인다** | ❌ 12건 전부 순서가 맞았다 |
| — | ✅ **단계 하나가 통째로 빠져 있었다** |
| — | ✅ **"끝내야 다음"이 없었다** |

`flow` 필드가 값을 한 이유는 **순서를 담아서가 아니라, 담을 자리가 없던 단계
하나를 실을 수 있게 해줘서**다. 실제로 그 단계는 `patternId` 없이 `label`만 있는
항목이었다(대응 패턴이 없어서).

> **일반화**: "구조가 사라졌다"고 느낄 때, 사라진 것이 정말 구조인지 **내용인지**
> 먼저 가른다. 이 프로젝트에서 지금까지 효과가 확인된 변경은 전부 내용 쪽이었다.

## 4. 부작용 — 1차의 의심은 잡음이었다

1차에서 대조 시나리오의 구조 골격이 흔들렸다.

```
1차  05-design           on: reference, workflow, reference   off: workflow ×3
     09-mismatch-office  on: workflow ×3                      off: reference, workflow, reference
```

**방향이 서로 반대**라 계통적 밀림으로 보기 어려웠다. 2차에서 `05-design`의
반복을 3 → 6으로 올려 갈랐다.

```
2차  on : workflow, reference, reference, workflow, workflow, reference  → workflow 3
     off: workflow, reference, reference, reference, workflow, workflow  → workflow 3
```

**차이 0건.** 사전 등록한 "2건 이하면 잡음" 기준에 따라 잡음으로 판정한다.

> 3차에서 나온 "시나리오당 3건으로는 한 건만 튀어도 판정선을 넘는다"가
> **대조군에서도 그대로 성립한다.** 대조 셀도 반복이 부족하면 없는 부작용을
> 만들어낸다.

## 5. 부수 관찰 (사전 등록 밖 — 근거로 쓰지 않는다)

- **자기 보고가 실제와 어긋난다.** 1차 `on` 6건 중 `four-phase-debugging-order`를
  썼다고 보고한 것은 3건인데, 내용으로는 5건에 2단계가 들어갔다. 출처 표기가
  보고 id에 의존하므로 **표기 누락 쪽으로 치우친다.** 별도로 볼 사안이다.
- **분량은 안 늘었다.** 1차 디버깅 평균 on 3,516자 / off 3,541자.
- **골격은 전부 `discipline`.** 24건 모두. 이 시나리오에서는 골격이 상수다.

## 6. 방법에서 배운 것

- **사후 발견 항목은 사전 등록하고 다시 돌리면 근거가 된다.** 1차의 5–0은 쓸 수
  없었지만, 같은 항목을 등록하고 돌린 2차의 6–0은 쓸 수 있다. 한 번 더 돌리는
  비용($1.4)이 결론의 지위를 바꿨다.
- **판정 항목은 회차마다 갈아야 한다.** 1차에서 변별력이 없다고 확인된 A·C를
  2차에서 계속 쟀다면 12건 중 8건이 상수인 자료가 됐을 것이다.
- **채점을 정규식으로 하지 말 것.** 1차에서 "전엔"과 "전에는"을 다르게 잡아 한 번
  잘못 셌다. 2차는 문장을 읽고 판정하고 근거 문장을 `SCORES.md`에 옮겨 적었다.
- **대조군에 답이 새는지 확인할 것.** "새로 넣은 것을 뺐는가"가 아니라 **"재려는
  정보가 대조군에 남아 있는가"**를 본다. 요약·제목 줄이 가장 흔한 누출 경로다.
