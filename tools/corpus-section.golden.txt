# 문서 구조 골격 (하나 선택)

골격은 "사용자가 원하는 게 무엇인가"로 고르세요:
- 값·옵션을 찾아보거나 정해진 기준을 일관되게 적용한다 → reference
- 정해진 순서대로 여러 단계를 밟아 결과물을 만든다 → workflow
- 개념이나 도구가 무엇인지 쉽게 설명한다 → explanation
- 지켜야 할 원칙이 핵심이고, 안 지키면 실제로 사고가 난다 → discipline

discipline은 마지막 수단입니다. 위 셋 중 하나로 설명되면 그걸 쓰세요.
Rationalizations·Red Flags 같은 섹션은 discipline을 골랐을 때만 쓰고,
다른 골격에 끌어다 붙이지 마세요.

### discipline — 규율형 (지켜야 할 원칙)
언제: 지켜야 할 원칙·규율이 핵심이고, AI가 '이번만 건너뛰자'며 합리화하기 쉬운 스킬 (예: 테스트 먼저, 완료 전 검증, 근본원인 우선). 단순 조회·설명·정해진 순서 실행에는 쓰지 마세요 — 그런 작업에 이 골격을 붙이면 불필요하게 무겁고 훈계조인 문서가 됩니다.
골격:

## When to Use — 항상 적용되는 경우 / 예외(사람에게 확인)
## <핵심 절차> — 단계별로, 규칙마다 Good/Bad 예시 쌍

## Red Flags — 'STOP하고 다시 시작' 신호 목록
## Verification Checklist — 완료 전 체크 항목

### workflow — 절차형 (순서 있는 워크플로)
언제: 순서 있는 여러 단계를 거쳐 산출물을 만드는 스킬 (예: 문서 공동작성, 브레인스토밍, 계획 작성).
골격:

# 제목
## Overview — 이 워크플로가 무엇을 만들어내는지 한 줄
## Stages — 번호 있는 단계. 각 단계: (a) 맥락/질문 → (b) 산출 → (c) 반복.
   단계 사이에 '다음으로 넘어가기 전 게이트'(승인/확인)를 명시
## Self-Review — 자리표시자·모순·범위 이탈 점검

### reference — 참조형 (옵션 제공·적용)
언제: 옵션/프로필을 정의하고 일관되게 적용하는 스킬 (예: 테마·디자인 시스템, 말투 프로필).
골격:

## Overview — 무엇을 일관되게 적용하는지
## Profile / Options — 정의할 항목(색·폰트·보이스 특성 등) 또는 선택지 목록
## Apply — 옵션을 먼저 보여주고 승인받은 뒤, 대비·가독성 등 제약을 지키며 전체 적용

# 좋은 패턴 (카테고리별)
## 테스트
- [test-first] (workflow-step) 구현 코드보다 실패하는 테스트를 먼저 쓴다: 새 기능·버그픽스·리팩터링 전에 실패하는 테스트를 먼저 작성하고, 그 테스트가 '기능이 없어서' 실패하는지 눈으로 확인한 뒤 통과할 최소 코드를 쓴다(Red-Green-Refactor). 테스트를 나중에 쓰면 이미 짠 코드에 편향돼 '무엇을 하는가'만 검증하게 된다.
- [one-behavior-per-test] (constraint) 테스트 하나는 한 가지 행동만 검증한다: 테스트 이름에 'and'가 들어가면 쪼갠다. 이름은 동작을 설명하고, mock의 동작이 아니라 실제 코드의 동작을 단언한다.
- [minimal-green] (constraint) 테스트를 통과시킬 최소 코드만 쓴다: 아직 필요 없는 옵션·추상화·에러 처리를 미리 넣지 않는다(YAGNI). 통과 후 리팩터 단계에서만 정리한다.

## 디버깅
- [root-cause-first] (workflow-step) 증상이 아니라 근본 원인부터 조사한다: 에러 메시지 정독 → 일관되게 재현 → 최근 변경 확인 → 컴포넌트 경계마다 진단 로그로 데이터 흐름을 추적한다. 데이터 흐름을 추적하기 전에 해결책부터 제안하면 안 된다.
- [three-fix-rule] (constraint) 3번 이상 고쳐도 안 되면 설계 문제 신호: 같은 문제에 세 번 넘게 고쳐도 안 되면 구현이 아니라 아키텍처 문제일 가능성이 크다. 계속 찔러보지 말고 구조를 의심한다.
- [verify-before-done] (verification) '됐다'고 말하기 전에 명령을 실행해 증거를 확인한다: 완료·수정·통과를 주장하기 전에 그것을 증명하는 명령을 새로 실행하고 출력과 종료코드를 직접 읽는다. 'should/probably/seems' 같은 표현이나 실행 없는 성공 주장은 금지.

## 계획·설계
- [design-before-code] (workflow-step) 구현 전에 설계를 먼저 합의한다: 맥락 파악 → 한 번에 하나씩 질문 → 2~3개 접근안을 트레이드오프와 함께 제시 → 승인 후 진행. '간단한' 작업일수록 검증 안 된 가정이 낭비를 만든다.
- [bite-sized-tasks] (workflow-step) 계획은 2~5분짜리 독립 작업 단위로 쪼갠다: 실패 테스트 작성→실패 확인→구현→통과 확인→커밋 흐름으로 잘게 나눈다. 'TBD'·'검증 추가' 같은 자리표시자 대신 실제 파일 경로·인터페이스를 적는다.
- [assume-low-context-reader] (output-rule) '도메인을 거의 모르는 유능한 개발자'가 읽는다고 가정: 계획은 추상적 표현 대신 구체적 구현 정보를 담는다. 읽는 사람이 이 코드베이스·도구를 모른다고 가정하고 실제 세부를 적는다.

## 코드 리뷰
- [review-early-often] (workflow-step) 자주, 일찍 리뷰한다: 작업·주요 기능 후, main 병합 전에 리뷰한다. '간단한' 변경이라고 건너뛰지 않는다.
- [severity-ordered-fixes] (workflow-step) 피드백은 심각도 순으로 처리한다: 치명적→중요→사소 순으로 고친다. 근거 없는 지적에는 기술적 근거를 들어 반박할 수 있다.
- [isolated-reviewer-context] (constraint) 리뷰어에겐 변경 diff와 요구사항만 준다: 세션 전체가 아니라 base·head 커밋의 diff와 요구사항만 전달해 리뷰어의 맥락을 격리하고 판단을 독립시킨다.

## 공통 기본 (모든 스킬) (공통·항상 적용)
- [trigger-first-description] (trigger) description은 'Use when...' 트리거 조건 중심으로: 워크플로 요약이 아니라 '언제 쓰는지'(어떤 요청·상황·에러·도구에서 호출되는지)를 구체적으로 쓴다. 에이전트가 검색할 키워드를 넣는다. description은 에이전트가 스킬 호출 여부를 판단하는 가장 중요한 필드다.
- [form-matches-failure] (constraint) 가이드 형태를 실패 유형에 맞춘다(→ 구조 원형 선택): 규칙 위반엔 금지문, 출력 형태 문제엔 레시피/예시를 쓴다. 규율형 스킬엔 합리화 표와 red flag 목록을 넣는다. 이 원칙이 곧 어떤 구조 원형(규율형/절차형/참조형)을 쓸지 결정한다.
- [skills-are-reusable-techniques] (constraint) 스킬은 재사용 가능한 검증된 기법이지 일회성 서사가 아니다: 한 번의 문제 해결 이야기가 아니라 반복해서 쓸 기법의 참고 자료로 만든다. 일회성 작업은 스킬로 만들지 않는다.

## 디자인·프론트엔드
- [ground-in-subject] (workflow-step) 주제 고유의 세계에서 디자인 선택을 끌어낸다: 브리프가 주제를 특정하지 않으면 먼저 직접 고정한다 — 구체적 주제 1개·청중·페이지의 단일 목적을 정하고 그 선택을 명시한다. 고유한 선택은 주제의 세계(소재·도구·산물·업계 용어)에서 나온다. 히어로는 주장이다: 주제 세계에서 가장 특징적인 것으로 연다.
  형식(섹션): 구체적 주제 1개 / 청중 / 페이지의 단일 목적
  값: 헤드라인 — 주장을 문장으로 — 카피 자체가 강할 때
  값: 이미지 — 주제의 실물·질감을 바로 보여줄 때
  값: 애니메이션 — 변화·과정이 주제의 핵심일 때
  값: 라이브 데모 — 직접 만져보는 것이 가장 설득적일 때
  값: 인터랙티브 순간 — 참여 자체가 메시지일 때
  이러지 말 것: 큰 숫자 + 작은 라벨 + 보조 스탯 + 그라데이션 액센트 — 히어로의 템플릿 답안. 정말 최선일 때만 쓴다
- [avoid-ai-default-looks] (constraint) AI 디자인이 몰리는 세 가지 기본 룩을 알고 피한다: 아래 셋은 어떤 브리프에는 정당하지만 선택이 아니라 기본값이며, 주제와 무관하게 반복해서 나온다. 브리프가 비워둔 축에서 이 셋으로 흘러가지 않는지 만들면서 확인한다.
  이러지 말 것: 따뜻한 크림 배경(#F4F1EA 근처) + 고대비 세리프 디스플레이 + 테라코타 액센트
  이러지 말 것: 니어블랙 배경 + 밝은 애시드 그린 또는 버밀리언 액센트 하나
  이러지 말 것: 헤어라인 괘선 + border-radius: 0 + 신문식 조밀 다단(브로드시트)
  예외: 브리프가 이 룩 중 하나를 명시적으로 요구하면 그대로 따른다 — 브리프의 말이 항상 이긴다
- [one-signature-element] (constraint) 대담함은 한 곳에 집중하고 나머지는 절제한다: 시그니처 요소 하나만 기억에 남게 하고 주변은 조용하고 규율 있게 두며, 브리프에 복무하지 않는 장식은 잘라낸다. 구조 장치(번호·아이브로우·구분선·라벨)는 내용에 관한 참인 무언가를 담아야 하고 장식이면 안 된다.
  이러지 말 것: 순서가 아닌 내용에 01 / 02 / 03 번호 마커를 붙이는 것
  이렇게: 실제 프로세스나 시점이 찍힌 타임라인처럼, 순서가 독자에게 정보를 줄 때만 번호를 쓴다
  예외: 모험하지 않는 것 자체가 위험일 수 있다 — 절제가 무난함으로 흐르지 않게 한다
- [deliberate-typography] (output-rule) 디스플레이·본문 폰트를 의도적으로 짝짓고 역할을 나눈다: 아무 프로젝트에나 반사적으로 쓰는 서체 대신 주제에 맞게 고른다. 타입 스케일을 명확히 잡고 굵기·너비·자간을 의도적으로 설정하며, 타이포 처리 자체가 기억에 남는 요소가 되게 한다. 역할은 헤더와 본문 둘로 나누는 것이 기본이고, 개성은 헤더에서 내되 본문은 가독성을 지킨다.
  형식(섹션): 헤더(디스플레이) / 본문 / 필요시 캡션·데이터용 유틸리티
  값: 세리프 헤더 — 격식 있고 전통적 — 신뢰·역사·전문성을 말할 때
  값: 산세리프 헤더 — 현대적이고 중립적 — 기술·명료함을 말할 때
  값: 굵은 헤더 + 보통 굵기 본문 — 대비로 위계를 만드는 가장 안전한 기본 조합
  값: 산세리프 본문 — 긴 글에서도 읽기 쉬움 — 본문에는 이쪽을 권한다
  예외: 실행 환경에 따라 쓸 수 있는 서체가 제한될 수 있다. 그때는 이름이 아니라 성격(세리프/산세리프, 굵기 대비)을 맞춘다
- [purposeful-motion] (constraint) 모션은 쓸 곳과 쓸지 여부를 함께 판단한다: 흩뿌린 효과보다 연출된 한 순간이 대개 더 세게 꽂힌다. 애니메이션이 과하면 'AI가 만든' 느낌에 기여하므로, 어디에 쓸지와 아예 쓰지 않을지를 함께 정한다.
  값: 페이지 로드 시퀀스 — 첫인상을 연출 — 한 번만 쓰고 짧게
  값: 스크롤 트리거 등장 — 읽는 속도에 맞춰 정보를 드러냄
  값: 호버 마이크로 인터랙션 — 조작 가능하다는 신호 — 작고 빠르게
  값: 앰비언트 분위기 — 배경에서 은은하게, 주의를 뺏지 않게
- [match-complexity-to-vision] (constraint) 복잡도를 택한 방향에 맞춘다: 맥시멀리즘 방향은 정교한 실행을 요구하고, 미니멀 방향은 여백·타입·디테일의 정밀함을 요구한다. 우아함은 택한 비전을 잘 실행하는 것이지 요소를 줄이는 것이 아니다.
- [design-token-plan] (output-rule) 만들기 전에 토큰 시스템 4종을 개수까지 정한다: 코드를 쓰기 전에 색·타입·레이아웃·시그니처를 한 벌로 정하고, 이후 모든 결정을 이 계획에서 파생시킨다. 개수를 정해두지 않으면 계획이 '분위기 설명'으로 흐른다.
  형식(개수): 색 명명 hex 4~6개 · 서체 2역할 이상 · 시그니처 정확히 1개
  형식(섹션): Color — 명명된 hex 4~6개 / Type — 디스플레이 / 본문 (+필요시 유틸리티) / Layout — 한 문장 산문 + ASCII 와이어프레임으로 안 비교 / Signature — 이 페이지가 기억될 단 하나의 요소
  형식(틀):
  ```
  Color: Deep Navy #1B2A41 / ... (4~6개)  |  Type: 디스플레이 + 본문  |  Layout: 산문 1문장 + ASCII 와이어프레임  |  Signature: 1개
  ```
- [plan-then-critique] (workflow-step) 계획을 브리프에 비춰 검토한 뒤에야 만든다(2패스): 계획의 각 부분이 '비슷한 페이지면 아무거나 나올 법한 기본값'으로 읽히는지 본다. 판정은 감이 아니라 절차로 한다 — 비슷한 프롬프트를 실제로 굴려 같은 결과에 도달하는지 확인하고, 고쳤으면 무엇을 왜 바꿨는지 말한다. 고유성을 확인한 뒤에야 코드를 쓴다.
- [brief-wins] (constraint) 브리프가 지정한 것은 그대로 따른다: 고유성을 요구하는 다른 모든 규칙에 우선하는 예외다. 브리프가 방향을 지정했으면 그대로 따르고, 브리프가 비워둔 축에서만 그 자유를 기본값에 쓰지 않는다. 이 규칙이 없으면 '고유하게 하라'가 사용자 지시를 무시하는 근거로 쓰인다.
- [quality-floor-unannounced] (verification) 품질 바닥선을 티내지 않고 지킨다: 아래 3항목은 자랑하지 않고 기본으로 지킨다. 문서에 '접근성을 고려했습니다'라고 쓰는 대신 항목을 실제 점검 대상으로 둔다.
  형식(섹션): 모바일까지 반응형 / 키보드 포커스가 눈에 보임 / prefers-reduced-motion 존중
- [ui-copy-is-design-material] (output-rule) 화면의 글도 디자인 재료로 다룬다: 카피는 장식이 아니라 디자인 재료다. 사용자가 다루고 알아보는 이름으로 부르고 시스템 구현 방식으로 부르지 않는다. 능동태를 기본으로 하고, 한 동작은 흐름 전체에서 같은 이름을 유지한다. 실패와 빈 화면은 분위기가 아니라 방향을 주는 자리다 — 에러는 사과하지 않고 무엇이 잘못됐고 어떻게 고치는지 말한다.
  이렇게: "Save changes" — 눌렀을 때 벌어질 일을 그대로
  이러지 말 것: "Submit" — 무슨 일이 나는지 말하지 않음
  이렇게: "Publish" 버튼이 "Published" 토스트를 낸다 — 이름이 흐름 내내 유지됨
  이렇게: "알림을 관리" — 사람이 아는 말
  이러지 말 것: "웹훅 설정"을 관리 — 시스템 구현 용어
- [cohesive-palette-and-fonts] (output-rule) 색·폰트·정체성 3종을 한 벌로 묶는다: 테마 하나는 세 가지로 구성된다 — hex 코드를 갖춘 응집된 색 팔레트, 헤더·본문의 상보적 폰트 짝, 맥락과 청중에 맞는 뚜렷한 시각 정체성. 셋 중 하나라도 빠지면 여러 콘텐츠에 일관되게 적용할 수 없다.
  형식(섹션): hex 코드를 갖춘 색 팔레트 / 헤더·본문 폰트 짝 / 맥락·청중에 맞는 시각 정체성
- [option-spec-format] (output-rule) 옵션 하나를 적는 형식 — 이름·값·역할 3부: 선택지를 제공하는 스킬은 옵션 하나하나를 같은 틀로 적는다. 색은 정확히 4개를 배경·주 강조·보조 강조·텍스트 자리에 배치하고, 각 항목은 부르는 이름·실제 값·쓰이는 자리 세 조각을 모두 갖춘다. 이름만 있으면 못 쓰고, 값만 있으면 어디 쓸지 모르고, 역할만 있으면 무슨 색인지 모른다.
  형식(개수): 색 정확히 4개 · 폰트 2역할 · 용도 4~5개
  형식(섹션): # 이름 / 성격 한 문장 (형용사 + 무엇을 연상시키는지) / ## Color Palette / ## Typography / ## Best Used For
  형식(틀):
  ```
  - **Deep Navy**: `#1B2A41` - 주 배경색
  ```
- [show-options-then-apply] (workflow-step) 옵션을 먼저 보여주고 승인 후 일관 적용: 선택지를 먼저 눈으로 보게 하고, 어느 것을 쓸지 묻고, 명시적 확인을 받은 뒤에 적용한다. 적용할 때는 대비·가독성을 지키며 전체에 일관되게 반영한다.
  예외: 보여주기용 자료(쇼케이스)는 보여주기만 하고 수정하지 않는다
- [wait-for-explicit-choice] (workflow-step) '제시했다'와 '확인받았다'를 다른 사건으로 다룬다: 선택지를 보여준 것만으로 진행하지 않고 명시적 확인을 기다린다. 한 문장으로 합치면 제시만 하고 적용해버리는 실패가 규칙 위반으로 잡히지 않는다.
- [custom-option-fallback] (workflow-step) 맞는 선택지가 없으면 만들고, 같은 승인 절차를 다시 밟는다: 기존 선택지 중 맞는 것이 없으면 새로 만든다. 이름은 조합이 무엇을 표상하는지 드러나게 붙이고, 사용자가 준 설명으로 값을 고른다. 만든 뒤에는 기존 선택지와 똑같이 검토·확인을 받고 나서 적용한다 — 예외 경로에서 승인 절차가 새지 않게 한다.
- [read-the-spec-not-memory] (workflow-step) 명세가 파일로 있으면 기억하지 말고 읽는다: 적용할 값이 별도 파일에 정의돼 있으면 그 파일을 열어 읽고 적용한다. 기억이나 추측으로 값을 채우면 파일과 결과물이 조용히 어긋난다.
- [context-appropriate-theme] (workflow-step) 용도를 형용사가 아니라 실제 상황으로 적는다: 맥락과 청중에 맞는 시각 정체성을 고르되, 어디에 쓰는 것인지를 실제 문서 종류·업종으로 적는다. 고를 때 필요한 판단은 '멋진가'가 아니라 '내 상황이 여기 있는가'이기 때문이다.
  형식(개수): 용도 4~5개
  이렇게: 의료 발표자료, 재무 보고서, 웨딩 기획, 기술 스타트업 데모
  이러지 말 것: '우아한', '전문적인', '모던한' 같은 형용사만 나열하는 것

## 말투·보이스
- [define-voice-profile] (workflow-step) 말투를 먼저 '프로필'로 정의하고 일관 적용한다: 정체성·핵심 신념·독자·보이스 특성(3~5개)·핵심 주제·선호/거부 어휘·금지 문구·채널별 규칙·예시 문단을 프로필로 정의하고, 그 기준으로 일관되게 쓴다.
- [banned-phrases] (constraint) 쓰지 말 표현을 명시적으로 목록화해 제거한다: 진부하거나 'AI스러운' 문구를 금지 목록으로 만들고, 선호 어휘 대 거부 어휘를 구분해 걸러낸다.
- [open-with-punch] (output-rule) 빌드업 없이 핵심으로 열고, 짧게 쓴다: 숫자·대담한 주장·의외의 관점으로 시작한다. 짧은 문장, 짧은 문단, 여백을 둔다.
- [substance-over-performance] (constraint) 태도가 아니라 근거로 뒷받침된 의견을 낸다: 데이터·경험으로 뒷받침한다. 과시성 글쓰기·허수아비·아랫사람 깔보기·선언문식 수사를 금지하고, 모든 문장이 값을 하게 한다.

## 문서 작성
- [context-gathering-first] (workflow-step) 쓰기 전에 배경·엣지케이스·트레이드오프를 질문으로 채운다: 초기 질문·정보 덤프·후속 질문으로 지식 공백을 메운다. 모르는 게 가장 많은 섹션부터 시작한다.
- [section-by-section] (workflow-step) 섹션 단위로 브레인스토밍→선별→초안→반복: 섹션마다 5~20개 옵션을 브레인스토밍하고 선별해 초안을 쓴 뒤 피드백을 반영한다. 전체 재작성 대신 타깃 편집(str_replace)을 쓴다.
- [fresh-reader-test] (verification) 맥락 없는 새 인스턴스로 읽혀 맹점을 찾는다: 저자는 알지만 독자는 모를 지점을, 맥락이 섞이지 않은 새 Claude로 문서를 읽혀 찾아낸다.
- [trim-filler] (verification) 군더더기를 덜어내며 마무리한다: 세 번 반복해도 변화가 적으면 무엇을 뺄지 묻는다. 마무리에 전체 흐름·일관성·군더더기를 점검한다.

## 설명형 (쉽게 설명)
- [everyday-analogy] (output-rule) 추상 개념을 일상의 구체적 장면에 빗댄다: 카페·알바생·메모처럼 누구나 아는 일상 상황으로 치환해 설명한다. (예: '스크립트 = 알바생에게 남긴 할 일 메모')
- [plain-words-first] (constraint) 전문용어를 먼저 꺼내지 않는다: 쉬운 말로 먼저 풀고, 전문용어는 필요할 때 뒤에 괄호로 곁들인다. 용어로 시작해 겁주지 않는다.
- [summary-then-detail] (output-rule) 한 줄 요약 먼저, 그다음 풀이: 짧은 한 줄로 감을 준 뒤 자세히 풀이한다. 처음부터 길게 늘어놓지 않는다.
- [include-why] (workflow-step) 무엇이 좋은지·왜 쓰는지를 곁들인다: 개념이 왜 필요한지, 쓰면 무엇이 편해지는지를 함께 알려준다. (예: '한 번 써두면 매번 사람이 시키지 않아도 알아서 처리')
